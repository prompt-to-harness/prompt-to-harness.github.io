## 产品规则与本轮过程

讲师要求先开发两个独立项目，并将该安排写入 TODO。随后指示“开始准备游戏”。Agent 在本轮直接实现以下默认规则，没有将这些默认选择记为讲师已经逐项确认。讲师后续试玩认为游戏本身没有明显需要修改的地方；这不补写为开发前已逐项确认需求。

- 记忆翻牌：6 对水果图案，两张记一步；不匹配等待 750ms，期间锁定翻牌；第一张开始计时，全部配对后停止；随时重开，清理待执行的翻回任务。使用原生 DOM、CSS、JavaScript。
- 躲避与收集：60 秒、3 条生命；青色圆点用方向键、WASD 或触屏按钮移动；金色方块每个 10 分，红色三角障碍扣 1 条生命，碰撞后保护 1 秒；时间到或生命耗尽结束。支持重开、暂停、切换窗口自动暂停。规则在 `dodge/simulation.js`，Phaser 渲染和 DOM 操作在 `dodge/main.js`。

第一份代码在读取游戏插件指导前写出；随后读取本地 Game Studio 的规划、架构、Phaser 与试玩 Skill，完成第二份代码。两次任务不同，不能据此比较开发效率。当前第一份也由 Agent 实现，尚未形成完整的“讲师试玩—反馈—修改”过程。

## Agent 浏览器试玩（2026-11-05）

按讲师“你来试玩”的要求，用浏览器可见控件和截图完成一轮体验；未修改游戏状态、随机数或计时速度，也未用内部状态选择牌面。以下是 Agent 试玩，不计作讲师人工试玩或教学效果验证。

- 记忆翻牌：只根据已翻开的牌面记忆并配对，本局 9 步完成全部 6 对；页面显示用时 6 秒。通关后重开，步数、配对数、计时和牌面均重置。未发现阻塞整局的缺陷。
- 躲避与收集：实际长按方向键以及屏幕方向按钮均可移动；暂停、继续可操作。第一局在剩余 42 秒时生命耗尽、得分 0；重开后第二局收集到 1 个方块，显示 10 分，在剩余 48 秒时生命耗尽。结束后暂停按钮禁用，“再来一局”可重置到 60 秒、3 条生命、0 分。
- 体验问题：在较矮的桌面窗口中，开始按钮将焦点移到游戏区后页面滚动，顶部 HUD 离开可见区域；画面与方向按钮也难以同时容纳。收集加分与扣命的反馈主要体现在 HUD 数字及玩家颜色，试玩中不够醒目。
- 后续建议：优先让 HUD、游戏区与主要操作在常见窗口中同时可见；补充明确的加分、受伤反馈，再评估难度。两局提前失败与 Agent 操作间隔有关，不能据此断定普通玩家的难度水平。本轮未活到 60 秒，超时结束仍只有规则检查证据；未做真实触屏设备测试。

## 开发流程复核（2026-11-06）

本次回读了原始开发会话中的用户请求、执行命令、工具调用和结果，并对照当前源码与本轮使用的 Game Studio 0.1.2 本地快照。没有重新开发游戏或运行 Skill 对照实验。原始会话不复制到公开仓库。

### 实际顺序与验证方式

1. 讲师提出“开始准备游戏”后，Agent 先补齐默认玩法并写出翻牌代码；此时尚未读取 Game Studio 正文，也没有完成一轮独立的翻牌验证。
2. 随后显式读取 `game-studio`、`web-game-foundations`、`phaser-2d-game`、`game-playtest` 及 Phaser 架构参考，声明按指导采用 Phaser、规则与渲染分离、DOM 状态栏，再写出躲避游戏。
3. 在讲师额外提出“你来试玩”之前，Agent 已自行编写并执行两个游戏的联合检查：用 Playwright 点击牌面完成翻牌通关、检查重开；操作躲避游戏的开始和暂停；截图检查窗口布局；导入躲避游戏的真实规则模块，检查计分、碰撞与结束条件。
4. 讲师提出“你来试玩”后，Agent 才另做持续浏览器操作：翻牌通关，躲避游戏两局提前死亡，并报告较矮窗口的状态栏可见性与反馈问题。

因此，本轮确实主动做了页面操作检查，不能描述成“只跑代码，要求试玩后才操作页面”。Playwright 脚本本身也可以完成端到端页面操作；决定检查层次的是它经过哪些输入和状态，而不是有没有写脚本。另一方面，两游戏的初次验证发生在读取 Skill 之后，没有单独的无 Skill 检查基线，不能据此断言 Skill 改变了主动验证行为。

### 完整游戏任务与现成指导的对应

| 开发工作 | 本轮游戏中的具体问题 | 本地 Game Studio 提供什么 |
| --- | --- | --- |
| 确定玩法 | 玩家重复做什么、奖励或挑战是什么、一局如何结束和重开 | `game-studio` 要求先明确玩家动作、玩法循环、失败条件及单局长度；没有替项目决定六对牌、三条生命等参数 |
| 选择技术路线 | 翻牌主要响应点击，躲避需要持续更新移动和碰撞 | 入口、基础与引擎选择参考提供带偏好的路线，2D 默认 Phaser；这不是所有小游戏必须使用引擎的行业标准 |
| 组织实现 | 规则状态、输入、画面和状态栏如何配合 | `web-game-foundations` 与 `phaser-2d-game` 要求规则状态独立、输入映射明确、场景轻量及 DOM 状态栏；本轮落实为 `simulation.js` 与 `main.js` 的分工 |
| 形成可玩的反馈 | 玩家能否及时看懂收集、受伤、暂停与结束 | UI 与试玩指导覆盖状态可读性、受伤反馈、游戏区域遮挡和输入状态；`game-ui-frontend` 本轮仅在复核时阅读，不记作开发时使用 |
| 验证后交付 | 规则是否正确，真实操作能否走通，手感和难度是否合适 | `game-playtest` 要求主要操作、代表状态截图、窗口与输入检查和具体问题报告；入口要求在宣称可正式交付前完成试玩循环，没有自动阻止提前结束的执行门禁 |

实际便利可以具体指认：规则独立后，检查脚本直接调用真实 `step` 函数，构造收集、受伤保护或接近结束的状态，不必靠反复操作碰到每个条件；界面仍需另行操作和查看。这个便利来自已采用的架构做法，不能换算成没有测量过的开发提速。

本轮没有完整呈现这条工作路径：前期规则大多由 Agent 直接选择，没有展开玩法和架构取舍；没有素材制作需求；首轮检查也没有包含持续躲避试玩。已读取的指导有落实之处，也有检查深度不足之处。教学选材应覆盖这些真实判断，不预设第二个游戏已经完整兑现全部指导。

背景核对：[MDN 的游戏运行循环说明](https://developer.mozilla.org/en-US/docs/Games/Anatomy)区分由玩家动作推进与持续按帧更新的游戏；[MIT 游戏测试讲义](https://www.ocw.mit.edu/courses/cms-611j-creating-video-games-fall-2014/551bfaf95f7c469483408a90e7ea92b5_MITCMS_611JF14_Tech_Tes.pdf)区分技术检查、自行试玩与用户试玩。这些资料解释任务本身，不用来证明本次 Agent 做过什么。
