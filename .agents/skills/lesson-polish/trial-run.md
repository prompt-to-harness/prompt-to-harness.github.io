# 试讲之后的整体修改

> 由 [SKILL.md](SKILL.md) 路由过来：讲师试讲或口头讲述了一节，带着录音转写或口头意见来改。2.1 在 2026-10-23/24 按这个顺序改了一轮（章 LOG C2-81 至 C2-90），下面是从中沉淀的做法。

规则本身在 `docs/production/editorial-checklist.md` 和课程设计原则里，本文只规定顺序。

1. **先汇总，不急着改。** 把转写里“讲不下去、讲师自己卡住、评审追问”的地方整理成清单，分成三类：结构（删哪些页、顺序）、逐页修改点、待讲师拍板的问题。转写口误多，按意思归纳，不逐字引用；评审的原话和讲师的意见分开标。
2. **删内容按主线，不按页数。** 先说清这一节的主线（一句话）和对应的讲透问题，主线外的页删掉或移到配套文档。不提“压到几页”这类方案：一节十二页左右是正常体量（课程设计原则，2026-10-23）。时长只作参考，不作删页的依据。
3. **逐条讨论，定下来再动。** 讲师逐条回复后，把定下的决定一次写进章 LOG（依据、重开条件），再按 SKILL.md 的分层从上往下改：章文件 → 分镜（分区结构先改本节内容，再改逐页安排）→ 页面源与口播 → 生成物。讲师说“先改分镜”时，页面不同步的部分登记在章文件“待定”。
4. **对照真实对象。** 每页拆解的东西（请求、diff、日志、配置）按它实际的顺序讲（ED-019）；事实按 `AGENTS.md` 的编辑底线核实，没核实的写“未核实”。
5. **统一全章说法。** 改完一节后，检查这一节的分类、贯穿全章的图和术语有没有和其他页、其他节对不上（ED-012；图的读法按视觉规范“贯穿全章的示意图”）。这类问题单看一页发现不了，在试讲后最容易暴露。
6. **数据有疑问就重跑，并留存原始记录。** 发现页面讲法依赖删节过的记录或某一次运行的偶然结果时，按 [2.1 复现说明“数据与运行的做法”](../../../courseware/ch02/lessons/01-request/tools/README-demo.md#数据与运行的做法其他章可沿用)重跑，原始记录放私有仓库，公开数据不删结构；讲法随新结果改，不为凑旧结果反复重跑。
7. **复查再锁定。** 按 [review.md](review.md) 复查，再在章 LOG 记一条冻结决定和重开条件。

## 少走弯路

- **写分镜时先问两个问题**：这页的顺序和真实对象一致吗？这个术语、这张图在全章只有一种读法吗？2.1 的返工大多来自这两点在试讲后才发现。
- **并行工作按文件分组。** 几个会话同时改同一节时，每个会话只负责一组文件，提交前先同步；否则只能事后逐个核对谁改了什么。
