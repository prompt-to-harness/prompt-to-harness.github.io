## 01 · 从翻牌清单推出应该改哪里

**反馈**：讲师指出，具体案例还在复述运行日志，应先明确要解释或证实的知识，再决定取什么材料。后续审阅又指出，历史请求突然出现，原版和修改版容易混指指导文件与生成结果。 [案例讲述目的纠正与全稿修订记录](../../../../docs/reviews/ch03/2026-11-09-3.2-revision-guide.md)

**原稿节选**：

> 这里换到十一月七日保存的对照。原版写了“结算 → 重开 → 可正常再玩”，结束和重开本来就有。不过，操作人还得自己补：从结算面板开始，点击哪个按钮，重开后看哪些变化。“正常”还没有展开。

**实际改稿节选**：

> 为了比较修改前后的差别，我在备课时另外做过一组调用，仍然是让 Codex 为翻牌游戏做规划。这组调用对原版和修改版使用同一条请求。这里先打开使用原版 Skill 生成的方案。它写的是“结算 → 重开 → 可正常再玩”。
>
> 假如让你照着这一条检查，你还要自己补充：从结算面板开始，点击重开以后，哪些东西应该消失，哪些数字应该归零，怎样才算正常再玩？这条清单还不够具体。
>
> 如果游戏没有规定重开后要恢复什么，我们应先补充本次游戏规则。而我们现在要改善的是清单的写法：让 Codex 把规则展开成别人能操作、能判断的步骤。以后写其他游戏的检查计划也需要这种做法，所以我们把它加到 Skill 里。

**改动理由**：用同请求的对照交代材料来历，再让学员站在执行者的位置找出具体缺口。新稿说出了可以带走的判断：缺本次游戏规则就补任务信息，缺把已有规则写成可执行检查的通用方法就改 Skill 正文。

**来源与状态**：旧稿 `b08/0/1` 保留在 `previousReuse`，改稿 `b06/5/1` 对应 `b06` 的现行讲述。改稿已写入讲师页源，修订记录显示已做作者复查，原讲师评论仍为 open。 [逐字稿源](../../../../courseware/ch03/lessons/02-rules/script.json) · [画面与稿件映射](../../../../courseware/ch03/lessons/02-rules/screen-plan.json)

## 02 · 说明为什么把资料分成四块

**反馈依据**：2.2 在 10 月 24 日试录后，讲师确认按转写反馈调整，口播按可照念的标准重写。公开记录保留整轮反馈摘要。 [第 2 章记录 C2-115](../../../../courseware/ch02/LOG.md)

**原稿节选**：

> 先在项目根目录准备 profile.md，分成基本信息、教育、工作经历、项目与开源四块。这里展示的是我的公开资料。事实由我们提供，Codex 负责放进页面。

**实际改稿节选**：

> 先准备资料。我们在项目根目录放一份 profile.md，分成四块：基本信息、教育、工作经历、项目与开源。我这里的内容，是从我自己的个人网站上挑出来的公开信息。为什么是这四块？因为一个个人主页，至少要让看的人知道：这是谁，在哪里读的书，做过什么工作，做过什么项目。这只是一份示例，大家做的时候，一定要换成自己的内容。

**改动理由**：原稿交代了文件结构和人机分工。改稿补出了选择这四类资料的依据，学员换成自己的资料时，可以按主页读者需要回答的问题来取舍。

**来源与状态**：`courseware/ch02/lessons/02-iteration/script.json` 的 `p29a[0]`，`6a19b6da` → `0e179155`。两版原文已核对，讲师确认记录对应整轮调整。

## 03 · 补上上一节留下的前提，再解释为什么写项目规则

**反馈**：讲师确认的试录修订要求纠正“上一节已经在请求里看到过规则”，并补写准备 `AGENTS.md` 的理由。上一节看到的是项目规则块为空。 [第 2 章记录 C2-115 第④项](../../../../courseware/ch02/LOG.md)

**原稿节选**：

> 上一节已经在请求里看到过规则。这次我们自己写一份：改完代码跑 build，并报告结果；不新增依赖。把它保存为项目根目录的 AGENTS.md。你跟做时，这一步选做。

**实际改稿节选**：

> 做选择之前，先补上一样东西：项目规则。上一节那张图上，规则那一块是虚线，因为这个项目还没有 AGENTS.md。现在我们来写一份。AGENTS.md 是写给 Codex 的项目说明，放在项目根目录，Codex 开始一段对话时，会把它装进请求。为什么要写它？有些要求，我们希望每一轮都遵守，不想每次都在 Prompt 里重复一遍，就写在这里。我们写两条：不新增依赖；改完代码，运行 npm run build，并报告结果。大家跟做的时候，这一步可以选做。

**改动理由**：先校正学员此前看到的事实，再解释当前动作的用途。学员既知道为什么这时要加文件，也能辨别什么样的要求值得作为项目规则反复使用。涉及工具行为的原句保留为历史口播，复用本例时需按录制环境重新核对。

**来源与状态**：`courseware/ch02/lessons/02-iteration/script.json`，`6a19b6da` 的 `p27a[0]` → `0e179155` 的 `p27a[1]`。两版原文已核对，修改点有讲师确认记录。

## 04 · 把“文件取回来了”拆成两次可观察的结果

**反馈依据**：讲师确认 2.3 围绕“取回来不等于看到了”等三点讲 Context。后续按录制稿形式重写逐字稿，在 p40b 用实际工具返回解释第一点。 [第 2 章记录 C2-105、C2-117](../../../../courseware/ch02/LOG.md)

**原稿节选**：

> 回到这一列方块。curl 取回的 HTML 和 CSS，就在工具返回这一块，记录里看得见。它刚才说的“左边日期、右边内容”，我们可以在返回里找到对应的那几行。

**实际改稿节选**：

> 这一次的工具返回里，有什么？只有两个数：HTML 两百零八行，CSS 三千九百零八行，也就是两个文件各有多少行。参考页已经存到了它的电脑上，可是进到请求里的，只有这两个行数。这时候，参考页的内容，还不在 context 里。
>
> 接下来，它开始读。cat 和 sed，都是在命令行里读文件的工具。HTML 不长，它整份打了出来。CSS 有三千九百多行，它没有一次读完，先看开头的二百四十行，再按行号，一段一段挑着读。每读一次，读到的那段代码，就作为工具返回，追加进请求。

**改动理由**：原稿把下载和读取压到一句话里。改稿先展示只返回行数，再展示代码片段怎样进入请求。学员换一份记录时，可以核对工具究竟返回了什么，再判断模型实际获得了哪些内容。改稿中的行数属于当次排练。

**来源与状态**：`courseware/ch02/lessons/03-review/script.json`，`6a19b6da` 的 `p40b[2]` → `d9d06d78` 的 `p40b[1]–[2]`，后一段只摘开头。两版原文已核对，C2-105 的讲法已获确认，C2-117 的整轮录制稿改写记录为待讲师确认。
