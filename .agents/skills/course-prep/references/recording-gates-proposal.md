# 录制验收门禁：待实施方案

仅在评估、设计或实现自动验收与放行机制时读本文。普通备课、页面改稿和人工录制验收无需读取；人工验收按 recording-alignment-workflow.md 执行。

本文保存系统方案及来源工作区的历史能力，不表示当前仓库已接入，也不授权本次内容编辑任务实现门禁或修改检查器。实际工具与命令须按目标项目核实。

## 1. Markdown 的作用与限制

Markdown 能说明要求、判断方法和例外，但不能强制 Agent 认真阅读，也不能证明它已经执行。提示词写“必须”或要求回复“已阅读”，都不产生可靠的执行证据。

应检查实际行为和交付物：完整范围是否覆盖、是否真正打开了目标位置、是否对照了当时的画面和正文、修改后是否复验。即使这些证据齐全，也不能数学式地保证教学内容完全正确。

## 2. 将要求分为不同层次

| 层次 | 建议机制 | 能检查什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 入口提醒 | 在项目指令或相关备课入口中链接本文，任务开始说明范围 | Agent 能找到流程，范围明确 | 已认真执行 |
| 结构完整性 | 从唯一正文源导出片段列表，与画面位置及操作清单交叉检查 | 漏段、错序、缺入口、失效页号、无意重复 | 内容讲得通 |
| 实际操作 | 浏览器按路线点击，记录目标状态、可见区域及操作结果 | 按钮可用、正确落点、展开状态、保留窗口 | 画面支持口播中的推论 |
| 内容核对 | 将实际截图、对应全文和前后片段一起复核，记录具体依据 | 对象、事实、关系、信息分工和衔接中的问题 | 所有判断绝不出错、教学效果已验证 |
| 修正后复验 | 源和依赖变化使旧结果失效，重新取得受影响项的证据 | 沿用旧截图或旧检查记录、改完未复验 | 复验者的判断一定正确 |
| 交付放行 | 构建/交付流水线拒绝缺记录、失效记录、失败项和未关闭问题 | 在受保护的执行路径中，未满足条件就无法放行 | 最终语义一定正确；编辑任务能绕过放行路径时，也无法强制流程 |

入口提醒负责让 Agent 知道该做什么；后面几层负责使遗漏可发现、未完成可阻断。不要把某一层通过扩张成整个流程通过。

## 3. 建议的机器可检查契约

以下是待实施的接口要求，不表示仓库已经提供对应文件或命令。字段可以适配项目已有结构，不必另建一套正文。

1. **片段清单来自真实源。** 从完整逐字稿枚举片段，引用稳定 ID 与实际段落，绑定画面位置和进入动作；校验器不能只相信 Agent 手写的一份“需要检查的片段列表”，否则漏掉的片段也不会被发现。
2. **捕获实际画面。** 执行器在操作后记录视口、页面地址、页/状态、目标可见性及截图。查到 DOM 元素不代表观众能看到；滚动与展开状态也必须核对。
3. **绑定内容与依赖。** 记录本段正文、相关 PPT/HTML、导航、共享样式、数据及生成工具的内容指纹，连同实际生成页面版本一起关联。依赖列表需要覆盖真正会改变呈现或结论的输入。
4. **保存语义核对证据。** 记录本段所讲对象、可见依据、逻辑是否成立、前后衔接及具体问题。空泛的固定成功语句不能作为有效的内容核对。
5. **修改后失效。** 正文或依赖变化时，将相关技术/内容结论标为待复验；顺序变化还影响前后片段。执行期间文件变化则丢弃混合版本的结果，重新检查。
6. **由执行器计算状态。** 没有当前版本的技术证据、内容核对或修正后复验，就不能得到完整通过。问题状态与其最新复验关联，不能只允许作者把“有问题”直接改成“通过”。
7. **缺失时阻断交付。** 缺证据、证据过期、检查失败或问题未解决均不得签发验收完成结果。草稿仍可交付为明确的未完成状态，不得自动降级成通过。

状态流程可表示为：

```text
未检查 → 技术及内容核对 → 通过
                     ↘ 发现问题 → 修改 → 待复验 → 复验通过
通过 + 相关源发生变化 → 待复验
```

## 4. 避免由同一个 Agent 自己证明自己通过

哈希、截图、状态字段和校验脚本，如果都由同一个有写权限的 Agent 控制，就仍可能被跳过、写成固定成功或通过缩小检查范围来规避。哈希能识别变化，本身不能证明证据可信。

需要更强约束时，把最终检查和放行交给独立控制的执行环境：

- 受保护的检查程序从实际源重新计算覆盖与指纹，自己执行浏览器操作，生成记录；不直接接受工作区里作者提供的“通过证明”。
- 检查规则、执行环境和放行凭据不由内容编辑任务随意改动。检查程序的变更单独审查，防止修改失败条件来迁就稿件。
- 内容复核可由讲师或独立复核服务读取实际画面与对应全文，查看作者的修改依据，并给出自己的判断。独立模型复核能增加发现问题的机会，仍可能犯错。
- 发布或正式交付入口检查受信执行结果与当前版本是否一致。编辑任务可以生成修复预览，但不能自行把未通过版本标为正式验收完成。

这套设计约束的是正式放行。若 Agent 同时有权修改检查器、签发记录、关闭门禁和发布，就不能声称已经建立了不可跳过的强制机制。强制程度来自权限和执行路径，而不是文档措辞。

## 5. 来源工作区与当前仓库的接入边界

分发包描述的来源工作区已有 [PPT 材料门禁](../assets/course-reference/docs/production/ppt-verification.md)与实现（课程仓库参考路径：`tools/ppt_gate.py`；未随包提供）：

- 验证器执行配置中的材料检查，输入发生变化后通过记录失效。
- PPT 生成、`make check` 和站点构建等入口已有相应检查；链接检查关注材料窗口的打开行为。
- 检查计划及具体断言决定实际覆盖范围。它们不能自动证明所有逐字稿与画面在语义上对应。
- 当前记录和检查器可在工作区修改，不应把本地通过文件视为独立受信的签发结果。

2026-11-09 核对：当前课程仓库未包含 `tools/ppt_gate.py`，上述能力不视作已接入本仓库；实际检查以当前 `Makefile` 为准。

在具备上述机制的环境，建议补充片段覆盖、录制路线、内容核对及修正后复验，避免再建一个与已有材料门禁相互矛盾的入口。现有材料验证继续遵守原顺序。

新增内容门禁应允许生成待检查的预览，再检查实际生成页面，最后控制正式验收与交付。不要要求先拿到最终页面的语义通过结果，才允许生成唯一可供检查的预览，否则形成循环依赖。

实施顺序建议：先把片段和正文真源连通，再加入浏览器与失效检查，然后接入内容复核和独立放行。接入前后分别报告能力；不能提前把本节方案写成现有功能。
