# 逐字稿写作与验收

按编号读取完整正文：从仓库根目录运行 `python3 tools/read-editorial-rules.py ED-编号 ...`；合并去重，已读且未变的不重读，缺号或截断时补取并核对结束标记。 新写或润色口播读 ED-002、ED-007、ED-010、ED-012；新写讲法或补推导加 ED-004、ED-008、ED-019，改变深度加 ED-006、ED-021；操作提示加 ED-013，材料分工加 ED-003，运行结论加 ED-020，保存生成加 ED-011、ED-017。

在课件制作阶段写、改或审查逐字稿时读本文。以本课已经确定的内容设计、已走通的讲述线、讲师口述或原稿和可核对的材料为依据。课程仓库的制作与编辑规则以 `docs/production/` 为准；按本文开头的编号用统一脚本读取。随包的[编辑规范](../assets/course-reference/docs/production/editorial-checklist.md)供跨项目参考。

本文维护口播写作、推导与朗读方法；仅修改页面布局、源节点映射和编辑交互时读取 [HTML 实现维护](narration-implementation.md)。完整口播在既有讲述线的对应位置补齐，写回本课唯一口播源，不另建逐字稿版本；课程层级与正式入口见 [Skill 入口](../SKILL.md#课程结构产物职责与维护入口)。

## 执行路径

### 第一步：核对讨论稿和已走通的讲述线

按编号读取 Discussion 本段及所属部分思路、小节目标与深度，核对已定知识和承接，再从当前讲述设计找到解释、证据与时序。写稿时据此保留学员作判断所需的条件。例如，翻牌案例已经定好要解释何时补游戏规则、何时改 Skill 正文，口播要把这个选择的依据说出来。

写整节新稿或重写整节时，先依据已定的讲述线和画面安排，用几句话讲通整节：从什么问题出发，依次要解释什么，最后凭什么得出判断。理顺这条线后，再展开各段口播。

改稿时先找出原段已经承担的解释、依据、推导和承接，再在本次范围内处理。若只找到要打开的材料，或讲述线缺少让学员理解的关键推导，回到讲述设计补清再写。涉及目标或范围变化时，指出对应的内容设计问题。 [讲述设计](narration-html.md) · [内容设计](discussion.md)

### 第二步：核实口播要用的事实和条件

逐项核对讲述线已经选定的原句、输出或变化，明确口播要指向哪一处，以及它能支持什么。需要比较时说清对象、共同条件和差别。若核对发现证据与讲法不符，回到讲述设计处理。

区分实录、回放、讲师口述与教学假设。回放开发记录时，先核对失败现象、原因、实际修改和同项复测，分别辨认实现错误、检查预期错误和环境问题。单次运行支持的判断保留当次条件。讲师口述可以说明思考过程，数字、输入输出和展示结果仍要与证据核对。

### 第三步：把事实为什么支持这条知识写进口播

把关键事实和学员需要听到的解释写在同一段讲述里。让学员听见遇到了什么问题、从哪项事实看出来、怎样据此作判断、在什么条件下还可以这样判断。案例只讲到足以理解的深度。概念可以先用一句话立住，再用事实讲明白，也可以从具体问题引出。承担解释的句子可以分布在讲述中，无需给每段另加总结。

比较、实验或复测的目的如果听众还不知道，在动作前用一句话交代。同一个问题顺着讲完。换问题、判断对象或判断依据时，如果听众需要知道为什么要换，再补一句简短的过渡。

已有讲师口述时，保留可用原句、思考顺序和关键中间步骤。仅做局部润色时，沿用该段原有教学职责。保留原稿中让学员看懂结论的必要前提、推导和承接。需要调整讲师推导或改动明确要求保留的原句时，先指出具体问题。

逐字稿沿用讲述线已分配的[画面职责](narration-html.md#怎样选画面和安排切换)，不在每次切回时重新展开同一推导。若必须反复解释才能听懂，先检查知识与实例是否缺少可见对应，回到讲述设计处理。

### 第四步：先连读纯口播，再对照实际画面

稿子写出来后做两遍检查。整节新写或重写时覆盖全节，局部改稿时检查受影响的段落及前后衔接。

1. **只读纯口播。** 从同一稿源抽出学员会听到的正文，暂时略过画面、操作提示、页码和备课备注，按讲述顺序连读。核对每段为什么在这里出现、前提是否已经交代、结论能否从前文推出。保留帮助理解的连接句，删去纯版面导览和同义重复。
2. **带画面走查。** 按讲述线和录制顺序核对，说到关键证据时画面是否已经出现，指代是否明确，切换和操作是否接得上。遇到抽象说法就落实到具体的人、对象和动作。操作提示放在实际发生处，具体格式见下文。

遇到实操时，交代真实输入、要发的请求和返回后检查什么。任务等待期间可以讲保存的记录，讲完回到刚才发出的任务。涉及修改与复测时，从同一起点说明这次要验证的假设，指出实际改动和复测对象，再根据结果决定保留还是继续调整。现场结果未知时先写观察和判断方法，尚未具备的操作或证据记在录制准备中。

口播改回唯一稿源；当前讲述设计就近保留，不能用成稿替换设计或把口播复制为设计。若写稿暴露解释、切换或证据问题，按授权更新对应讲述设计；目标、范围或关键结论变化回到 Discussion 处理，未解决的受影响片段不标为可录制。单纯措辞变化无需重写设计。共同操作与材料继续在原位置完善。整段涉及 PPT、逐字稿和演示顺序联调时，使用[录制对齐方法](recording-alignment-workflow.md)。

## 验收标准

1. **知识听得出来。** 只读学员会听到的口播，能找出讲明知识的句子，说出学员学到的判断、条件或方法。备课备注用来核对教学意图。
2. **案例撑得起这条知识。** 能指出具体事实，以及口播中解释这个事实为何支持判断的句子。条件、比较基准和结论范围与证据一致。改稿后原有的必要前提和中间推导依然完整。
3. **换个同类情境还会用。** 换一个同类对象或条件，学员仍能用稿里已经讲出的依据解释、判断或操作。验收可以在备课时做文本推演，学员是否实际掌握由试读或试讲观察。
4. **按实际画面能直接录。** 按录制顺序连读，关键证据在需要时可见，转场、指代、解释和操作都能跟上。讲师读稿时所需的理由已经写清。按项目约定完成技术检查，并按实际完成情况报告作者走查、出声试读、非作者复述和试讲。

## 常见问题

| 问题 | 怎么改 |
| --- | --- |
| 案例讲完，学员只记得发生了什么 | 找出本段要教的判断，留下能说明它的事实，在口播中讲出两者的关系。 |
| 结论给得太快 | 补上学员尚未看到的前提、观察或中间结果。<br>需要区分两种情况时，讲清哪项差别会改变判断。 |
| 概念只剩名称或口号 | 写明具体对象、发生的动作和结果，再用术语概括。<br>有条件的结论保留适用范围。 |
| 转场靠“接下来”，画面靠逐项报位置 | 从当前尚待解决的问题引出下一步。<br>定位与点击放在操作提示，口播说学员现在应观察什么以及为什么。 |
| 为了缩短而删掉理由，或重复总结拖慢推进 | 按句子是否提供必要事实、理由或承接取舍。<br>保留承担推导的原句，合并已经讲明的结论。 |

## 代表性真实改稿案例

### 翻牌清单：从复述检查项到教会学员找缺口

原稿已经指出“正常”需要展开。实际改稿进一步交代这份方案从哪里来，再让学员代入执行者，找出重开后应该核对哪些变化。稿里明确写出了要教的判断：

> 如果游戏没有规定重开后要恢复什么，我们应先补充本次游戏规则。而我们现在要改善的是清单的写法：让 Codex 把规则展开成别人能操作、能判断的步骤。以后写其他游戏的检查计划也需要这种做法，所以我们把它加到 Skill 里。

把对象换成躲避游戏的重开检查，同样先查项目有没有规定重开后恢复什么，再判断是补本次规则，还是改生成检查计划的通用方法。 [完整前后原文与反馈](spoken-script-cases.md#01--从翻牌清单推出应该改哪里)

### 下载网页：把结论所需的中间结果讲出来

原稿把取回 HTML、CSS 和代码出现在工具返回里连在一句。实际改稿拆出两个能在画面上核对的结果：下载那次只返回了行数，随后读取时，代码片段才作为工具返回追加进请求。这里保留中间步骤，是为了让学员看另一份记录时也会去核对工具实际返回了什么。 [完整前后原文与反馈](spoken-script-cases.md#04--把文件取回来了拆成两次可观察的结果)

其余已核对的反馈、原稿与改稿见[逐字稿真实改稿案例库](spoken-script-cases.md)。

## 呈现格式

- 整节开场交代要解决的问题和推进方式。小节标题写所解决的问题，教学段落按完整讲述组织，数量按本课实际需要确定。
- 将现有稿件采用的操作标记（如 **【操作】**、**【切换】**）放在实际发生处，写清窗口、页面或状态、材料位置、动作及必要的返回点。录前准备与现场动作分别写在对应位置。录制跳转沿用本课 PPT 或材料导航，备课页面保留就近可点的入口。
- 引用块放讲师可照读的连续口播。操作提示、素材状态和选材分析另放。必要的原文、比较对象和操作结果就近呈现。迁入 HTML 时保留操作与口播的先后关系，已有稿件沿用同一源和编辑坐标。讨论板使用 `segments` 时沿用其字段约定。
- 课件核对与录制验证分别记录。跨产物核对按[录制对齐方法](recording-alignment-workflow.md)。本仓库的口播编辑检查按当前制作约定执行。

## 表达问题的改写示范

错误包含当前稿原句和同类写法的概括；改写是示范，不冒充讲师原话，不要求以后逐字套用。

### 1. 介绍版面，代替讲事情（ED-008、ED-013）

错误：“左边是用户交给我们的话，右边是他要拿到的数据集名单，中间是检索库。”

改写：“用户想找宇树 G1 的数据。我们要从库里找出符合要求的数据集，把名单和来源给他。”

直接讲输入、工作和结果的关系。指位置、沿箭头、放大哪个区域等提醒主要放操作提示，用鼠标、指示或动画带到。不要逐项清点“这里有三个框”“下面是五项职责”。

空间信息属于内容时可以说，例如固定侧栏的位置、要比较的具体区域、两张图片分别是什么。必要指认可以保留；不能把最终稿中偶尔出现的“左边、右边”当成继续导览版面的理由，也不把这些词机械禁用。

### 2. 播报动画，代替解释变化（ED-008、ED-013）

错误：“查询向右移动，在理解和查询之间新增一个语义对齐节点。”

改写：“用户说的是 SO 系列，可库里存的是不同的型号名称。查询之前，我们还得先判断，这些名称里哪些属于 SO 系列。”

口播解释为什么需要这项工作；节点怎样移动写进操作提示。画面同步发生变化，不必再用口播复述动画。

### 3. 未产生需要，就给定义或结论（ED-002、ED-004）

错误：“我们得准备一组问题，逐题说清楚怎样算答对，这就是评测集。”

改写：“刚才我们问了一个问题，也拿到了回答。那它到底答对没有，我们怎么知道？比如用户要下载量最高的五个数据集，我们得先知道正确的五个是哪些，顺序是什么，才能核对它的回答。把产品需要回答的几类问题准备好，再给每个问题配上标准答案，就得到了一份评测集。”

让概念回应眼前已经出现的问题。学员已经理解的内容无需每次重新铺垫；新概念不能只靠命名完成解释。

### 4. 用抽象词压缩多个动作（ED-002、ED-010）

错误：“模型结合用户条件判断哪些符合，把匹配的真实值和判断依据交给查询。”

改写：“我们先把库里出现过的机器人名称取出来，交给模型。用户要找 SO 系列，就让它逐个判断：哪些属于这个系列，哪些不属于，哪些还拿不准。确定下来的名称，才用来查询。”

先讲清谁拿到什么、做什么，再引入“语义对齐”“准备证据”“交接”等概括。一个动作展开到能理解，再讲下一个；不能只把长句切成几个同样抽象的短句。

### 5. 每句都是新判断，删掉理解所需的承接（ED-002、ED-007）

错误：“题目覆盖需求。评分器检查结果。运行记录支持诊断。完整复测检查回归。”

改写：“问题和标准答案准备好了，接下来就让产品逐题回答。能按规则比较的部分，我们用程序来核对。不过，判错只告诉我们这题没有通过；要知道错在哪里，还得打开它的运行记录。”

保留承担迁移、比较和连接的复述。例如“前面让 AI 写代码，要说明怎样算完成；现在做问答产品，也要先知道怎样算答对”。删除空泛重复，不能以减少字数替代口播判断。

### 6. 用顺序词代替转场理由（ED-002、ED-008）

错误：“接下来看评测框架。然后回到报告。再看运行日志。”

改写：“题目准备好了，怎样让产品把这些题都跑一遍，并把结果留下来？”拿到报告后再说：“报告告诉我们哪些题没通过。我们挑一道打开，看看它在哪一步出了问题。”

下一段接住上一段留下的问题。不要只增加“再看、回到、接下来”；提问也应确实推动后续解释，不给每句结论强配问号。

### 7. 用审查说明打断案例（ED-002、ED-003、ED-010）

错误：“不能据此归因，不能保证正确，也不能用两个分数直接比较。”

改写：“这两轮除了拆分步骤，还改了评分规则，所以总分的变化里混着几项影响。我们先看同一道题，确认拆开以后，每一步是不是按预期工作。”

先说明当前证据支持的判断。必要限制解释具体理由，并帮助当前决定；其余历史核验说明放备课记录。不能为了好念删掉必要的事实边界，也不要先制造学员尚未提出的推论，再用否定句纠正。
