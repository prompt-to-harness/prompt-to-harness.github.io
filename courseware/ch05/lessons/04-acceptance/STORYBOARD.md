## 本节内容

### 先把还没看见的部分做出来

5.3 结束时，讲师和学员各自留下了可操作的双输入和错误路径，以及更新后的 `CH05_IMPLEMENTATION.md`。生产代码里已经有差异模型、合并图数据和两侧输入，但差异摘要、「只看变化」、超限提示和状态可辨认还没有接到界面上。进入本节，先确认当前副本仍在同一条功能分支上，前三个任务已经完成，再打开摘要、筛选与整体验收任务和它关联的规则、案例。讲师演示用的是 `course/ch05-baseline` 上已提交的 `docs/specs/`（当前基线上为 `TASK-04` 及关联的 `REQ-*`、`AC-*` 与 `docs/specs/fixtures/`）；讲师和学员的实际编号不必相同，每个人都要能在自己的文件里找到对应内容。

本节从学员会立刻追问的问题开始：各部分都做了，能说整个功能完成了吗？不要一上来就做整功能验收——摘要和筛选还没做出来，这个问题还问不完整。先用 4.4 / 5.1 / 5.2 / 5.3 同一组嵌套素材 `docs/specs/fixtures/nested/`，把还没看见的部分接到界面上并做局部检查：

Before：

```json
{"user":{"name":"Lin","age":20},"active":true}
```

After：

```json
{"user":{"name":"Lin","age":21},"role":"student"}
```

界面上要能直接读到差异摘要，摘要里的差异数为 3：`/user/age`、`/active`、`/role` 各计 1 处；`/` 与 `/user` 只带「下层有变化」标记，不计入差异数，所以不是 5（当前基线上为 `REQ-015`、`REQ-013`、`AC-003`）。5.3 在出错后仍能读到差异数，不等于摘要区已经完成。同一组案例还要用 `fixtures/subtree` 核对：摘要差异数为 2，只在 `/gone` 与 `/extra` 的根计处。

然后打开「只看变化」。5.2 已经在图数据里留下了筛选所需的祖先和 removed 节点，这一节才把它用到界面上。打开后，图上可见的路径应为 `/`、`/user`、`/user/age`、`/active`、`/role` 共 5 条，`/user/name` 被隐藏；通向差异的祖先 `/user` 是为了保留上下文才出现，差异数开关前后都仍为 3；关闭后 `/user/name` 重新出现（当前基线上为 `REQ-016`～`REQ-019`、`AC-004`）。

局部检查还要覆盖另外两件规格已经要求、但前三节还没有在网页里核对的事。一是状态除颜色外可辨认：把结果转为灰度后，仍能凭文字或符号区分 `added`、`removed`、`changed`、`unchanged`（当前基线上为 `REQ-026`、`AC-017`）。二是节点上限：开发环境上限为 2000，用 `fixtures/limit/over.json`（2100 个元素）做比较时，不渲染合并图，只提示图太大，提示中没有指向外部产品的升级链接，也不另定只对比较功能生效的上限（当前基线上为 `REQ-023`、`REQ-024`、`AC-015`）；再用 `fixtures/limit/removed-before.json` 与 `removed-after.json` 确认 removed 节点计入上限，并用 `under.json`（100 个元素）对照可以正常渲染（`AC-016`）。超限提示是 Diff 专用的新组件，单输入路径继续用原来的提示，不受影响。

这一段要让人看见的是：用户能不能看懂并筛差异。不要再走一遍任务流程。摘要的呈现形态、是否按状态分类计数，以及筛选打开后能否再查看被隐藏内容，仍是未决项（当前基线上为 `REQ-036`、`REQ-033`）；本节只保证摘要里能读到与模型口径一致的差异数，以及开关的开、关两种状态，不固化布局，也不做额外入口。

### 再问整个功能有没有做完

后半段才真正回答开篇那个问题。按当前 Acceptance 把整组案例走查一遍，包括前三节已经局部核对过、但还没有对照整组验收收口的项目：正常比较与错误恢复、节点上限、360px 窄屏、比较是否在本地完成，以及原有单输入路径。360px 正式走查、筛选时的网络面板步骤，以及 Graph / Tree / 导入弹窗 / `?json=` / widget 的完整回归，是 5.2、5.3 明确留给本节的；现在要把它们做完。模型核对、图映射核对和界面观察分别说明各自检查了什么，不能互相替代。最终结论要对照当前 `AC-*` 和任务完成定义。

当前基线上，窄屏验收（`AC-018`）要求在 360px 宽窗口里，两侧输入仍可操作，错误提示可读且能看出指向哪一侧，结果图与差异摘要都可查看、可操作。网络面板（`AC-019`）要在执行比较并切换一次「只看变化」时，确认发出的请求里不出现这两份 JSON 的内容；页面上其他无关请求不算违反。单输入回归要各走一次 Graph 视图、Tree 视图、导入弹窗、`?json=` 和 widget，确认既有行为与改动前一致。

若检查发现实现与已批准规则冲突，先定位代码、输入和核对过程，依据既定规则处理；若规则已定但案例确有遗漏，补上可核算的验收并核对任务，再实现与回归；若行为本身需要新决定，则由人批准后同步 Spec、Acceptance 和相关任务，再实施与回归。用实际发现决定走哪条路径。4.4 已为嵌套筛选安排案例，不能预设它一定缺失；如果本次没有发现规格缺口，就直接验证。真正需要改变产品规则时必须另行批准，不能将已批准规则重新说成 Open，也不能虚构一条缺失的需求。

Review 从本次 diff 与相关验收出发，按需查看源码、调用方和核对材料，核对关键数据流、错误处理及范围。审查意见要能指出触发条件、位置和依据，再由讲师判断接受、驳回或补充验证。是否引入新会话协助 Review 仍待讲师决定；无论采用什么形式，检查结论都以实际证据为准，不预设审查者会发现问题。本节可以使用产品自带的 `/review` 作为检查入口之一，但不把命令用法展开成教学内容；5.5 也只在口播里提一句，不作为演示项。

本节让 Codex 完成摘要、筛选与整体验收任务。允许修改的范围以当前任务文件为准；当前基线上写在 `TASK-04`：在 Diff 视图内新增差异摘要区、「只看变化」开关，以及无外链的超限提示组件；再按 Acceptance 走查全部案例，并回归既有单输入路径。不新增已批准规则之外的行为，不决定 `REQ-032`～`REQ-037`，不顺带修改 VS Code、浏览器扩展或其他非目标 workspace。第 6 章才批准「明确提示当前图是上次有效结果」的 CR-01；本节不把该提示设为必做，也不要求刻意移除已有的等价行为。

### 完成边界在哪里

不要再把任务闭环讲一遍。请 Codex 读取当前的摘要、筛选与整体验收任务，关联的 Spec 和 Acceptance、固定素材，以及全局约束和非目标，只完成这个任务。请求中要写清：输入是 5.1、5.2、5.3 已经验证的差异模型、合并图映射和双输入界面；本次先做出摘要与「只看变化」，并在界面上局部检查状态可辨认和节点上限；再按整组验收和 Review 判断整个功能有没有做完；允许改到哪里。不要把 CR-01 或 5.5 的招数写进这个任务。

验证沿用第 5 章已经核定的方式，不引入测试框架，也不在仓库里留下测试套件。当前基线上，这些检查是：运行 `pnpm --filter www run lint` 与 `pnpm build:www`；启动 `pnpm dev:www`（开发环境上限 2000），按 `AC-001`～`AC-019` 逐条走查，素材取 `docs/specs/fixtures/`；再做 360px 视口、灰度显示、网络面板三项专项核对；最后做单输入回归。若前序任务刚改过共享包，需先构建共享包再验收网页。检查结果以实际运行和人工在界面上的观察为准，不能把 Agent 的完成说明或 Review 回复当成核对结果。

当前基线上，本节用来判断摘要、筛选与整个功能是否完成的期望是：

**学员判断**：摘要和「只看变化」在嵌套案例上做完了，就能说整个 JSON Diff 通过验收吗？不能。这一段只说明还没看见的部分已经接到界面上，并且局部核对过；整组验收（含超限、灰度可辨认、360px、筛选时的网络面板、单输入回归）和 Review 还要对照当前 `AC-*` 与任务完成定义走完。前三节的模型、映射和错误恢复结果，只支持它们各自覆盖的行为，不能互相替代。
