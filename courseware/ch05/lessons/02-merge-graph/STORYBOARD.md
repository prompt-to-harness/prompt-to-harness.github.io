## 本节内容

### 先回到那条被删掉的字段

5.1 结束时，讲师和学员各自留下了已验证的差异模型、工作区外的一次性核对脚本和实际检查结果，以及 `CH05_IMPLEMENTATION.md` 初稿。生产代码里已经有按路径计算的状态，但还没有把这些状态接到 JSON Crack 现有的图上。进入本节，先确认当前副本仍在 5.1 的功能分支上，差异模型任务已经完成，再打开合并图映射任务和它关联的规则、案例。讲师演示用的是 `course/ch05-baseline` 上已提交的 `docs/specs/`（当前基线上为 `TASK-02` 及关联的 `REQ-*`、`AC-*` 与 `docs/specs/fixtures/`）；讲师和学员的实际编号不必相同，每个人都要能在自己的文件里找到对应内容。

本节从学员会立刻看见的问题开始：字段删掉了，结果图上怎样看见它？不要从映射步骤讲起，先打开 4.4 用过、5.1 也核对过的那组嵌套素材 `docs/specs/fixtures/nested/`：

Before：

```json
{"user":{"name":"Lin","age":20},"active":true}
```

After：

```json
{"user":{"name":"Lin","age":21},"role":"student"}
```

按已批准规则，`/active` 只存在于 Before，应记为 `removed`，并且要留在结果里（当前基线上为 `REQ-004`、`AC-010`）。与它同时出现的，还有 `/role` 为 `added`，`/user/age` 为 `changed`；`/` 与 `/user` 本身是 `unchanged`，但带「下层有变化」标记，不计入差异数。

先请学员判断：如果只拿 After 来构造图，这条被删掉的字段在哪里？答案是：它不在 After 里，所以只按 After 构图时，图上不会出现 `/active`。删除节点的原始信息来自 Before，必须把两侧信息映射到同一张能够表达这些状态的图上，`/active` 才可能被看见。

### 现有构图路径为什么不够用

有了这个判断，再打开 5.1 的差异结果和当前的图入口。现有 JSON Crack 的主路径是根据一份 JSON 解析并构图；那份输入相当于只看到一侧。即便差异模型已经算出 `/active` 为 `removed`，如果不把 Before 独有的节点写进图数据，渲染时仍然会丢。

这一节要让人看见的是：合并图不是并排两张图，也不是另做一套渲染引擎，而是把差异模型投影到现有图数据上，让一张图同时容纳新增、删除、变化和未变化的节点，并保持正确的路径与父子关系。`/role` 要作为 After 独有的节点出现；`/user/age` 要落在 `/user` 下面；`/user` 作为通向 `/user/age` 的祖先，必须能在图数据里被找到。只做最小映射：在共享包的差异模块里新增映射，给现有类型和共享组件增加可选入口；不修改现有 `parser.ts`，不改既有 `json` 入口，不改超限判定逻辑，也不引入第二套图组件。允许修改的范围以当前任务文件为准；当前基线上写在 `TASK-02`。

同一组嵌套案例还规定了「只看变化」时该留下什么：`/`、`/user`、`/user/age`、`/active`、`/role` 可见，`/user/name` 隐藏，差异数仍为 3（当前基线上为 `AC-004`）。本节检查的是图数据能不能表达这些状态，以及后面做筛选时还找不找得到必要的祖先和 removed 节点。完整的筛选开关、摘要和网页里的端到端走查留到 5.4，避免学员以为第二节就已经验收了「只看变化」。

除了嵌套案例，映射还要用 `fixtures/subtree` 核对：整棵被删子树的节点仍留在图数据里，差异数只在根计 2 处（当前基线上为 `AC-009`）；并用 `identical`、`key-order` 确认相同输入和键换序映射后仍是零差异，不能把节点 id 或建图顺序当成差异来源。错误输入属于 5.3；超限提示、状态除颜色外可辨认、窄屏和原有单输入界面的回归，在网页上走查时留给 5.4。本节若核对上限，只看映射产出的图数据是否把 removed 节点算进去，以及超限数据能否交给共享组件已有的扩展点，不在网页里看提示文案。
