## 本节内容

### 先做一次已经成功的比较

5.2 结束时，讲师和学员各自留下了可被现有图消费的映射、工作区外的一次性核对脚本和实际检查结果，以及更新后的 `CH05_IMPLEMENTATION.md`。生产代码里已经有差异模型和合并图数据，但用户还不能在网页里同时输入两份 JSON。进入本节，先确认当前副本仍在同一条功能分支上，差异模型和映射任务已经完成，再打开双输入与错误状态任务和它关联的规则、案例。讲师演示用的是 `course/ch05-baseline` 上已提交的 `docs/specs/`（当前基线上为 `TASK-03` 及关联的 `REQ-*`、`AC-*` 与 `docs/specs/fixtures/`）；讲师和学员的实际编号不必相同，每个人都要能在自己的文件里找到对应内容。

本节从学员会立刻碰上的问题开始：一边输入错了，已经得到的结果怎么办？不要从界面步骤讲起。先用 4.4 / 5.1 / 5.2 同一组嵌套素材 `docs/specs/fixtures/nested/`，做一次正常比较：

Before：

```json
{"user":{"name":"Lin","age":20},"active":true}
```

After：

```json
{"user":{"name":"Lin","age":21},"role":"student"}
```

界面上要同时有两个可编辑的输入位置，分别标注 Before 与 After；比较完成后应只有一张结果图，差异数为 3，`/active`、`/role`、`/user/age` 能在这张图上被看见（当前基线上为 `REQ-001`、`AC-001`，图的内容来自已经完成的映射）。用很短的一段沿这条路径说明：两侧输入先经过合法性解析，再交给已有的差异模型和图映射，最后更新界面。UI 只调用已有逻辑，不再复制一套算法。这一段只为后面的错误对照把「已经得到的结果」立住，不展开实现。

### 错误状态和上次成功结果是两件事

有了这张已经得到的结果图，再把其中一侧改成非法 JSON。打开 `docs/specs/fixtures/error/invalid-before.json`（内容为 `{"user": }`，故意不合法），把它写进 Before。

先请学员判断：已经得到的结果该怎么办？答案是：错误提示要指向出错的那一侧，但上次成功比较的结果仍应显示——合并图还在，差异数仍读作 3，不能被清空成空状态（当前基线上为 `REQ-020`、`REQ-021`、`AC-014`）。错误状态和上一次成功的比较结果是两件事，错误不能把已经得到的结果冲掉。

恢复成合法输入后，继续观察结果是否按当前两侧输入更新。还要检查另一种情况：刚打开页面、从未成功比较过，Before 一开始就是非法 JSON。这时没有历史结果可留，应显示空状态和指向 Before 的错误提示，界面上不能出现比较结果（当前基线上为 `REQ-022`、`AC-012`）。After 侧出错时，提示要明确指向 After，不能同时把 Before 说成出错方（当前基线上为 `AC-013`）。

本节让 Codex 把双输入和错误状态接到现有网页路径。允许修改的范围以当前任务文件为准；当前基线上写在 `TASK-03`：新增 Diff 视图的两份输入区，新增独立的 Diff 状态（第二份输入、最后一次有效比较结果、错误信息），并在现有编辑页增加 Diff 视图分支。不改 `useJson`、不改 `useFile.setContents` 链路，也不改 GraphView、TreeView、导入弹窗、`?json=` 和 widget 的既有行为。输入合法性沿用网页版既有解析依赖，不引入新的解析器。两份输入的最终形态与落位方式仍是未决项（当前基线上为 `REQ-032`），实现时保持可调整，不在本节固化布局。不顺带修改 VS Code、浏览器扩展或其他非目标 workspace。第 6 章才批准「明确提示当前图是上次有效结果」的 CR-01；本节不把该提示设为必做，也不要求刻意移除已有的等价行为。

「只看变化」开关、差异摘要、超限提示和 360px 窄屏的正式走查留到 5.4。当前基线上，窄屏验收（`AC-018`）还要求结果图与摘要都可操作，摘要尚未在本节完成；`AC-019` 的完整步骤还包含切换「只看变化」。本节若核对比对是否在本地完成，只看执行比较时请求里有没有带走这两份 JSON 的内容，不操作筛选开关。

### 完成边界在哪里

不要再把任务闭环讲一遍。请 Codex 读取当前的双输入与错误状态任务、关联的 Spec 和 Acceptance、固定素材，以及全局约束和非目标，只完成这个任务。请求中要写清：输入是 5.1、5.2 已经验证的差异模型和图映射；本次产出可操作的双输入界面和错误恢复；用哪些案例核对界面；允许改到哪里。摘要、筛选开关和超限提示留给后续任务。

验证沿用第 5 章已经核定的方式，不引入测试框架，也不在仓库里留下测试套件。当前基线上，这些检查是：运行 `pnpm --filter www run lint`；启动 `pnpm dev:www`，按首次出错、After 侧出错、出错后保留上次结果来走查；再用 `?json=` 与导入弹窗各走一次，确认单输入路径未被 Diff 状态污染。检查结果以实际运行和人工在界面上的观察为准，不能把 Agent 的完成说明当成核对结果。

当前基线上，本节用来判断双输入与错误路径是否完成的期望是：

| 场景 | 在界面上核对什么 |
| --- | --- |

若结果不一致，先确认输入、期望与 Spec，再看界面状态、已有模型和映射各自哪里偏离；不能为了让检查通过而把预期改成当前实现的结果，也不能在出错时把上次结果清掉，把「免得和错误混在一起」写成新规则。

**学员判断**：一侧输入非法时，错误状态与上一次成功的比较结果各由什么证据确认？要结合页面和输入操作来回答：错误提示指向哪一侧；上次结果是否仍在（合并图还在、差异数仍为 3，没有变成空状态）。只看 Agent 回复或一次正常路径，还不足以说明错误恢复符合验收。
