## 本节内容

### 从一组能立刻核对的输入开始

第 4 章结束时，讲师和学员各自留下了 JSON Crack 的规格基线：经人确认的行为、可核算的验收案例，以及结合源码拆好的实施任务。规格已经提交，生产代码里还没有 JSON Diff。进入本节，先核对当前副本处在规格提交上，工作区干净，再打开差异模型任务和它关联的规则、案例。讲师演示用的是 `course/ch05-baseline` 上已提交的 `docs/specs/`（`TASK-01` 及关联的 `REQ-*`、`AC-*` 与 `docs/specs/fixtures/`）；讲师和学员的实际编号不必相同，每个人都要能在自己的文件里找到对应内容。

本节从学员会立刻追问的问题开始：规格已经写好，怎样知道第一个任务做对了？先不要从任务步骤讲起，先看一组很小、但能当场核对的输入。打开 `docs/specs/fixtures/key-order/`：

Before：

```json
{"user":{"name":"Lin","age":20},"active":true}
```

After：

```json
{"active":true,"user":{"age":20,"name":"Lin"}}
```

字段与值相同，只是顶层和嵌套对象的键顺序不同。4.3 已由人决定：对象键顺序忽略；4.4 把这条规则写成了固定输入和零差异的期望（当前基线上为 `REQ-007`、`AC-006`）。学员先根据这条规则判断结果，再由讲师说明：差异数应为 0，所有路径都是 `unchanged`，也不该出现「字段顺序变化」这类条目。

检查的是键顺序，不是交换 Before 和 After 两侧的含义。两侧对调时，新增和删除本身就会反向，不能写成「输入顺序不能改变确定结果」。现有解析器按出现顺序发放节点 id；如果比较时复用这些 id，键换序会被误报成差异。差异模型要按路径对齐两侧，不复用那套 id。

这组输入让人立刻看见第一项工作的一部分应该达到什么结果，但它还不能覆盖任务要求的全部案例。当前基线上，`TASK-01` 还要在 `identical`、`nested`、`array-index`、`type-change`、`subtree` 上给出与已核算期望一致的结果；对应验收为 `AC-002`、`AC-003`、`AC-005` 至 `AC-009`、`AC-011`。筛选界面属于后面的任务，本节只核对模型是否给出状态、差异数，以及供后续筛选使用的「下层有变化」标记。

### 用很短的一段立住本章怎么干活

有了这个可核对的结果，再确定本次操作的起点。讲师从规格提交创建本地功能分支，核对版本和工作区。仓库没有测试框架，4.2 的调查和 4.5 的计划已经把验证方式核定为：用一次性脚本（不入库）把模型跑在 `docs/specs/fixtures/` 的上述六组素材上，对照已核算的期望；再运行 `pnpm --filter jsoncrack-react run lint`。本节不要引入测试框架，也不要在仓库里留下测试套件。若已有改动或检查受阻，保留现场并先处理起点；不能把未运行或失败的检查记为通过。

然后用很短的一段说明本章怎么干活：让 Codex 读取当前差异模型任务、关联的 Spec 和 Acceptance、固定素材，以及全局约束和非目标，再请它只完成这个任务。请求中要让 Agent 知道本次做什么、以哪些案例核对、允许修改到哪里。当前基线上，允许范围是新增 `packages/jsoncrack-react/src/diff/` 下的差异模型，并更新共享包导出；不改共享组件、不改渲染、不改网页版、不改现有 `parser.ts`。本次先做差异计算及其验证，图映射和界面留给后续任务。按需读取关联文件时，仍要带上适用的全局约束，不能只截一条规则就忽略非目标。`null` 与字段缺失仍是未决项，不要在本节写成实现决定；值等价判定要收敛到一个可替换的函数，除此之外不预设语义。

这段只讲一次，当作本章的工作方式，不要写成独立的「流程」小节，后面也不再重讲、不再画闭环图。5.2 起仍然做这些动作，但讲述重点放在每次新增的问题上。

### 完成边界在哪里

Codex 完成一次工作后，镜头不要停在「又走完一遍流程」，而要落到完成边界上。先看它实际改了什么：差异是否集中在当前任务允许的范围，是否有可重复的核对入口（那份一次性脚本留在工作区外，不提交），是否顺手修改了界面或其他客户端。再运行与当前任务相关的检查，打开固定输入和期望，先抽查对象键换序案例，再对照任务要求核对其余素材。检查结果以实际运行和人工核对为准，不能把 Agent 的完成说明当成核对结果。

固定期望来自已经批准的行为和人工核算，不能调用同一套待验证的比较逻辑来生成自己的期望。当前基线上，这六组素材的期望是：

| 素材 | 期望 |
| --- | --- |
| `fixtures/key-order` | 差异数 0，无任何状态或「下层有变化」标记 |
| `fixtures/identical` | 差异数 0，无任何标记 |
| `fixtures/nested` | 差异数 3；`/user/age` 为 `changed`，`/active` 为 `removed`，`/role` 为 `added`；`/` 与 `/user` 带「下层有变化」标记，不计入差异数 |
| `fixtures/array-index` | `[10,20]` 变为 `[5,10,20]`，差异数 3：下标 0、1 为 `changed`，下标 2 为 `added`，不报告移动或元素配对 |
| `fixtures/type-change` | `/v` 由数字 `1` 变为字符串 `"1"`，记为 `changed`，差异数 1 |
| `fixtures/subtree` | 差异数 2：`/gone` 与 `/extra` 各计 1 处；其子路径各自带状态，但不单独计处 |

若结果不一致，先确认输入、期望与 Spec，再看实现和核对脚本各自哪里偏离；不能为了让检查通过而把预期改成当前实现的结果。错误输入和节点上限属于后续任务，本节不必用那些素材判断差异模型是否完成。

**学员判断**：如果相同输入和对象键换序两个案例通过了，差异模型任务就一定完成了吗？没有。这两个结果只覆盖对应案例；数组、类型变化、嵌套路径和整棵子树计数若属于该任务，仍要按各自的要求检查。检查通过后，还要回看允许修改的范围和可解释的 diff，才有依据标记这个任务完成。其他任务的验收仍留给后续步骤。

学员用自己的规格和任务完成差异模型，并检查当前任务要求的案例。实现可以与讲师不同，但要能解释固定输入、预期、实际结果和代码改动。运行或环境受阻时，记录实际进展与错误，从学员已有的本地提交和课程提供的排障材料继续；不能承诺章节级恢复点。

完成本节后，留下差异模型、用于核对这批素材的一次性脚本和实际检查结果，以及 `CH05_IMPLEMENTATION.md` 初稿，记录本次任务、关联依据、实际检查结果和未解决的问题。下一节拿着已验证的模型，去看被删除的字段怎样出现在合并图里。
