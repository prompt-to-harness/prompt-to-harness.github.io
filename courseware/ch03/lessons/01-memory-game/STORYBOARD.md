## 本节内容

学生的直接收获仍是主页上的可玩游戏，以及理解大模型运行过程中的随机性。从第二章已有主页发出短请求，等待期间先看六份成品的不同效果，再只展开早期 05 与紫色版：从提前通关追到计数错误和验证分工，用紫色版对照正确计数与通关检查，再追溯难度、视觉设计和看图修正。从具体原因接到减少问题、保留好处、开发效率与 Skill。

讲完不确定性，直接回到本次主页中的游戏试玩。原请求已经包含主页接入，但没有要求公网发布；试玩通过后沿第二章更新发布，若本次版本已经在线则直接看公开效果。最后只留下如何稳定生成紫色风格的思考题，接到下一节。

六张页面共八个展示状态。PPT 承担本节主逻辑：作品目标 → 为什么结果会变 → HTML 里的案例与证据 → 回 PPT 区分设计空间与质量要求 → 复用开发方法 → 本次任务试玩与发布 → 回 PPT 总结作品与知识 → 风格稳定性思考题。证明和完整操作留在 HTML 或真实项目中，不把材料入口当作已经完成归纳。

两处回 PPT 的职责不同：p05 把案例发现归纳成下一次也能使用的判断，接住随机性并引出指导；p06b 在本次项目交付后收拢全节，明确学员做出了什么、怎样判断 AI 的过程与结果，以及如何复用经验。p01a 的具体样本用于解释更上层的任务与不确定性，不再六图平铺讲“几个游戏有什么差别”。

图示沿用实际图片与可编辑 SVG；讲师预留区、字幕安全区与阅读模式分别检查。每页只有一个标题，步骤只展开论证，不能靠换标题制造步骤差异。原稿、评论和既有跳转坐标保留。2026-11-09 整节对照后补明确的六图停留位置，关键代码与检查改用聚焦节选，游戏完整牌阵所需缩放写入提示；保留原正文坐标，只在第三段开头步骤的尾部追加六图讲述。详见 README 当前核验及正式审查记录。

每页底部 HTML 入口常显，另开窗口并保留 PPT。cases.html#checks 分析完成后返回 p05；cases.html#handoff 完成本次试玩发布后返回 p06b，再进入 p06a。六份快照、产品／视觉摘要、原稿与 3.2 入口继续可用，完整私有日志未扩大网络访问范围。

讲稿与画面引用来自 script.json 和 screen-plan.json；已有正文就近复用，原结尾收束段补充全节知识总结。PPT 源为 tools/memory-slides.py，由既有 build-lesson.py 调用。图片来源与录前缺口见 README。

## 第三段如何取材

讲师已确认按“差异 → 问题 → 好处 → 开发效率 → Skill”推进；最新要求删除 B2 深入讲述，只保留早期 05 与紫色版，并用运行记录解释差异的原因。六份概览与五段主导航保留。

本段要让学生理解：AI 自主补出的实现、设计和检查过程会影响成品质量；从具体结果中可以找出值得在后续任务中复用的做法。讲述按下面的因果关系推进，运行记录只承担相应的证据职责。

| 要讲清的判断 | 画面怎样支撑 | 怎样接到后文 |
| --- | --- | --- |
| 把玩法验收加入交付流程 | 早期 05 三对提前结束 → 张数与对数混用 → 计划只列构建和产物检查、试玩交给人 → 补上三对不能结束、六对才通关的验收预期 → 紫色版真实测试与完整一局检查 | 从错误和检查，转向 AI 还会主动补出哪些有用设计 |
| 自主补充的设计能够改善体验 | 切换三档牌数后，看实现前的产品规划：难度、分档成绩、通关后继续玩构成完整流程；对照早期 05 固定难度的范围选择。再看写界面前确定的整体视觉方向与交互反馈 | 先形成整体方案，仍要检查它能否在实际画面与行为中正确呈现 |
| 检查本身也要覆盖真实结果 | 紫色版 61 项检查通过，但初始牌面仍露出；检查只看状态标记 → 按玩家应看到的画面复核 → 修正正反面和动画并复查 | 从要求推导预期，核对检查覆盖范围，再归纳可以复用的方法 |

2026-11-08 最新调整：按讲师要求，难度与视觉部分改看实现前的设计决策，不从代码写法倒推设计动机。产品规划摘要对应三档难度、分档成绩和通关后选择；视觉摘要对应整体风格、信息组织和反馈。两处均据同一任务的原始会话补档整理，见材料 E12、E13；画面明确标为课程摘要。早期 05 的固定难度计划用于对照范围选择，不把任务条件不同讲成模型思考深浅的差别。原 HTML/CSS 记录保留备查入口。

2026-11-09 验证讲法补充：不能把“缺少玩法验证”和“测试本身依据不充分”混成一条链。早期 05 只按现存交付的验证范围讲补验收，不声称它从未测试或写了错误测试；紫色版用真实的状态检查与截图差异讲已有检查的局限。三对不能结束、六对才通关是课程提出的验收预期，不冒充历史测试结果。来源与边界见材料 E14。

随后回到案例归纳 PPT，把这些具体过程接回随机性：模型生成的方案和执行过程可能变化，一次做得好不能保证下一次还会采用同样的方法。难度、图案与配色可以留设计空间，关键规则和必要检查则需要明确。第三段提出“怎样让下一次也采用有效方法”，收在提前提供指导的需要。

案例分析后先回到 p05 归纳，再由第四段给出能迁移到下一个游戏的指导，再说明每次重写的重复工作；同类任务反复需要的经验适合单独保存、按需使用，由此引出 Skill。Skill 为任务提供可复用的依据，实际有没有采用、结果是否正确仍要检查。p06 用三个展示状态分别呈现方法、重复说明和 Skill 复用，讲师页只在这两次实际推进处另起画面块。完整逐字稿在 script.json，通过 screen-plan.json 就近配到操作下。A2 流程与 A1/A2 专门对照已退出当前讲述，其旧稿坐标保留在源文件分组中供追溯；不删除原始游戏和运行记录。

影响因果判断的请求分工与自主决定授权放在对应画面，其余配置和核验细节留备课说明。六份概览不标为六次严格同条件复跑，两个案例也不是控制实验。OLD5 的缺陷状态已有复现；正式录制以实际操作或明确的历史缺陷画面展示。紫色修错只展示原始记录，最终成品不冒充修复前画面。事件定位和证据边界见本节 README。

## 第五段怎样收尾

原请求是“在主页加入一个记忆翻牌小游戏”，完成标准是 build 成功。已核对 A1/A2 的主页接入与交付：本地主页已包含游戏，未执行公网部署。因此主线直接从本次主页进入游戏，试玩翻牌、配对进度、完整通关与重开，随后沿第二章更新发布并访问公开效果。实际已发布时跳过重复发布；若漏接入口则补齐，玩法出错则按真实现象修复并复验。

完成本次公开效果检查后先回到 p06b，收束作品交付与开发不确定性；再切到 p06a，留下“如果希望 AI 每次生成的游戏都稳定保持紫色风格，应该怎样做？”这道思考题。此处不演示改色、不追加视觉请求；下一节再展开 Skill。
