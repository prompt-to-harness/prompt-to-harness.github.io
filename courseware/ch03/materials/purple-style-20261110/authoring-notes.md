## 2. 提炼标准：什么算「风格」，什么算「这个游戏」

采用的判据是：**换一个玩法、换一套内容，这条规则是否依然值得遵守？**

→ **保留**：色彩角色与语义 token 分配、玻璃 vs 实体的材质分工、四级层次的光学逻辑、渐变方向一致性（92°–165°）、圆角/阴影梯度、hover/active/focus/selected 四态反馈、状态色的一次性出现、动效时长与缓动的档位、`tabular-nums`、浮层的焦点纪律、`prefers-reduced-motion` 降级、`localStorage` / `AudioContext` 的失败降级、3D 翻转与动画 `transform` 互相覆盖的坑。

→ **舍弃**：牌阵行列数与卡牌长宽比的具体取值、三档难度的命名与牌数、12 个 emoji、翻牌配对玩法本身、「步数/用时/配对/最佳」的统计口径与计分规则、胜负文案与庆祝 emoji、底部键盘操作提示文案、标题 emoji、localStorage 键名、音效频率表。这些在 Skill 正文 §14 里被显式列为「应自行替换」，避免后续会话把它们当成硬性规格。

→ **降级为「骨架」而非「规格」**：标题区→工具栏→统计条→主舞台→页脚的页面骨架、浮层的「图标→标题→说明→按钮」内容顺序。骨架被保留为默认起点，但 Skill 明确说明结构可替换。

→ **直接不写**：任何具体文件路径、原仓库目录结构、构建/测试命令、框架绑定。原游戏是零依赖的原生 HTML/CSS/JS，但 Skill 不把它当成强制技术栈，只在需要举例时给原生 CSS 片段。

### 本文件新增的判断（原作未直接规定，属提炼与建议）

- **色彩角色表的命名与分配方式**：原作是散落的 CSS 变量，Skill 把它们组织成「底色 / 光晕 / 主色 / 辅色 / 成功 / 失败 / 文字 / 玻璃」八类角色，并附加「主色同屏唯一」「青绿只给焦点环」等使用约束——原作代码符合这些约束，但约束本身是本次提炼补上的。
- **辅色只作焦点环**的理由：原作确实只在 `:focus-visible` 用了 `#56d6c6`，但「因为主色会被按钮填充吃掉」是本次的推断解释。
- **四级层次模型**（页面底 / 玻璃面板 / 交互实体 / 浮层）以及「靠亮度+模糊度+不透明度表达层次、不靠堆阴影」的总结：原作未写注释说明，属于对既有实现的归纳。
- **「状态色只在那一帧出现」**的总结，以及把成功/失败/中间态统一抽象为「改边色 + 改面色 + 加外发光」三件事。
- **阴影/圆角梯度的分级命名**（微反馈→卡片→主按钮→浮层），原作只有孤立数值。
- **「每列最多 108px」被提升为可保留规则**：这是原作 `.board` 的计算式，本次判断它比固定宽度更值得继承。
- **检查清单**（§15）：全部为本次新增。
- **应替换清单**（§14）：虽然其中多数条目确为原作事实，但「它们属于玩法而非风格」这一定性是本次判断。
- **把 3D `transform` 覆盖问题推广到「任何自带 3D 旋转又要叠加位移/缩放的组合」**：原作注释只针对翻牌案例，本次做了推广。

### 明确没有写进 Skill 的推断（避免把猜测当事实）

- 没有断言具体浏览器的渲染差异、模糊滤镜性能、动画帧率表现。
- 没有断言「最佳成绩显示格式」「统计口径」应当被沿用。
- 没有断言任何配色满足 WCAG 对比度阈值（未做计算与验证）。
- 没有引入原作不存在的组件（侧边栏、模态确认框、Toast、暗色切换等）。

## 4. 本初版的未验证项

1. **未运行原游戏**：全部视觉结论来自阅读 CSS/DOM 与三张静态截图，没有在浏览器里渲染核对。数值本身可信（直接摘自源码），但像素级呈现未复核。
2. **未验证跨浏览器表现**：`backdrop-filter`、`backface-visibility`、`aspect-ratio`、`background-attachment: fixed` 在 Safari / Firefox 上的渲染与合成差异未测试。
3. **未验证 reduced-motion 下的观感**：原作把动画时长压到 `0.001ms`，此时翻牌会瞬间完成、抖动与 pop 不可见；这种状态下的视觉是否仍然正确（尤其是 3D 翻转与 `is-open` 描边的配合）未实测。
4. **未做无障碍审计**：焦点可见性、对比度、屏幕阅读器播报顺序均未用工具验证；Skill 中的无障碍条目是照抄原作的合理做法，不是审计结论。
5. **截图本身的状态来源未确认**：`screenshot-initial.png` 里「最佳」已显示为「9 步 · 0:01」，说明截图并非全新状态（localStorage 已有记录）；该记录的来源未确认。另两张截图分别对应普通难度 4×4 与困难难度 4×6，不是同一局的连续画面。
6. **颜色未做色彩管理核对**：PNG 为 8-bit sRGB、无 alpha，但截图所用浏览器的色彩配置未确认，屏幕取色与 CSS 值可能存在细微差异；Skill 中的数值应以 CSS 源值为准而非以截图取色为准。
7. **声音与存储部分只做静态阅读**：`sound.js` 的实际音色、`storage.js` 在隐私模式下的降级路径未实测；这些内容在 Skill 中仅作为「工程约束」记录，不作为风格主张。
8. **Skill 本身未经他会话验证**：未做「只给这份 Skill、不给原项目」的新会话复现测试，因此「可被独立复用」这一点目前只是设计意图。后续若要在别的玩法上试用，最该先检查的是：色彩角色表是否足够让新会话做出配色决策，以及 §14 的「应替换清单」是否足够明确地阻止照搬牌阵与文案。
9. **源码中的两处非风格性观察**（不影响视觉，供参考）：`.board` 设置了 `--rows` 变量但 CSS 未使用（只用 `--cols`）；`game-core.js` 中 `buildDeck` 的奇偶注释说明「对数奇数是合法的」，与函数顶部「icons 数量为偶数」的注释措辞略有出入。
