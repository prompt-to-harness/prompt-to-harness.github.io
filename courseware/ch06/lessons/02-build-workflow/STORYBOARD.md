## 本节内容

### 先问怎么建流，再把目标说清楚

6.1 已经认清：第 4、5 章是工具无关的 SDD，GSD 用来接手已有规格，不能另起规划覆盖已有文档。进入 6.2，开场先问怎样在当前仓库把 GSD 工作流建起来，不把规则细节抢到第一句。但建流必须有靶子：本章目标仍是 CR-01，也就是给「上次有效结果」补一句对用户可见的说明。随后用一两页说清它改什么、不改什么，以及四个验收案例。第五章已经要求：Before 或 After 输入非法时，标明错误侧，并保留最后一次有效比较结果；但当时并不强制结果区域解释「这是旧结果」。CR-01 不改比较逻辑，只要求：已有有效结果且任一输入非法时，图与差异摘要继续保留，结果区域必须展示可见文本「上次有效结果（当前输入无效）」，错误区域仍分别标明 Before / After。仅当两侧恢复有效并完成重新比较，才移除提示并更新结果。首次输入就非法、还没有历史结果时，只显示错误或空状态，不声称存在上次有效结果。

四个固定验收已经写在内部大纲里，本节直接采用，不另发明一组案例：

| 验收 | 输入与动作 | 期望与证据 |
| --- | --- | --- |
| `AC-CR01-1` | Before 为 `{"n":1}`、After 为 `{"n":2}`，成功比较后将 After 改为 `{` | 保留 `n` 的一处 changed 与原摘要；显示旧结果文本及 After 错误 |
| `AC-CR01-2` | 在上一状态把 Before 也改为 `{`，随后只恢复 After 为 `{"n":2}` | 两侧非法时分别显示错误；仅 After 恢复后仍标 Before 错误，旧结果提示不消失，旧比较不变 |
| `AC-CR01-3` | 接着把 Before 恢复为 `{"n":2}`，等待比较完成 | 两侧有效，移除旧结果提示，摘要变为零差异 |
| `AC-CR01-4` | 全新页面还没有成功比较，直接输入非法 JSON | 错误或空状态正确，不显示不存在的历史结果与旧结果提示 |

规格处理是在原五层文档上追加 `REQ-CR01` 与上述 `AC-CR01-*`；Brief 记录变更原因，Plan / Tasks 追加本轮链接和状态。保留第五章提交与原验收，不把这条新规则追溯认定为旧实现缺陷。非目标也不变：不修改对象或数组差异算法、四种差异状态、计数口径、筛选语义、节点上限；不新增历史列表、自动保存、账号、网络上传或后端。这条提示与第 7 章快照四状态无关。

如果第五章的生成结果恰好已经满足 CR-01，本节只把规则写入工作流，并如实记下「行为已有、现纳入正式契约」这一检查点。真正补测试、受控变异或补提示，都留到 6.4，现在不预选分支。

### 当前仓库里，怎样用 GSD 建工作流

所谓「当前 repo」，不是课件仓库，而是学员从固定上游基线检出后建立的本地课程分支。第 4、5 章已经在这份副本里写出 `docs/specs/`，并实现过通过第五章验收的 JSON Diff。建流前要核对的输入仍写成检查点：可定位的本地实现提交、仍作为需求依据的五层规格、原验收状态、已有测试与已知缺口，以及能够解释的关键路径。不写死尚未存在的路径、测试名单、commit 或运行数字。

然后基于这些已有工作，把已有规格接进 GSD：导入 `docs/specs/`，形成可执行的计划、验证去向和停止条件。权威需求仍留在 `docs/specs/`，执行进度由框架工作区管理。验证方式在这里选定并写入工作流：纯逻辑走单元，界面状态走组件或交互，关键恢复路径走 E2E，视觉体验留给人工。原对象 / 数组 / 删除 / 错误 / 筛选 / 节点上限 / 隐私等验收仍要有验证去向。计划里建议不超过三个串行任务：原验收缺口补测；CR-01 失败测试与最小实现；浏览器回归与交付。每个任务标出来源、允许文件、测试目标、断言和停止条件。不按覆盖率或测试数量验收，不测试私有状态或 CSS 类名，不另写一套无关联的 GSD 产品需求。

本节以建流为主，还不是把提示改进产品。工作流跑起来，不等于 CR-01 已经做完。

### 完成边界在哪里

离开 6.2 时，应当留下：经人批准的 CR-01 规格、一份指向该目标的工作流、验证矩阵和计划初稿。原规格没有被覆盖，本节也还没有改生产实现。6.3 要问的是：这条流程是否符合预期，能不能拿去实施。
