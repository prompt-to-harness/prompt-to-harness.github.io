## 本节内容

### 先把名字说清楚

第六章要在已经验收过的 JSON Diff 上继续做事，但开场先不安装工具，也不派任务。先用一页回顾把名字说清楚，说完立刻进入 GSD。

这一页只留三句话：第 4、5 章已经是规格驱动；先写清再改代码；规格在 `docs/specs/`，不跟着换工具重写。SDD 就是先写下并批准「要做成什么」，再按这份规格去实现和验收。第 4 章把 JSON Diff 写成五层规格，第 5 章按这些已经批准的规格把功能做出来，当时并不依赖某个框架，所以前面两章已经是 SDD。不要把 4.1 的五层定义再讲一遍，也不要把 Brief、Spec、Acceptance、Plan、Tasks 再展开成新课。

### GSD 是什么，和前面那套做法是什么关系

GSD 是社区里的一套 SDD 实现，用来接手已经写好的规格，把调查、规划、执行和验证组织成可重复的工作流。它不是另一种需求，也不是让人把前面两章推倒重来。

本节要立住的硬边界是：不能另起一套规划，去覆盖已经批准的文档。权威需求仍然留在课程副本的 `docs/specs/` 里。GSD 可以帮你看清仓库、补验证、把后面的规则变更做成可执行的计划，但不能把已有规格静默换成框架新写的另一套，也不能把工具流程本身当成新需求。

GSD 固定为 `open-gsd/gsd-core v1.13.0`，commit `b5b9814f033b6d32810562fd4068e1f107da29ec`，MIT。安装、命令、映射和耗时尚未实测；未实测前，不能宣称实操已经走通。框架或派发不可用时，走标明来源的回放和第 4–5 章流程，并分别标记未完成项，不把降级结果当成框架通过。

### 先讲清，再上手

边界立住以后，再看 GSD 怎么用。上手的对象就是眼前这份已经验收的 JSON Diff：先做版本与权限审查，再做一次真正的接触——安装固定版本、新开会话、onboard，以及一次实际的 mapper 委派。四个 mapper 分别调查 tech、arch、quality、concerns，生产代码只读，调查文档分区写入；主 Agent 负责抽查证据和裁决冲突。Brooks / Conway 只用来解释「分工会带来协作成本」，不当作多 Agent 更快的证明。

本节的产出是认识，加上对工具的第一次接触，不是整条指向 CR-01 的工作流。把已有规格导入、批准变更、建成可执行计划，都留到 6.2。不要在本节把 JSON Diff 重新列成全套待开发任务，也不要开始改生产代码。

### 完成边界在哪里

离开 6.1 时，学员应能用自己的话说明：什么是 SDD，为什么第 4、5 章已经是 SDD，GSD 是社区里的一套实现，以及它不能另起规划覆盖已有文档。现场还应留下固定版本记录、一次经抽查的实际委派，以及工作区初态。原生产代码和规格没有被初始化重写。顺序调查、回放或 generic fallback，不能记作 Sub-agent 委派通过。

### 本节判断

第一次接触做完了，是不是就可以开始改规则了？还不可以。本节只证明：人还认得已有规格，框架也没有把它们覆盖掉，并且真正做过一次可核验的委派。指向 CR-01 的工作流，要到 6.2 才建。
