# 4.3 要求写得再细，为什么还会跑偏？

章内分工见[章级故事线](../../../../docs/outline/proposals/2026-11-02-ch04-storyboard.md)，制作状态见[章目录](../../README.md)；本文保存 4.3 的连贯内容（2026-11-09 讲师确认）、逐页安排与素材状态；章级故事线只保留摘要。

## 本节内容

### 从 Brief 的 Open 问题开始

4.2 结束时，我们手里有需求原文快照和 `docs/specs/BRIEF.md`。Brief 写清了这次要做网页版 JSON Diff、哪些不做、仓库里查实了哪些事实，最后一节是 Open 问题：原文里还没定下来、会改变实现的地方，每条都带着原文出处，有的下面还附着 Agent 的建议。

本节的问题是：“要求写得再细，为什么还会跑偏？”我们逐条处理这些 Open 问题，用几段很小的 JSON 看清每个问题有几种合理做法，由人选定一种，再写成第二份规格文档 `SPEC.md`。

每个人在 4.2 跑出来的 Brief 不完全一样：Open 问题的条数和编号不同，Agent 附的建议也可能不同。本节不依赖某个编号，打开自己的 Brief，找到对应的那一条即可。

### 同一句话，几种合理的结果

先看对象键换序。Before 是 `{"a":1,"b":2}`，After 是 `{"b":2,"a":1}`。两个字段的值都没变，只是顺序换了。一种实现逐个比对字段，结论是没有差异；另一种按文本逐行比对，会把两行都标成改动。两种都说得通，需求原文自己也写着“组里意见不太一致”。

再看数组插入。Before 是 `[10,20]`，After 是 `[5,10,20]`。按位置比，第 0 位从 10 变成 5，第 1 位从 20 变成 10，第 2 位新增 20，一共 3 处差异；按元素对齐，结果只是开头新增了一个 5。后一种更符合直觉，但要先回答“怎样算同一个元素”：数字可以按值认，商品列表里的对象要按哪个字段认？4.2 里 Agent 可能建议过 LCS 或业务主键，这些都是对齐的办法，选哪一种、做不做，仍要人决定。

最后看类型变化。Before 是 `{"n":1}`，After 是 `{"n":"1"}`。界面上都显示成 1，一种实现会认为没变，另一种认为值变了。需求原文第 5 条明确说“这种我们也想知道”。

这三组例子回答了本节的问题。原文已经写了“把不同的地方高亮出来”“数组也要支持”，写得再细，也没有说什么算不同、元素怎样对上。每个实现者都会用自己的默认做法补上空白，Agent 也一样，于是做出来的东西各不相同。能消除分歧的，是一个人看过各种结果和代价之后作出的决定，并把它写成规则。

### 讲师作为需求负责人逐项决定

本课程由讲师担任需求负责人，对每个问题说明选择和代价：

| 问题 | 课程决定 | 代价或范围 |
| --- | --- | --- |
| 对象键换序算不算差异 | 不算，对象键顺序忽略 | 真正关心字段顺序的场景不在本次范围 |
| 数组怎样比较 | 按索引逐项比较 | 规则简单、结果容易人工核算；中间插入一项，后面各项都会显示为改动，这一点要写进 Spec；按元素对齐、移动检测留在非目标 |
| `1` 变成 `"1"` | 值或类型改变都记为 `changed` | 不再细分“只是类型变了” |

### 从比较值到表达成图

JSON Crack 把数据画成图，差异也要在图上看得到。看一个嵌套的小例子：

Before：

```json
{"config":{"retry":3,"debug":true}}
```

After：

```json
{"config":{"retry":5}}
```

`retry` 从 3 变成 5，记为 `changed`。`debug` 只在 Before 里有，记为 `removed`；如果只画 After，这个节点就从图上消失了，需求原文第 4 条“删掉的字段也要能看出来”说的正是这件事。所以结果要画在一张合并图里，Before 独有的节点也保留下来。

`config` 本身在两侧都是对象，它没有被增删或改类型，只是里面有变化。它的状态仍是 `unchanged`，另外带一个派生标记 `hasDiffDescendant`，帮助用户顺着它找到下面的改动，但不计入差异数。这个例子的直接差异是 2 处。

由此得到四种直接状态：`added`、`removed`、`changed`、`unchanged`，再加上祖先的派生标记。

### 其余行为的决定清单

差异怎样判定、怎样画出来已经定了。用户还会筛选、输错、贴进很大的文件，这些行为也要在交给验收前定下来。讲师用一张清单逐行说明依据和决定：

| 行为 | 依据 | 课程决定 |
| --- | --- | --- |
| 差异计数 | 前面的状态规则 | 统计直接差异；只带派生标记的祖先不计入；新增或删除一整个对象或数组时只在它的根计 1 处，其中的节点仍逐个标为 `added` 或 `removed` |
| 只看变化 | 原文第 3 条 | 隐藏未变化的节点，但保留通向差异所必需的祖先和 removed 节点；切换筛选不改变差异数 |
| 输入出错 | 4.1 体验时看到现有编辑器遇到非法输入会保留上一次的图 | 指明出错的是 Before 还是 After，保留最后一次有效的比较结果；还没有成功比较过时显示空状态和错误提示 |
| 节点上限 | 4.2 调查查实的现有上限设定 | 合并图沿用 JSON Crack 现有的节点上限设定，不另定新数值；removed 节点也是图上的节点，一并计入；超过上限时不渲染合并图，只提示图太大，不沿用现有提示里的外部产品升级链接 |
| 本地处理 | 原文第 6 条 | 比较在浏览器本地完成，JSON 内容不因比较功能发送到网络 |
| 可辨认、可操作 | 网页版的使用条件 | 每种状态除颜色外还有文字或符号可以辨认；在 360px 宽的窗口里，两侧输入、错误提示和结果都能操作 |
| 其他客户端、数据格式 | Brief 的非目标 | VS Code 插件、其他数据格式标为 `Deferred` |

节点上限这一行要和调查对上：现有上限来自仓库配置，开发环境与生产构建的取值不同，没有配置时还有一个缺省值。Spec 只写“沿用现有设定”这一行为，具体数值属于实现环境。4.4 的节点上限案例统一在学员跟做时运行的 `pnpm dev:www` 环境下核算，此时上限是 2000。

### 写成 SPEC.md

这些决定进入 `docs/specs/SPEC.md`。每条规则一个 `REQ-*` 编号，写用户能观察到的行为，并标一个状态：已批准的写 `Approved`，这次不做的写 `Deferred`，还缺决定的写 `Draft` 并说明缺什么。每条注明来自 Brief 的哪一节或哪个 Open 问题，这样 Brief 里的每个问题都有去处。

4.1 立过一条分工：Spec 写行为，代码改哪里留给 Plan。拿两句话对照：“对象键顺序不同，不产生差异”是用户能看到、能检查的行为，写进 Spec；“在解析函数里先把键排序再比较”说的是实现安排，留到 4.5 结合源码决定。前一句不随实现方案改变，后一句换一种实现就要重写。

### Agent 起草，讲师逐条审

讲师把决定清单交给 Agent，请它依据 Brief 和清单起草 `SPEC.md`：每条规则编号、写可观察的行为、标状态、注明来源，最后列出 Brief 的每个 Open 问题对应到哪条规则。只新建这一个文件。

起草后讲师逐条审五件事：

1. Brief 的每个 Open 问题都有去处，或成为规则，或标为 `Deferred`，或留作 `Draft` 并写明缺什么
2. 每条 `Approved` 规则用户都能观察到，能说出怎样检查
3. 规则里没有文件名、组件名和函数名
4. 状态与决定清单一致，Agent 的建议没有被写成 `Approved`
5. 清单没覆盖的地方，Agent 没有自己补一个默认做法

审出的问题交给 Agent 修改，和 4.2 审 Brief 的做法一样。写完运行 `git status`，新增内容只在 `docs/specs/` 下；本节不提交，到 4.5 和其余规格文档一起提交。

学员用自己在 4.2 写的 Brief 和课件给出的决定清单完成同样的起草与审查，得到自己的 `SPEC.md`。课件给出审查五项，不给 Spec 的参考答案。

### 学员判断与下一节的起点

用一个判断检查本节：Spec 里有两条，一条写“两个值类型不同，标记为 changed”，另一条写“在合并图组件里调用比较函数”。哪条该留在 Spec？

第一条是用户能看到的行为，可以成为规则；第二条是实现安排，回到 Plan。审 Spec 时，同时找两类问题：还没决定的边界，和混进来的实现安排。

结束时，学员能用具体输入说明一句需求有哪几种合理解释，能分清 Agent 的建议与人的决定，并写出带编号、状态和来源、经过审查的 `SPEC.md`。下一节拿具体输入逐项核算，检查这些规则能不能给出一致的答案。
