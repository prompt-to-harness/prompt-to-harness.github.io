## 本节内容

### 已经有规则，怎样判断做对了

4.3 把人决定的产品行为写进了 `docs/specs/SPEC.md`。例如，对象键换序不算差异，数组按索引比较。讲师和学员各自审过 Spec，但每个人的规则编号和文档内容可能不同，本节要打开自己那一份作为依据。

本节从一句看似明确的规则开始：“只显示变化，并统计差异数量。”光靠这句话，还不足以判断实现是否做对。要拿一组确定的输入和动作，逐项对照应该出现的结果。这样，讲师、学员和之后接手实现的 Agent 看的就是同一把尺子。

先处理和本节案例有关、已经由人确认的规则。如果发现标着 `Approved` 的规则仍有冲突，先回去审清楚，再为它固定答案。与当前验收无关的 `Draft` 不必为了开始本节一并批准。

### 先拿两份 JSON 手算

先看一对嵌套数据。这是合成教学样例，以下结果依据课程已确认的规则手工推导，不是已经运行出来的产品结果。

Before：

```json
{"user":{"name":"Lin","age":20},"active":true}
```

After：

```json
{"user":{"name":"Lin","age":21},"role":"student"}
```

学员可以暂停，先判断哪些地方变了、各是什么状态；讲师随后按 Spec 核对：

| 路径 | 直接状态 | 理由 |
| --- | --- | --- |
| `/user/age` | `changed` | 数值由 20 变成 21 |
| `/active` | `removed` | 只存在于 Before |
| `/role` | `added` | 只存在于 After |

直接差异共 3 处。`/user` 两侧都是对象，本身保持 `unchanged`，但下层有变化，带 `hasDiffDescendant` 标记，不增加差异数。

再看“只看变化”开启后应该看到什么：`/user/age`、`/active` 和 `/role` 留在图上；`/user` 是定位 `/user/age` 所需的祖先，也保留；未变化的 `/user/name` 隐藏。

**学员判断**：筛选后的图保留了 `/user`，差异数是否要从 3 变成 4？不要。保留祖先是为了定位，计数仍为 3；开启筛选前后差异数不变。这里一次核对了差异路径、状态、数量和筛选上下文，每一项都能回到输入和规则解释。

### 把判断写成可重复核对的案例

刚才的判断不能只留在讲述里。把输入、动作和期望写下来，之后每次都能用同样的条件检查。这就是本节的 Acceptance（验收）：为已经决定的行为留下可观察、可核算的完成标准。

用 Given–When–Then 把上面的判断组织成一条案例：

| 部分 | 这条案例写什么 |
| --- | --- |
| Given（给定） | 上面固定的 Before 和 After，筛选设为关闭 |
| When（操作） | 比较两份输入，再开启“只看变化” |
| Then（预期） | `/user/age` 为 `changed`、`/active` 为 `removed`、`/role` 为 `added`；差异数为 3，筛选前后不变；`/user` 保留，`/user/name` 隐藏 |

这条案例要写进 `docs/specs/ACCEPTANCE.md`，给一个 `AC-*` 编号，关联自己 Spec 中关于直接状态、计数和筛选的 `REQ-*`。一个案例可以同时核对多条规则，一条规则也可以由多个案例检查；编号用于找到对应内容，不替代对预期的核算。

固定的输入和期望称为 fixture（验收与测试可重复使用的固定素材），放在 JSON Crack 练习仓库的 `docs/specs/fixtures/`，和其它规格资产放在一起。上面的 Before、After 与预期差异需要保存下来，不能只留“比较这两份 JSON 应该正确”或让以后每次运行自己生成一个新答案。筛选、错误、窄屏等涉及状态和操作的检查，还要在验收案例中写明操作顺序和观察点。

本节先建立验收依据。第 5 章实现后，才能拿实际功能与这些案例对照；需要人工操作的项目也要写清检查方法，不能因为有 fixture 就默认已经自动测试通过。

### 从一条案例扩展到一组验收

一个嵌套案例不能覆盖全部规则。回到 Spec 的当前 `Approved` 条目，找出还需要什么输入、初始状态和操作；优先复用 4.3 已经讨论过的小例子，再补错误和使用条件。

| 案例或检查组 | 需要固定什么、核对什么 |
| --- | --- |
| `same`、`object-order` | 相同输入，以及只改变对象键顺序的输入；直接差异数都为 0 |
| `add-remove-change`、嵌套 | 固定新增、删除、值变化与深层路径；核对状态、差异数和筛选上下文；整棵对象或数组增删时，还要核对根计 1 处、子树节点逐个标状态的口径 |
| `array-index` | `[10,20]` → `[5,10,20]`；按索引核算两处 `changed`、一处 `added`，共 3 处，不报告移动 |
| 类型、空值 | 固定类型变化的两侧输入并按已批准规则核算；`null` 与字段缺失按同样规则处理，并固定对应验收案例 |
| `invalid-before`、`invalid-after` | 分别固定某一侧非法的操作；已有有效结果时检查错误侧和保留的结果，首次比较即非法时检查空状态与错误提示；改回合法输入后再次比较并核对结果 |
| `node-limit` | 在约定上限及其两侧准备可重现的输入，写清合并图节点数的核算；核对超限提示及不渲染合并图 |
| 窄屏、可辨认与操作 | 在 360px 宽窗口中检查两侧输入能否操作、错误提示是否可见、结果能否查看；检查每种状态是否有颜色之外的文字或符号。键盘相关案例仅在 Spec 已有相应 Approved 规则时再补，不作为本节必做组 |
| 本地处理 | 写清比较时怎样检查相关网络请求，核对 JSON 内容不因比较功能发送到网络 |

节点上限案例以学员跟做的 `pnpm dev:www` 环境为准，按 2000 核算，合并图中的 removed 节点也计入；超过上限时只提示图太大，不渲染合并图。这里的 2000 是该环境的取值，Spec 的产品行为仍是沿用现有上限设定。构造边界输入时要能说明图中节点怎样计数，不能直接把 JSON 的行数当成节点数。

本地处理的检查关注本次 JSON 内容是否因比较而发出；不能把页面出现任何网络请求都当作违反这条规则。视觉和交互验收写清窗口尺寸、操作及能观察到的结果，不以逐像素一致作为默认要求。

案例组扩完后，再转问：如果第 5 章实现后，相同输入、键换序和数组案例都通过了，能否据此宣布整个 JSON Diff 验收完成？还不能。这些结果只说明对应案例通过，错误恢复、节点上限、窄屏、状态可辨认和本地处理等要求仍要按各自关联的案例核对。覆盖表帮助找到缺口，但有编号还要看案例本身是否能检查对应规则。

### Agent 起草，讲师核算和检查覆盖

讲师沿用当前 JSON Crack 副本，请 Agent 读取已经审过的 `SPEC.md`，根据其中已确认的规则起草 `ACCEPTANCE.md`、固定素材和需求与验收的对应关系。请求要说清案例需要固定输入、动作和预期，每条案例要关联哪些实际存在的 `REQ-*`，以及这一步只写规格与验收素材、不修改生产代码。尚未决定的行为列出来交给人判断，不由 Agent 补成标准答案。

Agent 起草后，讲师打开实际文件核查，而不只看回复里的“已完成”。先抽查上面的嵌套案例：输入是否保存，三条路径与状态、计数、筛选结果是否和手算一致；再选一个错误或边界案例，检查前置状态、动作和预期是否写得足以重做。若现场结果有问题，就指出实际问题和依据，请 Agent 修改后回看；没有发现问题时继续核对，不为了演示而预设 Agent 会出错。

最后按需求检查覆盖：每条当前 `Approved` 需求至少有一个对应的 `AC-*`，每个 `AC-*` 都能指回需求；同时检查关联的案例是否真的核对了那条行为。`Draft` 或 `Deferred` 不因为缺少验收案例而自动变成已批准。做案例时若发现规则冲突或缺少决定，先回 4.3 由人确认并修订 Spec，再回来固定相关预期。

学员以自己在 4.3 形成的 Spec 和课程决定为输入，组织请求，检查并修改生成的 `ACCEPTANCE.md`、fixtures 与追踪关系。讲师和学员的实际编号、生成结果可能不同，判断依据是各自文档中的已批准规则。检查工作区中的新增和修改，确认本节只增加规格与验收素材，没有改生产代码；本节不提交，留到 4.5 连同规格基线一起提交。

### 下一节的起点

本节结束时，学员留下 `ACCEPTANCE.md`、`docs/specs/fixtures/` 下的固定素材，以及 `REQ-*` 与 `AC-*` 的对应关系；阻塞案例的未决规则继续留给需求负责人决定。下一节拿着 Spec、Acceptance 和已有的源码调查，决定怎样实施，再把工作拆成有边界的任务。4.5 将把需求、验收与任务的完整追踪关系集中到 `TASKS.md`。
