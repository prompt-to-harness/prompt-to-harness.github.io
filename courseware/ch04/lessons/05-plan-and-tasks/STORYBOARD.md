## 本节内容

### 规则和案例都齐了，为什么还要写计划

上一节留下了已经审过的 `SPEC.md`、`ACCEPTANCE.md`，以及 `docs/specs/fixtures/` 里的固定素材（验收用的固定输入和期望）。讲师和学员各自的编号、案例条数可能不同，本节要打开自己的那几份作为依据。

本节从学员会追问的问题开始：规则和案例都齐了，把它们拼成一个长请求交给 Agent，为什么还要再写 Plan 和 Tasks？如果只靠一个很长的请求把整件实现做完，任务一长，过程中就可能自动压缩上下文，写在请求里的任务约束就有可能丢失或被冲淡，后面的行为会变得不稳定，事后也不容易检查。实现也不是把规则和案例再抄一遍。这次改动会同时碰到差异计算、图数据、输入状态和筛选摘要。要先看清改哪里、怎样验证、怎样留下检查点，而不是一次把整件功能写完再回头检查。

先处理和本节实施有关、已经批准的规则与案例。如果发现仍标着 Approved 的规则有冲突，先回到上一节的上一节，把规则审清楚再往下写。尚未决定的行为，尤其是 `null` 与字段缺失，不要在本节写成实现决定。VS Code、浏览器扩展和其他数据格式仍然延后，不纳入这次的任务。

### 先看清这次会改到哪里

本节以 4.2 已经核实、并写进 Brief 的仓库事实为起点，不再重复走一遍从输入到渲染的链路。还要补一轮很薄的、针对实施的核对：这次方案会改到哪些地方，入口在哪，用什么方式验证。没有源码依据，就不要把路径和命令写进计划。

4.2 做调查时，还没有完整的 Spec 和 Acceptance。现在带着已批准的行为和案例回去看，是为了把影响范围看具体，不是为了开始改生产代码。本节仍然只写规格资产。

### 比较两种改法，再写下计划

先比较两种和当前任务有关的改法。一种是在界面里直接比较两份输入，并生成展示；另一种是先形成独立的差异模型，再映射到现有图数据。对照已经核实的调用关系，看它们分别会改动哪里、怎样验证、会不会把计算和图展示缠在一起。

课程倾向把差异模型和图映射分开：先能单独核对“算得对不对”，再接到现有图上。这是有依据之后的选择，不是一开始就只能这样写。最终影响哪些文件、可复用入口和验证方式，要有源码依据后再写进 `docs/specs/PLAN.md`。

Plan 记录所选方案、取舍原因、影响范围、风险和回退安排。它接受 Spec 里已经批准的行为，同时允许调整实现手段。如果只是换一个图数据的适配位置，更新 Plan 和相关任务即可；如果要改变已经批准的行为，例如数组怎么匹配，就回到 Spec，由人决定，并同步验收。

### 按依赖拆成四项可检查的任务

方案有了边界，再按依赖拆开，写进 `docs/specs/TASKS.md`。下面的划分用来说明怎么切，正式编号等实际规格资产确定后再写。

| 任务 | 实施范围 | 主要验证对象 |
| --- | --- | --- |
| 差异模型 | 输入对应关系、直接状态与派生标记、计数 | 固定 JSON 输入与期望差异，先验证纯逻辑 |
| 合并图映射 | 将模型映射到现有图，保留 removed 节点与必要祖先 | 图数据能够表达既定状态及筛选上下文 |
| 双输入与错误状态 | 接入 Before/After、单侧错误与最后一次有效结果 | 正常比较、错误及恢复路径 |
| 摘要、筛选与验收 | 接入摘要、只看变化与非纯颜色表达，完成整体验收 | 当前验收项，以及原有单输入路径的回归 |

任务按顺序验证，后一项承接前一项已经确认的结果。每一项还要写明输入、允许范围、依赖、对应的已批准需求和验收案例、验证方法，以及怎样才算做完。执行时让 Agent 读取当前任务、相关规则和案例，同时保留全局约束与非目标，避免只读当前任务时漏掉仍然有效的限制。

小任务让一次改动的检查和本地回退更具体，仍要对照关联验收判断是否做完。这里不预设“一次性写完一定失败”，也不把模型碰巧漏项当作本节的转折。学员看到的是：范围缩小以后，人可以更清楚地核对改动、验证结果，并留下检查点。

### 用一条规则把需求、验收和任务串起来

用同一条“忽略对象键顺序”的需求走一遍追踪：Spec 写规则，Acceptance 固定换序样例和零差异的期望，差异模型任务引用它；整体验收再确认界面的计数与展示遵守同一规则。以后改这条需求时，也能沿着对应关系找到要复核的案例和任务。

需求、验收和任务的完整对应关系集中写在 `TASKS.md`。各文档用编号指向规则和案例正文，不靠把正文复制到每一处来保持一致。讲师和学员的实际编号可能不同，判断依据是各自文档里已经批准的内容和对应关系。

**学员判断**：差异模型的几个案例通过后，能不能把 JSON Diff 整个功能标记完成？不能。这只支持当前模型任务的相应结论；图映射、界面接入、错误恢复和整体验收，还有各自的任务和验证。

### 请 Agent 起草，人来审查范围和依赖

讲师沿用当前 JSON Crack 副本，请 Agent 读取已经审过的 Spec、Acceptance，以及 Brief 里已核实的仓库事实，在核对该实施影响面之后，起草 `PLAN.md` 和 `TASKS.md`，并补全需求、验收与任务的对应关系。请求要说清：只写规格资产，不修改生产代码；方案和任务范围要有依据；未决行为列出来交给人，不要写成实现决定。

Agent 起草后，打开实际文件核查，而不只看“已完成”。抽查所选方案有没有说清取舍和影响范围，四项任务的依赖和验证是否写得足以检查，以及一条已批准需求能不能走到对应的案例和任务。若范围、依据或依赖有问题，就指出实际问题和依据，请 Agent 修改后再回看；没有发现问题就继续核对，不为了演示而预设一定会出错。

学员以自己的 Spec、Acceptance 和已核实的仓库事实为输入，组织请求，检查并修改生成的计划与任务。检查工作区时，新增和修改只应出现在规格目录，不能改生产代码。确认之后，把 Brief、Spec、Acceptance、Plan、Tasks 和固定素材作为规格基线单独提交，作为第 5 章的起点。本节仍然不实现 JSON Diff。

### 这一节留下什么

本节结束时，学员留下 `PLAN.md`、`TASKS.md`，以及需求、验收与任务的完整对应关系；未决规则仍由人决定。规格基线已经提交，生产代码保持不变，交给第 5 章按任务实现。

回到本章开头的问题，沿着已经完成的工作回答：原文经过调查形成 Brief，歧义经过人决定形成 Spec，规则经过核算形成 Acceptance，方案和工作范围落实为 Plan 与 Tasks。今后仍通过 Prompt 发起工作，但实现依据是这些可以查阅、按版本维护的约定。
