## 本节内容

### 从读一份需求，转向日常怎么用工具

4.5 已经把规格基线交给第 5 章。这一节不再改 JSON Diff，也不接着写规格。开头顺着学员可能的追问：4.2 只用飞书 MCP 读过一份需求，日常要处理一组资料时，还能怎么把工具交给 Agent？MCP 是其中一种方式；飞书官方目前给个人用户的推荐，是官方命令行工具（飞书 CLI），通过技能调用，不是 MCP。本节飞书主案例用官方 CLI，AntV、高德和其他短演示仍用 MCP。本节用独立的合成教学材料来回答。这一节偏重演示：开场和接入只作很短的铺垫，后面每个工具都先出现要处理的材料和要核对的结果，再现场做。口播只点出该看什么、怎样判断，不单独开很长的知识页。学员以看懂为主，按自己的需要选做即可。

### 先讲清飞书的两种接入方式

4.2 只讲清了 MCP 是什么，并且只用飞书 MCP 开放了两个读取工具。当时说过，接入放到这一节补上。接入飞书现在有两种方式。按官方文档的用法：飞书 CLI 本质上是一组技能（Skill），安装后要重启 AI 工具让技能加载，Agent 通过技能调用命令行，适合个人使用；在团队环境里，需要搭建 Agent 工作流时，飞书 MCP 更适合。两种不要混为一谈，也不要把命令行工具说成 MCP。这一节是个人使用的场景，所以后面用飞书 CLI 作演示，不再补 lark-mcp 的自建应用、重定向地址和 3000 端口那一套。用 CLI 接入时要做的事：按官方文档安装飞书 CLI，重启 Codex 让对应技能加载，再用 `lark-cli auth login` 以本人身份授权一次。配置时默认会新建应用，也可以选用已有应用。不以本人身份登录时，就不能访问个人资料；这一节演示需要读讲师准备的文档，所以要完成登录。这里不再重复“MCP 是什么”。凭证和密钥不进入公开材料和画面。官方说明里，云文档的创建、读取、更新和评论，以及电子表格、多维表格和知识库，都在能力范围内，但仍要演练后按实际结果讲，做不到就保留实际范围。没有完成接入的学员，也可以通过准备好的教学文档和演示记录看懂后面的案例。做完这一段，就进入演示。

### 飞书：按资料类型分开演示

飞书仍用一场虚构的“开发者分享会”串起来，但按资料类型分开演示，不要把云文档、电子表格和多维表格当成同一种东西。

先做云文档。讲师准备活动方案、评审补充材料、几条教学评论，以及方案里一张报名意向普通表格。先让大家看见要处理的资料，再让 Agent 搜索对应云文档，读取正文和评论，整理已定安排、建议和待决定事项，每项保留来源。讲师抽查一条原文和一条评论，说明归纳怎样回到来源。建议不能直接写成已经通过的决定。内容核对后，讲师明确指定新整理稿的位置和范围，创建“评审结论与待办草稿”，再打开实际文档检查标题、正文、来源和待办。随后给出一个明确决定，例如“答疑环节确定为 20 分钟”，只修改整理稿里相关安排和待办，并比较实际变化。不能只看对话里的“已完成”。这一段用来看清：怎样找到正确文档，怎样区分正文和评论，读取和写入各要什么权限，怎样指定创建和更新的目标，以及怎样核对实际结果。演示写入只针对讲师准备的教学文档，不向群聊发消息。

接着单独演示电子表格。同一场活动另有一份电子表格，例如分场次的报名统计，不要用刚才云文档里的普通表格代替。先让大家看见表里有什么，再让 Agent 读取指定工作表，完成一项范围明确的核对或更新，例如核对某一场的人数，或按讲师决定改一个格子。打开实际表格检查变化。再单独演示多维表格。例如用一张多维表格记录主题、场次和跟进状态，让 Agent 按条件查出记录，或按讲师决定新增、更新一条，再打开实际多维表格核对。这两段都是短演示，让学员看见不同资料类型要用不同工具和权限，不是一节飞书产品课。电子表格、多维表格，以及云文档的搜索、评论读取、创建和定点更新，都要按官方 CLI 的实际能力再核实。哪一步当时做不到，就按实际完成范围讲，不改用别的工具来装作做完。

### 工具接续：把同一份数据变成图

然后做工具接续。从刚才已经核对过的报名数据里，取出三个主题和人数（教学数据：40、25、15）。先核对要交给绘图工具的输入，再用 AntV Chart MCP 生成柱状图。打开结果，检查类别、数值、中文标签和标题是否对应源表。这里要让学员看见：一个工具取得资料，Agent 整理出输入，另一个工具形成可见结果。不把图表自动回写到飞书当作必须完成的环节。AntV 默认使用远程渲染，本机启动 MCP 并不等于数据只留在本机。图表和中文显示以实跑为准。

### 高德短演示：把出行约束落到地点和路线

再换一个日常场景，用高德做短演示：周末从杭州东站出发，安排两个适合步行串联的景点，区分车站到景点的交通段和景点之间的步行段，并生成能在高德打开的专属地图。地点和路线以真实查询为准，不预先写好成功结果。讲师分别核对文字行程、地图结果和 APP 是否打开，按实际完成范围讲解。模型写了一段行程，不等于已经生成地图；返回一个链接，也不等于手机已经打开。

### 其余 MCP 的短演示

其余推荐的 MCP，也不再只放清单，各做一个能看见结果的短演示。12306-mcp 查一次具体车次或中转，说明这是社区实现、依赖上游接口，不是购票或抢票工具。Playwright 在浏览器里完成一项能看见的操作，例如打开指定页面并核对页面上的一项内容。Context7 针对一个具体的库或接口查文档，打开返回结果，看清版本和内容是否对得上当前问题。Blender 在本机做一个很小的三维操作，例如创建一个简单物体并在 Blender 里看到结果。这些短演示都先实跑；账号、网络、本机环境和插件等条件，讲的时候一并交代。哪一个当时做不到，就按实际完成范围讲，不换别的工具顶上。百度地图只作为高德的替代候选说明，不再单独做一遍地图演示。

### 其他推荐、学员判断与交接

演示结束后，先用一页介绍三个课上没有展开的 MCP：GitHub 官方 MCP、MiniMax 官方 MCP，以及 FreeCAD 社区 MCP。各配一张能看见结果的公开演示画面（动图或截图），并标明来源是项目公开演示，不是这一节已经实跑的结果。不要求学员装齐。口播顺带收住选用条件：要分清官方实现和社区实现，账号、网络和本机软件条件都要看清。再进入自检和小结。

学员判断仍落在飞书主案例上：Agent 回复“整理稿已创建”，接下来应检查什么？打开实际文档，核对位置、标题、正文、来源和待决定事项；定点更新后再看实际变化。这个判断也适用于后面的演示：对话说明和可见结果，各有要核对的对象。这一节留下的，是带来源与结果核对的演示材料，以及附使用条件的工具清单。JSON Diff 的实施，仍从 4.5 已经提交的规格基线进入第 5 章。演示加多后，时长会超过原先 25 到 35 分钟的预期，先按实际能做完的范围保留这些演示，时长交给剪辑压缩，不按页数删减。

2. 抽查一条原文、一条评论。建议抽查：方案里“答疑时长待确认”，以及评论“答疑时间需要明确”。口播只问这两处在整理结果里是怎么写的、来源是否还在；对不上就当场指出，不改写成预想答案。

**p63｜带解读的操作**　整理稿怎样创建，又怎样改一处？

2. 打开实际文档，检查标题、正文、来源和待办。口播：对话里说“已创建”还不够，要在真实文档里看到这些内容。
3. 给出一个明确决定，例如“答疑环节确定为 20 分钟”，只改整理稿里相关的安排和待办，再比较实际变化。口播：改的是整理稿，不是原始方案；也只改这一处，不要把其他待确认项一并写死。

创建和定点更新都还要按官方 CLI 的实际能力再核实。哪一步做不到，就按实际完成范围讲，不换别的工具顶上。
