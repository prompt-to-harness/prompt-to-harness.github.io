# 4.1 接手大项目，还能边聊边改吗？

章内分工见[章级故事线](../../../../docs/outline/proposals/2026-11-02-ch04-storyboard.md)，制作状态见[章目录](../../README.md)；本文保存已确认的连贯内容、A＋B 方法及官方依据，逐页安排留待后续讨论。

## 本节内容

### 从接手已有工程开始

本节的问题是：“接手大项目，还能边聊边改吗？”前面已经练习过从想法出发，逐步做出一个项目。这次转到另一种常见情境：接手正在研发、维护的工程，在现有能力上增加功能。我们会继续使用澄清、观察和核对的方法，但先要知道手里是什么项目、使用哪一版代码，以及它现在能做什么。

与第三章的联系由开场口播交代。所有操作都从独立的 JSON Crack 仓库、课程分支和新会话开始，讲述与演示所需材料在当前工程内自洽。

先分清工程与任务：JSON Crack 是本次接手的已有工程，它可以把 JSON 数据转成交互图，帮助我们浏览结构。JSON Diff 是准备在它上面增加的对比功能。取得的固定基线属于 JSON Crack，不能在开场把待开发的对比功能说成现有成果。

### 依据课件取得同一份工程起点

课件给出上游仓库、Release 和完整 commit SHA。讲师依据这些信息取得独立项目副本，核对本地 HEAD，再从指定提交创建课程分支。Release 帮助识别版本，完整 SHA 固定实际使用的代码；后面的启动方式、目录介绍和调查结论都要对应这一版。

该开源工程有明确的环境要求（Node.js ≥24 与 pnpm ≥10）。讲师在口播中提前说明：课件配套页给出了环境核验说明；若学员本地环境暂时不满足，先以看懂演示和掌握规格思路为主，这不影响后续对规格和架构的理解。

这一段把课件上的版本信息与学员手里的副本对应起来。核对仓库来源、本地 HEAD、分支和工作区状态，并留下记录。已有个人修改时，保留原目录，另建练习副本。

基线核对后，眼前仍是陌生工程。接下来借助 Agent 完成两件小事：先要一份能核对的新人简报，再带跑一个最小用例。它们共同服务于认识和体验项目，五层规格仍是本节要引出的知识主线。

### 技巧 A：先要一份带依据的新人简报

让 Agent 先阅读 README、项目文档、目录和启动配置，简要说明项目解决什么问题、主要目录各做什么、Web 应用怎样启动。每项重要结论给出可打开的依据，不确定的地方直接说明。同时明确要求 Agent 仅通过阅读文档与配置回答，暂时不要主动执行安装或启动命令，把运行动作留给下一步。讲师抽查与接下来启动有关的一项说明或配置，把回答与仓库里的实际内容对应起来。

这份简报帮助我们知道先看什么、怎样开始使用项目。目录用途以文档和配置能支持的范围为限；函数入口、模块如何协作、JSON 怎样经过解析变成图数据，在 4.2 带着需求继续调查。

这里的做法有公开官方文档支持。[GitHub 的工程探索教程](https://docs.github.com/en/copilot/tutorials/explore-a-codebase#example-prompts)给出项目用途、结构、关键部分和运行方式的概览示例，并在架构概览示例中要求“Provide evidence”。[Claude Code 的工程概览建议](https://code.claude.com/docs/en/common-workflows#get-a-quick-codebase-overview)强调先提出宽泛问题，再逐步缩小到具体区域。我们把它们转化成适合本节的请求：先取得简短导航，明确依据，阅读深度止于文档、目录和启动配置。

### 技巧 B：让 Agent 带跑一个最小用例

有了启动依据，再让 Agent 按当前版本的仓库说明带跑 Web 应用，并给出一个简单的使用例子。用包含普通字段、数组和嵌套对象的一段 JSON，观察输入内容怎样出现在交互图里。产品用途通过这一次操作讲清，方法介绍与功能演示使用同一份材料。

此时核对的是实际结果：执行了什么命令、服务来自哪个副本、输入是什么、界面是否呈现了相应数据。Agent 建议运行某条命令，说明它提出了一个步骤；命令输出和浏览器画面才说明这次走到了哪里。浏览器中的输入与观察可由讲师完成，按实际执行者记录。

[OpenAI 的验证与审查建议](https://learn.chatgpt.com/guides/best-practices#improve-reliability-with-testing-and-review)要求运行相关检查、确认结果，并核对最终行为是否符合请求。[Claude Code 的检查建议](https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run)进一步强调索取实际运行的命令及输出，或截图。这里将这些方法应用到首次启动：把文档中的建议变成一次可观察、可核对的项目体验。

若启动遇到阻塞，保留实际错误和当前进展，先确认环境条件。本节的任务是认识固定基线，不通过修改生产代码或升级依赖临时绕过问题。具体安装与启动步骤在排练后固化到准备材料；使用预录结果时注明基线与来源。

官方建议支持的是概览与核对的方法。本节的中文请求、阅读范围和最小输入是课程设计，尚未在当前基线上实跑；其他产品文档也不作为 Codex 具备同名功能的依据。

### 从现有能力走到新增需求

看过当前项目后，呈现本章唯一的初始需求：

> 为 JSON Crack 增加 JSON 对比功能，把不同的地方高亮出来。

这句话已经指向一个具体产品和改动方向，但还不足以说明谁在什么场景下使用、什么算“不同”、结果怎样检查，以及在现有工程中采用什么改法。

讲师顺势替学员抛出心里的疑问：我们在前面几章学会了写结构化 Prompt，甚至会开 `/plan`，那面对这个复杂需求，我把 Prompt 写到三千字，把能想到的各种细节全塞进去，让 AI 直接动手，不行吗？

不行。因为把字数写长，并不会自动替我们完成事实核验、规则批准、验收设计和实施安排这四件事。Prompt 天生是催 AI 赶紧动手的输入流，而我们眼前面对陌生大工程，需要的是进 Git 的活合同。讲师由此引出 SDD（Spec-Driven Development，规格驱动开发）：先形成可观察、可验收的约定，再据此组织实现。

开场的问题也有了具体落点。边聊边补要求时，决定可能散落在多轮对话里；接下来继续实现或修改，需要找到当前采用的规则及其变更。版本化规格让这些约定可以被查阅和维护。换会话后仍要让 Agent 读取适用版本，不能把存进 Git 讲成自动加载或永不遗漏。这里不以 Prompt 的长短划分对错，而是由五层规格分别承接这些不同的判断。

### 围绕同一句需求介绍五层关系

讲师围绕刚才的 JSON Diff 需求，依次解释 Brief、Spec、Acceptance、Plan、Tasks。先问它们要解决的问题，再给出名称与用途，五层图由同一项任务逐步展开。

| 层 | 眼前要回答的问题 | 要留下什么 |
| --- | --- | --- |
| Brief | 谁在什么场景下要比较两份 JSON，这次做到哪里？ | 目标、范围、非目标、约束、成功信号和开放问题 |
| Spec | 什么算不同，用户应该观察到什么行为？ | 经人确认、带编号的行为规则 |
| Acceptance | 给定输入与操作，怎样判断符合规则？ | 可核算的案例与检查标准 |
| Plan | 现有工程如何承接这些行为，选择什么改法？ | 依据调查形成的方案、取舍、影响范围和风险 |
| Tasks | 按什么顺序实施，每一步怎样确认完成？ | 有范围、依赖、验证方法和完成定义的小任务 |

讲师在此提前立下一条核心原则：**Spec 只锁死用户看得见的可观察行为，严禁出现具体的文件名或组件名；代码怎么改、函数怎么调，完全留给 Plan。** 这样稳定的需求行为（What）与易变的技术实现（How）彻底解耦，后续换方案不必重写需求，改小规则也不会搅乱架构。

五层图既表达形成顺序，也表达对应与返回关系。验收案例对应需求，实现任务指向相关需求和验收。若案例暴露规则没有决定，先返回 Spec 和人的决定；若只是实现方案需要调整，回到 Plan 和相关任务核对。这样学员能看出文档之间怎样共同支持实现和变更。

这是本课程采用的组织方式，五层图也将作为 4.1–4.5 的全章视觉锚点图，后续各小节依次点亮对应层。各层的具体内容会在后续小节逐步形成。对象键顺序、数组匹配、删除节点等在本节仍作为待回答的问题，不提前给出课程规则。

### 学员判断与下一节的起点

用三个问题检查五层的用途：“谁需要这个功能？”“键换顺序算不算变？”“先改哪里？”请学员先判断它们分别应放在哪一层，再由讲师解释。

第一个属于 Brief，需要说明使用者、场景和目标；第二个属于 Spec，需要人决定可观察行为，随后再配验收案例；第三个属于 Plan，需要结合现有代码选择方案。判断时先指出这句话正在决定什么，再将它放到相应层。

结束时，学员能说明固定基线的用途，用 A＋B 认识现有工程，并把一个新增需求的问题放回五层中的对应位置。下一节从外部需求笔记出发，接入飞书 MCP 取得原文，再进入源码调查，形成 Brief。最小接入与读取在 4.2，详细飞书用法与案例在 4.6。

### 演示请求草案

以下两条请求落实 A＋B，供后续排练使用；没有对应运行轨迹，不预设 Agent 的回答措辞与工具调用顺序。

**A：新人简报**

> 我刚接手这个项目。先看 README、项目文档、目录和启动配置，简要介绍它做什么、主要目录各做什么、怎样启动 Web 应用。关键结论给出处，不确定的直接说明。仅通过阅读文档与配置回答，暂时不要执行安装或启动命令，先不深入实现代码，也不修改文件。

**B：最小用例**

> 按当前版本仓库里的说明，带我启动 Web 应用，用一段简单 JSON 体验现有功能。告诉我怎样操作、看什么，区分建议步骤和实际验证到的结果。遇到阻塞先说明，暂时不修改源码或升级依赖。

用于最小体验的教学输入：

```json
{
  "name": "Alice",
  "skills": ["JavaScript", "Python"],
  "profile": { "city": "Hangzhou" }
}
```

核对输入字段与实际交互图之间的对应关系，不预写节点数量、布局、颜色或耗时。浏览器操作和观察者按实际情况记录。
