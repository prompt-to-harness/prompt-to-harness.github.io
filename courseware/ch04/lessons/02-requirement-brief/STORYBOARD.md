# 4.2 贴上需求原文，就能直接写吗？

章内分工见[章级故事线](../../../../docs/outline/proposals/2026-11-02-ch04-storyboard.md)，制作状态见[章目录](../../README.md)；本文保存 4.2 的连贯内容（2026-11-07 讲师确认）、逐页安排与素材状态；章级故事线只保留摘要。

## 本节内容

### 从一份需求原文开始

4.1 结束时，我们手里有一份对上版本的 JSON Crack 副本、一份能核对的新人简报，也跑通过一次最小用例。那句初始需求还只有一行字。这一节，需求方把更完整的想法写进了飞书里的一份需求笔记：背景、希望做到的事、还没想清楚的地方，以及怎样算做好。

本节的问题是：“贴上需求原文，就能直接写吗？”我们先把原文取回仓库，再带着它调查源码，最后把愿望、查实的事实和还要人决定的问题分开，写成第一份规格文档 Brief。

### 先认识 MCP，再接入飞书

需求笔记在飞书里，不在仓库里。让 Agent 读到它，可以复制粘贴，也可以让 Agent 通过工具直接读取。MCP（Model Context Protocol）就是让 Agent 连接外部工具的一种约定：客户端（这里是 Codex）连上一个 MCP 服务，服务列出它提供的工具，每个工具有名称、参数和说明；Agent 决定调用哪个工具，工具的返回进入对话，和第 2 章看到的工具返回是同一回事。

这里只讲到这个程度。本课程接入的是飞书官方开源的 OpenAPI MCP（`@larksuiteoapi/lark-mcp`），由 Codex 在本地启动，以讲师本人的用户身份访问飞书，只开放两个读取工具：解析知识库节点、读取文档正文。讲师已经在本机接好。学员这一节不需要接入，直接用课件给出的原文快照。飞书更完整的日常用法放在 4.6：那一节飞书主案例改用官方命令行工具，不再补这里的 lark-mcp 完整接入步骤；4.2 仍如实记录当时是用 MCP 读取。

接入时要讲清一个边界：MCP 服务是一段在本机运行、带着我们凭证的程序，所以先看它来自哪里、能调用哪些工具，再决定开放什么。这和第 1 章的最小权限是同一个判断。lark-mcp 目前标为 Beta，接入方式可能随版本变化，录制时以实际版本为准。

### 读取原文，先核对来源

讲师在基线副本里新开 Codex 会话，请 Agent 读取指定链接的需求笔记：知识库链接先解析节点，再读取正文；把正文原样保存到 `docs/specs/sources/requirement-note.md`，不总结、不改写，并说明调用了哪些工具。

读取之后先核对，再使用。看三件事：工具调用的顺序和返回是否对得上（先解析节点，再读取正文）；保存下来的文件和飞书里的原文是否一致，讲师打开飞书抽查一段；这次读取的来源是什么，包括链接、文档标题、读取身份、读取时间和所用实现。这些来源信息稍后写进 Brief 的“来源”一节。

学员没有接入 MCP，或录制时 MCP 不可用，就把课件给出的原文快照保存到同一个位置，并在“来源”里写明采用了快照。后面的调查和 Brief 不受影响。

### 原文够不够让人决定行为

原文读进来了，再回到本节的问题：这些话已经足够让人决定实现行为了吗？逐条看会发现三种不同的话。有的是愿望，比如“同时放两份 JSON，把不同的地方高亮出来”；有的是约束，比如“最好不要上传到别的地方”；还有的连需求方自己也没想清楚，比如“字段顺序有时会变，这算不算改动”。

“高亮不同”没有说什么算不同，“数组也要支持”没有说元素怎样对上，“只看变化”没有说保留哪些上下文。这些话写得再顺，也不会自己变成规则。原文还提到“文件可能几千行”，这一条要回到代码里看现有能力才能判断。

### 带着需求调查源码

接着回到同一个仓库，承接 4.1 的新人简报，这次带着需求往下查。请 Agent 沿“输入 → 解析 → 图数据 → 渲染”找出最小链路，并找到已有的验证入口。要回答的是会影响 JSON Diff 的问题：用户的 JSON 从哪里进入，在哪里被解析成图数据，图怎样渲染；现有的节点数量上限在哪里设定；哪些代码同时被网页版和其他客户端使用；仓库现有哪些检查命令可以用来验证改动。

每条结论都要给出处，讲师打开相关源码或配置抽查一条。调查只读不改，结论对应固定基线。具体文件、函数和数字以调查结果为准，本稿不预写。

### 分开愿望、事实和未决问题

有了原文和调查结果，就能把三类信息分开：

| 类别 | 例子 | 依据 |
| --- | --- | --- |
| 愿望与目标 | 同时放两份 JSON，对比后高亮不同 | 需求原文 |
| 已查实的事实 | 现有图数据从哪个入口产生、节点上限由什么设定 | 源码与配置，附出处 |
| 未决问题 | 键换序算不算差异；数组按索引还是按业务元素对齐；删除的字段怎样显示 | 需要人决定，留给 4.3 |

Agent 可以给出建议，比如根据现有代码或常见做法建议“数组按索引比较”。建议可以连同依据一起记下，但它仍是未决问题，不因为写得有道理就变成规则。

### 形成 Brief

由 Agent 依据原文快照和调查结果起草 `docs/specs/BRIEF.md`，讲师逐节审，并亲自确认“目标”一节。Brief 固定七个小节：来源、使用者与场景、目标、非目标、已核实约束、成功信号、Open 问题。

目标先收窄到本次的网页版 JSON Diff。原文里“以后 VS Code 插件也能用”写进非目标，其他数据格式、云端保存也一样。“不要上传”写进约束。“能一眼看出改了哪里”写进成功信号，它现在还不能核算，留到 4.4 落成验收。键顺序、数组对齐、删除字段、类型变化和计数进入 Open 问题，带着原文出处，留给 4.3。调查查实的事实写进“已核实约束”，附上源码出处，不另建调查记录文件。

这是第一次往 JSON Crack 仓库里写文件。写完运行 `git status`，新增内容只应出现在 `docs/specs/` 下，生产代码没有改动。本节不提交，规格文档到 4.5 和其余几份一起提交。课件给出 Brief 的小节模板，不给完整的参考答案；学员用自己的调查结果写。

### 学员判断与下一节的起点

用两个判断检查本节：Agent 建议“数组按索引比较”，能不能直接写进 Brief 当作已批准规则？需求原文最后一句“开发同学看完可以直接动手做”，算不算可以跳过 Open 问题的授权？

第一个：可以记录建议和依据，但采用与否仍要人决定，留在 Open 问题里。第二个：这句话是需求方的说法，记录下来即可；规则没定、会改变实现的问题还在，就不能动手。判断时先问这句话出自谁、有没有依据、由谁决定。

结束时，学员能说明 MCP 在这里做了什么、读到的原文怎样核对来源，能把需求原文里的话分成愿望、约束和未决问题，并写出带出处的 Brief。下一节逐项决定 Open 问题里的行为，让“高亮不同”有确定的含义。
