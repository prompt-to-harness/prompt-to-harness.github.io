本节范围、时长和验收见[章文件](../../README.md)的 2.4 一行；页型、方式、层与讲透问题这几栏的含义也在章文件“全章约定”里。[课件](index.html) · [逐步讲稿](speaker.html)。决策和实测见 [LOG.md](../../LOG.md)。

## 本节内容

### 从本地主页走向公开 URL

上一节参考 Hyperspace 调整了主页风格，让 Codex 提交了 homepage-v2。内容和样子已经在本地看过，这一节要让别人也能通过一个公开 URL 打开它。我们和 Codex 一起完成发布，并用实际结果确认页面可用。贯穿这一节的问题是：为了完成下一步，它现在需要知道什么，这些信息从哪里来？

### 先确定这份项目可以公开

先在自己的 GitHub 账号下建一个空仓库，暂时设为私有，把本地 origin 从课程模板改成它，核对地址，先不推送。首次推送会带上当前分支的全部历史，所以检查范围是 `HEAD`：看提交和改动文件、读实际改动、核对作者姓名与邮箱。后来删掉的文件也可能留在早先的提交里，个人资料文件同样会随历史公开。

这里只作发布所需的判断：源码、历史和截图里有没有 secret、未经同意的他人信息或不愿公开的个人信息；首屏身份是不是自己的，参考素材的出处是否保留。发现问题先停下处理，确认本人愿意公开后再继续。命令细节和改写历史的帮助入口留在操作材料，不在这里展开 Git 历史教程。

### 准备部署配置，审过再提交

部署需要一个 GitHub Actions 工作流，在 GitHub 的机器上构建并发布；还需要 Vite 的 `base`，让资源路径对上发布地址。把自己的仓库名和地址告诉 Codex，沿用四要素说明目标、范围和完成标准，这一轮只写配置，不推送、不改远端设置，并解释每项权限的用途。

我们审四项：`base`、build 后的资源路径、权限是否只要发布所需、触发分支是否与准备推送的分支一致。发现问题就让它在原范围内修改，审过再让它提交。提交后核对最终要公开的历史，需要时把仓库改为公开。到这里，本地已经准备好怎么部署，但 GitHub 上的 Pages 来源设置是否就绪，还需要查询。

### 查询 Pages 状态，依据返回完成设置

我们可以在网页里查 Pages 设置，也可以用命令查询。GitHub 提供了官方命令行工具 GitHub CLI，命令叫 `gh`。前面用的 `git` 负责版本记录和提交的推送、拉取；gh 把 GitHub 平台的功能带到终端，让我们和 Codex 都能用命令访问。

gh 的能力是逐步增加的：2020 年 9 月发布的 1.0 已经能调用 GitHub API；2021 年 4 月的 1.9 又加入了 Actions 的专用命令，可以查看工作流、运行状态和日志（[1.0 公告](https://github.blog/changelog/2020-09-17-github-cli-is-generally-available/)、[1.9 公告](https://github.blog/changelog/2021-04-15-github-cli-1-9-enables-you-to-work-with-github-actions-from-your-terminal/)）。今天，通过 gh 的专用命令和通用 API 入口，已经可以完成许多常见的 GitHub 操作，包括仓库、Issue、PR，以及这节要用的 Pages 设置和部署查询；具体用法见[官方手册](https://cli.github.com/manual/)。建议使用较新的稳定版本，旧版本可能还没有演示里的命令、参数或返回字段，课程演示仍以核验过的版本为准。

从这里也可以看到平台开放能力对 coding agent 的意义：平台通过 API 提供程序可调用的功能，CLI 和 SDK 则让人或程序更方便地使用这些接口。随着这些入口逐步覆盖更多功能，原来需要人在网页里完成的操作，也可以交给 agent 调用工具完成，再由人审查和确认。这次就让 Codex 用 gh 查询 Pages 的当前状态，再按需要把来源设为 GitHub Actions。

第一次调用出现时，回到本章的请求锚点图：工具列表里没有单独的 gh，Codex 通过 `exec` 调用本机安装并登录好的命令。它知道怎样写命令，不代表已经知道远端状态；安装、登录和连接是否可用，也要通过实际查询确认。上一节通过命令取得参考网站的代码，这一节沿用同样的调用方式，取得决定发布下一步所需的远端状态。

查询的输出作为工具返回进入下一次请求，模型据此判断：来源已经正确，就确认；尚未配置或来源不对，才进行所需的创建或修改。具体返回以本次运行为准，不要求一定出现 404。修改后再查一次，确认设置已经生效。我们沿着“查询 → 返回 → 判断 → 修改 → 复查”看请求，重点是每一步依据什么继续行动。

在本章已排练的课程环境里，gh 联网需要申请到沙箱外运行。第一次申请时看清命令、理由和目标仓库，修改类操作确认方法和范围后再批准；请求外的动作拒绝。工具返回提供判断依据，人的批准决定是否允许执行。请求记录中能看到调用申请和执行后的返回，看不到人在界面里点击同意的动作。设置完成后，我们也在网页 Settings → Pages 刷新核对来源。

### 推送后，取得这次部署的结果

由我们自己推送已审查的提交，触发远端部署。此时出现一个新问题：刚才那份代码在 GitHub 上跑得怎么样？设置已经正确，不能据此推断这次运行也已成功。部署结果在 GitHub 上，需要取得执行之后的新状态。

让 Codex 用 gh 找到对应这次提交的运行，查询状态，再按需要查看各个 job 和日志。这一步只查看，不重跑、不改设置和文件。运行还在进行，就等待后再查；失败就依据失败步骤和日志定位；成功则继续验收。不为演示准备固定失败，也不让它顺手扩大到修依赖等任务。

状态和日志通过 gh 的输出进入工具返回，成为下一次判断的依据。日志存到本机文件，并不意味着整份日志都进入了请求；实际读到的部分才会带进来。模型的结论要能对应这次提交、这次运行和它真正取得的内容，接回上一节“它看到了什么、还有什么没看到”的问题。

### 打开公开页面，确认交付完成

部署状态和日志回答这次构建、发布是否完成；页面能否让别人正常使用，还要在浏览器里检查。我们用未登录窗口打开公开 URL，确认 Network 没有 404，停用缓存后刷新仍然正常。发现问题就根据实际问题继续定位，三项都过才算发布完成。

最后给这个版本打 `ch02-homepage-live`，只推送这一个 tag，留下可定位的发布版本。学员最终留下一个可公开访问的主页，也能说明 Codex 在哪个判断点查询了什么、返回怎样进入请求，以及哪些动作由人决定。

### 和本章主线的关系

2.1 认识一次请求里有什么，2.2 看内容怎样累积、被清空和压缩，2.3 分辨它看到了什么、还缺什么。2.4 把这些认识用到一次真实发布：本地配置、远端设置、部署结果分别需要不同的证据；Codex 通过工具取得当前状态，返回进入 context 后支持下一步判断，执行后还要取得新的结果来核对。gh 的调用方式解释这些信息怎样进来，贯穿全节的是依据外部状态完成发布，最后由人确认页面可用。

### 事实边界与待实测

- 推送前检查用 `HEAD` 而不是 `origin/main..HEAD`：换 origin 后旧的 `origin/main` 引用可能还在，按它做增量检查会漏掉模板提交和其中后来删掉的文件（2026-10-12 讲师确认先克隆模板、发布前再建个人空远端；Git 2.56.0 临时仓库验证）。`--stat` 会列出历史中出现过、后来又删除的文件。先用统计定位，再用 `-p` 读实际文字；二进制文件另行打开。若把已有内容的私有仓库改公开，还要查远端已有内容。
- GitHub 文档（2026-10-03 查阅）：从命令行推送的提交用本地 `user.email`；改配置只影响之后的提交；noreply 地址格式按录制时设置页核对，画面不写格式。不做改写历史配套页（2026-10-05 讲师确认），p46 指向官方文档。
- 先为仓库启用自定义工作流再推送（2026-10-05 查阅 Using custom workflows with GitHub Pages）；先推送导致失败时在 Actions 对失败的运行 Re-run。Pages 设置界面按录制时 GitHub 版本核对。首次部署若自然出错，保留真实过程，不准备错误的 `base`（C2-05）。
- 启动方式：Agent Lab 默认复用本机 `gh` 登录，10-25 排练用全新的 AGENT_LAB_HOME 直接可用，不用 `CLEAN_CODEX_GH=1`。gh 没登录时（10-25 实验：`GH_CONFIG_DIR` 指向空目录、另开 AGENT_LAB_HOME，发同一句设置请求，记录在 lab-runs 同目录 `nologin/`）：它没有申请 `gh auth login`，而是查环境变量（只看有没有）、找到环境外真实的 `~/.config/gh` 并遮盖令牌读了 hosts.yml，再申请用 `GH_CONFIG_DIR=…/.config/gh gh api user` 联网；拒绝并说明后，它停下给出登录和执行步骤。那份登录是实验里藏起来的，真没登录的学员不会有；能说明的是：受阻时它会去找别的凭据，读取几乎不受沙箱限制，批准框里要看清用的是谁的登录。用 `clean-codex.sh` 且不带开关时，Codex 会自己申请 `gh auth login --web`（2026-10-21 实测）。
- 学员前置：course-starter 环境检查单里有 GitHub CLI 一行，本人运行 `gh auth login --scopes workflow`；默认登录不含 `workflow`，Git 用它推送 `.github/workflows/` 会被拒绝（2026-10-07 实测）。
- p48b 的设置 Prompt 写明“没有就用 POST 创建，已有就用 PUT 修改”，避开 PUT 404 后改用 POST 的弯路（2026-10-20 讲师决定）。凭据边界：令牌不放环境变量、不贴进对话（预检中检查环境变量的命令会把 token 原文打印出来）。
- 能力目录开时每次调用是 `exec` 工具里的一小段 JavaScript，调 `tools.exec_command`，`sandbox_permissions: require_escalated`、`justification`、`prefix_rule` 写在这段代码的参数里（2026-10-20、10-25 实测）。批准后命令可能超过等待时间，返回先是“Script running with cell ID …”，结果在随后的 `wait` 调用返回里。
- 网页搜索：请求的 tools 里有 `web_search`（由服务端执行），调用出现在模型返回的 `web_search_call` 里，Codex 不弹批准框。本节不讲（C2-114），p49a 的工具列表里看得到它，被问到时一句带过。
