# 2.4 逐页分镜：发布上线，看 Codex 怎么用 gh

本节范围、时长和验收见[章文件](../../README.md)的 2.4 一行；页型、方式、层与讲透问题这几栏的含义也在章文件“全章约定”里。[课件](index.html) · [逐步讲稿](speaker.html)。决策和实测见 [LOG.md](../../LOG.md)。

## 本节内容

### 把本地主页发布出去

上一节参考 Hyperspace 调整了主页风格，让 Codex 提交了 homepage-v2。内容和样子已经在本地看过，现在要让别人通过一个公开 URL 打开它。项目向前走时，我们重点看两次查询：发布前，Codex 怎样知道 GitHub 上的 Pages 设置；推送后，它怎样取得这次部署的结果。

讲师提前在 `prompt-to-harness` 组织下建公开空仓库，命名 `ch02-pages-release-<日期>-<场次>`，准备好仓库的 HTTPS 地址、账号、依赖和请求查看器。学员使用自己的仓库。现场先核对目标和空仓库状态，再查看原 origin、改成这次的仓库地址，最后核对 fetch 与 push；不重新演示建仓、登录或切换可见性。空仓库已经公开，本地的代码和历史要等推送才会上传。

### 确认可公开，准备部署配置

推送前先检查本地内容，包括当前分支的完整提交历史、后来删除的文件、作者邮箱和个人资料。现场把这项需求交给 Codex 做本地只读检查，请它列出发现、文件或提交依据、实际覆盖范围和不能判断的部分；不预写一定有问题。人核对一两条依据，再决定是否继续。文件列表帮助定位，实际文字和截图也要看。有没有 secret、未经同意的他人信息或不愿公开的资料，首屏身份是否正确，参考素材的出处是否保留，都由人判断。有问题先停。完整历史的查看命令与处理帮助放在操作材料，主讲只保留这些必要判断。

确认可以继续，让 Codex 为这个仓库准备 GitHub Actions 工作流和 Vite 的 base。Prompt 写清本次仓库与发布地址，限定只写配置、不推送、不改远端设置，并解释权限。我们把实际文件和发布目标对照：路径与分支是否匹配，权限是否只要发布所需，build 后资源路径是否正确。审过后让 Codex 提交，并核对新增提交。提交是这次任务的收尾，不另展开成一套流程。文件准备好了，GitHub 那边的 Pages 来源是否就绪，还要查。

### 用 gh 查设置，看返回怎样支持下一步

GitHub CLI 的命令叫 `gh`，把 GitHub 平台功能带到终端；git 负责版本记录和提交的推送、拉取，gh 可以访问仓库、Issue、PR、Actions，也能通过通用 API 入口操作 Pages。它的能力逐步增加：2020 年 9 月的 1.0 已有 API 调用，2021 年 4 月的 1.9 加入 Actions 专用命令，今天已能完成许多常见 GitHub 操作。建议用较新的稳定版，具体命令以当前版本为准；出处见 [1.0 公告](https://github.blog/changelog/2020-09-17-github-cli-is-generally-available/)、[1.9 公告](https://github.blog/changelog/2021-04-15-github-cli-1-9-enables-you-to-work-with-github-actions-from-your-terminal/)与[手册](https://cli.github.com/manual/)。平台通过 API 提供程序接口，CLI、SDK 帮助人和程序使用这些接口；开放更多功能，人和 coding agent 就能通过工具完成更多操作。

这次让 Codex 查询 Pages，按需要把来源设为 GitHub Actions，设置后复查。看已有请求记录，只抓住调用、返回和接下来的动作：工具列表没有单独的 gh，Codex 通过 exec 运行本机命令；gh 查到的状态作为工具返回进入下一次请求，模型才据此继续。在排练中查到 404，随后创建并复查到 workflow；这是一次例子，现场已有正确来源时可以直接确认。

第一次涉及远端修改时，结合批准框看清命令、目标仓库和修改范围，再决定是否放行。排练环境中的联网申请、批准参数，以及人的点击不在请求记录里这些细节，随眼前操作解释；完整调用留在原始记录里，不让它们另起主线。设置后在网页上核对来源。

### 推送以后，再查这次部署

由人推送已审查的提交，触发 GitHub 上的部署。现在要取得执行之后的新状态：对应的是否是刚才这次提交，运行有没有完成，构建和部署是否成功。让 Codex 用 gh 查询，按需要读 job 和日志。这一步只查看；运行中就等后再查，失败就依日志定位，成功后继续页面检查。

PPT 用已有补跑的真实工具返回说明依据：提交标识、运行状态与 job 结果通过工具返回进入请求，支持它的回答。完整命令、日志和偶发警告保留在原始记录与操作材料里，不在主画面逐项讲。日志存在文件里，还要实际读回的部分才会进入 context。补跑是同一项目的新会话，当时部署已经结束；现场结果单独查看，不假装两份记录连续。

发布前后两次查询可以归纳为同一个做法：用工具取得外部状态，让返回进入 context，再据此判断下一步。Anthropic《Building effective agents》的环境反馈原则为这一归纳提供佐证；示意图中的 gh、Pages 和部署判断来自本课演示。发布前查设置，决定是否需要修改；推送后查对应提交的运行，决定等待、排错或继续页面验收。

### 打开页面，保存发布版本

部署结果回答流程有没有完成，页面可用性由人在浏览器验证：未登录窗口打开公开 URL，Network 没有 404，停用缓存后刷新仍然正常。有问题继续定位，三项都过再打 `ch02-homepage-release`，只推送这个 tag。

从本地主页到公开地址，我们既完成交付，也看清模型判断的依据怎样进来。2.1 认识请求组成，2.2 看内容怎样变化，2.3 分辨它看到了什么；这一节通过发布前后的两次查询，把工具返回变成可核对的行动依据。最后自检仍围绕这些信息和人的执行决定。

### 内容分层（ED-020）

| 层 | 本节内容 | 用在哪 |
| --- | --- | --- |
| 机制 | 首次推送公开当前分支全部历史；请求的工具里没有 gh，它经 exec 在本机运行，已有知识支持写命令，当前版本和状态要核对；gh 的输出是工具返回；取得当前设置后决定下一步，执行后再取得新的结果；工具调用里有完整命令和批准申请，人的同意不在记录里；Actions 成功不等于页面可用 | 页标题、转场、自检、小结 |
| 稳定现象 | 默认沙箱没有网络，gh 逐条申请到沙箱外；它先跑 `gh auth status` 探路，沙箱里会误报令牌无效（10-25 两次）；读 `~/.config/gh` 下的文件不经批准（10-25 两次，都遮盖了令牌）；“先告诉我再执行”停不住它（10-07、10-20、10-21、10-25 都是）；`.git` 只读，提交要先失败再申请提权；它会想自己起服务或截图验证；读日志时先存文件再挑着读 | 口播说“通常会”“几次排练都出现过” |

### 事实边界与待实测

- 推送前检查用 `HEAD` 而不是 `origin/main..HEAD`：换 origin 后旧的 `origin/main` 引用可能还在，按它做增量检查会漏掉模板提交和其中后来删掉的文件（2026-10-12 讲师确认先克隆模板、发布前再建个人空远端；Git 2.56.0 临时仓库验证）。`--stat` 会列出历史中出现过、后来又删除的文件。先用统计定位，再用 `-p` 读实际文字；二进制文件另行打开。若把已有内容的私有仓库改公开，还要查远端已有内容。
- GitHub 文档（2026-10-03 查阅）：从命令行推送的提交用本地 `user.email`；改配置只影响之后的提交；noreply 地址格式按录制时设置页核对，画面不写格式。不做改写历史配套页（2026-10-05 讲师确认），p46 指向官方文档。
- 先为仓库启用自定义工作流再推送（2026-10-05 查阅 Using custom workflows with GitHub Pages）；先推送导致失败时在 Actions 对失败的运行 Re-run。Pages 设置界面按录制时 GitHub 版本核对。首次部署若自然出错，保留真实过程，不准备错误的 `base`（C2-05）。
- 启动方式：Agent Lab 默认复用本机 `gh` 登录，10-25 排练用全新的 AGENT_LAB_HOME 直接可用，不用 `CLEAN_CODEX_GH=1`。gh 没登录时（10-25 实验：`GH_CONFIG_DIR` 指向空目录、另开 AGENT_LAB_HOME，发同一句设置请求，记录在 lab-runs 同目录 `nologin/`）：它没有申请 `gh auth login`，而是查环境变量（只看有没有）、找到环境外真实的 `~/.config/gh` 并遮盖令牌读了 hosts.yml，再申请用 `GH_CONFIG_DIR=…/.config/gh gh api user` 联网；拒绝并说明后，它停下给出登录和执行步骤。那份登录是实验里藏起来的，真没登录的学员不会有；能说明的是：受阻时它会去找别的凭据，读取几乎不受沙箱限制，批准框里要看清用的是谁的登录。用 `clean-codex.sh` 且不带开关时，Codex 会自己申请 `gh auth login --web`（2026-10-21 实测）。
- 学员前置：course-starter 环境检查单里有 GitHub CLI 一行，本人运行 `gh auth login --scopes workflow`；默认登录不含 `workflow`，Git 用它推送 `.github/workflows/` 会被拒绝（2026-10-07 实测）。
- p48b 的设置 Prompt 写明“没有就用 POST 创建，已有就用 PUT 修改”，避开 PUT 404 后改用 POST 的弯路（2026-10-20 讲师决定）。凭据边界：令牌不放环境变量、不贴进对话（预检中检查环境变量的命令会把 token 原文打印出来）。
- 能力目录开时每次调用是 `exec` 工具里的一小段 JavaScript，调 `tools.exec_command`，`sandbox_permissions: require_escalated`、`justification`、`prefix_rule` 写在这段代码的参数里（2026-10-20、10-25 实测）。批准后命令可能超过等待时间，返回先是“Script running with cell ID …”，结果在随后的 `wait` 调用返回里。
- 网页搜索：请求的 tools 里有 `web_search`（由服务端执行），调用出现在模型返回的 `web_search_call` 里，Codex 不弹批准框。本节不讲（C2-114），p49a 的工具列表里看得到它，被问到时一句带过。
