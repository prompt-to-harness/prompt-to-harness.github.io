本节范围、时长和验收见[章文件](../../README.md)的 2.4 一行；页型、方式、层与讲透问题这几栏的含义也在章文件“全章约定”里。[课件](index.html) · [逐步讲稿](speaker.html)。决策和实测见 [LOG.md](../../LOG.md)。

## 本节内容

### 从 homepage-v2 开始，第一次推送

上一节参考 Hyperspace 改了两轮风格，让 Codex 提交了 homepage-v2。到现在为止，所有提交都只在自己电脑上。这一节第一次推送，把主页发布成一个公开 URL。推送以后公开的不只是页面，还有当前源码和整段提交历史，推出去就收不回来。

发布要和 GitHub 打交道：改 Pages 设置、看部署跑得怎么样。前三节 Codex 做的都是本机上的事，读文件、跑命令、提交；这一节它要用一个工具列表里没有的工具，GitHub CLI（gh）。本节看清两件事：它是怎样用上 gh 的，GitHub 上的设置和部署状态又是怎样进到请求里的。

### 推送前，看清即将公开的历史

先在自己的 GitHub 账号下建一个空仓库，把本地 origin 从课程模板改成它，暂时不推送、不公开。首次推到空仓库，当前分支的全部历史都会过去，所以检查范围是 `HEAD`，不是“比课程模板多出来的提交”。用 `git log --stat` 看每次提交动过的文件（包括后来删掉的），`git log -p` 读实际文字，再列出所有作者。会看到三类容易漏的东西：每个提交都带着作者的姓名和邮箱；课程模板带来的提交，作者是别人，克隆时就在历史里，其中后来删掉的文件推送后照样能看到；我们自己放进去的个人信息，`profile.md` 本身就在 homepage-v1 里。`-p` 的输出往往很长，大半是依赖锁文件，可以先排除它再读。文件列表只回答“有什么”，能不能公开要由人逐项判断：有没有 secret、他人信息、截图里的隐私，首屏是不是自己的名字，借来的风格出处还在不在，本人愿不愿意公开。有一项不行就先停下。改写历史不进主课，指向 GitHub 官方文档。

### Codex 写部署配置，我们逐项审

部署要两样东西：一个 GitHub Actions 工作流，在 GitHub 的机器上构建并发布；Vite 的 `base`，让资源路径对上仓库名。Prompt 沿用四要素，写清自己的仓库名和地址，约束里写明不推送、这一轮不改设置、说明每个权限。审四项：`base`、build 后的资源路径、权限是否只要发布所需、触发分支。哪一项不对就让 Codex 在原范围内改，改完再审。审过让 Codex 提交，和前两节一样在批准框里看清文件和提交说明。

### Pages 来源交给 Codex 用 gh，推送由我们来做

提交后再跑一遍推送前检查，看最终要公开的提交；需要时这时才把仓库改成公开。Pages 的来源交给 Codex 用 gh 设为 GitHub Actions。

请求里的工具列表没有 gh，只有 `exec` 这样的通用工具。gh 是本机装好、登录好的一个命令，Codex 用 `exec` 运行它；会不会用 gh、命令怎么写，靠模型自己的知识，装没装、登没登录、连不连得上，要它自己先跑命令看。默认沙箱没有网络，每条 gh 命令都申请到沙箱外运行：模型发出的调用里是一条完整命令、一个“到沙箱外运行”的标记和一句理由，批准框显示的就是这些。批准以后命令在我们电脑上执行，gh 和 GitHub 通信，输出作为工具返回进入下一次请求，它据此决定下一步。Prompt 里写“执行修改前告诉我”停不住它，停住它的是批准框；它要做请求外的事，就在这里说不。我们点的同意不在请求记录里，记录里只看得到申请和执行后的返回。

改完它会再查一次，但它看不到网页，我们自己在 Settings → Pages 刷新确认。推送由我们执行。

### 推送之后，让 Codex 用 gh 看这次部署

部署在 GitHub 的机器上跑，结果不在项目文件里，也不在 context 里，和上一节页面的样子一样。推送后，让 Codex 用 gh 去看这次运行：成没成功、每个 job 的结果、日志里有没有警告或错误。这些都是 gh 查回来的文本，作为工具返回进到请求里；日志很长时它先存成文件再挑着读，读了多少就进来多少。这一步只看不改：重跑部署、顺手查依赖漏洞这类请求外的事，在批准框说不。

### 证明页面可用，只推送一个 tag

gh 说部署成功，只说明流程跑完了。别人能不能正常打开，要我们自己看：未登录窗口打开公开 URL、Network 没有 404、停用缓存后刷新仍正常，三项都过才算发布成功。给这个版本打 `ch02-homepage-live`，只推送这一个 tag，不用 `--tags`。最后三道自检题都只考机制：gh 是怎样用上的，部署状态是怎样进来的，谁在哪一步说了算。

### 和本章主线的关系

2.1 认识一次请求里有什么，工具是其中一块；2.2 看它变长、被清空和压缩；2.3 问依据在哪一块、哪些东西不在里面。2.4 指着工具和工具返回：工具列表里没有的 gh，经 `exec` 在本机运行；GitHub 上的设置和部署状态本来不在 context 里，gh 查过才作为工具返回进来；改 GitHub 的每一步，经我们批准。

| 机制 | 首次推送公开当前分支全部历史；请求的工具里没有 gh，它经 exec 在本机运行，会不会用靠模型自己的知识；gh 的输出是工具返回；GitHub 上的设置和部署状态本来不在 context 里，gh 查过才进来；工具调用里有完整命令和批准申请，人的同意不在记录里；Actions 成功不等于页面可用 | 页标题、转场、自检、小结 |

### 事实边界与待实测

- 推送前检查用 `HEAD` 而不是 `origin/main..HEAD`：换 origin 后旧的 `origin/main` 引用可能还在，按它做增量检查会漏掉模板提交和其中后来删掉的文件（2026-10-12 讲师确认先克隆模板、发布前再建个人空远端；Git 2.56.0 临时仓库验证）。`--stat` 会列出历史中出现过、后来又删除的文件。先用统计定位，再用 `-p` 读实际文字；二进制文件另行打开。若把已有内容的私有仓库改公开，还要查远端已有内容。
- GitHub 文档（2026-10-03 查阅）：从命令行推送的提交用本地 `user.email`；改配置只影响之后的提交；noreply 地址格式按录制时设置页核对，画面不写格式。不做改写历史配套页（2026-10-05 讲师确认），p46 指向官方文档。
- 先为仓库启用自定义工作流再推送（2026-10-05 查阅 Using custom workflows with GitHub Pages）；先推送导致失败时在 Actions 对失败的运行 Re-run。Pages 设置界面按录制时 GitHub 版本核对。首次部署若自然出错，保留真实过程，不准备错误的 `base`（C2-05）。
