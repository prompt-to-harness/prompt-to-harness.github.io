## 两步 Prompt（草稿）

两步先看初始请求，再看读代码后的请求。问法提前设计，调用与回答以实际记录为准。

**p08 第一步（与项目无关）**：

```text
你好，用一句话介绍你能帮我做什么。
```

目的：不触发工具调用，只看 context 的基本组成。录制前确认这一句在冻结版本下不会触发读文件；若触发，换成更短的问候并记下原因。

**p07 第二步（与项目相关、只读）**：

```text
只读任务，不修改任何文件。
这个个人主页的项目区现在显示什么？数据写在哪个文件里？
请说明依据来自哪个文件的哪几行；
不确定就写“不确定”，不要猜。
```

目的：让 Codex 自己去找产品代码，在记录里看到工具调用和返回。答案应来自当前项目区的数据和渲染代码，不依赖前章过程文件。新问法尚未重跑，对应回复、调用和对比待录。

**p14a 点名对照**：在相同快照和配置下另开会话，保持第二步的问题不变，只增加已经核实相关的源码路径。路径由当前代码确定，不预写固定文件名。比较前先核对两边回答的正确性、依据和缺失项，再列实际读取文件、请求次数与输入量；两组各一次的结果只说明本例。不要求学员重跑。

## p14 按实际记录选择讲法

| 实际结果 | 讲法 |
| --- | --- |
| Codex 读取了 `src/App.tsx` 等文件，说出了项目区显示的内容和数据所在的行 | 在记录中指认那次读取文件的工具调用：对照工具返回、后续请求和回答，检查来源与理解是否相符 |
| Codex 没读文件，凭目录名或代码猜 | 核对完整请求与工具返回后指出依据缺失；这正是 Prompt 要求“说明依据”的原因 |

还可能出现“读到了但理解错了”或“没有找到依据，回答不确定或继续查找”。均按实际结果讲解，保留原始记录，不重跑凑结果。
