# 陈天 AI 训练营的多项目组织方式

Research date: 2026-09-03
Scope: 研究公开课程时间线、项目列表和 6 个项目详情页，只分析 project/作业如何组织，不评价课程效果，也不决定本课程最终交付状态。

## Executive Summary

陈天训练营给出的不是“一个项目从头做到尾”的单一路径，而是：

`按主题学习 → 用小项目练习一个能力 → 换项目练习另一个能力 → 用一个综合项目串起全流程`

公开页面显示，项目 1 是 Ticket 管理系统，项目 2 是数据库查询工具，项目 3 是 pg-mcp，项目 4 是 Agent 日志可视化，项目 5 是 Code Review Agent，项目 6 是全栈智能文档助手。[TC-P-03][TC-P-04][TC-P-05][TC-P-06][TC-P-07]

这几个项目之间没有表现为同一代码库的连续演进。它们分别挂到第 1、2、5、6、6、7 周，覆盖原型、Prompt/数据安全、MCP、Agent 可观测性、Code Review 和全流程交付。[TC-P-01][TC-P-08]

因此，它更准确地属于 **“多个独立能力项目 + 一个综合项目”**。这个结构对你们的启发是：可以让“课程能力”递进，而不要求“代码库”递进；同时保留一个综合项目或完整案例，避免课程最后只剩下一堆零散 demo。

## 对你们当前想法的启发

### 1. 递进的对象可以是能力，不一定是代码

如果所有项目都在一个 repo 里递进，前一项目的失败可能阻塞后续章节。陈天的组织方式把风险拆开：数据库查询工具做不好，不会直接导致 MCP 项目无法开始；但学习者仍然沿着“工具 → Prompt → MCP → Agent → 全流程”的能力线前进。[TC-P-01][TC-P-08]

这与“系统能力递进型 + 原理与实践交替型”并不矛盾。可以让章节顺序递进能力，每个项目在自己的范围内完成：

`问题/原理 → 小项目演示 → 学员实现 → 测试或 Review → 方法复盘`

### 2. 小项目最好各自有明确的“能力主张”

陈天项目页不会只写项目名字，而会同时说明目标、技术栈、架构、实现步骤和学习要点。这种写法可以避免“做了一个网页”却说不清学到了什么。[TC-P-03][TC-P-04]

你们的 X/Y/Z 也应先按能力定义，再选题：

- **项目 X：GitHub 个人主页**：可视化结果强，适合展示从自然语言描述、Prompt、vibe coding 到最小测试和发布；不适合承载复杂 SDD 或 Harness。
- **项目 Y：简单游戏网页**：反馈快、迭代直观，适合讲需求变更、交互验收、浏览器测试和“小步修改”；适合把 Prompt/Vibe 过渡到计划化协作。
- **项目 Z：既有代码库上的功能变更**：例如 Issue/PR 助手、文档检索工具或小型 CLI。适合承载代码库探索、SDD、Review、Harness 和真实工作迁移。

X/Y/Z 不需要共享业务代码，但应共享一套方法产物，例如 `SPEC.md`、`PLAN.md`、测试证据、`REVIEW.md` 和复盘记录。

### 3. 综合项目不一定要从第一章开始

可以先用一两个“看得见结果”的项目建立动手信心，再在中后段引入一个需要理解存量代码、写 SDD 和搭 Harness 的项目。这样学员不会在第一章就被复杂代码库挡住，也不会一直停留在 vibe coding。[TC-P-03][TC-P-07]

### 4. 项目数量要和课程服务能力匹配

多个项目能降低单一技术栈失配的风险，但每个项目都需要 starter repo、运行说明、参考实现、测试、故障排查和评分 rubric。不能只增加项目名字，不增加维护和批改能力。

## 可讨论的项目组合 Options

### Option P1：三个独立小项目 + 一个选定的完整案例

- X：GitHub 个人主页，突出可见产出和快速反馈。
- Y：简单游戏网页，突出交互、需求变更和浏览器验证。
- Z：既有代码库功能变更，突出代码库理解、SDD、测试和 Review。
- 学员从 X/Y/Z 中选一个，提交完整的“需求到交付”记录；三个项目都提交关键过程产物。

优点是覆盖面和迁移性较好，且不要求维护一条连续产品线。风险是“选一个完整案例”会降低横向可比性，需要统一 rubric 和最低提交协议。

### Option P2：两个独立项目，分别承担“可见结果”和“真实工程”

- X/Y 合并为一个轻量可视化项目，例如主页或游戏二选一。
- Z 作为中等规模存量项目，完整走 SDD、Harness、测试和 Review。
- 前者用于 model/prompt/vibe coding，后者用于方法迁移和工程交付。

优点是课程叙事更紧，制作与维护成本较低。风险是轻量项目可能被当成玩具，两个项目之间需要清楚解释为什么方法在复杂度变化后仍然成立。

### Option P3：多个独立专题项目 + 统一综合任务

参考陈天的 6 项结构：每个主题配一个 4--8 小时小项目，最后再提供一个 8--12 小时综合任务。综合任务可以是智能文档助手、Issue/PR 助手或个人工作流工具。

优点是每章/每组能力都有独立练习，前置失败影响小。风险是总项目数、starter repo 和评测工作量明显增加，容易超过 10 章录播课的服务能力。

## 一个重要的评价设计

如果项目并列，最终不应只问“哪个项目做得最好”，而应同时评价：

- 项目结果：功能、交互、测试、可运行性
- 方法证据：需求澄清、SPEC、PLAN、验证、Review、Harness
- 迁移能力：同一套工作流能否应用到另一个项目或新需求

这样学员可以在项目主题上有选择，但课程仍然能评价相同的能力。

## Contradictions And Uncertainty

- 项目列表页面的统计文案写“5 个实战项目”，但页面同时列出 Project 1 至 Project 6；本报告按逐项卡片和详情页记录 6 个项目，不把“44+ 小时”作为精确总量。[TC-P-02]
- 公开页面能证明项目定位和目录写法，不能证明所有项目在实际教学中都按页面描述完成。
- X/Y/Z 的具体主题仍是假设，尚未验证 starter repo 的开发成本、运行门槛和学员兴趣。
- “一个完整案例”是否必需，取决于你们最终更看重作品集展示还是跨场景工作流迁移；这仍是课程目标层面的未决问题。

## Method

访问课程时间线和项目列表，随后逐页读取 project-1 至 project-6；同时核对仓库中的 `src/data/curriculum.ts` 和 `src/data/projects.ts`，以确认项目所属周次、目标和实现步骤。将项目关系分为代码递进、能力递进和综合收束三类，再把观察映射到 X/Y/Z 以及独立/递进项目选项。
