# AI Coding 课程项目候选方向研究

Research date: 2026-09-03
Scope: 面向高年级本科生、研究生和毕业 1--2 年工程师，寻找除“代码库入门助手”外仍有真实使用价值、能够训练 AI-assisted engineering 且适合 10 章录播课的项目方向。代码库入门助手作为已保留候选参与比较；本报告不锁定最终项目组合。

## Executive Summary

建议把项目选择标准从“AI 能不能生成一个看起来完整的应用”改成：**是否存在真实且反复出现的问题，能否切出一个可运行的垂直闭环，能否留下可验证的过程证据，能否在输入变化后继续工作**。

调研到的成熟工具边界支持几类很适合目标用户的场景：代码库上下文地图（aider）、研究资料组织与引用（Zotero）、数据清洗和发布（OpenRefine、Datasette）、实验可复现（MLflow、DVC）、任务和项目跟踪（Taskwarrior、GitHub Projects）。[CP-02][CP-03][CP-04][CP-05][CP-06][CP-07][CP-08][CP-09]

当前推荐优先讨论的候选是：

1. **代码库入门助手**：保留，最贴合 AI coding 的核心工作迁移。
2. **研究证据工作台**：把资料、摘录、结论、冲突和引用组织成可追溯证据链，适合学生和研究生。
3. **可复现数据报告助手**：从 CSV/SQLite 到清洗、分析、HTML 报告和运行记录，结果确定性强，适合自动评测。
4. **实验记录与结果比较工作台**：记录参数、指标、工件和运行差异，适合研究和工程实验。
5. **工作输入到行动项工作台**：把会议/需求记录转成决策、任务、负责人、验收标准和开放问题，贴近早期工程师的日常协作。

其中前四个更适合中型工程项目；第五个适合中型项目或综合项目的一个领域变体。`Learn X the AI way` 可以保留为选做方向，但必须做成“诊断式学习循环”，不能停留在一次 Deep Research + HTML 页面。[CP-01][CP-13]

## 项目选择策略

### 外部项目参考显示的共同结构

陈天训练营把 Ticket、NL2SQL、MCP、日志可视化、Code Review Agent 和智能文档助手分成多个独立专题，再用综合项目收束；企业级 AI Coding 参考也让不同项目分别承担 SDD/Harness、分布式系统、陌生代码库改造和开源贡献。[CP-11][CP-12] 共同点不是技术栈，而是每个项目都有明确的用户/工作场景、能力主张、实现步骤和估时。

因此，本课程的项目筛选应遵循：

- **先找反复发生的问题，再决定 AI 形态**：项目应服务于学习、研究、交付、协作或个人管理中的真实摩擦。
- **每个项目只承担一条主能力线**：例如代码库理解、证据追溯、数据质量、实验复现或协作落地，不要求每个项目都覆盖全部课程主题。
- **从输入到输出必须可观察**：输入资料/仓库/数据，输出结构化结果、变更、测试和复盘，而不是只有一张生成页面。
- **必须有状态变化或反馈循环**：例如资料更新后的增量重算、用户确认后的任务状态、失败测试后的修正、不同实验的比较。
- **写清非目标和边界**：不接真实银行、邮箱、日历或企业系统；不要求全量复制成熟产品；默认使用本地或脱敏数据。
- **优先选择可确定性评测的项目**：功能测试、schema 校验、引用完整性、数据统计、回归和权限边界应能由 harness 检查。
- **项目独立，方法递进**：starter repo 可以各自独立，递进的是需求澄清、代码库探索、SDD、实现、验证、Harness 和迁移能力。

## 候选项目详述

### 1. 代码库入门助手（保留）

**用户问题**：接手陌生项目时，入口、模块、运行方式、数据流和高风险区域分散在代码和文档中，AI 也容易凭局部上下文臆测。

**最小垂直切片**：输入一个受限规模的 Python/TypeScript 仓库和运行命令，生成机器可读的代码地图，再生成 HTML 导览；页面必须链接到真实文件/符号，列出入口、依赖、关键数据流、运行/测试命令和不确定项。aider 的 repository map 直接说明了“向 LLM 提供 git 仓库代码上下文”的产品边界。[CP-02]

**抗一次性生成设计**：加入一个变更任务或第二个 commit，要求更新受影响的地图；加入“证据链接完整性”和“未知项不得编造”的隐藏测试；要求一次人工问答/定位任务能依据地图完成。

**课程价值**：最直接训练代码库探索、上下文管理、渐进式披露、引用证据和迁移工作流。建议作为中型工程项目或综合项目。

### 2. 研究证据工作台

**用户问题**：学生、研究生和工程师阅读网页、论文、技术报告后，摘录散落在笔记里，结论与来源难以追溯，冲突观点容易被遗漏。

**成熟边界参考**：Zotero 的 collections/subcollections、tags 和 saved searches 说明研究资料的基本组织不是简单文件夹，而是可多重归类、可检索的资料集合。[CP-05]

**最小垂直切片**：输入一组本地 Markdown/HTML/PDF 文本和元数据；用户或 AI 创建 `source → excerpt → claim → caveat` 记录；系统生成带片段引用的主题报告，并列出没有证据或存在冲突的结论。

**抗一次性生成设计**：引用必须指向来源和片段范围；新增/替换来源后只重算受影响结论；隐藏测试使用相互矛盾的两份资料，检查系统是否标出冲突而不是强行合并；报告与结构化 evidence ledger 必须一致。

**工程训练**：需求建模、结构化输出、检索/引用、增量更新、评测和人工确认。适合 3--6 小时中型项目；不应扩展成完整 Zotero、向量数据库或通用 tutor。

### 3. 可复现数据报告助手

**用户问题**：课程作业、实验和工作分析经常从 CSV/SQLite 开始，但清洗步骤、异常记录、统计口径和最终图表难以复现。

**成熟边界参考**：OpenRefine 覆盖数据转换、聚类、网页数据拉取和导出；Datasette 定位为探索和发布结构化数据的工具。[CP-03][CP-04]

**最小垂直切片**：输入固定 CSV 或 SQLite；AI 先生成数据剖析和质量问题清单，用户确认后执行有限的清洗规则；输出清洗后的数据、变换配置、统计摘要和静态 HTML 报告；同一输入和配置应得到可比较结果。

**抗一次性生成设计**：禁止把结果硬编码到 HTML；隐藏数据包含空值、重复、类型错误和异常值；测试变换幂等性、统计口径、输入 schema 和报告中的数字一致性；要求重新运行生成相同摘要。

**工程训练**：数据契约、确定性测试、错误处理、CLI/脚本、可复现构建和结果审阅。是首期最容易做出可靠自动评测的候选之一。

### 4. 实验记录与结果比较工作台

**用户问题**：研究和工程试验中，参数、代码版本、指标和输出文件经常散落在 notebook、聊天和文件名中，无法回答“这次为什么更好”。

**成熟边界参考**：MLflow 将实验跟踪定义为记录 parameters、metrics、artifacts，比较运行、可视化并复现模型；DVC 则把数据版本、流水线、指标和实验管理纳入可复现流程。[CP-07][CP-08]

**最小垂直切片**：输入一个本地实验脚本和若干运行配置；系统记录 run id、代码/数据版本、参数、指标和产物摘要；提供两次运行对比和一份带结论依据的报告。

**抗一次性生成设计**：要求指标 schema 校验、缺失产物告警、不同代码版本对比和重新运行；隐藏测试更换参数顺序或增加失败运行，检查记录是否仍可查询；禁止依赖真实 GPU 或云服务。

**工程训练**：状态建模、日志/工件处理、可复现性、CLI/API、失败路径和评测。对研究生尤其贴近，但需要把领域限定为“可运行的小型脚本实验”，避免变成 ML 平台。

### 5. 工作输入到行动项工作台

**用户问题**：会议纪要、需求讨论和 issue 里有大量决定、任务、负责人、截止时间和未决问题，但信息常停留在自然语言中，交付时容易遗漏。

**成熟边界参考**：GitHub Projects 支持 table/board/roadmap、多视图、custom fields、模板、自动化，并与 issues/PR 双向同步，说明“状态化工作项”是实际协作系统的稳定边界。[CP-09]

**最小垂直切片**：输入脱敏的会议/需求文本；AI 提取 decisions、actions、owner、due date、acceptance criteria 和 open questions；用户确认后写入本地 JSON/SQLite，并提供按状态、负责人和截止时间的视图和变更记录。

**抗一次性生成设计**：抽取结果必须可人工确认/修改；保留原文证据和字段来源；测试日期、负责人缺失、重复行动项、否定句和需求变更；不自动发送邮件、不改真实日历、不调用企业账号。

**工程训练**：结构化抽取、人工审批、状态迁移、变更追踪、权限边界和工作流设计。现实价值高，但自然语言歧义使纯自动评分较难，适合有人工复核的综合项目。

### 6. Learn X 的工程化版本

**用户问题**：学习新技术或非编程领域时，资料太多，学习计划与个人基础不匹配，阅读后也不知道是否真正掌握。

**风险判断**：若流程只是“资料 → Deep Research → HTML 学习页面”，Codex 可以一次生成大部分产物，难以证明学习者理解，也没有持续状态。这个风险与开发者高频使用 AI 做学习、文档和搜索但仍不完全信任输出的现象相符。[CP-01][CP-13]

**可接受的最小垂直切片**：输入一组带来源的资料、学习目标和学习者背景；输出前置依赖图、阶段目标、练习题和片段引用；学员提交答案后，系统给出带证据的诊断并生成下一步计划；保存计划版本和资料变更。

**抗一次性生成设计**：隐藏测试替换主题和资料；检查引用、练习-目标关联、错误答案诊断、增量更新和版本差异；HTML 只作为 JSON/结构化模型的视图。

**定位**：选做强化或小型研究项目，不建议首期作为唯一综合项目；不做泛化 AI tutor、自动判定“学会了”或无边界的网页生成器。

### 7. 求职证据矩阵

**用户问题**：学生和早期工程师面对职位描述时，难以把课程/项目经历映射到技能要求，简历中的成果证据也不完整。

**最小垂直切片**：输入脱敏 JD、简历和项目记录；输出技能/证据矩阵、缺口、可补强的小任务和针对某岗位的简历改写建议；每条建议链接到原始经历。

**主要限制**：个人隐私和主观判断较强，评分容易退化为文本相似度；如果没有“证据链接、改写前后差异、反事实检查”，很容易被一次提示词生成。适合小项目或选做，不建议承载 SDD/Harness 深度训练。

### 8. 个人任务与周复盘

**用户问题**：工作和学习任务散落在聊天、便签和 issue 中，无法稳定地安排、过滤和复盘。

**成熟边界参考**：Taskwarrior 的文档包括日期、优先级、标签、上下文、重复任务、过滤、报表、JSON 导入导出和 hooks，说明可复用的最小任务域模型比“再做一个 Todo UI”更丰富。[CP-06]

**最小垂直切片**：自然语言输入转为结构化任务；用户确认后支持状态、优先级、标签、截止时间；生成每日/每周复盘，引用完成记录和未完成原因。

**主要限制**：用户价值明确但工程新颖性和抗一次性生成能力偏低；若没有导入、状态迁移、重复任务、复盘证据和确定性 CLI 测试，会变成 CRUD 小练习。适合第 1--2 章小项目。

### 9. 资料/书签整理队列

**用户问题**：文章、文档和视频收藏后没有后续处理，重复资料和未读队列不断增长。

**最小垂直切片**：本地 URL/Markdown 导入、去重、标签建议、阅读状态和摘要引用。

**主要限制**：与研究证据工作台高度重叠，且容易退化为“抓网页、生成摘要、做漂亮列表”；外部网页可访问性、版权和内容变化也增加维护成本。建议作为研究项目的一个输入适配器，而不是独立项目。

### 10. 证件/合同截止日管家

**用户问题**：证件、租约、账单和申请材料的截止日期容易遗漏。

**最小垂直切片**：输入脱敏文档和人工确认的日期；抽取事项、截止日、提醒窗口和所需材料；提供本地日历式视图和变更记录。

**主要限制**：生活价值高，但涉及个人敏感信息，日期抽取错误的代价高；不应自动操作真实账户、邮件或日历。首期只适合作为安全边界演示或选做，不适合作为主项目。

## 推荐梯队

### 第一梯队：最值得做成中型工程项目

**代码库入门助手 + 研究证据工作台 + 可复现数据报告助手**。

这三个项目覆盖代码、知识和数据三种输入形态，仍然共享同一套工程方法：探索输入、建立结构化模型、生成结果、引用证据、运行测试、处理变更和复盘。它们都能在本地完成，适合独立 starter repo 和隐藏测试；同时项目完成后有机会继续使用，而不是只在课堂里展示。

### 第二梯队：适合综合项目或替换项

**实验记录与结果比较工作台**适合研究生和有数据/模型经验的学员；**工作输入到行动项工作台**更贴近早期工程师和团队协作。如果你们想让综合项目更“工作化”，优先选择后者；如果想让课程兼顾研究场景，优先选择前者。

### 第三梯队：小项目或选做

**Learn X 诊断式学习循环、求职证据矩阵、个人任务与周复盘**都对目标用户有直接价值，但要么评测主观性较高，要么工程深度不足。它们适合用来让学员体验“把 AI 放进自己的工作/学习系统”，不适合作为唯一主线。

### 首期不建议独立成主项目

纯静态学习页面、泛化个人知识库、完整 Todo/记账应用、任意文件自动整理、自动发邮件/改日历/操作银行或企业系统。这些方向要么容易被一次生成替代，要么隐私、权限和外部依赖会压过课程真正要训练的能力。

## 对 Learn X 风险的直接回答

风险是真实存在的，而且不只是“页面可能被生成得太快”。如果验收标准只看 HTML 是否漂亮、内容是否丰富，学员和 Codex 都可以绕过需求建模、证据追溯、评测和迭代。

要把它变成 AI engineering 项目，至少需要四个不可替代的状态：

`资料版本 → 学习模型 → 学员回答 → 诊断与下一步计划`

其中 HTML 只是呈现层；核心验收应检查结构化数据、引用、错误诊断、版本差异和对新资料的增量处理。若课程制作资源有限，建议把 Learn X 作为选做强化，并将“研究证据工作台”作为更稳健的主项目候选。

## 未决问题

1. 项目是否要服务“个人继续使用”，还是优先服务“作品集展示”？前者偏证据/数据/任务工具，后者可能偏网页/交互应用。
2. 综合项目是否允许领域选择？允许选择会提升迁移性，但需要按同一输入/输出协议设计 rubric。
3. 是否接受学员上传自己的脱敏资料？这会显著增加隐私、版权和评测一致性成本。
4. 课程是否需要展示真实外部集成？若需要，建议只读 API 或本地模拟器，不把账号授权作为必做条件。
5. 评分更重“最终结果”还是“过程证据”？研究和协作类项目需要更强的人工复核，不能只依赖 AI 总分。

- 矩阵估时按本课程已有的 3--6 小时中型项目边界估计，不是公开产品项目的真实开发耗时。
- 没有把候选项目与具体深蓝学院作业批改系统绑定；平台和评测设计仍需另行决策。

## Method

先复核仓库中的深蓝学院、陈天训练营和 AI Coding 作业评测研究，再按研究/学习、工作协作、数据/实验、求职、个人管理五类扩展候选。优先读取 OpenRefine、Datasette、Zotero、Taskwarrior、MLflow、DVC、GitHub Projects、GitHub template repository 和 aider repository map 的官方文档，记录其直接描述的产品边界；最后使用统一矩阵评估课程可行性，并增加“一次 Deep Research + HTML 生成即可完成吗？”这一反向检查。研究目标是形成可讨论的候选池，不声称穷尽所有项目方向。
