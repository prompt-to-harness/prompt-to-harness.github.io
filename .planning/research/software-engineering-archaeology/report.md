# 软件工程拾遗：哪些经典思想值得放进 AI Coding 课程

Research date: 2026-09-06

Scope: 面向本课程的高年级学生、研究生和毕业 1--2 年工程师，考察从 1960s 到今天仍能解释软件开发困难的经典思想。研究优先使用作者原文、作者存档页和一手项目资料；AI coding 的对应关系是课程设计判断，不是经典作者的历史预言。

## Executive Summary

建议把这条线命名为 **软件工程拾遗**。它不是补一门旧课，而是从历史上有影响力的人物、论文、书和争论中，捡回今天容易被 AI 的速度感掩盖、但仍然能帮助我们判断软件的思想。它应当是一条“复杂度与证据”线，而不是 SOLID/Clean Code 术语线。最值得优先分享的核心是：

1. **软件为什么难**：Brooks 的 essential/accidental complexity，加上 Dijkstra 对“可理解、可验证程序”的要求。它能直接解释 AI 为什么让代码产出变快，却没有替人决定需求、规则和边界。[SE-01][SE-03][SE-04]
2. **复杂度放在哪里**：Dijkstra 的分离关注点、Parnas 的信息隐藏，以及 Ousterhout 的 deep modules。它们能把“好的架构”从审美偏好变成一个问题：调用者必须知道多少，变化能否集中在一个地方。[SE-02][SE-06][SE-07]
3. **变化如何被控制**：Fowler 的小步、保持行为的重构，加上 Agile Manifesto 对工作软件和响应变化的平衡表述。它们适合在 Agent 已经生成可运行代码后做现场演示。[SE-08][SE-09]
4. **组织如何进入系统**：Conway 的原始论文比一句“康威定律”更有价值，因为它说明通信路径会影响可实现的设计空间；这可以自然迁移到多人或多 Agent 并行开发。[SE-05]
5. **测试是什么证据**：Dijkstra 的“测试能显示 bug 存在，不能证明不存在”适合作为边界条件，再配合行为测试、集成测试、运行时检查和 Review，避免把覆盖率当成质量本身。[SE-01]

你提供的 Ousterhout/Martin 材料把这个命名的教学气质补得很完整：两位作者都关心让后来阅读代码的人更容易理解和修改，却在方法长度、注释、TDD 和设计先行上有实质分歧。[SE-15] 这类分歧比“唯一正确的最佳实践”更适合拾遗：学员看到人物、原文、争论和代码证据，然后形成自己的判断。

这场对谈及其视频简介还提供了一张人物阅读地图：Dijkstra、Hoare、Dahl、Parnas、Meyer、Knuth、Gamma 等人的作品被列为相关书籍或讨论背景。[SE-22] 这应被视为候选池，不是“Bob 认可的完整榜单”；每位人物仍需回到原始作品核验。

建议的讲解顺序是：**软件与复杂度 → 模块/接口/信息隐藏 → 变化与重构 → 测试与交付证据 → 组织/Agent 协作**。SOLID 和 Clean Code 放在模块与变化之后，作为诊断词汇；“软件熵”只做有边界的解释性隐喻，暂不作为核心定律。

## Findings

### 1. 先讲“为什么软件工程存在”，再讲方法名

Dijkstra 在《On the reliability of programs》中把问题描述为：大型程序由许多部分组成，单纯把系统当黑盒并增加测试并不能让人有足够信心；他主张寻找“intellectually manageable programs”，通过结构、抽象和纪律降低理解与验证的负担。[SE-01] 这非常适合作为课程的第一场考古：学员先看到一个今天仍成立的失败模式，再看到模块、抽象和测试为什么会出现。

Brooks 的 1986 原文把软件工作区分为 essential tasks 和 accidental tasks，并说明软件的本质困难包括复杂度、对外部约束的服从、持续变化和不可见性。[SE-03][SE-04] 这为 AI coding 提供了稳妥的现代映射：模型可以显著减少语法、样板、检索和部分工具摩擦，但不会自动决定产品规则、冲突取舍、接口契约或“什么算完成”。“AI 已经终结软件工程”不是这篇论文能支持的结论。

**课程建议**：做一次同一需求的双轨演示。第一轨允许 Agent 一次生成；第二轨先写验收条件、边界和失败情况，再让 Agent 实现。比较两者的代码量没有意义，比较未验证假设、返工位置和人需要理解的范围才有意义。

### 2. 用“复杂度在哪里”解释模块和接口

Dijkstra 在 EWD447 明确提到 separation of concerns，并用 thin interface 描述一个自洽知识领域与外界的连接。[SE-02] Parnas 的 1972 论文则给出可操作的反例：几乎总是错误地按流程图步骤切模块，应该从困难或可能变化的设计决策出发，把这些决策隐藏在模块里。[SE-06] 他的 KWIC 例子展示了两种分解在存储格式变化、理解成本和独立开发上的差异，非常适合直接改造成课程实验。

Ousterhout 的现代综合把问题说得更接近今天的代码 Review：深模块用相对小的接口隐藏较多复杂行为，浅模块把实现知识泄漏给调用者；设计的目标是降低复杂度，而不是增加抽象层。[SE-07] 这与 AI coding 的关系很直接：Agent 容易复制局部模式、铺开参数和转发层；学员需要检查新增接口是否真的减少了调用者需要知道的事情。

Knuth 的 `Literate Programming` 原文为这张卡增加了一个有趣的第三角度：程序不仅要告诉机器做什么，也要按最有利于人类理解的顺序解释概念、变量和算法。[SE-24] 因此“代码可读性”不能缩减为短函数或少注释；它还包括解释结构、算法选择和读者的阅读路径。

**课程建议**：为同一个功能让 Agent 设计两个版本。要求学员记录每个调用者需要知道的参数、不变量、错误模式和配置，再通过一次需求变化比较哪一版把修改集中得更好。这个练习比背“高内聚低耦合”更可评审。

### 3. 把 SOLID 降级为诊断工具

SOLID 适合介绍，但不适合作为这条线的历史主轴。它提供一组很方便的提问方式：一个模块是否被不相关的变化牵动？替换一个适配器时契约是否成立？调用者是否被迫依赖不需要的事实？高层策略是否依赖稳定的接口？这些问题建立在更底层的变化、信息隐藏和接口契约之上。

本轮没有找到足够可靠、统一的 SOLID 原始发表记录来支撑完整词源史，因此不建议在课程中声称“五条原则自某年某文档起正式成立”。应把它标成后来的工程词汇，并明确它们不是“每个类必须抽象、每个方法必须短”的机械规则。[SE-10]

**课程建议**：只选 2--3 个与当前 Project 直接相关的原则，每个原则用一个坏设计、一个改动压力和一个反例讲完。不要安排 SOLID 全套背诵或原则打分。

Martin 2000 年的原始文章还提供了一个很好的历史入口：设计腐化会表现为 rigidity、fragility、immobility 和 viscosity，然后才进入 OCP、LSP、DIP、ISP 等原则。[SE-16] 课程应先展示“改一个地方为什么要动很多地方”，再给原则命名。

### 4. Clean Code 要讲“阅读和修改成本”，不要讲风格崇拜

Fowler 的重构说明提供了更可操作的路径：重构是对已有代码进行一系列小的、保持行为的变换，测试帮助控制风险，代码异味提示可能存在设计问题。[SE-08] Ousterhout 的作者页还明确记录了他与 Clean Code 在方法长度、注释等问题上的分歧。[SE-07] 这说明 Clean Code 本身也应被当作可讨论的实践集合，而不是不可争论的美学标准。

**课程建议**：给 Agent 一个“能跑但难改”的模块，要求先补行为测试，再做一到三个小步重构。学员依据 diff、测试和下一次需求变化判断改进是否真实。命名、函数长度、DRY 等只在影响理解或变化局部性时出现。

### 4.1 一场值得直接使用的当代争论

Ousterhout 和 Robert Martin 的公开对谈可以作为一张完整的“拾遗卡”，而不是只当书籍宣传材料。双方围绕 Knuth 的 `PrimeGenerator` 例子讨论：小函数何时提供深度，何时变成浅接口和 entanglement；注释何时补足接口知识；TDD 如何与设计思考、重构和测试安全网配合。[SE-15]

它的价值不在于替学员选边，而在于把判断标准具体化：

- 代码是否减少了读者必须同时掌握的信息？
- 拆分之后，接口是否比实现更容易理解？
- 注释是否提供代码无法表达的意图、约束或原因？
- 测试节奏是否帮助设计，还是把注意力锁死在下一个小行为？

建议让学员先阅读一小段双方原文，再对同一函数做两种改写，最后用下一次需求变化、测试和 Review 证据说明选择。视频 [Book Overflow follow-up](https://www.youtube.com/watch?v=3Vlk6hCWBw0) 可以作为补充观看材料；本轮未稳定取得字幕，因此不把视频中的具体人物引述写入事实账本。

### 5. 测试是证据链的一部分，不是完成证明

Dijkstra 的原话适合建立测试的边界：测试能有效显示 bug 存在，但不能显示 bug 不存在。[SE-01] 这不意味着少写测试，而是要求测试与结构、规格和风险共同工作。模块接口应成为主要测试表面；集成测试检查适配器和真实组合；运行时检查验证用户可见行为；Review 负责找出测试覆盖不到的需求误读和权限风险。

**课程建议**：让 Agent 实现并声称完成一个变更，故意保留一个未覆盖的失败分支。学员从验收条件、测试、运行结果和 diff 中找出“尚未证明”的部分，再决定补测试、改规格还是退回实现。这个练习同时连接 SDD、Harness 和软件工程暗线。

如果课程需要一个比 SOLID 更稳定的接口契约入口，可以补 Meyer 的 Design by Contract 和 Liskov/Wing 的 behavioral subtyping：先写清调用者前置条件、模块后置保证和状态不变量，再替换实现检查契约是否仍成立。[SE-17][SE-18] 这能把 LSP 从一句口号还原为“使用者能否观察到替换后的行为仍满足原性质”。

### 6. 变化与重构比“从零搭架构”更接近真实工作

Brooks 在《No Silver Bullet》中提出原型和“grow, not build”作为应对软件复杂性的方向之一。[SE-04] Agile Manifesto 强调工作软件、客户协作和响应变化，同时明确右侧的文档、合同和计划仍有价值。[SE-09] 二者合起来能避免两个极端：一开始写一份无法验证的巨型设计，或把持续变化误解为不需要规格和记录。

**课程建议**：不要让所有 Project 都从空目录开始。至少安排一次接手陌生仓库、先建立代码地图、再添加功能、再做小步重构的闭环。学员需要提交变化前后的接口、测试和 Review 证据。

### 7. Conway 值得讲，但要讲原文条件和 AI 版本的推断边界

Conway 的原始论文不是一句“系统复制组织结构”就结束。作者先定义设计组织和系统的图结构，再论证通信路径会约束可实现的设计选择；作者自己的 2015 注释也把流行说法明确为 informal version。[SE-05] 这比把康威定律当成宿命更准确。

对 AI coding 的映射是一个有价值的课程推断：并行 Agent 的分工、共享上下文、接口协商和合并方式，会影响系统结构和冲突数量。但“多 Agent 一定重演某个历史项目”属于假设，必须用实验或案例支持，不能借 Conway 原文背书。

**课程建议**：把同一任务分成不同 Agent/小组结构，观察接口协商、冲突和最终模块形状；讨论哪些通信路径缺失，哪些设计因此无法被有效探索。

### 8. “软件熵”可以讲，但不能伪装成精确科学

本轮查到的高质量一手来源更直接使用 complexity、changeability、understandability、maintenance 和 design 等概念，没有找到一个统一权威、可量化的“软件熵”定义。[SE-11] 因此它适合做一个帮助初学者建立直觉的隐喻：重复规则、临时修补、失真文档和泄漏边界会增加下一次变更的摩擦。它不适合作为代码质量分数，也不应声称能像物理熵一样计算。

**课程建议**：用连续三次小需求展示“每次都能跑，但修改范围扩大”的现象；让学员指出具体重复、耦合和未知项。把“熵上升”翻译成可观察证据，而不是要求学员接受一个抽象比喻。

DRY 和 YAGNI 可以作为两枚刹车片放在这一节之后：DRY 针对同一知识的权威表示，YAGNI 针对尚未被真实需求支持的假定功能；两者都不等于“禁止重复”或“不做设计”。[SE-19][SE-20]

### 9. Ward Cunningham：技术债最初是一个关于整合的故事

Ward Cunningham 的 WyCash 经验报告提供了比“技术债就是坏代码”更准确的历史入口：第一次实现可以帮助产品尽快进入真实反馈，但如果不持续整合和重写，未完善的实现会产生利息，最终让代码变得无法掌握、组织变得不灵活。[SE-23]

这对 AI coding 尤其有用，因为 Agent 可以把“第一次实现”做得极快。真正的问题不是是否允许临时实现，而是是否能让债务可见、记录偿还条件，并在需求变化前完成有价值的整合。

**课程建议**：让学员接受一次“能跑但不理想”的 Agent 实现，记录它带来的速度收益和维护利息；下一次需求到来时，比较直接叠加功能与先还一部分债的总成本。不要把所有重构都叫还债，也不要用技术债作为不具体的抱怨。

### 10. Peter Naur：代码交接时丢掉的不是文件，而是理论

Peter Naur 在《Programming as Theory Building》中反对把编程简单理解为生产程序和文档，提出程序员是在形成对问题和解法的理解，即一种 theory。[SE-25] 这个角度非常适合今天的 Agent 场景：上下文文件、代码地图和测试可以传递大量信息，但仍可能无法完整传递设计者为何这样建模、哪些变化被刻意排除。

**课程建议**：让 Agent 接手一个没有对话历史的仓库，只给代码、测试和一份普通 README；再补一份记录设计决策、未知项和反例的“理论卡”，比较两次接手的错误假设和修改范围。重点不是要求学员写长文档，而是让隐性知识有机会被识别和验证。

| Tom DeMarco、P. J. Plauger、Meilir Page-Jones | 结构化分析、系统规格和模块设计的早期工程化语言 | 需求/数据流图短案例 | **资料扩展**；先补原文再决定 |

其中最有潜力形成第一季内容的是 **Dijkstra → Brooks → Parnas → Ousterhout/Martin → Fowler/Meyer → Conway**。这不是按年代排的历史课，而是按一个工程问题逐步展开：保持理解力、控制复杂度、选择边界、处理分歧、表达契约、组织协作。

## “拾遗卡”的人物模板

每位人物只需要一张卡，避免讲成传记：

1. **他/她当时看见了什么失败？** 给出项目、论文或代码背景。
2. **原话和原方案是什么？** 标明年份、版本和来源级别。
3. **后来的人把它简化成了什么口号？** 找一个常见误读或反例。
4. **AI coding 今天重演了哪一部分？** 明确这是课程映射，不是历史预言。
5. **学员如何用一个实验判断？** 实验必须留下代码、diff、测试、日志或决策记录。

例如，Ousterhout/Martin 这一卡可以围绕同一个 `PrimeGenerator` 展开：先读两位作者对方法长度、注释和 TDD 的原文，再让 Agent 产出两种实现，最后根据下一次需求变化、读者认知负担和行为测试做评审。[SE-15]

## Recommended Topic Tiers

### 核心话题

| 话题 | 为什么值得讲 | 最小项目证据 |
| --- | --- | --- |
| 软件为什么难：本质/偶然复杂度 | 解释 AI 提速的真实边界，避免银弹叙事 | 一次性生成与规格驱动实现的返工/未验证假设对比 |
| 分离关注点、模块、接口、信息隐藏 | 提供架构判断的共同语言 | 模块地图、接口草图、一次需求变化后的 diff |
| 测试与验证边界 | 把“模型说完成”变成证据问题 | 行为测试、集成检查、运行截图/日志、未覆盖风险 |
| 小步重构与持续变化 | 把维护从事后救火变成日常动作 | 行为保持的重构提交和回归结果 |
| 版本控制、Review、最小权限 | 形成可回滚、可审阅、可控的交付闭环 | 小提交、Review 评论、权限/审批记录 |

### 诊断话题

| 话题 | 讲法 | 主要限制 |
| --- | --- | --- |
| SOLID | 从变化压力和接口契约提问 | 不做词源神话和机械打分 |
| Clean Code | 从阅读/修改成本和重构证据讲 | 不把个人风格偏好当定律 |
| 深/浅模块、接缝、适配器 | 用两个接口和一个真实变化比较 | 需要避免把抽象泛化成越多越好 |
| 康威与多 Agent 协作 | 观察通信结构如何影响设计 | AI 版本是课程推断，需要标注证据等级 |
| 软件熵、技术债 | 只用可观察的摩擦作隐喻 | 不教成物理定律或精确指标 |

### 展望/阅读

Brooks《人月神话》中的协调成本和概念完整性、Lehman 软件演化定律、形式化方法、领域建模、架构演化和可观测性体系，都值得进入阅读推荐或后期案例。本轮没有完成全部一手来源核验，不建议现在把它们写成核心课承诺。

## Suggested Archaeology Format

每个话题用同一张“考古卡”讲，控制在 10--20 分钟：

1. **当时的问题**：作者面对什么失败，不先从术语定义开始。
2. **原始主张**：给出一段短引文和年份，说明来源类型。
3. **后来修正**：哪些部分被过度简化、反例是什么、适用边界在哪里。
4. **今天的映射**：它如何解释 Agent、SDD、Harness 或代码 Review 中的具体现象。
5. **现场实验**：让学员在当前 Project 中改变一个变量，留下 diff、测试、日志或决策记录。
6. **一句判断题**：学员必须说明何时适用、何时不适用，而不是复述名词。

建议每张卡只保留一个核心问题。例如：

- Brooks：哪些工作是表达摩擦，哪些工作是产品规则本身？
- Parnas/Ousterhout：调用者为了使用这个模块必须知道什么？
- Fowler：这次重构是否保持行为，下一次变化是否更局部？
- Dijkstra：这个测试发现了什么，仍然没有证明什么？
- Conway：谁和谁没有通信，因此哪种设计根本没有被探索？

## Contradictions And Uncertainty

- “没有银弹”经常被转述为“任何技术都不会带来巨大收益”。Brooks 原文更窄：没有单一发展独自承诺数量级提升，同时组合式、持续努力仍可能带来数量级改善。[SE-03]
- Agile 经常被简化成不要文档、不要计划；原文明确说右侧仍有价值，只是左侧优先。[SE-09]
- Conway 的流行短句压缩了原文的图结构论证和条件；教学需区分作者原文与后来的 informal version。[SE-05]
- SOLID、Clean Code 和软件熵都存在明显的二手传播和术语漂移。本轮只把它们放在诊断/隐喻位置，没有把未经核验的词源当成历史事实。[SE-10][SE-11]

## Gaps

Parnas 全文与 DOI 已补齐，见证据表 SE-06。本轮没有完成 Brooks《人月神话》具体章节、Lehman 原始论文、SOLID 词源、Clean Code 原书对反例的系统核验；这些适合下一轮定向补证。研究也没有比较不同课程样本的实际学习效果，因此“值得讲”的排序是基于原始问题、迁移性和可演示性的课程设计判断，不是教育实验结论。

对谈视频的字幕本轮未能稳定取得，报告只使用 YouTube 页面公开元数据和 Ousterhout/Martin 作者共同维护的 GitHub 对谈原文；视频中的未核实具体发言不作为事实引用。

## Method

先读取仓库现有课程定位、Project 约束和软件工程知识图谱，抽取已有候选及其证据缺口；再按复杂度、模块边界、变化、验证、组织结构五个子问题寻找作者原文或第一方页面；增加反向核查，专门记录流行简化、来源缺失和 AI 时代推断不能冒充经典事实的地方。研究停止条件是：核心候选已经能形成稳定的讲解顺序，继续搜索主要只会增加书目而不会改变首轮选题。
