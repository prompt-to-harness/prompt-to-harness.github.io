# 把反馈收集拆成两条渠道

> 调研日期：2026-10-11。依据 `research_notes/课件反馈收集方案比较/` 下四份笔记整理。标注约定：**【已核实】** 表示读过官方文档、源码或做过接口实测；**【待实测】** 表示只有二手资料、搜索摘要或推断，落地前必须验证。本文是方案比较，不是已上线的决定，也没有经过真实学员试用。

**结论先行：不存在一个方案能同时做到“大陆稳定可达、无需账号、定位到段落、可程序化导出、零运维、无密钥”。比较现实的做法是按人群分成两条渠道。** 邀请的少量 reviewer 用**自建的 `?review=1` 评审模式**：选中文字后写评论，按 scene id 和原文锚定，存在 localStorage 里，导出 JSON，或者生成预填的 GitHub Issue Form 链接。这条渠道不依赖任何第三方服务；如果 reviewer 愿意注册账号，且实测能访问，**Hypothesis 私有群组**可以作为现成替代。持续的公开读者用**飞书多维表格表单**：URL 预填课次、scene 和页面地址，并把这些字段隐藏，读者免登录填写；GitHub Actions 定时用 API 拉取，交给 AI 分诊。有 GitHub 账号的读者另给一个预填 Issue Form 链接。giscus 不比这两条渠道更简便：它要求评论者有 GitHub 账号，不能预填段落位置，内容默认公开，大陆访问也没有可靠测量，适合以后做社区讨论，不适合作为反馈主渠道。两类人群的方案里，演示模式都可以做到页面上不加载任何第三方脚本。对整体判断影响最大的未知数有三项，都要先实测：飞书免费版能否用 `prefill_`/`hide_` 和开放平台 API，hypothes.is 在大陆是否可达，以及 github.com 的登录和 Issue 提交在校园网下是否顺畅。

## GitHub 系方案定位精确、身份可追溯，但门槛卡在账号和网络

giscus 是 GitHub 原生方案里最成熟的。**每个页面映射到一条 Discussion，第一次有人评论或点 reaction 时才创建**（[giscus README](https://raw.githubusercontent.com/giscus/giscus/main/README.md)）。`data-mapping="specific"` 配合 `data-strict="1"`，可以把 `lesson-id/scene-id` 这种稳定 ID 当作键；父页面通过 `postMessage` 发送 `setConfig`，不重载 iframe 就能切换 `term` 和 `backLink`，所以做到 scene 级定位在技术上可行【已核实】（[ADVANCED-USAGE](https://raw.githubusercontent.com/giscus/giscus/main/ADVANCED-USAGE.md)）。嵌入代码里的 `repo-id` 和 `category-id` 是公开的节点 ID，不是密钥；导出可以用 GitHub GraphQL 的 Discussions 接口（[GitHub 文档](https://docs.github.com/en/graphql/guides/using-the-graphql-api-for-discussions)）；审核用 GitHub 自带的锁定、隐藏和屏蔽功能，基本没有额外运维。问题有三个。第一，**评论者必须有 GitHub 账号并 OAuth 授权**【已核实】。第二，`setConfig` 的字段里**没有预填评论文本**，段落位置只能靠读者自己描述。第三，评论公开，并挂在评论者的实名 GitHub 身份下。大陆访问方面，只有“似乎未被墙”“体验有点炸裂”这类无测试方法的博客说法（[云游君](https://www.yunyoujun.cn/posts/third-party-comment-system)、[lixueduan](https://www.lixueduan.com/posts/blog/02-add-giscus-comment/)）。giscus.app 部署在 Vercel 上（[dejavu.moe](https://blog.dejavu.moe/posts/giscus-selfhost/)）；即使自托管，OAuth、数据读写和头像仍然要访问 github.com、api.github.com 和 avatars.githubusercontent.com。还有一个容易忽略的推论：学员能打开 `*.github.io` 上的课件，**并不能说明这三个域名同样可达**。

GitHub 系里，**Issue Form 预填链接最值得用**。`issues/new` 支持 `title`、`body`、`template` 等官方参数，Issue Form 的自定义文本字段也可以**按字段 `id` 用 URL 参数预填**【已核实】（[Creating an issue from a URL query](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue#creating-an-issue-from-a-url-query)）。在每个 scene 旁放一个按钮，生成 `issues/new?template=feedback.yml&lesson=ch03&scene=07&quote=...`，读者打开后看到的是一张填好位置的结构化表单，AI 解析时按固定的 `### 字段名` 切分即可。有三个坑。第一，外部读者没有加 label 的权限，带 `labels` 参数会**返回 404**，默认标签应写进表单 YAML。第二，URL 太长会返回 **414**，但 GitHub 没有公布阈值；中文每个字编码后占 9 个字节，所以引用的原文要截断，比如只取前 200 字。第三，提交仍然需要 GitHub 账号。`discussions/new?category=&title=&body=` 的预填**只有 2020–2021 年的社区说法，官方文档没有提**（[community #2892](https://github.com/orgs/community/discussions/2892)），在实测通过之前不应依赖。Edit this page 确实能让非成员一键 fork 并开 PR（[Editing files](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files#editing-files-in-another-users-repository)），但课件是十几个 scene 挤在一个 HTML 里，要非开发者在源码里找位置并不现实，而且读者直接改文案会绕过 `editorial-checklist.md`，只适合讲师和熟练贡献者。

## 中文自托管评论门槛最低，但“零运维”已经做不到

Waline、Twikoo、Artalk 都由中文社区维护，**默认允许免注册匿名评论**，都带管理后台和邮件通知（[Waline 组件属性](https://waline.js.org/reference/client/props.html)、[Twikoo FAQ](https://raw.githubusercontent.com/twikoojs/twikoo/main/docs/faq.md)、[Artalk 前端配置](https://artalk.js.org/guide/frontend/config.html)）。它们也都允许用任意字符串代替 URL 作为分组键：Waline 和 Twikoo 用 `path`，Artalk 用 `pageKey`，并提供 `update()` 方法。所以“每页挂一个实例，切换 scene 时换键”可以做到 scene 级定位，但段落级锚点要自己生成。截至 2026-10，这三个项目和 Remark42 都在持续发版：Waline 最近一版在 2026-09-30，Twikoo 在 2026-10-09，Remark42 在 2026-09-14【已核实，GitHub API】。在评论区里实现私有反馈的通用做法是**开启全量审核，并且永不放行**：Waline 的 `COMMENT_AUDIT` 开启后，评论要管理员审核才显示（[Waline 服务端环境变量](https://waline.js.org/reference/server/env.html)）；Artalk 的数据里有 `page_admin_only` 字段，实际效果【待实测】。导出能力最完整的是 Remark42：`/api/v1/admin/export` 可以导出全站 JSON，还有每日自动 gzip 备份（[Remark42 API](https://raw.githubusercontent.com/umputun/remark42/master/site/content/docs/contributing/api/index.md)）。Artalk 的 Artrans JSON 带 `page_key` 和 `is_pending` 字段（[Artalk 数据迁移](https://artalk.js.org/guide/transfer.html)）。前端只需要一个公开的 `serverURL`，管理员凭证和数据库密码都放在服务端或 CI secret 里，不进公开仓库。

真正的问题在托管。过去“零服务器、国内可达”的标准答案是 LeanCloud，但 **LeanCloud 已从 2026-01-12 起冻结新注册和新建应用，2027-01-12 全部关停**（[LeanCloud 停服公告](https://docs.leancloud.cn/sdk/announcements/sunset-announcement/)）。腾讯云 CloudBase 的免费体验版**不能配置跨域域名，云函数超时固定为 3 秒**，跑不了 Twikoo，实际要买 **19.9 元/月的个人版**（[Twikoo 部署文档](https://raw.githubusercontent.com/twikoojs/twikoo/main/docs/backend.md)）。Twikoo 文档也写明 Vercel 在大陆“访问速度较慢甚至无法访问”，而 Waline 的官方快速上手恰恰是 Vercel 加 Neon（[Waline 部署](https://waline.js.org/guide/deploy/vercel.html)）。剩下的现实选项是 Twikoo 官方评为 4 星的“Netlify 免费函数（每月 12.5 万次请求）加 MongoDB Atlas”，以及一台国内或香港的小 VPS 用 Docker 跑单容器。前者的境外数据库延迟【待实测】；后者每月几十元，价格是市场常识，【待实测】。2026 年 Railway 和 Hugging Face 的免费层都收紧了，说明**平台退出风险才是这类方案的主要成本**，课程反馈的流量反而可以忽略。反垃圾方面，reCAPTCHA 在大陆基本不可用（社区共识，【待实测】），Artalk 内置的图片验证码和极验更稳。综合来看，自托管评论适合将来想在页面上开公开讨论区的阶段。现阶段只为收集反馈，它带来的服务器、备份和版本对齐（Twikoo 要求前端和云函数版本一致）负担，比表单方案重得多。

## 表单最适合公开读者，选区批注最适合 reviewer

**表单类方案的回复默认只有所有者可见**，和公开评论相比，更适合“收集意见，交给 AI 分诊”。各家能否把位置信息带进表单，差别很大。腾讯问卷的自定义参数和预填答案**都是付费功能**，参数值限 128 字符，且不允许 `/`、`:`、`.` 等字符（[腾讯问卷自定义参数](https://wj.qq.com/docs/custom_args/)、[预填答案](https://wj.qq.com/docs/autofill/)）。问卷星的预填和 `hideq` 隐藏题目“仅限尊享版”（[问卷星帮助](https://www.wjx.cn/help/help.aspx?helpid=456)）。金数据免费版只能用一个 `x_field_1` 参数；多字段传参必须带 HMAC 签名，**只在 23,999 元/年的企业高级版提供**，而且在前端计算签名等于公开密钥（[金数据 URL 传参](https://help.jinshuju.net/v4/articles/api-url)）。Tally 的隐藏字段对所有用户免费【已核实】（[Tally Hidden fields](https://tally.so/help/hidden-fields)），但它在大陆的可达性没有任何来源；Jotform 的子域名就曾在大陆被间歇性屏蔽（[Jotform 论坛](https://www.jotform.com/answers/1641301-firewall-forms-blocked-in-china)）。**飞书多维表格表单是唯一兼顾境内服务、多字段预填加隐藏和成熟 API 的选项**：链接写成 `prefill_字段名=值&hide_字段名=1`（[Lark 帮助](https://www.larksuite.com/hc/en-US/articles/167527675676-prefill-default-values-for-base-forms)、[大象笔记自测](https://www.sunzhongwei.com/add-parameters-feishu-form-link-achieve-automatic-field-filling)）；表单可以设置为“互联网上获得链接的人”可填（[飞书帮助](https://www.feishu.cn/hc/zh-CN/articles/356120632302)）；开放平台的 search records 接口单次最多返回 500 行，用自建应用的 `tenant_access_token` 调用（[飞书开放平台](https://open.feishu.cn/document/docs/bitable-v1/app-table-record/search?lang=zh-CN)）。不过这些信息都来自**搜索摘要和第三方自测，免费个人版能否同时用这三项能力还没有确认**。另外，字段名改了，旧的预填链接就会失效，所以表单字段名必须冻结。

选区批注方面，**Hypothesis 是现成方案里最贴近需求的**。本次实测确认，`api.hypothes.is/api/search` 读公开数据**不需要 token**，返回的 `target.selector` 同时包含 `TextQuoteSelector`（含 `exact`、`prefix`、`suffix`）、`TextPositionSelector` 和 `RangeSelector`，`/api/search` 支持按 `uri` 和 `group` 过滤，单页最多 200 条（[h API spec](https://raw.githubusercontent.com/hypothesis/h/main/docs/_extra/api-reference/hypothesis-v1.yaml)）。私有群组只有受邀成员能看到批注（[How to Create a Private Group](https://web.hypothes.is/help/how-to-create-a-private-group/)）。嵌入只需一个 `<script>`，可以在 `?review=1` 时才插入（[client config](https://github.com/hypothesis/client/blob/main/docs/publishers/config.rst)）。CI 里用一个群组成员的机器人 token 就能拉取。它的代价是**每位 reviewer 都要注册账号、点邀请链接入组，还要记得把侧边栏的 scope 从 Public 切到群组**；中文界面、国内邮箱能否收到验证邮件、大陆访问都没有来源【待实测】。另外，课件的 scene 如果是 `display:none` 切换的，隐藏区域里的文字能否锚定和高亮也要实测。

自建方案的成本比想象的低。课件本来就有 scene 结构，`data-scene-id` 是比 XPath 更稳的天然锚点。`?review=1` 时才加载一个 review.js：取得选区后，记录 `exact` 加前后各约 32 字的上下文、scene id、页面版本，弹出输入框，结果存进 localStorage。导出有两个出口，一是“下载 JSON”，二是“生成预填 Issue Form 链接”。中文没有分词问题，重新定位时直接在 scene 内 `indexOf(exact)`，有多处命中再用前后文消歧，反而比英文简单。笔记估计原生 JS 写 150–300 行；`@recogito/text-annotator` 还提供现成的高亮、`getAnnotations()` 和 `setAnnotatingEnabled(false)`（[text-annotator-js](https://github.com/recogito/text-annotator-js)）。这个行数只是估算，没有实际写过。它的弱点很清楚：**没有后端，提交要 reviewer 手动完成，也没有身份管理**。对于几位受邀 reviewer，这两点都不是问题。Agentation 的思路最接近（选中文字后输出给 coding agent），但它依赖 React，而且许可是 **PolyForm Shield，不是 MIT**（[agentation README](https://github.com/benjitaylor/agentation)），不适合直接采用。截图发到飞书或微信，对 reviewer 门槛最低，但图片和聊天记录无法程序化定位，只能作为兜底。

## 推荐组合：reviewer 在本地批注，公开读者走表单，两条渠道汇入同一个分诊管线

**邀请的少量 reviewer：以自建 review.js 为主，Hypothesis 私有群组作为备选。** 优先自建，是因为它是唯一同时满足零账号、零外部依赖、中文界面、按 scene id 锚定、零运维的方案；人数少的时候，“手动提交”的成本几乎为零。有 GitHub 账号的 reviewer 点“生成 Issue”，提交后直接进入自动化流程；没有账号的，把导出的 JSON 发给讲师，由讲师放进私有仓库 `ai-coding-resources/` 的收件目录。如果 reviewer 本来就用 Hypothesis，或者需要彼此看到批注、在批注下讨论，而且实测确认大陆可达，就改用 Hypothesis 私有群组，以 W3C 选择器作为统一的数据格式，自建 review.js 也沿用同一结构，方便以后迁移。

**持续的公开读者：以飞书多维表格表单为主，Issue Form 预填链接为辅。** 阅读模式下每个 scene 旁放一个“反馈”按钮，点击后用 `window.open(..., 'noopener')` 在新标签页打开飞书表单，预填并隐藏课次、scene 和页面地址，读者只需写意见，必要时粘贴原文。旁边放一个次要入口“用 GitHub 提交”，生成预填的 Issue Form 链接。GitHub Actions 每天定时运行一次：用存放在 Actions secrets 里的飞书 App ID 和 Secret 拉取新记录，用内置的 `GITHUB_TOKEN` 读取新 Issue，合并后交给 AI 分诊。明确可改的问题（错别字、链接失效、与 `editorial-checklist.md` 冲突）直接开 PR；需要讨论的开 issue，并标给讲师；处理完的记录在多维表格里回写状态。这套设计有两个前提。第一，表单里的反馈可能含个人信息，**AI 生成的公开 issue 或 PR 只能写脱敏后的问题描述，原始反馈留在飞书或私有仓库**，这符合本仓库的公开边界规则。第二，URL 参数都在客户端，读者可以篡改，分诊时不能把预填字段当作可信来源。如果实测发现飞书免费版不支持 `hide_` 或开放平台 API，**退一步用金数据免费版**：把 `lesson|scene` 拼进唯一的 `x_field_1`，讲师每周手动导出 CSV 交给 AI。如果想要页面内的评论框，再考虑 Waline 加 `COMMENT_AUDIT`，部署在国内 VPS 上，但要接受相应的运维。

演示模式的隔离对所有方案都一样，而且都容易做到：反馈按钮在演示模式下用 CSS 隐藏，review.js 和 Hypothesis 只在 `?review=1` 时动态插入，表单只在新标签页打开。这样录屏时页面上不加载任何第三方脚本，也不会弹出网络失败的提示。giscus 不在推荐组合里，主要不是技术原因：评论区会把答疑公开化，与“不把讨论细节升级为对外承诺”有张力；它还要求账号，又不能预填段落位置。课程上线后如果确实需要学员之间公开讨论，再把它作为第三条渠道加进来。

## 结论

这次调研最大的修正是：问题不在于“giscus 太重，换一个更轻的评论系统”，而在于**评论系统本身就不是反馈收集的合适形态**。评论区的设计目标是公开、实时、对话；本场景需要的是私有、可定位、可批处理，正好相反。所以更简便的路径不是挑一个更好的评论挂件，而是让位置信息由页面生成：URL 预填或选区捕获，再由 CI 汇总到同一个 AI 分诊管线。这样一来，具体用哪种收集前端反而可以替换。

第二个变化是，“零运维”的边界在 2026 年明显后移。LeanCloud 停服，CloudBase 免费版和 Railway、Hugging Face 的免费层都在收紧，依赖免费 BaaS 的评论方案随时可能需要迁移；境内 SaaS 表单和纯前端代码，反而成了最不容易失效的组合。真正的不确定性集中在大陆网络这一项上，而这一项任何文档都给不出答案。所以第一步不是选型，而是请两三位身处大陆不同网络的 reviewer，把上表前四项各走一遍。
