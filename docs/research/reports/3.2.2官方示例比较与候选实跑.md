## 选择前先区分两件事

“只有 SKILL.md”是打包结构，不代表运行不依赖工具、外部服务或平台特有机制。
“官方用来介绍某功能的例子”也不等于“最适合本课第一次精读的例子”。
本部分的案例应满足：正文可独立理解，任务前提少，采用情况能直接核对，并且学生能区分用户需求、正文要求与模型自己的选择。
不要求一份文件必须同时出现规范、默认做法、条件、例子、检查等所有内容。

## 单份正文主要有哪些组成

根据上表，可以让学生读懂几类做事依据，但不将它们固定为必填目录：

| 内容 | 具体要读懂什么 | 单文件示例里的表现 |
| --- | --- | --- |
| 任务与适用范围 | 这份指导负责什么，当前任务是否属于它。 | API 约定负责接口编写；演示应用指导负责建立一个新应用。 |
| 目标与约束 | 要交出什么，哪些条件必须满足。 | 文件位置、技术选型、禁止额外 UI 库等。 |
| 方法、步骤与条件 | 先后怎样做，什么情况下采用不同处理。 | 创建项目、安装、配置、实现；调试时信息不足再读取完整日志。 |
| 输出或完成标准 | 怎样判断任务交付，而不是只看模型说完成。 | 文件存在、开发服务可启动、返回包含指定摘要或风险。 |
| 必要示例 | 示例帮助理解什么，哪些值不能直接当作本次答案。 | 目录示例、命令示例或格式示例。 |

第二张 PPT 可以把“规范、默认、条件、例子”改成上述内容的简短概览，口播说明每份文件按任务选择组织方式。
之后精读真实文件时按其实际顺序走，不按上表重新排列原文。
篇幅讲解仍是内容取舍，不以凑齐栏目或接近某个行数为目标。

## 文案实验：能核实部分规则，但不足以支撑原讲法

真实调用的返回为：

```text
1. 保存失败提示

Could not save your settings. Check your connection and try again.

2. 项目列表为空提示

正文：
No projects yet. Create your first project to get started.

按钮：
Create Project
```

这次确认读取了候选正文，错误提示含问题与下一步动作，按钮使用具体动作名称。
但空状态仍是普通、直接的表达，两个结果没有清楚呈现原先希望讲的语气差异。
部分结果也属于模型通常就能写出的文案，因此不能仅凭它们断言这些措辞由该 Skill 导致。

准备的无 Skill 对照主动越出工作目录，搜索并读到了同一试跑根目录中的源文件，已污染。
该对照不计入有效基线，不报告有无 Skill 的收益差别，也不挑选它看起来有利的结果。

**选材判断**：这次运行可以解释几条规则的采用，但不足以证明此前的“错误提示和空状态切换语气”教学安排成立。
因此不继续把 brand-guidelines 当作已经确定的最佳案例。

## OpenAI 示例实跑：可以支持哪些具体讲解

调用请求只有任务和 Skill 名称，没有在请求中重写目录、组件数或技术约束：

原版示例正文完整进入了本次上下文，随后第 5 行 JSONL 事件再次完整读取该文件。
Skill 副本只有 SKILL.md，原文未改；放在课程 CLI 使用的 `.agents/skills/setup-demo-app/` 下，未沿用旧文章中的 `.codex/skills/` 路径。

| 正文提供的依据 | 本次实际证据 | 可以讲什么 |
| --- | --- | --- |
| 指定目录和组件 | 生成 Header.tsx、Card.tsx，App 使用一个 Header 与两个 Card。 | 请求未逐项规定的结构，可以由 Skill 提供。 |
| 技术和样式约束 | 组件为 TypeScript 函数，配置 Tailwind Vite 插件和 CSS 导入，没有 CSS Modules，也未新增 UI 组件库。 | “怎样实现”可以受到正文具体要求的约束。 |

## 本轮推荐与讲法

**建议把 OpenAI 的 setup-demo-app 作为本轮主候选，brand-guidelines 暂退为备选。**
理由是它同时满足官方教学示例、单份正文、开发者熟悉的任务和可检查的具体要求；本轮也取得了可讲的实际证据。
若讲师更希望完全不生成项目，Claude Code 的 api-conventions 可以作更短的阅读例，但其三条概括不宜扩写后仍称官方原件，也不足以单独解释所有正文写法。

本案例生成一个独立的最小展示应用，不接入个人主页，不新增学员主线交付物。
安装和环境处理不承担教学主线，现场等待可切换明确标注的实录；不能把本次绕路写成每次必经步骤。

| 展示顺序 | 本次明确讲什么 |
| --- | --- |
| PPT：文件结构 | 回顾 name、description，指出正文在文件中的位置。 |
| PPT：正文作用概览 | 说明正文可提供工作约定、流程、约束和交付标准，示例和条件按任务需要出现。 |
| 真实 SKILL.md | 按官方文件顺序读适用场景、交付要求、约束、步骤、完成标准，不逐条讲 React 技术。 |
| Codex 与实跑材料 | 先展示原始请求，再用必要过程和文件说明 Header、Card、两个实例及样式方案怎样落实。<br>调用这一步的目的，是把一条正文要求对应到一次实际动作和产物，而不是再教一次如何选中 Skill。 |
| 浏览器与代码对照 | 看到实际标题和两个卡片，再指出“两个卡片”有正文依据，“课程简介”等具体文案并非文件固定答案。 |
| 回 PPT 总结 | 回收四件事：正文写了什么，怎样参与工作，哪些明确哪些留给判断，哪些内容值得占用正文篇幅。<br>不宣布所有 Skill 都应使用本例标题或顺序。 |

关于 500 行，仍按建议而非硬上限讲，长资料与脚本的展开留给下一部分。
本轮结论仅为可用选材建议，尚未讲师试讲或录制。

## 真实正文与 PPT 补充表达方式怎样配合（2026-11-10）

讲师提出：用 setup-demo-app 完成原始正文阅读与调用，再用 PPT 中的短例补充它未充分呈现的常见表达方式。
本轮判断这个方向合理，不调整 3.2 的五部分结构，也不把简单正文扩成完整 Skill 编写训练。
以下为调研后的讲法建议，未制作 PPT，未写回 discussion.md。

### 先限制从主案例归纳出的结论

采用讲师转来的建议：区分“适合第一次读正文”和“足以代表全部真实写法”。
setup-demo-app 是 OpenAI 为评估教程提供的简化示例；快速建立临时展示或复现应用是成立的用途，但本轮没有团队长期使用证据。
其 What to build 表示要构建什么，内部包含交付物、目录规格、技术选择和禁止事项，不是开始运行 build 的时机。
讲解的对象是这些具体指导，不只是四个章节标题。
本轮已有课程环境实跑，能够说明此次采用与核验，不能推成所有运行有效。

### 有规范依据的要求与常见实践分开讲

| 层次 | 已核实的依据 | 教学上怎样表述 |
| --- | --- | --- |
| 格式规范 | [Agent Skills 的 Body content](https://agentskills.io/specification#body-content)明确正文没有固定格式要求，推荐步骤、输入输出示例和常见边界情况。 | 文件格式有约定，正文没有统一必填栏目和顺序。 |
| 反复出现的编写实践 | [OpenAI Define the workflow boundary](https://developers.openai.com/plugins/build/skills#define-the-workflow-boundary)强调输入、步骤、输出、不应推断的事实，以及追问或停止条件。<br>[Anthropic Common patterns](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices#common-patterns)介绍模板、例子和条件工作流。 | 不同任务可能需要不同指导，不能仅以是否有标题或编号判断完整性。 |
| 内容选择与控制程度 | [Agent Skills 的 Calibrating control](https://agentskills.io/skill-creation/best-practices#calibrating-control)讨论具体程度与风险、默认方案及可复用方法。 | 约束与判断空间可以共存，一份 Skill 不必每一句都同样严格。 |

上述来源支持的是若干共同实践，不是行业已经统一了正文模板。
单份 Skill 是否需要某项内容，由任务和实际缺口决定。

### 可用于 PPT 的阅读线索

以下例子均是课程自拟的文字示意，不冒充官方原句，不写入或改变主案例 Skill。
它们只用于读懂一种表达的作用，未经过独立调用实验，不据此报告行为效果。

| 指导方式 | 它解决什么问题 | PPT 可用的简短示意 | 与主案例的关系 |
| --- | --- | --- | --- |
| 有顺序的步骤 | 多项动作之间有什么先后关系。 | 先建立项目，再安装与配置，最后实现界面。 | 主案例已能解释，回顾即可，不必再单独重讲一遍。 |
| 规格与明确约束 | 什么必须满足，哪些做法不在本任务范围内。 | 使用函数组件，不增加额外 UI 组件库。 | 已有实际文件和依赖证据，注意要求并不意味着引擎强制保证执行。 |
| 前提、条件与追问 | 输入或环境不同，是否还应沿原路线继续。 | 若目录已有项目，先确认是扩展现有项目还是另建演示，不直接覆盖。 | 用“当前目录已经有项目怎么办”引出，但这是补充示意，原版没有写出该分支。 |
| 默认做法与判断空间 | 未指定时怎样选，什么时候可以替代。 | 未指定包管理器时采用 npm；项目已有锁文件时沿用对应工具。 | 说明默认不等于永远必须，本例固定 npm 的选择也不代表所有 Skill 都应固定。 |
| 输出模板与输入输出例子 | 交付结构是什么，例子帮助理解哪种风格或细节。 | 模板约定“问题、位置、建议”；另用一组具体输入输出解释怎样填写。 | 把结构约定与具体示范区分开，主案例没有输入输出对照时不用硬补进原文件。 |
| 检查与反馈循环 | 怎样判断完成，检查未通过后怎样处理。 | 检查失败时读取报错、修正并复验，再报告结果。 | 主例有完成标准，完整失败恢复未展开，此处只说明这种正文指导也可能存在。 |

这些类型可以交叉，一条条件句也可能同时包含约束和动作。
不把列表、表格、代码块等 Markdown 排版方式，与规范、条件、示例等指导作用混成同一套分类。

### 对“一页一种方式”的判断

可以把一项讲解问题放在一页，页内呈现情境、短例和它指导 AI 的动作或判断。
不能只放“步骤型”标签及一段编号文字，也不因为分了六类就固定做六页。
已经在真实文件和调用中讲透的步骤、约束与完成标准，PPT 只用原例片段回收认识。
需要补充的前提与条件、默认和判断空间、模板与示例，再按理解关系安排页面；同页对照有助于分清时不强行拆开。

例如“如果当前目录已经有项目呢”可以成为一页：先保留主例的建项步骤，再展开课程自拟条件说明，指出这条补充在什么情况下改变下一步。
本页让学生认出条件的作用，不要求他们现场改 Skill 或另跑一轮已有项目实验。
若未来要演示这条新增指导实际改变行为，必须另做调用并保留真实记录。

### 与四件事保持对应

- 正文写了什么：主文件精读，加少量指导方式短例。
- 怎样影响本次工作：用已有实跑对应正文、动作和产物，不以 PPT 示意替代实证。
- 哪些明确、哪些需要判断：结合真实规格与模型补充，再用条件、默认短例扩展认识。
- 为什么不需要写得很长：说明只保留任务需要的依据，不要求把所有类型塞进正文，篇幅数字仍作为建议。

建议的连续讲法为“PPT 文件结构与简短概览 → 原版文件精读 → 调用及结果对应 → 回 PPT 归纳本例 → 补充未出现的指导方式 → 正文组织与长度小结”。
它保留一个清楚的真实对象作为主线，再帮助学生迁移到其他简单 Skill；复杂资源、Plugin 组织和从零制作仍留在后续部分。

## 与 3.1 游戏经历怎样衔接：Plugin 候选复核（2026-11-10）

### 推荐的连续讲法

1. 沿用讲师确定的 PPT 结构图和简短内容概览。
2. 打开 setup-demo-app，按其实际顺序读懂适用场景、交付要求、步骤和完成标准，区分其中的规格、约束与方法。
3. 用已有真实调用核对正文与动作、文件、页面之间的对应，再回 PPT 归纳阅读方法。
4. 回到第一节的一处验收经历，打开 game-playtest 的相关原句，解释同类方法怎样以通用指导保存；指出翻牌规则仍须由任务提供。
5. 从“如果当前目录已有项目怎么办”等问题进入常见条件、默认、示例等 PPT 补充，最后讲正文组织与篇幅取舍。
