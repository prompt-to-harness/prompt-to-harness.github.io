## 对本课讲法的影响

1. **先说清可观察的目标，再展示生成。** 一句自然提示词可以保留。讲师在看结果前选出少量重要要求，比如复用紫色主题、结算文字可读、玩法可以按项目独立设计。随后看实际初稿，用这些要求解释保留、改写和删除。文件头格式和触发优化沿用 3.2，只有实际造成选用问题时再展开。
2. **用实际输出完成审阅。** 从空目录实跑里追主题 CSS 的来源与画面。文件存在证明不了调用时能找到它，复制 CSS 也只回答主题复用，画面还需人判断。候选局部任务可用窄屏结算面板，同时观察紫色面板和游戏结果是否清楚。若要验证放宽统计格的要求，改用带明确状态需求的 HUD 小任务。按要验证的改动选任务。
3. **按研究问题选基线。** 验证修改用原稿与修订稿。验证代码示例的作用用相同正文、相同任务，只改变示例及读取入口。验证是否有 Skill 的贡献用有无 Skill 对照。已有空目录与翻牌改造的比较回答项目起点问题，不能直接证明代码示例、修改或 Skill 带来了提升。
4. **讲解深度以能作出判断为准。** 建议 3.3.1 完成初稿审阅和一次针对性修改，3.3.2 用选定版本完成开发与验收。已有实跑用原稿及补齐的资源，修订版需预跑。开发后若出现可回指正文并值得跨任务修正的问题，再用同一小任务讲独立迭代。评估框架、脚本评分、触发覆盖率和多模型测试留作参考。

对 3.2 的依赖集中在工作边界、规则与默认、资源入口、调用和实际读取。讲师如需上课核对官方说法，建议打开 setup-demo-app 同篇文章的成功标准或手动调用段落。其余原文供备课查阅，当前未选定外部证据页。
