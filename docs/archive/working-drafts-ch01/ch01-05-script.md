## 01 · 准备执行

**画面标题**：把确认的请求变成首页

**画面要点**：今天做到一个可检查、可继续修改的 v0

### 口播

上一节已经决定首页放什么，这一节让 Codex 把它做出来。打开确认过的请求，看看课程名、项目介绍和入口行为有没有变化。有新想法先记下来，这轮仍按这一版做。

先核对练习目录、起点提交和工作树状态，再确认已有项目能按说明启动。这里只用你自己的独立练习副本。如果还没有拿到课程 Starter Repo，先看操作方案和判断题，等起点发布后补做，不在课程讲义目录里生成网站。

本章主操作仍在 App 里完成，第 3 节的 CLI 记录用于对照目录和权限。具体界面以你的实测环境为准。

## 02 · 核对小计划

**画面标题**：计划有没有偷偷变大

**画面要点**：先看目标、修改文件和检查顺序

### 口播

把这一条执行请求和上一节确认的完整 Prompt 放在同一轮里。不要只发送按刚才的要求做，让一个新会话猜刚才是什么。

它回复以后，对照允许文件清单看一遍。比如它准备为两个项目加后端，这就与本轮范围不符。请它修正计划，等目标和检查顺序对齐后再确认。

计划可以很短，能说明这次做什么、改哪里、怎样检查就够了。都符合这次的要求，就确认，让它开始修改。

### 请求

```text
请按我们已确认的四段式 Prompt 和内容卡完成首页 v0。
先对照当前目录、起点和允许文件清单，用几句话复述目标及运行、构建、diff 的检查顺序；有未解决问题就先提出。等我确认后再修改。
不增加新依赖、不发布、不提交或打 tag。需要扩大范围时先停下。
```

## 03 · 观察修改

**画面标题**：留意它正在改哪些文件

**画面要点**：首页与必要样式，做到本轮约定的范围

### 口播

确认以后让 Codex 执行。可以等待它完成一组连贯的首页修改，同时留意文件列表和需要你批准的动作。不需要每写一行都打断它。

如果它说缺一个图标包，先看能否沿用已有资源。确实要增加依赖，也应重新说明理由、修改范围和检查方法，再由你决定，而不是用顺便安装混过去。

颜色和间距还有改进空间很正常，先达到这轮约定的结果。新的视觉想法记到下一轮反馈里，避免这一节一直停在生成阶段。

## 04 · 运行与观察

**画面标题**：页面打开以后，逐项试一下

**画面要点**：内容、入口、窄屏和控制台各留一份证据

### 口播

在项目根目录执行准备页已经核验的开发命令，打开终端实际打印的本地地址。不要猜端口，也不要看到服务进程在运行就认为页面正确。

对照内容卡检查课程名、介绍和两个项目。用鼠标点击查看项目，再用 Tab 找到入口、按 Enter 激活；它应当到本页项目区。已有导航也点一下，确认这次没有破坏。

接着看桌面和手机尺寸，检查文字是否被遮挡、有没有横向溢出。打开浏览器开发者工具的 Console，刷新后再操作一次。出现错误就记下触发步骤，不能只截一张好看的首页。

## 05 · 构建检查

**画面标题**：再看 production build

**画面要点**：启动成功与构建成功，回答不同的问题

### 口播

页面观察之后再跑 production build。我们的验收清单写的是 npm run build，执行前先核对项目有这个脚本，Node、包管理器和锁文件也与环境卡一致。实际 Starter Repo 没选定前，不能据此宣称构建路径已经验证。

如果选定项目使用其他包管理器，要先记录并审核它的实际构建命令，同步这份验收清单。不要为让命令显示成功，改掉脚本或跳过检查。

保留完整输出和退出状态。构建失败时，从第一处相关错误定位；修复后重跑受影响的检查。构建通过也不会替我们验证查看项目的按钮行为，刚才的浏览器检查仍然需要。

## 06 · 看完整差异

**画面标题**：页面之外，还改了什么

**画面要点**：对照起点检查已跟踪和新增文件

### 口播

回到 Git。用开始时记录的完整提交编号比较这轮所有改动，而不只看 Codex 最后一条回复。diff 告诉我们哪些内容变了，文件统计帮助找范围，git status 还会列出未跟踪的新文件。

逐个打开新增文件，确认没有把课前准备页或环境检查页做进正式网站。再看看 package.json、锁文件和配置有没有意外变化，内容和素材有没有夹带密钥、私人资料或未授权图片。

不理解某段修改，就先请它解释用途并核对行为；解释仍对不上，先缩小或退回这部分。分不清改动来源时保留整份目录，按配套恢复说明处理，别一键清空。

## 07 · 保存检查点

**画面标题**：通过后，再留下可恢复的版本

**画面要点**：检查点对应已检查过的代码

### 口播

页面、构建、控制台和 diff 都通过后，才保存这一版。先把确认过的文件逐个暂存，再看暂存差异，然后提交。不要用一个全选命令把没检查的文件也带进去。

记录提交编号，并给它一个尚未使用的本地 tag，例如 ch01-home-v0。若这个名字已经存在，先查看它指向哪里，换一个名字，不覆盖旧检查点。这一步不推送，也不发布。

记录要对应这个提交。如果检查后又改了代码，就补相关检查再保存。v0 仍然是可以继续迭代的原型，检查点只是让我们能找回这一版。

## 08 · 暂停判断

**画面标题**：两项通过，能算全部通过吗

**画面要点**：页面能启动，build 成功，但多了依赖和图片

### 口播

假设页面已经启动，build 也成功，但 diff 里多出课前准备页、一个新依赖和两张来源不明的图片。现在能把 v0 标成通过吗？先暂停，指出还缺哪一类证据。

缺的是范围和来源检查。准备页不该进入正式应用，新依赖没有在本轮确认，图片也没有使用依据。保留现场，逐项处理以后，再看改动是否影响页面和构建。

能截图和能构建都很有用，但只能支持它们各自覆盖的结论。我们保存的是完成本轮验收的版本。

## 09 · 交接下一章

**画面标题**：把页面和证据一起留下

**画面要点**：第 6 节回看权限；第 2 章在这个版本上迭代

### 口播

把确认请求、起点、页面检查、构建输出和最终提交放进同一份记录。还有哪些没验证、下一轮想改什么，也直接写下来。

工具暂时不可用，可以先用本节题目判断证据够不够；实际首页和检查点还要之后补做。看到别人的截图不能记作自己完成了生成。

下一节用这轮任务回看权限选择。进入第二章时，我们会从这个 v0 的真实页面开始观察和反馈，不必重新生成一个项目。
