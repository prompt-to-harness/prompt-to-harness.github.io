## 01 · 从一次小改动开始

**画面标题**：让 Codex 改一段项目介绍

**建议时长**：约 1 分钟

**画面与切点**：HTML 开场，说明小练习的用途；不逐项讲框架。小窗始终在右上角。

### 口播

这一章，我们用 Codex 做一个网站。这一节先打开项目，让它改一段介绍，再看看文件里发生了什么变化。

这段文字直接手改也很快。我们用它练一下 Codex 的操作，改动少，前后对照起来也容易。第一次演示，我会把阅读和修改分开发，方便大家看清每一步。熟悉以后，这样的小改动可以用一条请求完成。

工具安装和项目下载放在课前准备页。准备好以后，先看这次要改的文件。

### 实操与证据

开场可短暂展示已准备好的课程主页效果，注明它是目标示例；不要将其标成这一节刚生成的成果。

保留：学员知道本节要发出一个修改要求，并找到、检查实际文件变化；教学拆分不等于每次小改动都要多轮请求。

## 02 · 找到要改的段落

**画面标题**：先改一段项目介绍

**建议时长**：约 1 分钟

**画面与切点**：先切 App 打开练习项目、指出原段落，再用 HTML 展示待替换文字。

### 口播

用 Codex App 打开刚下载的练习项目，找到 README.md。README 是项目的说明文档，这次要改的是里面的「项目介绍」。

我们要把这里的文字换成课程网站的介绍。屏幕上是准备换上的内容，其他段落先保留。等会儿就用这段文字和实际改动做对照。

### 实操与证据

展示 README.md 的「项目介绍」实际原文和相邻内容；录前核实段落，不用占位原文冒充真实文件。

保留：画面显示实际项目目录和待修改段落；这里仍无文件修改。

## 03 · 检查练习目录

**画面标题**：先确认打开的是练习项目

**建议时长**：约 2 分钟（含实际检查）

**画面与切点**：在终端逐条执行目录、状态、起点三条命令，对着真实输出解释。

### 口播

先在系统终端进入这份练习项目的根目录。第一条命令会显示项目路径，和 App 里打开的目录对一下。

再运行 git status --short。命令成功、没有输出，我们就继续。如果列出了文件，先保留这个目录，按准备页另建一份练习副本。

最后记下 git rev-parse HEAD 输出的提交编号，存到项目外的笔记里。之后检查改动时，可以用它找到这次练习的起点。这份副本只用来做本次练习，先不提交，也不要同时在别的窗口修改。

### 命令与检查

- `git rev-parse --show-toplevel`：项目目录。输出应与 App 打开的练习目录一致

- `git status --short`：已有改动。命令成功且没有输出，就可以继续

- `git rev-parse HEAD`：起点提交。把完整编号存到项目目录之外的笔记里

### 实操与证据

课前按准备页核对分支。课内运行三条检查命令并保存起点；Node、包管理器和启动检查放在准备页，按环境卡另行试跑。

保留：真实路径、分支、初始 git status 和起点提交编号；工具版本另存环境卡。

## 04 · 让 Codex 找到段落

**画面标题**：先让 Codex 找到这一段

**建议时长**：约 2 分钟（含 App 真实回复）

**画面与切点**：展示简短请求，切 App 输入；对照真实文件核对原文和一句话修改打算。

### 口播

把这条请求发给 Codex，让它先找到刚才那段介绍。它回复以后，我们回到 README 对一下，看看找得对不对。

再看它准备改哪里。这次的计划用一句话就能说清楚：替换介绍段落，保留其他内容。如果它打算连页面一起调整，就先提醒它只改这段介绍。

### 实际输入

```text
我想更新 README.md 中的「项目介绍」。
请读一下这个文件，找出这一段现在的内容，用一句话说明准备改哪里。
先不要修改，等我提供新介绍。找不到这一段就告诉我。
```

### 实操与证据

按真实回复讲解，不预写成功结论。找不到目标段落时，先核对目录和文件。若出现权限请求，解释它要做什么，再按当前任务需要决定。

保留：真实读取对象、找到的原文和简短计划；无需为替换一句介绍调查运行方式。

## 05 · 修改项目介绍

**画面标题**：把新介绍发给它

**建议时长**：约 1–2 分钟（含实际修改）

**画面与切点**：切 App 执行；只加速或剪去等待，保留关键操作与结果。

### 口播

确认它找对了位置，修改打算也合适，就把这段新介绍发给它。

发送以后，看一下它正在处理哪个文件。如果弹出权限请求，先看清操作和目标目录，再决定是否允许。等它回复完成，我们就打开 diff。

### 实际输入

```text
请将 README.md 的「项目介绍」段落替换为：

这是「从 Prompt 到 Harness」的课程网站，包含课程讲义、讲师介绍和项目示例。

保留其他段落，不修改其他文件，本轮不提交 commit。
完成后告诉我改了哪里。
```

### 实操与证据

执行单段修改，记录真实等待与操作。若前一步未通过核对，不进入此步。

保留：真实文件改动应符合目标；学生自定义文案允许不同，不要求逐字复制讲师介绍。

## 06 · 检查修改结果

**画面标题**：用 diff 核对改动

**建议时长**：约 2 分钟（含 diff 走读）

**画面与切点**：HTML 中明确标注示意；切换到 App 的实际修改展示或真实 Git diff。

### 口播

diff 就是修改前后的差异。先看这张示例：减号这一行是原来的占位文字，加号这一行是新的课程介绍。

回到实际项目，运行第一条命令，看看介绍有没有换对、位置对不对，README 里还有没有别的变化。

接着看文件统计，再用 git status --short 看一下文件状态。我们预期只有 README 被修改；如果出现了其他文件，就打开对应的差异看看。新增文件也要检查。

文字和位置都正确，也没有额外改动，这次练习就做完了。这里只改说明文字，不需要启动网站或运行构建。

### 实操与证据

检查前再次运行 git rev-parse HEAD，与起点记录核对；一致时展示 README diff、文件统计和 git status。若不一致，按准备页用起点编号检查。指着真实差异作判断，保留起点与结果记录。

保留：文字和位置正确，没有额外改动；无法确认来源时保留现场，按准备页处理。

## 07 · 想一想

**画面标题**：多改了三个文件怎么办

**建议时长**：约 1 分钟（学员暂停时间另计）

**画面与切点**：先只显示题目；口播提示暂停，短停顿后再点击解析。

### 口播

现在换一种情况：介绍已经改对了，但文件列表里还多了三个源码文件，Codex 说只是顺手格式化了一下。这时，你会把任务标成完成吗？可以暂停想一下。

我会先打开这三个文件的差异。即使确实只改了格式，也多出了这次没有要求的改动。确认它们来自本次练习后，按准备页的恢复步骤撤回，再重新检查。分不清来源时，先保留现场。

所以检查时，除了看介绍有没有换对，还要看文件列表。只读 Codex 的完成说明，就可能漏掉这三个文件。

### 实操与证据

这是预设自检题，不向真实项目植入额外格式化改动。不要伪装成现场意外发现。

保留：答案指出格式化也属于额外改动，给出查看差异、确认来源和恢复后重新检查的顺序。

## 08 · 自己试一次

**画面标题**：换成自己的介绍再试一次

**建议时长**：约 1 分钟

**画面与切点**：回到 HTML，用文字、位置和文件列表布置练习；记录模板给入口，不逐项念元数据。

### 口播

现在换一段自己的介绍，在新的练习副本里做一次。做完打开 diff，检查文字和位置，再看看有没有其他文件被改动。

把这次请求、Codex 的回复和检查结果存到项目目录之外，和起点记录放在一起。准备页有记录模板。

如果暂时用不了工具，可以先看本节的 diff 示例，等环境准备好再补实际操作。下一节我们回看这次对话：Codex 怎样找到文件，又怎样完成修改，从中认识 Agent、Context 和 Tool。

### 实操与证据

展示本节记录保存位置；结束前留短停顿供剪辑。

保留：学员能按文字、位置和其他改动自查；请求、回复和检查结果可用于下一节。
