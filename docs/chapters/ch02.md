## 本章主线

**一句话**：把第 1 章做出的个人主页补完整并发布上线；一路打开 Codex 实际发出的请求，看清 context 长什么样、怎么变。

**主知识点**：Context。第 1 章讲 context 里该放什么，本章打开请求看它实际长什么样、怎么变。每节一个项目动作，配一个 context 视角。项目 `AGENTS.md` 在 2.2 作为 context 的一个来源露出，不算主知识点。

**学员获得**：

- 一个公开 URL，以及一份评审过、可回退的提交。
- 能从一份请求记录里指出不是自己写的内容，并说出缺了会怎样。
- 能根据会话的状态选择继续、`/clear`、压缩或新建会话，并说出理由。
- 习惯在接受改动前问“它当时看到了什么”。

**贯穿线索**：同一套配置下的 claude-tap 请求记录，2.1 第一次打开，后面每节都回到它。

## 各节要点

项目动作按顺序推进（看请求 → 补经历 → 审改动 → 发布），每节换一个 context 视角（2026-10-21 确认，C2-45）。

| 节 | 项目动作 | context 视角 | 验收要点 |
| --- | --- | --- | --- |
| 2.1 只说了一句话，模型收到了什么（25 分钟） | 重启开发服务器，问两句 | **组成**：一次请求里有什么；工具调用和返回怎样进入 context；放什么由谁决定（点名文件和让它自己找，代价差几倍） | 指出至少四类非用户内容，说出缺了会怎样；指出一次工具调用和返回 |
| 2.2 补上项目经历，看对话怎么变长（25 分钟） | 写两三行 `AGENTS.md`，`/clear` 后让 Codex 放进人提供的项目经历 | **增长与管理**：历史每次重发，代价是 token 和注意力；`/status` 看还剩多少；`/clear` 清对话不清文件，`AGENTS.md` 重新进入；手动和自动压缩只留摘要 | 经历由人提供、已呈现；build 通过；能说出会话选择的理由 |
| 2.3 它看到了什么，才这样改（15 分钟） | 审查 diff，接受、缩小或拒绝，提交一次作为检查点 | **可见范围**：它依据请求里的哪些内容改；它看得全吗（输出会被截断）；它看不见什么（没读的文件、浏览器里的页面） | 能指出 Codex 改动的依据；说出它看不见的一样东西；提交一次检查点 |
| 2.4 发布上线，看 Codex 怎么用 gh（20 分钟） | 推送前看清整段历史，部署 GitHub Pages | **context 和外部**：context 发给了谁；网页搜索的结果进 context；`gh` 调用把动作送出去 | URL 未登录可访问、没有 404 资源、刷新可用；推送前看过完整历史 |
| 2.5 用好 context 的三个做法（10–15 分钟） | 无，另一位讲师分享 | 看懂重发的代价；换会话时自己写交接；换一个工具看同一句话的请求 | 看懂即可 |

## 交付物与退出门禁

- 1 轮必做的内容迭代，形成评审过、可回退的 homepage-v1 提交，提交说明写明本轮目标与改动文件；
- 推送前看过完整历史，以及一个可公开访问的 GitHub Pages 个人主页；
- 学员能用公开 URL、Network 面板和 Actions 日志验证发布结果，不把 Actions 成功当作页面可用；
- 能从讲师请求记录中指出 context 的组成；能用这个会话里已经读过的文件、做过的事解释一次会话选择。
