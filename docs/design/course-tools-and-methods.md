> 状态：2026-09-04 参考资料整理，吸收 0903 讨论。本文记录工具、方法、教学提醒和待验证参考；不规定课程章节、Project 组合或实施路径。

## 这份文档讨论什么

课程的目标不是让学员记住某个 Agent 的命令，而是让他们在可控边界内使用 AI 完成真实开发任务。因此需要同时讨论：

- 学员如何理解 AI coding 的能力边界；
- 学员如何获得和准备工具、代码库与网络环境；
- SDD、Skills、Harness 等方法如何被演示和练习；
- 哪些内容是稳定的工程原则，哪些内容会随工具版本变化；
- 如何照顾没有完整外网访问或官方账号条件的学员。

课程目标和跨文档共识见 [course-design-principles.md](course-design-principles.md)。本文只补充工具和方法层面的参考，不把候选写成课程承诺。

## 教学提醒：避免三类偏差

### Unknown unknown

初学者往往不知道自己还缺少哪些问题。课程不能只回答学员已经提出的问题，也要通过演示失败、反例、检查清单和复盘，主动暴露他们尚未意识到的风险，例如：

- AI 看似完成了任务，但没有验证边界条件；
- Agent 修改了错误的文件或误解了项目约束；
- 生成的结果缺少来源、测试或可复现步骤；
- 工具的网络、账号、权限和模型限制导致结果不稳定。

这意味着每个重要方法都应配一个“哪里会失败、如何发现、如何纠正”的例子，而不是只展示成功路径。

### Curse of Knowledge

课程设计者熟悉 Codex、Claude Code、Git、SDD 和 Harness 后，容易默认学员也理解这些概念。对入门开发人员来说，术语、界面、权限提示和仓库状态本身都可能成为障碍。

因此课程应：

- 先解释任务背景、预期结果和判断依据，再出现工具术语；
- 把“为什么这样做”与“具体怎么操作”同时讲清楚；
- 为每个演示提供可从干净环境开始的运行说明；
- 允许学员跳过不影响学习目标的高级配置；
- 把 Git 命令作为实现细节教学，课程不要求学员先熟记命令。

### Feynman Technique

课程不应只检查学员能否让 Agent 产出代码，还应要求学员用自己的话解释：

- 这个任务要解决什么问题；
- AI 做了哪些决策，哪些决策由人确认；
- 代码库中哪些事实支持当前方案；
- 测试和 Review 证明了什么，不能证明什么；
- 如果重新做一次，工作流会如何调整。

可以把简短的“讲给别人听”或复盘说明作为过程证据的一部分。这比要求学员提交完整聊天记录更能检验理解，也更适合异步课程。

## 工具与环境

### 前期环境 Setup

课程前期应先帮助学员把 Coding Agent 跑起来，再进入较抽象的 Prompt、SDD 或 Harness 概念。Setup 材料至少需要覆盖：

- Codex App 和 Codex CLI 的基本入口、适用场景和切换方式；CLI 是主要的可复现工作流，App 是较低门槛的上手或替代路径；
- 国内模型或服务的可行接入方式，以及模型、账号、费用和隐私限制；
- 一个能运行的 starter repo、依赖安装、基本 Git 状态和最小权限设置；
- 常见安装失败、网络失败和模型不可用时的替代路径。

学员不需要在课前准备好某个特定 Agent、Skill、Plugin 或 MCP。环境材料应让学员尽快完成一次最小的 `Chat → Plan → Execute` 任务，同时把工具边界和人工确认点说清楚。

### 网络访问

课程项目和资料可能依赖 GitHub、包管理器、模型服务或在线文档。需要单独讨论没有完整外网访问的学员如何完成核心路径。

可考虑的支持方向：

- 实践环境需要考虑可下载或可镜像的项目、依赖说明和必要数据；
- 不应把临时访问外部网站作为学习目标的隐含前置条件；
- 在线访问可以增强体验，但课程目标不应依赖某一种网络条件；
- 可以评估 Gitee 镜像或备用资料入口，例如课程团队的 [MiaoDX Gitee 主页](https://gitee.com/miaodx)；
- 对需要实时网络访问的环节，提前说明域名、账号、费用和失败时的替代路径。

仍需讨论：是否为完全没有外网访问的学员提供单独支持，以及支持到什么程度。可选方案包括：

1. **最低支持**：只提供下载包和离线说明，学员自行解决模型访问。
2. **课程级镜像**：提供 Gitee/压缩包/依赖缓存等镜像，模型仍由学员自行准备。
3. **统一远程环境**：通过远程开发机或浏览器环境提供代码、依赖和模型入口，降低本地网络差异，但会增加运营和成本。

### Git

学员需要理解 Git 的基本对象和协作结果：仓库、分支、commit、diff、PR，以及如何回到一个可复现状态。

不要求在课程开始前熟记具体命令。Codex 或其他 Coding Agent 可以协助执行 Git 操作，但学员必须能判断：

- 当前修改是否属于预期范围；
- 哪个 commit 是可运行和可提交的状态；
- diff 是否包含无关改动、敏感信息或危险操作；
- 如何在错误修改后恢复到上一个已知状态。

Git 教学应服务于过程可追溯和安全交付，而不是变成独立的 Git 命令课程。

### Coding Agent 与模型

**Codex CLI** 作为主要工具参考样例，适合终端、仓库上下文、命令执行和可复现流程；**Codex App** 适合桌面工作流、多任务协作和前期低门槛上手。课程不要求所有人从 CLI 开始，但应让学员理解何时需要切换到更可复现的 CLI 流程。

相关入口：

- [Codex Linux App 文档](https://learn.chatgpt.com/docs/linux/linux-app)
- [Codex Linux `.deb` 下载](https://persistent.oaistatic.com/codex-app-prod/linux/deb/latest/chatgpt_amd64.deb)

其他 Coding Agent、IDE 助手和命令行工具也可以支持相同工作。学习成果应针对任务理解、过程证据、验证和风险控制，而不是厂商命令或界面。

可以讨论的替代模型/工具包括：

- Claude Code；
- 国内模型和服务，例如 Kimi、MiniMax；
- 其他具备代码阅读、文件编辑、命令执行和测试协作能力的 Agent。

Claude Code、Codex 官方账号和付费额度对部分国内学员可能较复杂，因此不应作为课程完成的硬性前置条件。社区可以讨论提供额外 token 支持或统一额度的可行性，但这涉及账号、费用、隐私和公平性，不能在没有运营方案前写成承诺。

### Paseo 与远程访问

Paseo 可以作为远程访问或浏览器交互的候选工具，用于：

- 在远程环境中访问课程项目；
- 演示 Agent 与浏览器/外部界面的交互；
- 帮助没有合适本地环境的学员完成部分实践。

当前不把 Paseo 设为所有学员的必需工具。它是否进入正式课程，需要验证稳定性、并发、账号、隐私、成本和录播可复现性。

## SDD 与相关方法参考

### 从最小闭环理解 SDD

正式讲 SDD 前，先让学员用自然语言 Prompt 让 Agent 走通 `Chat → Plan → Execute`，并把计划写入仓库中的 plan 文件。这个版本的目的，是让学员先感受到“先想清楚再改代码”的收益，而不是提前记住一组术语。

随后补充验证和复盘，再讨论需求、spec、design 和 plan 的职责。接着使用 GSD、Spec Kit 等公开社区实践作为案例，比较它们如何把讨论、规格、计划、执行和验证留存下来，再抽取稳定原则。最后再讨论学员如何根据自己的任务组合一套流程，而不是把讲师自制方案或某个仓库目录结构当成唯一标准。

### 需要展示什么

SDD 不应只展示一套文件名或模板。学员需要看到它如何改变工作方式：

`需求澄清 → 规格 → 设计/计划 → 实现 → 验证 → Review → 复盘`

重点展示：

- 需求如何从模糊描述变成可验证的验收标准；
- spec 如何约束 Agent 的实现范围；
- 计划如何拆成可以独立验证的任务；
- 需求变化后哪些文档和任务需要重新规划；
- 测试、Review 和运行结果如何反过来修订方案。

### 参考实现和仓库

以下仓库可作为方法研究和课堂演示素材，暂不代表课程必须采用：

- [open-gsd/gsd-core](https://github.com/open-gsd/gsd-core)：可用于观察以阶段、计划和执行为核心的工作流组织方式；
- [github/spec-kit](https://github.com/github/spec-kit)：可用于观察 GitHub 生态中的 spec-driven development 工具化尝试；
- [mattpocock/skills](https://github.com/mattpocock/skills)：可用于讨论如何把可复用的 Agent 技能、规则或工作步骤外化；
- [MiaoDX/intuitive-flow](https://github.com/MiaoDX/intuitive-flow)：可用于讨论自定义工作流、阶段路由和人机协作边界。

课堂展示这些材料时，建议采用“同一需求的不同方法”或“抽取其中一个稳定原则”的方式，而不是逐个讲仓库功能。需要避免让学员误以为某个开源项目的目录结构就是 SDD 的唯一标准。

### Project 中的使用范围

SDD 可以用于短演示、项目或新任务。参考资料本身不能决定展示范围；这个问题应和课程目标、项目维护成本及学员负担一起讨论。

## Skills 与自定义工作流

### Skills 的教学位置

Skills 可以被讲成一种工程实践：把重复出现的知识、检查步骤、命令和约束外化，让 Agent 在不同任务中稳定复用。

建议从项目中真实出现的重复操作出发，例如：

- 检查项目启动和测试命令；
- 生成或更新代码库地图；
- 按统一格式执行 Review；
- 验证提交是否包含必要证据；
- 在只读权限下查询外部资料。

不要把 Skills 讲成必须安装的一组插件，也不要要求学员照抄某个仓库的全部内容。学员应能够解释一个 Skill 的输入、输出、适用条件、失败处理和人工确认点。

### 自制流程

可以鼓励学员根据自己的任务组合流程；是否采用某套完整框架，需要结合课程目标再决定。

可参考 [MiaoDX/intuitive-flow](https://github.com/MiaoDX/intuitive-flow) 讨论：

- 什么时候先澄清问题，什么时候直接执行；
- 如何把复杂任务拆成有停顿点的阶段；
- 哪些步骤可以委派，哪些步骤需要人确认；
- 如何在失败后重新规划，而不是继续堆叠上下文。

### 与软件工程经验连接

Skills 和 Harness 不是替代软件工程基本功的快捷方式。课程应在项目中穿插 SOLID、接口契约、测试边界、diff/PR、回归、技术债、可维护性和最小权限等 Good Old Experience，并解释对应的行业黑话。重点不是假设模型已经自动正确吸收了这些经验，而是让学员看到清晰的模块边界、验证反馈和约束如何改善 Agent 的工作结果。可参考 [mattpocock/skills](https://github.com/mattpocock/skills) 观察团队经验如何被外化，但不要求学员安装或照抄整套仓库。

## 工具与概念参考

Feishu MCP、SDD project、Game studio、代码地图、LSP/clangd 等可以作为实践或演示候选。Feishu MCP 若进入教学，应优先采用只读、合成数据和沙盒账号；是否进入课程以及如何组织，尚未决定。

RAG、Autoresearch、OpenAI/Anthropic Agent SDK、Kernel ops、DSH 等概念先作为任务驱动的短演示或前沿展望。只有当它们能解释失败、减少重复劳动或帮助判断边界时，才进入核心路径。

后期可以用高难度开源仓库、Kernel Ops 或 AutoResearch 展示 AI 在特定领域中的能力上限和 Harness 的作用。这类内容用于拓展视野或强化练习，不作为入门学员完成核心 Project 的必要条件。

## 官方教程与 Harness 参考

### 官方材料

官方教程和文章适合用来说明工具作者对可靠使用方式的建议，也可以直接作为课堂材料整理成图文或讲稿；但它们不应被直接等同于本课程的完整教学方案。候选材料包括：

- [Claude Code best practices](https://code.claude.com/docs/en/best-practices)：用于观察上下文、任务拆解、验证和协作习惯；
- [OpenAI Harness Engineering](https://openai.com/index/harness-engineering/)：用于讨论如何通过环境、工具、规则和反馈循环支持 Agent 工作；
- 其他 OpenAI、Anthropic、GitHub 及相关工具的官方文档：用于补充当前版本的安装、权限和功能说明。

### Harness 的课程表达

Harness 不应被描述成一个固定配置目录，而应描述为 Agent 能否可靠工作的环境系统：

`电脑/仓库环境 + 规则与上下文 + 工具与权限 + 执行循环 + 测试/反馈 + 人工把关`

从工程角度看，Harness 通常可以逐步包含：

1. 先提供项目运行命令、测试入口和基本规则；
2. 观察 Agent 反复遇到的错误和重复劳动；
3. 把稳定的检查、知识和操作外化为规则、命令或 Skill；
4. 增加权限、hooks、日志和人工审批边界；
5. 在新的任务或代码库中验证 Harness 是否能复用。

最终学员应能说明自己的 Harness 限制了什么风险，而不是只展示配置文件存在。

## 参考判断与待讨论事项

### 当前参考判断

- Codex CLI 是主要的可复现工作流样例，Codex App 是较低门槛的入口或替代路径，其他工具也应能按相同方法理解；
- CLI 偏向可复现的仓库、命令和测试工作流，App 偏向桌面端使用体验；
- Git 基础需要理解结果和风险，具体命令可由 Agent 协助执行；
- SDD、Skills 和 Harness 讲共同原则与选择理由，不把某个开源仓库作为唯一标准；
- SDD、Skills 和 Harness 应服务于稳定的工程判断，而不是成为固定模板或插件清单；
- 实践数据应优先考虑 starter repo、脱敏数据或合成数据；
- 需要为网络受限学员准备至少一种可行的离线/镜像/远程替代路径；
- 工具资料需要标注版本和有效期，避免把短期界面细节误当成长期方法。

### 待讨论事项

1. 是否为完全没有外网访问的学员提供统一远程环境，还是只提供镜像和下载包？
2. 社区是否提供额外 token 支持？如果提供，如何处理额度、公平性、隐私和失效后的替代方案？
3. Paseo 是否只用于讲师演示和故障排查，还是作为部分学员的正式实践入口？
4. SDD 参考仓库需要展示几个，还是只讲共同原则？
5. 是否需要维护一份“最新工具状态”在线页，记录 Codex App/CLI、国内模型和替代工具的安装及差异？
6. 哪些 Harness 能力属于必做：规则文件、Skills、hooks、权限说明、日志或其他？

这些问题会影响课程的公共承诺、账号和基础设施成本、隐私边界及作业可复现性；它们不应在工具参考文档中预先决定课程结构。
