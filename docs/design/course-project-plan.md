# AI Coding 课程 Project 目标与约束

## 为什么要做 Project

Project 把 AI Coding 方法放回实际任务：尽早得到可运行结果，练习需求、上下文、变化与验证，说明人和 Agent 的分工，并能迁移。项目不是唯一成果，也不反过来绑死全部内容。

采用多个规模可控、复杂度逐步增加的局部闭环。能力递进，代码不必强依赖；前一任务没完成，仍应能通过独立起点继续后续学习。理解机制的观看路径不能被记作已经完成动手能力。

## 三种实践，分别设计

| 类型 | 作用 | 边界 |
| --- | --- | --- |
| 教学案例 | 让一个机制或问题可以观察 | 可以是代码、日志、文档或评测题，不自动成为正式项目 |
| 微练习 | 练习一个动作或一次判断 | 自带检查/解析，范围受控 |
| 正式 Project | 学员自主组合方法并形成结果 | 有起点、阶段任务、验收、参考实现和迁移证据 |

“看懂 Coding Agent”的搜索小站可作教学案例，不必升级为全课唯一项目。

## 四种项目角色与优先候选

| 角色 | 候选 | 主要观察窗口 |
| --- | --- | --- |
| A 快速结果 | 个人主页或轻量实用工具 | 需求表达、素材、首次运行、修改与发布边界 |
| B 交互变化 | 游戏或交互应用 | 规则澄清、状态变化、规格、调试和回归 |
| C 已有系统 | 代码地图与存量仓库功能变更 | 入口、模块、依赖、数据流、事实依据和 Review |
| D 外部能力 | 只读工具或 MCP 集成 | 工具契约、权限、错误处理、来源与审计 |

四种角色不等于四个必做项目。可验证 3～4 个局部闭环；代码地图可以是 Skill、工具或阶段产物。至少一次任务在没有既有对话记忆时理解陌生仓库并修改功能。

早期简单页面或游戏可以一次生成成功；不能以此否定其建立信心的作用。中后期任务则需有真实变化、约束和验证空间，避免整个项目仅剩一次性生成。必要时采用已有仓库扩展，而不是堆复杂部署。

高难度仓库、Kernel Ops、Autoresearch 可做强化/展望，不作核心前置；结尾迁移任务不自动意味着再开发一个大型项目。成果不必内置 AI。

## 筛选标准

明确用户和用途；可观察的输入、输出和状态；能在边界内运行与验证；有值得解释的需求、假设或质量问题；本地/公开/脱敏/合成数据；可控的 starter、依赖、测试与维护成本；明确的失败与恢复路径。

项目复杂度应来自判断与变化，而不是框架数量、真实账号接入或部署规模。B/C/D 应能展示一次生成之后仍有价值的修改或验证；A 不受“一次生成必须失败”的要求约束。

## 录播项目的交付底线

每个正式项目提供：起点版本、任务与非目标、阶段检查点、参考实现、验收样例与运行说明、可接受差异、主要排障、继续路径。检查点恢复前保留学员工作，不用危险覆盖命令。

演示先说明起点和预期结果，再展示关键操作与决策，最后看证据。可以剪辑等待和重复操作，但注明省略；真实模型轨迹、教学重放、人工故障分别标识。不假定所有学员同步操作到同一步。

代码布局、UI 风格、局部实现和工具顺序可以不同；用户目标、关键行为、范围、权限与验收底线不能随意变化。通过参考测试仅证明其覆盖范围，不证明可以直接接入真实生产环境。

## 共同证据方向

学员应说明目标和完成标准、所用事实、AI 与人的职责、实际验证及其遗漏、发现与修正的问题、可迁移和不可迁移之处。可用简短交付卡配代码与测试，不默认提交全部聊天记录或大量形式化文档。

正式提交协议、是否人工评阅、评分/证书和必做/选做待确认。自检解析需随课提供，不等群答疑。

## 明确不做

不把纯静态页面或 Deep Research 结果作为唯一工程成果；不默认选完整 Todo、记账、通用 AI tutor 或完整个人知识库；不要求真实银行、邮箱、日历、企业账号或公司代码；不要求多 Agent、模型训练、云端大规模部署或独立 MCP/SDK 开发。

Feishu MCP 等只作候选，优先只读、合成数据或沙盒；需要外部服务的操作须验证权限与失败替代，不把“换个模型接口”当作兼容性证明。
