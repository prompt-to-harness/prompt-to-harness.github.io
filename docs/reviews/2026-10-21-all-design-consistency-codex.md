## 一套能够串起来的解释

以下是对既有目标的归纳建议，不是新排课决定，也不要求增加内容：

| 章 | 学员当前要解决的问题 | 本章比前面新增什么 |
| --- | --- | --- |
| 1 | 怎样把任务说清并完成第一次可检查的改动 | Prompt 与 Agent 循环，最小授权和人工检查 |
| 2 | 模型此刻看到了什么，接着工作时信息怎样变化 | Context、会话选择、必要的项目约定；交付公开首页 |
| 3 | 怎样重复有效做法并借用外部能力 | Skill/Plugin 的适用边界；保留探索、调试与需求取舍 |
| 4 | 新仓库中，究竟要做出哪些行为 | 来源核对、人工决定、可追踪规格和验收 |
| 5 | 怎样按规格做出增量，并检查实现是否偏离 | 任务级闭环、独立审查与规格回写 |
| 6 | 怎样用框架组织变更，同时保留验证和人的责任 | GSD、明确委派、测试与 UAT 的证据 |
| 7 | 换会话后，怎样仍能找到事实并运行检查 | 项目级可靠上下文与统一验证环境 |
| 8 | 执行遇到失败，什么能继续、什么必须停下 | 有限修复、技术门禁与人工交接 |
| 9 | 这些规则和流程究竟有没有帮助 | 可比较评测、单因素改进、保留或删减的判断 |

AGENTS.md 和 Skill 提前出现，不会使 Harness 阶段失去意义：早期解决一条约定或一段重复操作，后期才把多项约束组织成可重复环境，并检查效果和维护成本。同理，SDD 的新增价值是可观察契约及变更追踪，不是“终于开始写文档”；GSD 的价值需要由既有规格和验证约束，不能靠框架名字证明。

三仓库切换已经明确“迁移方法、重新核验事实”，因此不是叙事断裂。真正需要补的是每次为什么新增一层约束，以及新增之后保留哪些人工判断。
