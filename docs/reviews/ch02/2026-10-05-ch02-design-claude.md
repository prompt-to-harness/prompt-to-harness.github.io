## 总体判断

三条反馈贯穿全章、第 2 条从 2.1 一直用到 2.5，这条线索设计得好，建议保留。但从学员的角度看，这一章有三个结构问题，改措辞解决不了：

1. 全章唯一的一次迭代，是往数组里加三条字符串（+10 −2）。它不需要 AI，也没有可审查的内容，却配了全套流程。
2. 2.1 和 2.2 的口播有一半以上在讲请求解剖和会话机制，第一次改代码排在全章口播过半的位置。这些机制支撑的判断（继续还是新建会话）在本章几乎没有代价差别。
3. 2.4 是学员最容易卡死的一节，却明确不给兜底；全章主转折“公开的还有历史”在多数学员身上查不出东西，唯一常见的发现（提交邮箱）的补救办法又不在课内。

## 一个更大的替代方案：先发布，再迭代

提案决定 13 选了“先在本机给熟人看，最后发布”。我认为反过来更好，供讲师权衡：

- 2.1 就把 v0 发布出去（含推送前检查）。页面一公开，“上面什么都没写”不需要虚构的熟人来指出；学员也可以把链接发给真人，拿到真实反馈。
- 之后每一轮迭代都以“推送 → 部署 → 在线上核对”结束，“Actions 成功不等于页面可用”会被练习两三次，而不是只讲一次。
- 2.3 的“收不收”有了真实代价：收下的提交会公开；`revert` 而不是 `reset` 的理由也不用预告“下一节要公开”，因为历史已经公开了。
- 全章最高的风险（部署失败）放在开头，学员精力最足，后面的内容也不会被它挡住。

代价：第一节就是 Git 和 GitHub 配置，没有 R3 的兜底会在开头流失学员；公开一个占位页，有些学员会不愿意；章节标题和平台交付版的节次要改，属于对外承诺的变更。如果不采纳，R4 的分支问题和“课程示例反馈”的虚构感仍然要单独处理。

讲师决定（2026-10-05）：不采纳，保持最后发布。
