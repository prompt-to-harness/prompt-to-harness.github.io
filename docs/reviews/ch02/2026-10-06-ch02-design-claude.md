## 总体判断

前几轮审查已经把“迭代太小”“机制知识过多”“发布缺兜底”“分支没接住”这些问题讲透了，讲师也已对其中几条作了决定。本轮换一个角度，看**最终交付物**和**学员实际与 AI 打交道的方式**，发现三个更根本的问题：

1. 跟做学员最后公开的页面，首屏仍然是第 1 章的占位身份“示例同学”。章目标“可以拿给认识的人看”在跟做路径上不成立，而且全章没有任何一页提到这件事。
2. 本章叫 Vibe Coding，但全章没有一次“AI 没按预期做 → 我拿证据告诉它 → 它改”的回合。讲师的六轮主线重跑里，所有检查全部通过。唯一一次自然出现的意外（Codex 自己写 Swift 程序量文字宽度，花了 14–16 分钟）被改 Prompt 消掉了，而这一段恰恰是本章最好的真实素材。
3. 有两处课程没有执行自己的标准。一处是 1.2 承诺的“截图反馈”在本章落空；另一处是让学员用未固定版本的第三方代理转发 API 密钥，没有任何审查步骤。

这三条都不需要新增小节，也不违反“不伪造失败”（决定 7）。我认为它们比继续打磨页面更值得先处理。

## 问题（按重要程度排序）

### R1 · P1：公开的 v1 首屏仍是“示例同学”，章目标在跟做路径上不成立

- 范围与规则：2.2 p29 → 2.4 p45–p50；章目标；ED-004 / ED-009
- 证据：
  - `course-starter/PLACEHOLDER_CONTENT.md` 规定首屏姓名“示例同学”、简介“正在学习 AI 协作开发。”；第 1 章 1.4 口播（`courseware/ch01/lessons/04-prompt/script.md:168`、`:229`）让跟做学员采用这组占位内容。
  - 第 2 章五节口播里，“示例同学”只出现在 2.2 p29（`02-iteration/script.md:331`），原话是“首屏还是示例同学，这一轮只改项目区，所以先不动它”。之后 2.3、2.4、2.5 没有任何一步处理首屏身份。
  - 2.4 的推送前检查只问“能不能公开”（secret、他人信息、截图隐私、本人意愿），不问“公开的页面说的是不是我”。三项发布检查也只检查技术可用性。
- 后果：跟做学员按课件走完，得到的是 `<自己的用户名>.github.io/<仓库名>/`，首屏写着“示例同学”，项目区是自己的经历（或课程合成示例）。这样的页面没有人会拿给熟人看。本章一句话主线“把本机 v0 变成可以拿给认识的人看的 v1”，在最终交付物上落空了。codex 的学习设计记录 R7 指出了讲师演示的身份拼接，本条说的是学员这一侧：这是一个交付物缺口，不只是演示观感问题。
- 连带问题：示例反馈卡上没有“这是谁？”这一条，而它是熟人看到“示例同学”时最可能说的第一句话。三条反馈里，第 3 条“看不出你做过什么”之所以“必然成立”（提案原话），是因为占位内容只有一句。也就是说，第 2 章修的是第 1 章故意留下的占位，学员很容易看穿这一点，会觉得反馈是课程安排好的。
- 建议（二选一，都不加小节）：
  1. **把第 3 条扩成“看不出这是谁、做过什么”**：本轮的一个连贯结果是“首屏身份 + 项目经历都换成我愿意公开的真实内容”，仍然由人提供、AI 只呈现。diff 会涉及首屏和项目区两处，2.3 有了更多可读的内容，还能部分回应前一轮设计审查 R1 说的“迭代太小”，又不用新增功能。
  2. 保留现在的第 3 条，在 2.4 p46 的判断清单里加第五项“页面上的身份是我愿意公开的称呼吗”。这一项和本节主题“公开的不只是页面”正好契合：昵称和真名都可以，但不能是占位。代价是这一步变成发布前的一次小改动，需要提交，再走一遍推送前检查。
- 我倾向方案 1：它让“给熟人看”从开头到结尾说的是同一个人。
- 状态：待处理

### R2 · P2：全章没有一次“纠偏 AI”的回合，而唯一一次自然出现的意外被改 Prompt 消掉了

- 范围与规则：2.2 p29–p31，2.3 p39，提案决定 7、10；ED-004 / ED-009
- 证据：
  - `courseware/ch02/materials/mainline/README.md` 记录了六轮主线重跑：六轮里 2.1 都认出既有决定，2.2 都先出计划，最终 `App.tsx` 逐字相同，五项检查全部通过，评审全部“接受”。按这个结果，录制时学员看到的大概率是：第 1 条未复现，Tab 不变，build 通过，diff 干净，历史无问题，部署成功（部署这一步没有重跑数据）。整章的证据全部是“没有问题”。
  - 同一文件第 69 行记录：Done when 原来写“360/768/1440 宽可读”时，第 1、2 轮 Codex 想自己验证，先试无头 Chrome（在沙箱内失败），再在 `/tmp` 写 Swift 程序用系统排版引擎量文字宽度，执行多花 14–16 分钟。2026-10-06 把 p29 改成“我在浏览器查……；你跑 build”之后，这个现象消失了。
- 判断：Vibe Coding 的核心技能是第二句话：看到结果不对，拿证据告诉 AI，再收窄或纠正。第 1 章已经练过第一句（结构化 Prompt）。本章的主线只有一句 Prompt 和一句“确认，按计划执行”。2.3 p39 的“缩小 / 拒绝”和 2.4 的失败定位都依赖现场运气（codex 记录已指出）。被消掉的那一段恰好是本章最有教学价值的真实素材：
  - 它说明完成标准怎么写，Agent 就怎么去证明，甚至会自己造工具去证明；
  - 它说明 AI 的自证不等于人的验证（量文字宽度不等于“可读”），直接支撑决定 10“视口由人检查”；
  - 它是一个真实、可复现（2/3 轮）、不伪造的“需要人介入”时刻，完全符合决定 7。
- 建议：把修改 p29 的过程本身讲出来，而不是只展示修好以后的版本。主线可以照常用新 Prompt；在 p29 或 p31 加一段约 1 分钟的“讲师备课时发生的事”：放第 1 或第 2 轮的录屏片段（14 分钟压缩成几十秒，展示无头 Chrome 失败 → 写 Swift 程序），然后讲师说明当时怎样中断、怎样改写分工，再落到现在这版 Done when。这样学员看到了一次完整的纠偏：现象 → 判断 → 第二句话 → 结果。取舍：多一段素材；并且要承认 p29 现在的写法是从失败里改出来的，我认为这比展示一个顺滑的 Prompt 更有价值。
- 顺带：2.3 p42 说“Review 全靠人工”，但初级开发者实际最常用的是“请 AI 帮我审一遍 / 解释这段 diff”。本章完全不碰 AI 辅助审查，学员的真实工作方式在课程里没有位置。建议 2.3 至少示范一次“新会话里请 Codex 解释这份 diff 动了什么，再由人逐条对照”，把它和人工 Review 的边界说清。平台交付版第 3 节本来就承诺了“让 Codex 解释组件树、数据流和 CSS 影响面”（`docs/course-outline.md` 第 2 章第 3 节），现在课件没有兑现。Codex CLI 0.160.0 是否有内置的 review 命令，**待核实**。
- 状态：待处理

### R3 · P2：1.2 承诺的“截图反馈”在第 2 章落空，而第 1 条反馈正是它的用武之地

- 范围与规则：1.2 → 2.1 p05-live/p06/p17；内部大纲 6.1 附表；ED-002
- 证据：内部大纲 6.1 附表“多模态理解”一行写“衔接后续截图反馈……根据页面截图指出布局问题”；第 1 章 1.2 口播（`courseware/ch01/lessons/02-agent/script.md:323`）对学员说“后面会用截图反馈”。第 2 章五节口播里“截图”只作为证据和隐私对象出现，从来没有把截图交给 Codex。

### R4 · P2：让学员用未固定版本的第三方代理转发 API 密钥，课程自己的第三方审查标准没有执行

- 范围与规则：2.1 p06-tap、p16 复现步骤 5；`tools/clean-codex.sh:95`；内部大纲 1.3 第三方工具核验要求、3.4；ED-002 / 安全
- 证据：p06-tap 讲师提示写“API 密钥会经过本地代理”；p16 复现步骤 5 让学员（选做）用 `uvx claude-tap --tap-client codex -- …` 跑自己的日常配置；`tools/clean-codex.sh` 同样调用 `uvx claude-tap`。全仓库没有找到带版本号的调用（提案只记录了核对时是 0.1.145）。`uvx` 不带版本时，每次都会取当时 PyPI 上的最新版本。
- 判断：课程在 1.6 讲最小权限，在 3.4 才第一次系统地教第三方来源审查，大纲 1.3 还要求演示第三方工具前确认来源、许可证、版本、网络访问和数据边界。2.1 却让学员把自己的模型密钥交给一个未固定版本的代理，口播里没有交代任何“我们为什么信它”的理由。这是课程没有执行自己的规矩，也错过了一个现成的示范。
- 建议（成本很低）：
  1. 所有命令改成固定版本，例如 `uvx claude-tap@0.1.145`。uv 是否支持这种写法、以及应该写哪个版本，**待核实**。
  2. 在 p06-tap 加两三句口播，说明为什么用它：MIT 许可、只在本地运行、trace 存在哪里、导出时只保留鉴权头前缀。这些在提案里都已经核对过，口播本身就是一次简短的审查示范。
  3. 建议学员做这类实验时用单独的、额度受限的临时密钥。
  4. 在 3.4 回指这里：“2.1 我们其实已经信任过一个第三方工具，当时检查了哪几项？”这样把 2.1 的做法接到 3.4 的审查方法上。
- 状态：待处理

### R5 · P2：2.5 有两张卡的“AI 说明”直接写出了行为变化，五张卡的分拣实际只有一张能逼出行为检查

- 范围与规则：2.5 p54–p56；ED-002 / ED-009
- 证据：卡面上的说明分别是 ③“项目按名称排序”、⑤“项目卡可以用键盘聚焦”（`05-refactor/lesson.js` 卡面，`script.md:39`）。光读说明就知道这两张改了行为，不用打开页面。p56 口播却说“提交说明也帮不上忙，五张都写着 refactor”（`script.md:91`），和卡面对不上。
- 判断：分镜写的设计理由是“判断只能靠方法”，但五张卡里只有 ④“缩短类名”真正需要并排比较才能发现。真实的风险恰恰是 AI 用听起来像整理的措辞，描述一个其实改了行为的改动。现在的 ③⑤ 把答案写在了题面上，学员学到的是“读说明就够了”，和本节要教的结论相反。这一条和 codex 学习设计记录 R3（①② 证据不足）不同：即使 ①② 的 diff 补全，③⑤ 仍然可以被一眼识破。
- 建议：保留五张卡和它们的 diff，只改说明的措辞，改成 AI 常用的、听起来不改行为的说法。例如 ③“整理项目数据的组织方式”，⑤“改进项目卡的可访问性语义”。这两句话字面上不算错，但都没说出行为变了。改完之后，③ 只能打开页面看顺序才能发现，⑤ 只能按 Tab 才能发现，和 p55 的揭晓顺序一致。改写后的措辞是否仍然算“标明的教学材料、不冒充真实输出”，由讲师判断；我认为在卡面注明“教学材料”就够了。
- 状态：已修复（2026-10-06）：讲师决定说明写成语义总结，露出行为变化可以接受；改为在 ③ 页明确教“说明自己写出新行为，对照定义就能识破”，④ 仍是只有行为检查才能发现的那张，p56 改口为“说明只能帮一部分”。同时 p54–p55 改为总览加一张卡一页

### R6 · P2：请求解剖一边要求“以实际请求为准”，一边用仓库文件说明了实际请求里没有的行为来源

- 范围与规则：2.1 p09–p11、p26；ED-002 / 事实
- 证据：
  - p10 口播列出基础指令的章节，其中包括“计划”，并说“我们感受到的……‘它会先列计划’，很大一部分来自这份指令”。同一页的核对记录写的是：讲师环境实际发出的指令**恰好删掉了** Planning 一节（0.160.0 默认关闭计划工具）。STORYBOARD“事实边界”一节又要求“画面以实际请求为准、仓库文件作对照”。
  - 本章学员看到的“先说计划，等我确认”，来自 2.2 p29 用户 Prompt 里的那句“先说计划，等我确认再改”，并不来自系统指令。
- 判断：这是一个具体的自相矛盾，而且出现在本节最强调证据来源的段落里。它比 codex 学习设计记录 R7 说的“反事实结论偏强”更直接：口播把一种行为归因给了一段实际上没有发出的文本。
- 更大的问题：本章所有关于“Codex 行为”的观察，都来自 Codex + MiniMax 这个组合。按 p26，这个组合里模型名不在目录中，Codex 发的是通用后备指令，计划工具默认关闭。p11 的“调用不存在的 `read_file`”很可能和模型、Harness 不匹配有关，而不是一般规律（原因**待核实**）。这些都是课程有意选的基线（决定 28），本身没有问题。但这个前提要在第一次看请求时（p08/p09）就用一句话交代清楚：“我们看到的是 Codex 加一个非 OpenAI 模型的组合，换模型，有些行为会变，p26 会演示。”否则学员会把这个配置下的观察当成 Codex 的一般特征。
- 建议：p10 去掉“计划”这一节和“先列计划”这个例子，换一个在实际请求里确实存在的章节作例子，或者直接说明“计划这一节这次被删掉了，所以这次是我们在 Prompt 里要求它先说计划”。这句话本身就是一个很好的“请求按配置组装”的例子，可以和 p11 末尾的说法合并。p08 加一句说明配置基线。
- 状态：待处理

### R7 · P3：章末的伏笔跳过了第 3 章，“全部手工重查”和第 3 章的“快速迭代”接不上

- 范围与规则：2.5 p58 → 3.1/3.2；ED-007
- 证据：p58 的结论是“这个项目没有覆盖这些行为的自动测试，所以每改一次，就得手工全部重查一次……是后面规格和 Harness 章节要解决的问题”，这些章节在第 4 章以后；紧接着的第 3 章 3.1 写的却是“快速形成垂直切片”，3.2 讲“探索状态空间”。
- 判断：codex 课程设计记录已指出“不应由没有自动测试推出全量手查”。本条补的是和下一章的衔接：学员带着“每次都要全量手查”进入第 3 章，第 3 章马上要求快速迭代一个状态多得查不完的小游戏。学员要么觉得两章说法矛盾，要么直接放弃手查。
- 建议：p58 的伏笔改成指向下一章：“这张清单会越来越长。下一章的小游戏状态多到查不完，我们要学会按风险挑着查”，再顺带提一句规格和 Harness 是更远的答案。这样 2.5 的手工清单就成了 3.2“探索状态空间”的起点。
- 状态：待处理
