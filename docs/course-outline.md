# Part1：课程详情页文案

## 为什么要学这门课程

AI Coding 正在从"辅助补全"走向"智能体驱动开发"。以 Codex 为代表的 Coding Agent 已经能够读取仓库、执行命令、编辑文件并运行测试，开发者的角色正在从"逐行写代码"转向"定义目标、审查结果、构建系统"。然而，绝大多数学习者仍停留在两个极端：要么把 AI 当作高级代码补全工具，只生成孤立片段；要么盲目信任 AI 输出，在看不懂的实现上叠加功能，最终留下难以维护的技术债务。

**从行业需求来看**，掌握 AI Coding 的开发者获得了效率优势和职业竞争力。能够用 Prompt 清晰表达需求、用 Vibe Coding 快速迭代原型、用规格驱动开发（SDD）固定需求契约、用 Harness 构建可重复工程环境的人，正在重新定义"高效开发者"的标准。

**从技术学习来看**，市面上的 AI Coding 教程大多是 Prompt 模板合集或者工具操作演示，缺乏从"模糊想法"到"可验证交付"的完整工程闭环训练，更缺乏在复杂项目中实践的机会。本课程通过三个层层递进的真实项目，带你掌握 Prompt → Vibe Coding → SDD → Harness 四层能力，实现从"会用 AI 写代码"到"能用 AI 交付项目"的核心跃迁。

## 课程大纲（详细到三级目录，作图时可以每三章一个模块）

课程前3章可在开课前免费学习，详情请添加客服咨询。

### 第1章：Prompt \- 从环境启动到首页原型

**本章目标**：把一句模糊想法改写为可执行 Prompt，得到第一个可构建、可审阅的首页原型。

#### 第1节：环境搭建与第一次 AI 协作闭环

- 按已核验路径完成环境检查，记录版本、路径、分支和初始工作树状态

- Agent 在执行前复述目标并给出小计划的协作方式

- 实际结果与 diff 的人工检查，改动仅位于允许范围

- 操作前说明目录、文件范围和确认点

#### 第2节：课程主线、Agent 与通用能力地图

- 从首次任务讲清 Agent、Context、Tool 与执行循环

- 区分输入、请求和结果，Context Window 为什么要求筛选信息

- Prompt → Vibe Coding → SDD → Harness 四层主线建立

- 后续工具在首次使用时再展开的学习原则

#### 第3节：Codex CLI、桌面端与权限边界

- CLI 与桌面端的选择理由和替代边界

- CLI 的路径、状态和权限核对方法

- Sandbox、Approval 与外部副作用的理解

- 不使用危险的全权限配置，外部副作用保留人工确认

#### 第4节：从一句话到四段式 Prompt

- Prompt 四要素：Goal、Context、Constraints、Done when

- 让 Codex 先阅读、提问和提出小计划的协作方式

- 写明非目标、文件范围和停止条件

- 未知项由人确认，不被 AI 偷偷决定

#### 第5节：首页 v0：第一次正式受控生成

- 依据确认的 Prompt 生成首页 v0，运行开发服务器和 production build

- 查看 Git diff 与建立检查点（tag）

- 无明显控制台错误，diff 只包含目标范围

- v0 仍是 Prompt 原型，不把当前视觉和行为冻结为正式产品规格

#### 第6节：工程经验：为什么不能给 Agent 所有权限

- 最小权限原则的解释（Saltzer \& Schroeder 系统保护原则）

- 把权限选择对应到具体任务的判断方法

- 不把 Prompt 中的禁止语句当作已生效的技术限制

- 复用本章记录做判断，不重复权限操作

### 第2章：Vibe Coding \- 迭代首页并发布 GitHub Pages

**本章目标**：完成"观察 → 描述 → 修改 → 运行 → 评审"的 Vibe Coding 循环，发布第一个公开版本。

#### 第1节：用真实页面建立反馈基线

- 用页面证据形成问题清单，区分视觉现象、行为事实和个人偏好

- 先讲清会话、文件与进程的区别，再选继续、恢复、压缩或新建会话

- 360×800、768×1024、1440×900 三种视口的检查方法

- 至少覆盖布局、键盘和内容三类检查

#### 第2节：小反馈、小改动、小验证

- 按已选会话策略完成小改动与前后验证

- 一轮只解决一个连贯结果，Prompt 必须引用当前证据

- 修改后运行并比较，发现新问题时不顺带扩大范围

- 不为修一个 CSS 问题重写全部组件或引入大型 UI 依赖

#### 第3节：读懂 AI 代码、Review 与回退

- 走读候选代码、Review 影响范围

- 让 Codex 解释组件树、数据流和 CSS 影响面

- 完成修正或回退并形成可发布提交

- 无法解释或验证的候选必须缩小、拒绝或回退

#### 第4节：GitHub Pages 首次发布

- 公开仓库、Vite production build、GitHub Actions 和 Pages 的关系

- 建立最小部署流程，人工确认后发布

- 检查 base 配置、资源路径和工作流权限

- 在公开 URL 验证，CSS/图片路径正确，刷新后仍可用

#### 第5节：工程经验：AI 说只做重构，意味着什么

- 区分保持行为的重构与需求变化（Fowler《重构》）

- 指出需要复查的证据，判断引用具体行为证据

- 不因函数更短或截图更好看认定重构正确

- 需求变化应另行确认，不新增一轮无必要重构

### 第3章：Vibe Coding \+ Plugin \- 用小游戏体验快速迭代与 Plugin

**本章目标**：用普通 Vibe Coding 完成记忆翻牌，再用 Game Studio Plugin 创建第二个小游戏，亲自发现仅靠聊天迭代的需求债务，形成进入 SDD 的真实动机。

#### 第1节：用 Vibe Coding 加入记忆翻牌

- 用普通 Vibe Coding 完成记忆翻牌的可玩切片

- 允许 Codex 提少量问题并给出计划，但暂不建立正式规格

- 保持一个仓库和现有视觉语言，保留首页原功能

- 能翻牌、配对、完成和重开，production build 通过

#### 第2节：探索状态空间而不是只走 Happy Path

- 先画游戏状态图，再探索快速操作、等待和重开

- 初始、首张牌、两张不匹配、匹配、等待翻回、完成、重开等状态

- 每个问题有最小步骤、期望、实际和截图或日志

- 至少覆盖快速操作、重开和移动端，本节不试修

#### 第3节：基于证据调试一次真实缺陷

- 先复现再修改，根据复现与日志定位根因

- 让 Codex 列可证伪假设，用日志和状态变化缩小范围

- 完成最小修复与回归，修复只处理根因

- 原场景和相邻场景复验，不伪装成现场随机发现

#### 第4节：理解 Plugin 与 Skill，并审查 Game Studio

- 区分 Plugin 与 Skill：Plugin 是可安装能力包，可包含 Skill、Connector、MCP、Hook 等

- 完成 Game Studio 的来源、能力和权限审查

- 审查 manifest、所含 Skills 与脚本，指出能力声明与实际权限

- 不可用或未通过审查时明确使用课程快照/普通协作降级

#### 第5节：Game Studio Plugin：创建"60 秒躲避与收集"

- 按审查结论安装或启用 Game Studio，完成游戏创建

- 游戏具备移动、收集、障碍、HUD、结束和重开完整循环

- playtest、Review、停用与无 Plugin 复验的完整生命周期

- 停用或移除 Plugin 后项目仍可运行，diff 没有无理由更换技术栈

#### 第6节：Memory 对照与需求债务

- Memory 的辅助回忆边界：跨会话辅助回忆，但不能成为团队规则或项目事实的唯一来源

- 启用/禁用 Memory 的对照实验，比较有帮助、无关或过时的信息

- 用来源对照提取需求债务，区分仓库证据、Memory 和模型猜测

- 每条需求债务指向证据，能说明 SDD 将解决什么、不能解决什么

#### 第7节：工程经验：为什么重开游戏后，旧计时器还在影响结果

- 用既有时间线解释状态、副作用与资源清理

- 预测快速重开的结果，指出具体状态和副作用

- 不把所有状态变化都当 Bug，不新增后端重试或支付场景

- 幂等与重试的基本概念（为后续章节铺垫）

### 第4章：SDD \- 为 JSON Diff 建立可执行规格

**本章目标**：进入 JSON Crack 开源仓库，在不修改生产代码的前提下，把"加入 JSON Diff"转化为工具无关、可追踪、可验收、可分步实施的五层规格资产。

#### 第1节：理解五层规格与外部需求来源

- 五层规格各自用途：BRIEF → SPEC → ACCEPTANCE → PLAN → TASKS

- 用只读 MCP 或标明来源的快照摄入需求

- 外部原文不等于批准规则，外部文档不直接成为 Approved 需求

- 来源、权限、时间、路径和固定基线可追溯

#### 第2节：调查陌生仓库并形成 Brief

- 在固定分支只读调查 JSON Crack 源码和验证入口

- 定位入口、组件、状态和验证命令，形成有依据的 Brief

- Brief 包含目标、非目标、约束、成功信号和开放问题

- 会影响实现的规则保持 Open，没有生产代码变更

#### 第3节：Spec：固定可观察行为

- 将人工批准的产品行为写成带 REQ\-\* 编号的 Spec

- 定义对象顺序、数组匹配、删除、错误恢复、筛选等规则

- 区分实现选择与需求规则，不在 Spec 中写组件名或文件路径

- 不用 JavaScript 对象枚举顺序、字符串序列化或第三方库默认行为代替产品决定

#### 第4节：Acceptance：把"正确"写成固定案例

- 将 Approved 需求转成固定输入、动作和可核算结果

- 使用 AC\-\* 编号和 Given\-When\-Then 格式

- 建立 REQ/AC 追踪关系，每条 Approved 需求至少关联一个 AC

- 客观结果可由 fixture 核算，视觉标准有明确视口和检查项

#### 第5节：Plan 与 Tasks：调查影响面后拆实现

- 依据源码与验收比较方案，拆出可验证、可回退的 Tasks

- Plan 记录方案、取舍、影响文件、风险和回退

- Tasks 使用 TASK\-\* 编号，每项有输入、范围、依赖、验证和完成定义

- 单独提交规格基线，文档 diff 中没有生产代码

#### 第6节：工程经验：为什么写了需求，双方仍可能理解不同

- 用遗漏条件的教学摘要辨认契约歧义（Meyer 的契约视角）

- 解释前置条件和不变量，区分未决需求、实现选择和验收缺口

- 不把第三方库默认行为当产品规则

- 本章仍无生产代码变更

### 第5章：SDD \- 按规格分片实现 JSON Diff

**本章目标**：让 Codex 按 TASK\-\* 小步实现 JSON Diff 功能，每一步都对照规格、运行相关验证、解释 diff，在发现规格缺口时先返回 SDD 文档。

#### 第1节：差异模型与确定性 fixtures

- 先讲一次任务级执行闭环，再按固定 fixtures 实现纯差异模型

- 固定输入与期望状态可人工核算，对象键换序为零差异

- 数组规则与 Spec 一致，输入顺序不能改变确定结果

- 测试不复制实现逻辑来"自证正确"，不为方便实现而缩小 fixture

#### 第2节：合并图映射与 removed 节点

- 复用任务流程，将差异模型映射到 JSON Crack 现有图

- 保留 removed 节点和必要祖先，路径和父子关系正确

- 相同输入无误报，旧图数据主路径持续通过

- 只做最小映射，不修改渲染引擎，也不引入第二套图组件

#### 第3节：Web UI 与交互接入

- 接入双输入、错误恢复与 Web UI，不在 UI 复制算法

- 正常和单侧错误路径可操作，错误不会覆盖最后一次有效结果

- 规定窄屏不阻塞操作，现有单 JSON 可视化主路径没有回归

- 不顺带修改 VS Code、浏览器扩展或其他非目标 workspace

#### 第4节：验收、Review 与规格回环

- 完成剩余功能与验收，当前 TASK\-\* 全部有结果

- 依据实际缺口补规格/案例，不把已经批准的规则伪装成未决问题

- 实现与规格冲突时不能只改代码或测试，走规格回环

- 学员能解释关键数据流和模块边界，Review 无未处理阻塞项

#### 第5节：工程经验：为什么改一个地方，会牵动另外几个地方

- 用源码关系图解释耦合、模块和信息隐藏（Parnas 模块分解论文）

- 仅分析变化影响，不追加新功能

- 不把有依赖等同于坏设计，不为解耦增加无用层

- 原验收与产品范围保持明确

### 第6章：社区 SDD \- 用 GSD 构建测试闭环并完成规则变更

**本章目标**：引入社区 SDD（GSD）工作方式，使用 Sub\-agent/mapper 分工协作，为 JSON Diff 建立完整测试闭环，并完成一次规则变更（CR\-01）的全流程实践。

#### 第1节：GSD 接手已有项目与 Sub\-agent 调查

- 沿用五层规格，了解 GSD 接手与 mapper 分工的工作方式

- 实际委派 Sub\-agent 进行只读调查，主 Agent 核验结论

- mapper 写入互不重叠，主 Agent 不以行数代替事实核验

- 原生产代码与规格未被初始化重写，五层文档继续作为需求依据

#### 第2节：用 GSD 明确验证目标并规划 CR\-01

- 先讲验证方式选择（类型检查、lint、单测、组件测试、E2E、截图、人工评价）

- 批准 CR\-01 规则变更，形成 GSD 验证矩阵和串行计划

- 原对象/数组/删除/错误/筛选/节点上限/隐私验收仍有验证去向

- 不按覆盖率数量验收，不测试私有状态或 CSS 类名

#### 第3节：用 GSD 执行失败测试、规则实现与回归

- 按批准计划取得失败/通过证据，先写失败测试再实现

- 完成最小规则实现和回归，失败测试因正确原因失败

- 不通过跳过测试、改期望或吞异常制造绿色

- 生产修改保持串行，不与 mapper 或其他执行者冲突

#### 第4节：GSD 验收、最终 Review 与迁移说明

- 操作 UAT（用户验收测试），汇总门禁并 Review

- 目标 E2E 真正操作功能，视觉结果经人工复核

- 框架标记完成不能替代发布批准，UAT 必须来自实际观察

- 版本、源规格、派发及执行证据可追溯，交付 v2

#### 第5节：工程经验：测试全绿，到底证明了什么

- 解释测试和 UAT 证据能支持的结论，指出未覆盖项

- 能解释具体断言支持哪条需求

- 不将覆盖率、测试数量或一句经典名言作为正确性证明

- 测试的边界与局限（Dijkstra 的测试边界思想）

### 第7章：Harness \- 建立可复用的项目环境

**本章目标**：进入 dependency\-cruiser 开源仓库，从无 Harness 的冷启动摩擦出发，构建最小项目 Harness，使新会话能够发现正确上下文、调用真实工具、执行统一验证并在高风险动作前停下来。

#### 第1节：无 Harness 冷启动与摩擦基线

- 先区分 Worktree 文件隔离与 Session 对话

- 在 A 运行前冻结任务、评分与对照条件

- 记录无课程 Harness 的真实结果，失败和成功均如实保留

- A 工作树与后续 B 工作树隔离，一次运行只作为本课对照证据

#### 第2节：自举代码地图与版本化上下文

- 讲清个人偏好、常驻项目规则和按需地图的区别

- 全局 \~/\.codex/AGENTS\.md（个人跨项目偏好）与项目根 AGENTS\.md（团队共享规则）

- 核验 dependency\-cruiser 入口后建立版本化上下文

- CODEBASE\_MAP\.md 记录入口、数据流和证据，不存在尚未运行成功却写成事实的命令

#### 第3节：建立任务模板与统一检查入口

- 复用冻结任务与已验证命令，建立统一检查入口

- TASK\_TEMPLATE\.md 保存 Goal、Context、Constraints、Done when

- 建立 Harness v1，检查实际运行成功，命令不暗中修改文件

- Harness patch 与任务包、产品实现分离，不提前封装 Skill

#### 第4节：工程经验：上下文与文档为什么会过期

- 用独立过期地图判断失效与维护责任（Naur《Programming as Theory Building》）

- 解释文档为何不自动等于理解

- 能区分仓库事实、AI 推断和个人偏好

- 不把未经核验的命令写成事实，不把多写文档当作唯一解法

### 第8章：Harness \- 执行任务与处理失败

**本章目标**：在 Harness 条件下执行相同固定任务，处理检查失败后的有限修复与人工交接，建立自动化触发与确定性门禁。

#### 第1节：在 Harness 条件下执行固定任务

- 在隔离 B 工作树用 Harness v1 完成与第 7 章相同的任务

- 保留未被教学故障污染的原始证据

- 两次输入、设置、权限和停止条件一致，结果互不污染

- 四状态判定（fresh/equivalent/stale/unknown）及输入顺序无关案例可重复

#### 第2节：检查失败后的有限修复与人工交接

- 先分类失败，再在独立练习中有限修复、复验或停止交接

- 成功路径能因正确原因失败并在修复后通过

- 停止路径说明已尝试内容、剩余问题与所需人工决定

- 教学故障不混入 A/B 评测，不修改验收期望来消除失败

#### 第3节：自动化触发与确定性门禁

- 先区分触发、执行、阻断与批准

- 完成低风险自动化的失败/恢复演示（Hook、codex exec）

- 本地与 CI 运行一致，失败不能继续发布或覆盖证据

- Agent 判断不替代客观测试，Hook 与 codex exec 不要求成为永久依赖

#### 第4节：工程经验：自动化的责任边界与快速失败

- 改换已有故障的条件，判断重试、副作用和人工接手边界

- 能说明何时继续、何时停止以及谁对验收和发布负责

- 不把所有失败都归为可重试，不引入真实外部写入实验

- 最小权限原则与 Retry / Side Effect 主题

### 第9章：Harness \- 评测、改进与沉淀 Harness

**本章目标**：用 A/B 对照实验科学评测 Harness 效果，改进一个因素，将已验证流程沉淀为项目 Skill，完成最终 Review 与评测包交付。

#### 第1节：比较 Harness 前后结果并改进一个因素

- 先核对可比条件（模型、设置、权限、输入、时间、停止条件一致）

- 评分并改进一个因素，结果与成本分开记录

- 产品正确率、人工介入、耗时与可观察成本分开记录

- 无证据时可保留 v1 并说明暂不能证明改进，不强造 v2

#### 第2节：将已验证流程沉淀为项目 Skill

- 只将已验证的重复经验封装为 Skill

- Skill 包含输入、步骤、输出、停止条件和验收标准

- 验证调用、不触发和移除后的检查

- Skill 不包含臆造路径或理想流程，能解释适用边界

#### 第3节：最终 Review 与评测包交付

- 从干净 checkout 复现门禁，完成 Review

- 固定基线可追溯，干净环境能复现四状态判定核心和适用检查

- Harness 前后条件可比较，没有声称已完成未实现的功能

- 无 secret、源码正文、机器绝对路径或许可证遗漏，Review 无未处理阻塞项

#### 第4节：工程经验：度量与过度工程

- 判断规则收益与维护成本，列出未验证项

- 不以一次胜负宣称普遍提升，改进不得损害其他固定案例

- 不按规则数、抽象层数或 Skill 数量评分

- 能说明哪些环节仍需人工，Ousterhout《软件设计的哲学》的复杂度观点
