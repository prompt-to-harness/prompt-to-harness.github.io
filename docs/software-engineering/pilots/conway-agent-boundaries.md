# 拾遗卡：Mel Conway，通信结构会进入系统结构

## 预计时长

内部试讲样稿，12--15 分钟。历史问题 3 分钟、两种 Agent 分工 4 分钟、Harness 实验 5 分钟、AI coding 收束 2--3 分钟。

## 开场

把一个功能同时交给三个 Agent：一个改数据模型，一个改 API，一个改前端。大家都说自己完成了，最后合并时却发现三个人对字段名、错误格式和空值含义的理解不同。

这时问题不一定是某个 Agent 不够聪明。也可能是任务分工和通信路径，已经把系统会长成什么样限制住了。

## 人物与史料

Mel Conway 在 1968 年的《How Do Committees Invent?》中讨论设计组织的通信结构与系统设计之间的关系。原文不是一句“系统复制组织结构”的口号，而是从通信路径和设计结构的对应关系出发，说明缺失的通信会排除一些设计可能。[原文](https://www.melconway.com/Home/Committees_Paper.html)

把它连接到多 Agent 是课程推断，不是 Conway 对 AI 的预言。我们真正要观察的是：谁知道什么、谁能修改什么、哪些接口需要协商，以及这些通信安排怎样影响最终代码。

## 两种协作结构

### 方案 A：按文件切人

```text
Agent 1：修改 src/models/ReadingItem.js
Agent 2：修改 src/api/report.js
Agent 3：修改 src/ui/ProgressPanel.js
共享规则：最后统一合并，遇到冲突再讨论。
```

这种分工看起来并行度高，但字段语义、错误协议和验收条件没有明确负责人。每个 Agent 都可能在自己的文件里做出合理决定，组合起来却不一致。

### 方案 B：先协商契约，再分配接缝

```text
契约负责人：先写字段、错误和边界案例，不能直接改业务代码。
模型负责人：实现领域规则和行为测试，只能修改 src/domain/ 与测试。
适配器负责人：接入 API 和 UI，必须使用契约中的字段和错误格式。
Harness：拒绝越权文件修改；合并前运行契约测试和集成测试。
```

这里牺牲了一点并行自由，换来明确的通信路径。关键不在于“角色越多越专业”，而在于每个变化是否有唯一归属、每个接缝是否有可检查的约定。

## Harness 实验

运行 [配套脚本](agent-harness.mjs)。它把方案 B 中最小的一条 Harness 规则写成可执行检查：每个任务只能修改自己负责的目录；契约文件只能由契约负责人修改；越权修改在进入测试前就被拒绝。

```js
const ownership = {
  contract: ["docs/spec/", "tests/contract/"],
  domain: ["src/domain/", "tests/domain/"],
  adapter: ["src/api/", "src/ui/", "tests/integration/"],
};
```

课堂上先让 Agent 自己写一个类似检查，再故意提交三种变化：修改正确目录、修改别人的目录、同时修改契约和实现。比较“模型说它遵守了边界”和 Harness 实际阻止越权之间的差别。

## 与 prompt、model、SDD 的关系

- **Prompt**：告诉 Agent 它的角色、允许修改的范围、必须读取的契约和交付证据。
- **Model**：可以负责分析、实现或审查；模型能力越强，越应该让它解释跨边界的假设，而不是给它无限写权限。
- **SDD**：记录字段、状态、错误和验收条件，为不同 Agent 提供同一份语义来源。
- **Harness**：把目录权限、命令、测试、格式检查和合并门槛变成可执行约束。

一个好的 prompt 不能替代 Harness；一个严格的 Harness 也不能替代 SDD。前者传达意图，后者限制行动，中间还需要一份人能审阅的契约。

## 观察问题

让两组 Agent 完成同一功能：一组按方案 A，只给文件范围；一组按方案 B，先交契约再实现。保持 model 和任务描述尽量一致，记录：

1. 字段和错误格式出现了几种版本；
2. Agent 是否修改了不属于自己的文件；
3. 冲突是在代码合并时才出现，还是被 Harness 提前阻止；
4. 最终修复是改变代码，还是补充了通信和契约。

## 带走的思想

多人或多 Agent 系统的架构，不只由代码能力决定，也由通信、权限和交付规则决定。设计协作流程时，先画出变化和信息的流向，再决定并行边界；不要先把任务按文件平均切开。

## 讲师备注

Conway 原文讨论的是组织和设计结构，AI 版本是需要实验验证的类比。试讲不应得出“多 Agent 一定更好”或“串行一定更安全”的结论。真正的收获是让学员看到：Harness 是组织通信规则的一部分，也是架构的一部分。
