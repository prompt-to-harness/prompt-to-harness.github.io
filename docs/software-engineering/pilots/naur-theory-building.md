# 拾遗卡：Peter Naur，交接时丢掉的不是代码，而是理解

## 预计时长

内部试讲样稿，12--15 分钟。开场和人物 3 分钟、两种上下文 4 分钟、SDD 实验 5 分钟、AI coding 收束 2--3 分钟。

## 开场

把一个小需求交给 Agent。你给它仓库、文件和一句话任务，它很快写出一版能跑的代码。第二天换一个 model，或者换一个没有对话历史的 Agent，它也能继续修改吗？

如果答案不稳定，丢掉的可能不是文件，而是原作者对问题的理解：哪些规则是业务要求，哪些行为只是当前实现，哪些看似合理的变化其实不能做。

## 人物与史料

Peter Naur 在 1985 年的《Programming as Theory Building》中反对把编程简单理解成生产程序和文档。他把编程描述成程序员逐步形成对问题、解法和实现限制的理解，也就是一套 theory。[原文重印](https://pages.cs.wisc.edu/~remzi/Naur.pdf)

这里的 theory 不是一份漂亮的设计文档，而是能让维护者判断“为什么这样写、什么不能改”的工作理解。文档、测试和代码可以帮助传递它，却不自动等于它。

这个观点很适合 AI coding，但要标明边界：Naur 没有在预测 Agent。今天把它映射到 prompt、model 和 SDD，是我们根据“理解如何形成和交接”做出的课程解释。

## 同一个任务，两种交接

任务：给阅读清单增加“有效学习时长”。规则是：只有已完成的资料，且学习时间至少 30 分钟，才计入进度。

### Prompt A：只有动作

```text
给阅读报告增加 completed 过滤，只统计已完成的资料。
请修改代码并运行测试。
```

### Prompt B：带一张小型 SDD

```text
目标：报告中的有效学习时长只统计满足规则的资料。

规则：
- completed 必须为 true；
- minutes >= 30；
- 标题数量、明细和总分钟数都使用同一批有效资料；
- 其他输出格式保持不变。

验收：
- 未完成但 45 分钟的资料不计入；
- 已完成但 29 分钟的资料不计入；
- 已完成且 30 分钟的资料计入；
- 空列表仍输出 0 分钟。

非目标：不改变资料排序，不新增持久化字段，不改动报告之外的调用者。

请先列出拟修改文件和未决问题，再实现；完成后报告测试、diff 和仍未验证的假设。
```

Prompt B 不一定产生更好的代码，但它把需要传递的 theory 暴露出来了：统一规则、边界、非目标和完成证据。它也给 model 留出了提出问题的空间，而不是把缺失信息偷偷补成假设。

## 代码实验

先让两个 model 使用同一仓库、同一代码、同一任务，只改变上下文：一次使用 Prompt A，一次使用 Prompt B。不要只比较代码行数，记录四件事：

1. model 是否把“已完成”误解成唯一条件；
2. 过滤是否只改了明细，漏掉了标题数量或合计；
3. 它是否修改了非目标文件，或者创建了没有必要的抽象；
4. 它交回了哪些测试和未验证假设。

然后运行 [配套脚本](sdd-handoff.mjs)，用四个边界案例验证 SDD 里的规则。脚本不模拟 model，它只检查“规格写出来以后，行为是否有证据”。

## 与 model 的关系

不要把这节讲成“强 model 不需要 SDD，弱 model 才需要”。更强的 model 可能更善于补全缺失意图，也可能更有能力把错误假设扩散到更多文件。可迁移的判断是：

- model 负责提出实现和问题；
- prompt 负责把当前任务、上下文和输出格式说清楚；
- SDD 负责留下规则、边界、非目标和验收条件；
- 人负责判断这些内容是否真的代表需求。

换 model 时，真正应该保持的是验收证据，而不是某个 model 的口头承诺。

## 带走的思想

每次让 Agent 接手代码，都问一句：它需要重建哪一套理解？如果答案只存在原作者的记忆里，代码地图、SDD、测试和决策记录就不只是文档工作，而是交接接口的一部分。

## 讲师备注

Naur 的原文不是“多写文档”的主张，也不能推出某种 SDD 模板。试讲重点是让听众发现：同一个 prompt，缺少一条业务规则就可能产生一版自洽但错误的代码。未进行真实 model 对比时，不要声称某个 model 一定更好；先收集 prompt、diff、测试和返工记录。
