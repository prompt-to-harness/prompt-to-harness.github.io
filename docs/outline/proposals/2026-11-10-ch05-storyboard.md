## 本章故事线

**一句话主线**：拿着第 4 章的规格和任务，在 JSON Crack 中分步实现 JSON Diff，让每一步的代码、验证结果与已批准的行为对得上，最后交出可解释、经过本章验收的功能。

第 4 章回答了“要做什么、怎样算做对，以及准备怎么做”。现在学员拿到一份已有工程和一套规格，还没有 JSON Diff 的生产实现。我们从其中一个任务出发：对象里的键换了顺序，为什么结果仍应是零处差异？讲师把已批准的规则、固定输入和任务范围交给 Codex，再检查实际代码和验证结果。一个任务完成后，继续把差异模型接到图数据、双输入和交互界面，最后回到同一组验收案例，检查整个功能。

实现中可能遇到不同情况：代码与已批准规则不一致，需要定位实现或测试；验收没写清楚，需要依据已有规则补案例；产品行为本身仍未决定，则由人确认后再修订规格。讲师按实际发现选择下一步，不预设 Agent 一定犯错。模型任务通过后留下的只是这一部分的证据；到本章末，还要检查图、输入、错误恢复、筛选和原有功能，再把结果交给第 6 章。

### 本章要讲透的两个问题

1. **怎样让一个任务有可检查的完成边界？** 5.1 首次讲清任务级执行：读取本任务和关联规则、案例及全局约束，限定修改范围，实施并运行相关检查，结合 diff 和结果决定是否完成。5.2–5.4 沿用这一做法，每次实际检查，不重复讲一遍流程定义。
2. **实现、案例和规格对不上时，该回到哪里？** 先找出冲突涉及什么：规则明确时对照规则检查实现与测试；案例缺失时补验收并检查覆盖；需要改变或补充产品行为时，由人决定并同步相关文档。5.4 把这条关系放到整体验收与 Review 中讲清。

第四章介绍五层规格，本章使用它们做实施与反馈；第六章再用 GSD 承接已完成的功能和原验收。本章不是 GSD 教程，测试要随任务实际开展，也不把第六章的完整测试闭环提前压进来。

## 5.1 规格写好了，怎么知道第一个任务做对了？

### 从一条规则和一组输入开始

第 4 章结束时，讲师和学员各自留下了 JSON Crack 的规格基线：经人确认的行为、可核算的验收案例，以及结合源码拆好的实施任务。进入本节，先核对当前副本与规格提交，打开差异模型任务和它关联的规则、案例。讲师的实际编号不要求与学员相同；每个人都要能在自己的文件里找到对应内容。

先看一组很小的输入：Before 为 `{"name":"Lin","age":20}`，After 为 `{"age":20,"name":"Lin"}`。字段与值相同，只是对象键的顺序不同。4.3 已由人决定：对象键顺序忽略；4.4 给这一规则安排了固定输入和零差异的期望。学员先根据这条规则判断结果，再由讲师说明零差异的依据。这里用一组合成数据讨论讲法，演示时打开第四章实际交接的 fixture；检查的是键顺序，不是交换 Before 和 After 两侧的含义。

这组输入让我们知道第一项工作的一部分应该达到什么结果，但它还不能覆盖数组、类型变化和嵌套路径。差异模型任务要完成哪些规则、哪些固定案例，仍以 4.5 形成的任务和关联验收为准。

### 把一个任务交给 Codex

有了任务，再确定本次操作的起点。讲师从规格提交创建本地功能分支，核对版本和工作区，按 4.5 确定的方式检查已有工程基线。若已有改动或检查受阻，保留现场并先处理起点；不能把未运行或失败的检查记为通过。

4.2 的一次仓库调查记录只找到 lint 和 build，没有发现测试命令。因而本节不能直接假设仓库已有可用的单元测试入口。先核对 4.5 对检查方式的调查和选择：如果现有入口足够，就说明它怎样运行本任务的固定案例；如果不足，就结合实际工程确定最小验证方式，并在任务范围内建立所需入口。具体工具、依赖、文件和命令留待源码核实与备课实跑，不能预写测试已经跑通。

讲师让 Codex 读取当前差异模型任务、关联的 Spec 和 Acceptance、固定素材，以及全局约束和非目标，再请它只完成这个任务。请求中要让 Agent 知道本次做什么、以哪些案例核对、允许修改到哪里；具体内容来自实际的 Plan 和 Task，而不是把整份规格交出去后只等一个“完成”。本次先做差异计算及其验证，图映射和界面留给后续任务。按需读取关联文件时，仍要带上适用的全局约束，不能只截一条规则就忽略非目标。

这里第一次讲清本章的任务级执行：找到任务及依据，限定范围，实施，检查实际结果，再由人决定是否继续。5.2 起仍做这些动作，但把讲述重点放在每次新增的工程问题上，不重复定义步骤。

### 对照案例检查实际结果

Codex 完成一次工作后，先看它实际改了什么：差异是否集中在当前任务允许的范围，是否有可定位的验证入口，是否顺手修改了界面或其他客户端。再运行与当前任务相关的检查，打开固定输入和期望，抽查对象键换序案例，结合测试输出核对结果。检查结果以实际运行和人工核对为准，不能把 Agent 的完成说明当成测试结果。

固定期望应从已经批准的行为和人工核算得到。比如键换序的预期是零差异；数组 `[10,20]` 变为 `[5,10,20]` 时，按已批准的索引规则核算为两处 `changed`、一处 `added`。测试不能调用同一套待验证的比较逻辑来生成自己的期望。若结果不一致，先确认输入、期望与 Spec，再看实现和测试各自哪里偏离；不能为了让测试通过而把预期改成当前实现的结果。

学员用自己的规格和任务完成差异模型，并检查数组、类型变化和嵌套路径等当前任务要求的案例。实现可以与讲师不同，但要能解释固定输入、预期、实际结果和代码改动。运行或环境受阻时，记录实际进展与错误，从课程提供的检查点或排障材料继续；具体检查点和恢复方式要在后续备课核实。

### 判断完成范围，再交给下一节

请学员判断：如果相同输入和对象键换序两个案例通过了，差异模型任务就一定完成了吗？讲师打开当前任务的完成定义说明：这两个结果只覆盖对应案例；数组、类型变化、嵌套路径等若属于该任务，仍要按各自的要求检查。检查通过后，还要回看允许修改的范围和可解释的 diff，才有依据标记这个任务完成。其他任务的验收仍留给后续步骤。

完成本节后，留下差异模型、任务要求的目标测试，以及 `CH05_IMPLEMENTATION.md` 初稿，记录本次任务、关联依据、实际检查结果和未解决的问题。记录为后续复查服务，不预设固定的模型回复或运行耗时。下一节拿着已验证的模型，解决被删除的字段怎样出现在合并图里。

## 5.2 字段删掉了，结果图上怎样看见它？

4.4 的嵌套案例中，`/active` 只存在于 Before，规则要求它作为 `removed` 留在结果里。讲师先回到两份输入，让学员判断：如果只拿 After 构造图，在哪里能看到这个字段？随后打开 5.1 的差异结果和当前任务，检查现有图数据的入口，说明为什么需要把两侧信息映射到能够表达这些状态的图结构。

本节让 Codex 完成合并图映射：保留新增、删除和变化节点及正确的路径、父子关系；为后续筛选保留所需的祖先信息。讲师用固定案例核对 `/active`、`/role` 和 `/user/age` 的位置与状态，再检查相同输入以及原有单 JSON 图数据路径。具体实现位置和命令以 4.5 方案与实跑结果为准。这里验证图数据能否表达规则，完整的“只看变化”界面和摘要留到 5.4。

**学员判断**：只在 After 中找节点，为什么无法核对删除？因为删除节点的原始信息来自 Before；要看映射后的实际节点和关系，才能判断是否保留。完成后留下映射实现、相关检查及结果，再进入双输入接入。

## 5.3 一边输入错了，已经得到的结果怎么办？

前两节已有可以检查的差异逻辑和图数据，但用户还需要在 Web 界面输入两份 JSON。讲师从一次正常比较开始，沿实际代码解释输入、解析、差异模型和图更新的路径；再把其中一侧改成非法 JSON，按 Spec 检查错误侧与最后一次有效结果。恢复合法输入后，继续观察结果如何更新。首次输入就非法时，还要按对应验收检查没有历史结果的状态。

本节让 Codex 把双输入和错误状态接到现有 Web 路径，讲师核对操作、错误恢复、约定的窄屏及原有单输入主路径；UI 调用已有差异逻辑，不再复制一套算法。测试与人工操作各自覆盖哪些情况，以实际检查记录为准。第 6 章才批准“明确提示当前图是上次有效结果”的 CR-01；本节不把该提示设为必做，也不要求刻意移除已有的等价行为。

**学员判断**：一侧输入非法时，错误状态与上一次成功的比较结果各由什么证据确认？结合页面与输入操作回答；只看 Agent 回复或一次正常路径，还不足以说明错误恢复符合验收。完成后留下可以操作的双输入和错误路径。

## 5.4 各部分都做了，能说整个功能完成了吗？

讲师接着完成差异摘要、“只看变化”和非纯颜色表达，再回到 4.4 的嵌套案例操作完整功能：三处直接差异是否对应输入？筛选后 `/user` 是否为了保留上下文而出现，计数是否仍为 3？然后按当前 Acceptance 检查错误、节点上限、窄屏、本地处理及原有单输入路径等实际适用的项目。模型测试、图映射测试和界面观察分别说明各自检查了什么；最终结论要对照当前 `AC-*` 和任务完成定义。

若检查发现实现与已批准规则冲突，先定位代码、输入和测试，依据既定规则处理；若规则已定但案例确有遗漏，补上可核算的验收并核对任务；若行为本身需要新决定，则由人批准后同步 Spec、Acceptance 和相关任务，再实施与回归。用实际发现决定走哪条路径。4.4 已为嵌套筛选安排案例，不能预设它一定缺失；如果本次没有发现规格缺口，就直接验证并可回指 4.3 已记录的 `null` 与字段缺失冲突，结合最终处理状态说明为什么当时要回到规格。

Review 从本次 diff 与相关验收出发，按需查看源码、调用方和测试，核对关键数据流、错误处理及范围。审查意见要能指出触发条件、位置和依据，再由讲师判断接受、驳回或补充验证。是否引入新会话协助 Review 仍待讲师决定；无论采用什么形式，检查结论都以实际证据为准，不预设审查者会发现问题。

**学员判断**：差异模型和映射测试都通过了，但错误恢复还没有操作过，可以宣布整个 JSON Diff 通过验收吗？不能。前两类结果支持它们覆盖的行为；错误恢复需要其对应输入、操作和观察结果。完成当前任务、验收和 Review 后，留下实际结果、可解释的 diff、本地检查点及已知缺口，交给第 6 章。

## 5.5 为什么改一个地方，会牵动另外几个地方？

从本章实际形成的数据流出发，找到差异模型、图映射和 Web UI 各自使用的信息。假设需求负责人批准调整一条比较规则，请学员先判断可能影响哪些模块、哪些接口和检查需要复核；讲师随后打开实际源码与调用关系，解释判断依据。这里只分析影响，不增加功能。

再比较两种职责分配：由差异模型提供比较结果、UI 消费结果；以及在 UI 中再写一套比较规则。讲师结合本次实际代码解释，规则知识放在哪些位置会影响以后核对和修改的范围。由此引出模块、耦合和信息隐藏；有依赖本身不是坏设计，也不为了减少依赖而增加没有职责的层。Parnas 的模块分解视角用于解释取舍，具体源码关系与例子待实现后核实。

**学员判断**：假如比较规则发生变化，哪些位置需要修改，哪些位置至少需要重新验证？答案依据本次实际依赖和测试，不预设 UI 一定不受影响。将模块关系与影响范围判断补进 `CH05_IMPLEMENTATION.md`。

## 第 5 章与第 6 章的交接

本章结束应有：通过当前验收的 JSON Diff、本章任务及验证记录、关键 fixtures 与测试、Review 结果，以及可定位的本地实现提交。还要能解释从输入到差异计算、状态更新和界面呈现的关键路径。向第 6 章交接实际完成的 commit、五层规格、原验收状态、现有测试和已知缺口。

第 6 章沿用这份成果接入 GSD，补齐验证，并由人在 6.2 批准 CR-01。第五章已要求输入非法时保留最后一次有效结果；CR-01 新增的是对用户明确显示当前结果为上次有效结果。若第五章实际实现已经有等价提示，应如实交接，不把新规则追溯成旧实现的必然缺陷。
