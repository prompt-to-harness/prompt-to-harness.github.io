# 提案：用“讲透问题”和两层结构设计每一章

> 状态：讨论稿（2026-10-22）。方向由第 2 章负责讲师 MiaoDX 在讨论中认可，先在第 2 章试点（见 [ch02.md](../../../courseware/ch02/README.md)），效果好再推广；作为全课做法，推广前需要两位讲师确认，确认后并入[制作手册](../../production/lesson-authoring-playbook.md)，再删本提案。
> 针对：每章的设计顺序、内容取舍、时长、实验与起点快照、决策记录。全课怎样组织见[一页全课表](2026-10-22-course-one-page.md)。
> 本文不是课程承诺，未经试讲。

## 为什么要有统一做法

第 2 章前后调整了十几轮，每一轮都有道理，但缺一个大家都认的判断依据，下一轮又会被推翻。回头看，返工大多来自“先改页面，后定标准”。下面的做法把判断依据放到最前面，并固定改动的顺序。

## 一、讲透问题：每章的起点

每章先写 5–8 个“学完能回答的问题”，再做别的。同一组问题同时用于：

| 用途 | 怎么用 |
| --- | --- |
| 章目标 | 问题就是目标，不另写“理解 xx”“掌握 xx” |
| 内容筛选 | 每一页至少对应一个问题；对不上任何问题的页移出本章 |
| 时长控制 | 先按问题分配时间，超时砍深入层，不砍问题 |
| 去重 | 每个问题只归一节负责，别的节只能引用，不重讲 |
| 自检 | 章末自检直接用这组问题 |

讲透问题和“每章一到两个大知识点”不冲突：大知识点是主题，讲透问题是它的验收标准。

## 二、两层结构和锚点图

- **主线**（约三分之二时长）：每节一个项目动作，配大知识点的一种状态，学员跟做，计入验收。
- **深入**（约三分之一时长）：每一条都回答主线引出的一个追问，只要求看懂，以自检为准。深入层只收“机制”类内容（见第三节）。
- **锚点图**：全章反复回到的同一张图，主线和深入都指着它讲。学员看到的是同一个东西在几种情况下的状态，而不是一串零散知识点。

## 2.5、外部佐证在章设计时选

讲透问题定下后、写节表之前，为每个问题找外部佐证（官方文章、研究、X 帖子），由项目 skill `external-sources` 批量调研，讲师挑选。章文件里留一张表：哪个问题、用哪条材料、什么形式（帖子引用卡、证据页大图、重画、现场打开原网页）。分镜按这张表留出页面和版式，不在课件做完后再找图塞进去。规则见 [external-sources.md](../../production/external-sources.md)。

## 三、先跑实验，再写页面

顺序：讲透问题 → 设计实验 → 同一流程跑 2–3 次 → 给观察到的现象分类 → 写页面。

| 稳定性 | 含义 | 怎样用 |
| --- | --- | --- |
| 机制 | 由源码、配置或我们自己的流程决定，每次都一样 | 可以上屏当结论，标来源 |
| 常见 | 两次以上运行都出现，但出不出现、什么形态取决于模型 | 上屏写成“经常会”，录制时按当次记录讲 |
| 单次 | 只在一次运行里见过 | 只放讲师提示，不上屏当结论 |

每章附一份可讲点清单，标出稳定性（第 2 章的见 [2026-10-21-ch02-teachable-points.md](2026-10-21-ch02-teachable-points.md)）。

## 四、项目连续，证据不连续

项目在章与章之间延续，但每章的教学依据不依赖上一章留下的过程文件和决定。

1. **文件写明身份**：课程材料和学员的过程记录开头加一行状态说明，例如“第 1 章首页 v0 的需求说明，不随后续迭代更新”。文件不删。
2. **每章一份起点快照 `chNN-start`**：上一章参考答案的产品代码，加课程材料，加本章任务卡；由脚本生成，跑过 build 后打 tag，录制前冻结。讲师演示和所有实验都从它开始；没跟上的学员从它开始；跟上的学员继续用自己的仓库。
3. **课件只引用两样东西**：当前的产品代码和本章任务卡，不引用上一章的过程记录，也不用跨章节号当钩子。
4. （可选，等第 1 章重录时一起做）course-starter 把课程材料统一移到一个目录（如 `course/`），根目录只留产品代码。course-starter 发布基线目前待发布，改结构的成本最低；代价是第 0、1 章课件里的路径要跟着改。

第 1 步里第 1 章的部分（1.4 让学员给 `PROMPT_V1.md` 加状态说明）和第 4 步，由第 1 章负责讲师决定。

## 五、只从上往下改

改动只按这个方向流动：讲透问题 → 外部佐证 → 节表（主线、深入、时长、验收）→ 分镜 → 课件。在课件层发现问题，先回到上层判断要不要改，不直接在页面上修。

## 六、决策记录写依据和重开条件

每条决定除了“决定了什么”，再写两句：

- **依据**：对应哪个讲透问题，或哪条原则；
- **重开条件**：什么情况下重新讨论（例如“试讲时学员答不出第 3 题”）。没有满足重开条件，就不重开。

## 七、一章做完的标准

录制前逐项核对：

1. 每个讲透问题都能从页面里找到答案；
2. 每一页都对应至少一个问题；
3. 上屏的结论都是机制类，并标了来源；
4. 时长在预算内；
5. 验收只写在章文件一处；
6. 讲师演示和实验都从冻结的起点快照开始。

## 八、第 2 章留下的经验

1. 先改页面后定主线，导致多轮返工。
2. 把单次运行的现象写成结论，每次重录都要改。
3. 项目和概念两条线各走各的，显得不直观。
4. 上一章的过程文件进入 context，引出不少支线（例如 `PROMPT_V1.md`）。
5. 跨章节号当钩子，学员记不住。
6. 验收写在多处，彼此不一致。
7. 画面上的数字太多，冲淡了结构本身。

## 待两位讲师确认

1. 是否把本做法定为全课统一做法，并入制作手册。
2. 第 1 章是否采用第四节的第 1、4 步。
3. 其他章从哪一章开始用（建议从还没开工或改动最少的章开始）。
