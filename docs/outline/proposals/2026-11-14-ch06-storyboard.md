### 写法原则

- 6.1 只给 SDD 定位，不把 4.1 的五层定义再讲一遍；重点是「先有规格再实现，而且当时不依赖某个框架」。
- 开场先认清 SDD 与 GSD 的关系，再上手；不要用安装步骤或命令清单当开场。
- 不能另起一套规划覆盖已有文档。已验收的行为和规格不能丢。GSD 只负责接手、建工作流和补验证，不能把工具流程当成新需求。
- 本章指定目标在 6.2 开头明确说成 CR-01，让后面的建流、验收和执行都有具体靶子；不要把目标留到实施时才出现。
- 6.3 先验收工作流是否符合预期，6.4 再用这条已验收流程把 CR-01 做完并做人工 UAT。框架完成状态不替代人的观察。
- 不为起伏安排情节，不预设 Agent 一定会写错测试或漏做提示。若第五章实现里已经有等价提示，如实记录「行为已有、现纳入正式契约」，用受控变异证明断言，不把新规则说成旧缺陷。
- 第五章的输入写成检查点，不以尚未交接的文件路径、测试名单、commit 或运行数字充当事实。5.5 不是进入本章的门禁。
- 6.5 与 5.5 必须分工：5.5 讲 Codex CLI 招数，并预留语音、`/app`、桌面版补充；6.5 讲 ChatGPT 应用本身。对学员提到课程里的可选编码界面时，使用「Codex App」，不要用「ChatGPT App」代指它。
- 未实测前不宣称 GSD 或 ChatGPT 应用功能已经走通；课上只演示核验过的能力，受套餐或地区限制的功能如实标明。

## 6.1 已有规格，为什么还要再接一套框架？

本节先定位，再上手。开场问句已定为「已有规格，为什么还要再接一套框架？」。

对 SDD 的回顾压成一页，只留三句话：第 4、5 章已经是规格驱动；先写清再改代码；规格在 `docs/specs/`，不跟着换工具重写。要让学员看见的是：先写下并批准要做成什么，再按规格实现和验收；而且那一轮是工具无关的做法，并不依赖某个社区框架。第 4 章交出五层规格，第 5 章按自建规格把 JSON Diff 做出来，这已经是规格驱动，不是「先写代码再补文档」。这里只做定位，不把 4.1 已经讲过的五层定义、每层写什么、怎样追踪，再讲一遍。说完立刻进入 GSD。

然后讲清什么是 GSD、应该怎么用。GSD 是社区里的一套 SDD 实现，用来接手已有项目和已批准的规格，组织调查、规划、执行和验证。它不是另一种需求，也不是用来推翻前面两章的成果。最硬的一句仍然是：**不能另起一套规划，覆盖已有文档。** 已验收的行为和规格不能丢；GSD 只负责接手和补验证，不能把工具流程、框架生成的任务列表或自动综合当成新需求。

边界讲清之后，再给案例和上手实操：版本与安装审查、一次接入，以及 GSD 怎样看待已有规格。四个 mapper 若在本节出现，只用来说明「调查可以分工，但生产代码只读、主 Agent 仍要抽查结论」；完整的、指向 CR-01 的工作流放到 6.2 再建。原生产代码与规格不得被初始化重写；已完成的 JSON Diff 不得被列成全套待开发任务。

须记录实际派发路径。顺序调查、回放或 generic fallback，不能计为 Sub-agent 委派通过。派发不可用时走降级路径，并标明实操未完成。未实测前，不把本节上手写成已经走通的操作保证。

## 6.2 怎样在当前仓库把 GSD 工作流建起来？

本节开场先问怎样在当前仓库把 GSD 工作流建起来，不把规则细节抢到第一句。目标仍是 CR-01，随后用一两页说清它改什么、不改什么，以及四个验收案例，再核对接手检查点并把工作流建起来。

本章指定目标仍是 CR-01。它不是改比较逻辑，也不是改对象或数组规则，而是在原规则之上增加一句对用户可见的说明，并写成可测试、可验收的正式约定：

- **原规则**：Before 或 After 输入非法时，标明错误侧，保留最后一次有效比较结果。第五章并未强制结果区域解释「这是旧结果」。
- **新增规则**：已有有效结果且任一输入非法时，图与差异摘要继续保留，但结果区域必须展示可见文本「上次有效结果（当前输入无效）」，错误区域仍分别标明 Before / After。仅当两侧恢复有效并完成重新比较，才移除提示并更新结果。首次输入就非法且没有历史结果时，只显示错误或空状态，不声称存在上次有效结果。
- **规格处理**：在原五层文档上追加 `REQ-CR01` 与下表 `AC-CR01-*`；Brief 记录变更原因，Plan / Tasks 追加本轮链接和状态。保留第五章提交与原验收，不把新增规则追溯认定为旧实现缺陷。
- **非目标**：不修改对象或数组差异算法、四种差异状态、计数口径、筛选语义、节点上限；不新增历史列表、自动保存、账号、网络上传或后端。这条提示与第 7 章快照四状态无关。

四个验收案例沿用内部大纲，不另编：

| 验收 | 输入与动作 | 期望与证据 |
| --- | --- | --- |
| `AC-CR01-1` | Before 为 `{"n":1}`、After 为 `{"n":2}`，成功比较后将 After 改为 `{` | 保留 `n` 的一处 changed 与原摘要；显示旧结果文本及 After 错误；组件/交互测试与可见截图 |

## 6.3 怎样判断这条 GSD 流程符合预期？

本节验收的是工作流，不是先把 CR-01 做完。开场问句已定为「怎样判断这条 GSD 流程符合预期？」。对照 6.2 留下的计划增加一页现场观察，只列检查点，不预写结果。

要让学员看见：框架标记完成、计划页变绿、任务被勾掉，都不能单独当成「这条流程符合预期」。必须有实际观察：它是不是还在用已有规格，而不是另起一套需求；验证方式是不是对得上要检查的行为；停止条件清不清楚；人能不能在关键点介入。原验收和 CR-01 的四个案例，都应该在流程里找得到去向。

本节同时讲清使用中要注意的问题：

1. **钻牛角尖。** 为了让某一步「看起来更完整」，在同一个问题上连续加细节、加指令、加新任务，却不再核对这一步是不是还服务于 CR-01 和已批准规格。发现自己在原地打转时，应停下来，回到目标和已有文档。
2. **XY problem。** 把「怎么让 GSD 做成某一步」当成目标，忘了真正要交付的产品行为：用户在输入非法时，要能看见「上次有效结果（当前输入无效）」。流程步骤是手段，不是验收对象。
3. **遇到问题应该怎么做。** 先复现，再缩小范围，再对照已有规格，然后决定是改流程还是改实现。不要连续加指令硬推，也不要在还没看懂失败原因时扩大修改范围。
4. **不要另起规划覆盖已有文档。** 这是全章边界，在验收流程时要再核对一次。
5. **还没核验映射就派发。** 主 Agent 不以「写了多少行」代替事实核验；没有实际委派，不能标记 Sub-agent 通过。
6. **先改实现再补永远能通过的测试。** 这会让后面的 6.4 失去「失败测试先行」的意义；在验收流程时就要挡住。
7. **把「流程跑完」当成「结果对了」。** 这是本节最要拆开的一对判断，也为 6.4 的 UAT 做铺垫。

内部大纲里「常见错误与风险」仍可对照，例如不要安装 `@latest`、不要把 verify-work 当成单元测试执行器、不要用覆盖率代替行为证据。派发或框架不可用时，走标明来源的降级路径，并分别标记未完成。

**本节判断**：计划已经生成、框架也显示完成，这条 GSD 流程是不是就可以用来改产品了？还不一定。要先用实际观察确认：它接住了已有规格，指向了 CR-01，并且知道怎样证明自己有没有做成。

## 6.4 用已验收的流程，怎样把 CR-01 做完并让人认可？

本节用 6.3 已经验收过的流程，把 CR-01 做完，再用人实际操作收口。

先把失败测试先行做透：为 CR-01 写下组件或交互测试，确认它因缺少旧结果提示而以正确原因失败，再做最小提示状态与文本，让测试通过；同时补原验收中有证据支持的缺口，并跑恢复路径和旧路径回归。人要检查：断言是否独立于实现、失败是否来自规则差距、修复是否越界。不能靠跳过测试、改期望或吞异常制造绿色。生产修改保持串行。

若第五章生成结果恰好已满足 CR-01，如实记录「行为已有、现纳入正式契约」：补齐测试后，在隔离的本地检查点受控移除提示，证明断言会失败，再恢复。不能故意破坏原版本，并伪装成原始缺陷。

算法、原统计与筛选不应回归。学员要能解释测试目标与实际 diff，不要求背测试框架 API。

然后做一次人工 UAT。自动检查、任务 Summary 和框架「已完成」只能说明约定的检查跑过了。用户是否认可，要人实际操作并报告观察：沿一条「有效比较 → After 非法 → 两侧非法 → 仅一侧恢复 → 全部恢复」的路径，查看旧结果提示、错误侧、键盘、窄屏和必要的控制台或网络现象。目标 E2E 必须真正操作功能，视觉结果经人工复核。发现问题先核对诊断和修复计划，再执行与复验。

核对 `REQ-CR01`、四个 `AC-CR01-*`、计划、Summary、UAT 与 diff，汇总适用的门禁。版本、源规格、派发及执行证据要可追溯。原单 JSON 主路径无回归。说明下一次在已有项目里变更时从哪里进入，以及快捷路径的适用边界；不把第 7 章的仓库或 Harness 预支到这里。

本节结尾要带走的一句是：**测试全绿，只证明约定的检查过了，不等于用户已经认可。** 能指出一个具体断言支持哪条需求，也能指出哪些体验仍需人工观察。不把覆盖率、测试数量或一句经典名言当成正确性证明。

**本节判断**：测试都绿了，是不是就等于 CR-01 已经被用户认可、可以交付？不是。绿色只覆盖约定去检查的那些点；用户认可还要看实际操作过的部分，以及明确未覆盖的项。

## 6.5 ChatGPT app 有哪些 trick 值得带走？

本节是工程经验分享，讲 ChatGPT 应用本身，包括网页、桌面和手机。先有趣，再实用，看懂即可，不新增练习，不改 JSON Diff，也不作为进入第 7 章的门禁。

必须和 5.5 分工。5.5 分享的是 Codex CLI 招数（`/side`、`/fork`、按画面改界面，以及 Remotion 等官方插件），并预留语音、`/app`、桌面版的补充。课程术语里，可选的编码图形界面叫 **Codex App**，不要用「ChatGPT App」代指它。本节不重复 5.5 已讲或已预留的 CLI 命令，也不把 Codex App 的操作演示再做一遍。

部分功能受套餐和地区限制，课上只演示已经按录制版本核验过的能力；未核验的只留官方说明，不现场猜测，也不编造操作细节。下列技巧供讨论和备课时挑选，确认后再进入逐页。

1. **用「项目」把文件、指令和对话放在一起。** 需要和其他聊天隔离时，使用「仅项目记忆」，避免上下文串到别的对话里。官方说明：[ChatGPT 中的项目](https://help.openai.com/zh-hans-cn/articles/10169521-projects-in-chatgpt)。
2. **从一条回复「在新对话中分支」。** 想试另一条路时，把这条回复分出去，主线不被带跑。这正好呼应 6.3 的钻牛角尖：不必在原对话里连续加指令硬推。
3. **桌面版用 Option+Space 打开 Chat Bar，可以直接截图提问。** 官方说明：[How to launch the Chat Bar](https://help.openai.com/en/articles/9295241-how-to-launch-the-chat-bar)。实际快捷键和入口以录制版本为准。
4. **分清 Chat、Work 和 Codex。** 问答用 Chat，长任务和成品用 Work，写代码用 Codex。只有桌面版 Work 才能用本地文件；云端和本机不要选错。官方说明：[ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)。对学员提到课程里的可选编码界面时，仍使用「Codex App」这一名称。
5. **定时任务。** 可以按时间运行，也可以按 Gmail、Slack、GitHub 等事件运行；但在项目里创建的任务，访问不到该项目里的文件。这是很好的课堂「坑」，用来说明入口选对了、上下文却没带上。官方说明：[ChatGPT 中的定时任务](https://help.openai.com/zh-hans-cn/articles/10291617-scheduled-tasks-in-chatgpt)。
6. **临时对话。** 默认不进入历史；处于临时状态时，对话不用于改进模型。开始前还可以选择不带个性化。适合演示「这次只想问完就走，不要留下，也不要带进习惯设定」。官方说明：[Temporary Chat](https://help.openai.com/en/articles/8914046-temporary-chat-in-chatgpt)。
7. **手机里的 Remote 页可以接着看桌面上的 Codex 任务**，它和云端任务不是同一条通路。课上只指出「看的是哪一条任务通路」，不扩展成远程操控教程。具体界面以录制版本核验为准。

第 7 章从独立仓库冷启动，不继承本仓库的 `.planning/`、GSD 地图或会话。方法可以带走，项目事实必须在新仓库重新核验。

**本节判断**：不设学员必做判断。看懂这些招数各自解决什么问题、有什么边界即可。
