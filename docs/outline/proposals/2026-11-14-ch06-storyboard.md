## 本章故事线

**一句话主线**：用 GSD 接手第五章已经验收的 JSON Diff，而不是从零再建一套；先把已有规格接进来，再补上可验证的测试闭环，最后交出人实际操作过的成果。

第五章已经交出一份通过本章验收的 JSON Diff，以及作为需求依据的五层规格。现在不是重新做一遍功能，也不是换一套文档再规划一次。先要讲清：GSD 能接手的是已有项目和已批准的规格，不能推翻的是这些已经写下、已经验收的内容。边界立住以后，再真正接入框架、核验映射。

## 6.1 已有规格和功能都在，GSD 该另起一套规划吗？

本节先讲清边界，再上手。

GSD 能接手的是已有项目、已验收的 JSON Diff，以及作为需求依据的五层规格。它不能推翻的是这些已经写下、已经验收的内容。最硬的一句是：**不能另起一套规划，覆盖已有文档。** 已验收的行为和规格不能丢；GSD 只负责接手和补验证，不能把工具流程、框架生成的任务列表或 onboard 的自动综合当成新需求。

边界讲清之后，再做版本与安装审查、接入和完整 mapper。四个 mapper 调查技术、结构、质量和风险，生产代码只读，文档分区写入；主 Agent 抽查结论，不以「写了多少行」代替事实核验。首次导入规格时，人要审批实际输入和目标文件，核对原需求编号与映射。原生产代码与规格不得被初始化重写；已完成的 JSON Diff 不得被列成全套待开发任务。

本节输入是第五章的交接检查点，而不是尚未存在的具体文件清单：可定位的本地实现提交、仍作为需求依据的五层规格、原验收状态、已有测试与已知缺口，以及能够解释的关键路径。5.5 只看不跟做，不改实现，也不是进入本节的门禁；缺 5.5 页面不阻碍 6.1 开始设计，但缺第五章可交接的实现检查点，就不能把映射核验写成已经发生的事实。

须记录实际派发路径。顺序调查、回放或 generic fallback，不能计为 Sub-agent 委派通过。派发不可用时走降级路径，并标明实操未完成。

**本节判断**：框架已经初始化，是不是就可以按它生成的规划往下做？不能。还要核对：原规格是否仍在、映射是否抽查过、已验收行为有没有被写成待开发。

## 6.2 原验收都有验证去向了吗？

本节先集中讲清验证方式怎么选：纯逻辑用单元测试，界面状态用组件或交互测试，关键恢复路径用 E2E，视觉体验仍要人看。这是测试类型的主要讲解位置；前面各章若已按场景做过必要解释，这里收成一张可带走的选择图，不重讲五层定义。

然后对照原验收、第五章留下的测试和已知缺口，看每条原验收是否还有验证去向。不是在这里第一次发明需求，而是问：已经批准要保留上次有效结果，现有检查有没有覆盖「用户能看见这是旧结果」？第五章并未强制结果区域解释「这是旧结果」。缺口被看见之后，再由人批准 CR-01。

CR-01 不是改比较逻辑，也不是改对象或数组规则。它是在原规则之上增加一句对用户可见的说明，并写成可测试、可验收的正式约定：

- **原规则**：Before 或 After 输入非法时，标明错误侧，保留最后一次有效比较结果。
- **新增规则**：已有有效结果且任一输入非法时，图与差异摘要继续保留，但结果区域必须展示可见文本「上次有效结果（当前输入无效）」，错误区域仍分别标明 Before / After。仅当两侧恢复有效并完成重新比较，才移除提示并更新结果。首次输入就非法且没有历史结果时，只显示错误或空状态，不声称存在上次有效结果。
- **规格处理**：在原五层文档上追加 `REQ-CR01` 与下表 `AC-CR01-*`；Brief 记录变更原因，Plan / Tasks 追加本轮链接和状态。保留第五章提交与原验收，不把新增规则追溯认定为旧实现缺陷。
- **非目标**：不修改对象或数组差异算法、四种差异状态、计数口径、筛选语义、节点上限；不新增历史列表、自动保存、账号、网络上传或后端。

四个验收案例沿用内部大纲，不另编：

| 验收 | 输入与动作 | 期望与证据 |
| --- | --- | --- |
| `AC-CR01-1` | Before 为 `{"n":1}`、After 为 `{"n":2}`，成功比较后将 After 改为 `{` | 保留 `n` 的一处 changed 与原摘要；显示旧结果文本及 After 错误；组件/交互测试与可见截图 |
| `AC-CR01-2` | 在上一状态把 Before 也改为 `{`，随后只恢复 After 为 `{"n":2}` | 两侧非法时分别显示错误；仅 After 恢复后仍标 Before 错误，旧结果提示不消失，旧比较不变 |
| `AC-CR01-3` | 接着把 Before 恢复为 `{"n":2}`，等待比较完成 | 两侧有效，移除旧结果提示，摘要变为零差异；一条浏览器回归路径覆盖此恢复过程 |
| `AC-CR01-4` | 全新页面还没有成功比较，直接输入非法 JSON | 错误/空状态正确，不显示不存在的历史结果与旧结果提示 |

计划应串行、范围清楚，并标出允许修改的范围、断言和停止条件。原对象 / 数组 / 删除 / 错误 / 筛选 / 节点上限 / 隐私等验收仍要有验证去向。不按覆盖率或测试数量验收，不测试私有状态或 CSS 类名。本节还没有生产实现修改。

对照「现有测试」时，只用第五章交接来的测试与缺口记录；在实跑交接之前，故事线只保留这套对照方法，不预写缺口清单。

**本节判断**：原功能能跑，是不是就不必再补验证、也不必把「旧结果提示」写成正式约定？不是。能跑只说明已经有一份实现；还没有验证去向的行为，不能当成已经验收。是否批准 CR-01，由人决定。

## 6.3 怎样先证明这条规则现在还没被满足？

本节把失败测试先行做透，不把重心提前放到「把提示做出来」。

按批准的计划执行：先为 CR-01 写下组件或交互测试，确认它因缺少旧结果提示而以正确原因失败，再做最小提示状态与文本，让测试通过；同时补原验收中有证据支持的缺口，并跑恢复路径和旧路径回归。人要检查：断言是否独立于实现、失败是否来自规则差距、修复是否越界。不能靠跳过测试、改期望或吞异常制造绿色。生产修改保持串行。

若第五章生成结果恰好已满足 CR-01，如实记录「行为已有、现纳入正式契约」：补齐测试后，在隔离的本地检查点受控移除提示，证明断言会失败，再恢复。不能故意破坏原版本，并伪装成原始缺陷。

算法、原统计与筛选不应回归。学员要能解释测试目标与实际 diff，不要求背测试框架 API。

**本节判断**：先改实现、再补一条总能通过的测试，能不能算验证？不能。先要看到失败是因为规则还没被满足；恢复或实现之后再通过，这次绿色才有意义。

## 6.4 检查都过了，怎样才算用户认可？

本节收口到 UAT，而不是再展开一轮实现。

自动检查、任务 Summary 和框架「已完成」只能说明约定的检查跑过了。用户是否认可，要人实际操作并报告观察：沿一条「有效比较 → After 非法 → 两侧非法 → 仅一侧恢复 → 全部恢复」的路径，查看旧结果提示、错误侧、键盘、窄屏和必要的控制台或网络现象。目标 E2E 必须真正操作功能，视觉结果经人工复核。发现问题先核对诊断和修复计划，再执行与复验。

核对 `REQ-CR01`、四个 `AC-CR01-*`、计划、Summary、UAT 与 diff，汇总适用的门禁。版本、源规格、派发及执行证据要可追溯。原单 JSON 主路径无回归。说明下一次在已有项目里变更时从哪里进入，以及快捷路径的适用边界；不把第 7 章的仓库或 Harness 预支到这里。

**本节判断**：框架标记完成、测试也全绿，能不能直接当作可以交付？不能。还要人实际操作过，并且这些观察能对上批准的验收。

## 6.5 测试全绿，到底证明了什么？

本节不再安装框架、不重跑全套测试、不重讲 6.2 的分类图。把 6.3 的失败/通过记录和 6.4 的 UAT 并排放，追问：这条证据支持哪条结论，还缺什么。

要带走的一句是：**测试全绿，只证明约定的检查过了，不等于用户已经认可。** 能指出一个具体断言支持哪条需求，也能指出哪些体验仍需人工观察。不把覆盖率、测试数量或一句经典名言当成正确性证明。已有 CR-01 行为时，沿用受控变异证据，不伪造旧缺陷。

第 7 章从独立仓库冷启动，不继承本仓库的 `.planning/`、GSD 地图或会话。方法可以带走，项目事实必须在新仓库重新核验。
