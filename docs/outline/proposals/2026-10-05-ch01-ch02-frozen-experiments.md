## 建议：同一项目积累产物，机制实验使用独立副本

讲师主线保持连续：原始 Starter → 欢迎语修改 → 首页需求决定 → 首页 v0 → 反馈核对 → 内容迭代 → Review 与提交 → 发布。

提前完成并验收这条主线，保存真实运行材料，在关键位置冻结代码、决定和必要记录。后续小节读取前一阶段实际产物。讲稿中的文件、数字和结论依据冻结材料整理；若替换上游快照，须重新核对受影响的下游材料。

权限、请求组成、恢复、压缩、回退和重构对照从相关检查点另建实验副本。实验完成后回到主线，主线不吸收实验造成的撤回或行为变更。学员可在独立目录重做，不需要为了每个演示覆盖自己的项目。

固定三类东西：

1. **起点和条件**：源 commit、文件、依赖锁、工具版本、配置、任务、人工作答、必要进程和会话前置。会话实验不能只发代码 ZIP。
2. **验收对象**：例如改动范围、Tab 焦点、历史中的文字、压缩前后可见输入；预先写清允许不同的输出与继续条件。
3. **一份真实参考记录**：用于录播讲解、模型不可用时观察。重跑产生新记录，不能用参考记录冒充重跑结果。

模型输出、工具选择、请求次数、缓存命中、摘要遗漏和远端服务状态不因冻结代码而固定。涉及这些因素的实验，稳定性应来自明确的观察问题与参考记录。

## 与旧约定的关系

- 冻结真实运行、提供检查点和单独机制实验与当前主线兼容。旧设计已有这些入口，主要需要补齐材料与制作方式。
- 原提案决定 7 明确“不准备坏 diff、错误 base 分支”。若增加这两种固定故障实验，即使标注为教学材料，也需要先讨论修改该决定；本稿没有授权实施。
- 原有“不把准备好的缺陷包装成现场事故”继续适用。自然失败、人工构造、脚本重放与真实回放各自说明来源。
- 1.1 大纲要求一次修正记录，而排练实际一次成功：建议讨论将验收写清为“实际问题的修正记录，或独立标注的示例修正练习”，避免学员为凑记录制造失败。
- 2.1 课件部分记录仍写隔离步骤待测，但已有提案实测与启动脚本；制作时应统一状态，不能简单认定整个 setup 从未完成或已全部完成。

## 学员路径的取舍

**建议默认保留个人项目连续推进。** 讲师视频使用同一条冻结历史；机制实验提供统一副本和参考记录。个人项目用共同验收标准判断，代码不要求与讲师一致。

若更重视第二章跟做的一致性，可让学员在第二章先进入统一 v0，完成一次反馈、修改与 Review，再迁移方法到自己的主页。这会提高现象一致性，也增加一次项目切换与可能重复的工作，并改变当前“默认在自己的同一仓库连续做”的路径。需要讲师选择，不能默认实施。

## 制作优先顺序与通过条件（建议）

1. 先串起真实 v0 → 内容迭代 → Review → v1 的材料，确保三条反馈与决定前后一致。
2. 优先整理压缩、会话/文件/进程、回退、公开历史和 A/B 重构实验；权限与请求对照同步补齐冻结环境说明。
3. 每个实验只需一份简短说明：来源与类型、起点、setup、操作、观察对象、允许差异、结束后如何继续、参考记录、已测环境。
4. 准备者从新目录重建，再由另一位讲师仅按材料复现，记录实际结果与缺失步骤。涉及模型的实验允许输出变化，但观察问题必须仍能回答。
5. 核对材料发布入口。目前第二章 `materials/` 不进 Pages；不能在课上只说“配套材料里有”，却不给实际可访问的入口。

实验复现检查与课件的 `make check` 分开记录。后者检查课件、构建与链接，不证明真实 Codex 操作、模型服务或 Pages 部署可复现。本稿未改变大纲、课件或项目快照。

## 2026-10-05 后续讨论：知识实验主动独立于项目主线

本节记录讲师进一步表达的设计倾向，具体实施尚未确认；前文“主要补齐现有材料”的建议需要据此重新评估。

### 讲师表达的倾向

- 知识内容可以主动构造输入做演示，尤其是与主体 demo 关联较弱或不易自然复现的机制。
- 主体 demo 应更小，减少承担知识讲解的任务，保留项目推进与交付所需的过程。
- 当前先设计 PPT，希望实验能够支持预定的知识讲解，减少因某次项目运行没有出现现象而大幅改写讲稿和课件。
- 优先利用独立模型配置形成干净的复现环境；考虑用 Docker 固定 Codex 版本，支持版本间系统指令等对照实验。
- 用户以“compile”和 Memory 举例；“compile”暂按前文 compact 理解，尚未确认。Memory 在此作为方法适用范围的例子，不据此将它提前加入第一、二章。

### 建议据此调整的设计

主线交付与知识实验分别设计输入和验收，在讲述顺序上衔接。知识实验可以借用主页中的文件或任务作背景，但无须继承主线完整会话或等待主线发生特定事故。学员做完实验后可以回到自己的项目，不要求把实验产物合入首页。

构造输入、环境和故障前置是候选教学手段；须说明哪些由教师设置。关于产品真实行为的结论仍由真实执行结果支持。固定返回或人工摘要可解释机制，但不能作为真实 Codex 行为的实测证据。主线不准备坏 diff、错误 base 的原约定暂不变；是否允许新增这类独立知识实验另行确认。

建议将制作顺序调整为：知识问题与 PPT 结构草稿 → 定义可观察的实验结果 → 最小可行实验预检 → 冻结环境与素材 → 完成具体画面和口播。先设计 PPT 可以继续，但“必定遗漏某句话”等未经验证的具体结果不要先写成既定事实。如果多次真实实验不支持所讲结论，应调整结论；如果只是主线没有提供合适条件，可以构造独立实验输入。

Docker 作为可选实现方案待验证，不默认成为所有学员的安装前置。候选环境需要记录镜像、Codex 版本、配置、模型/provider、输入与状态初始化方式。固定客户端环境不等于固定远端模型输出。会话、Memory 等涉及持久状态的实验还需分别定义空白起点、构造步骤与实验间隔离方式，具体功能支持与行为另行核验。

可复现性按实验分别判断：固定源码对比要求相同差异；固定本地状态操作要求相同状态变化；真实模型实验要求操作可重做、目标现象和结论在规定条件下有证据支持，文字无需逐字一致。对仍不能稳定出现的现象，保留真实记录供观察，并明确重跑边界。
