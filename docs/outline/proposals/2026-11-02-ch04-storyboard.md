## 本章故事线

**一句话主线**：接手 JSON Crack，把“增加 JSON 对比并高亮不同”这句需求，逐步变成经人确认、有验收样例、能分步实施的规格基线，再交给第 5 章实现。

学员已经用过结构化 Prompt，也体验过边看结果边补要求。这次换到一个陌生的已有项目：先看清 JSON Crack 现在能做什么，再读需求笔记、调查代码。调查会带出几个具体问题：两份 JSON 只是键的顺序不同，算不算变化？数组插入一个元素，后面的元素怎样比较？图里已经删掉的字段还显示在哪里？这些问题需要人作决定，不能靠增加指令的字数来自动解决。

规则定下来以后，还要用具体输入核算预期结果，避免各自理解一套。最后再结合源码选择改法，拆出能检查、能保留本地检查点的任务。4.1–4.5 连续完成这件事；4.6 从需求读取延伸到日常工具使用：飞书主案例用官方 CLI，AntV、高德和其他短演示仍用 MCP。

### 要讲透的核心判断

本章的主知识点是 **SDD（Spec-Driven Development，规格驱动开发）**：先确定可观察的行为与验收依据，再据此组织实现。前几章已经练习澄清和完成标准，本章将这些做法深化为可维护、可追踪的项目资产。MCP 是获取与处理外部资料的实践线，在 4.2 最小使用，在 4.6 展开。

“Prompt 写得再长，为什么也替代不了 Spec？”要落在一个准确的判断上：**增加字数，并不会自动完成事实核验、规则批准、验收设计和实施拆分。** 一份长 Prompt 如果已经承担了这些职责，也可以当规格用，但课程不推荐这样做：这类工作往往是长 Prompt 加长上下文，经过多轮补充和执行后上下文可能被压缩，写在 Prompt 里的约束条件很容易丢失或被冲淡，事后也不容易发现。课程采用五份文档，是为了把这些判断分别写进可查阅、按版本维护的文件；学员应能说明每份文档解决了什么问题。

版本化文档让当前约定及其变更可以被查阅。换会话后仍需明确让 Agent 读取适用版本，不能把“存进 Git”讲成自动加载或永不遗漏。

## 4.5 都定清楚了，为什么不一次写完？

本节拿着 Spec 和 Acceptance 回到源码。开头顺着学员的追问：既然规则、案例都齐了，把它们拼成一个长请求，为什么还要写 Plan 和 Tasks？先展示这次改动同时涉及差异计算、图数据、输入状态和筛选摘要，让学员看到需要审查的范围。

先比较两种与当前任务有关的改法：在 UI 中直接比较输入并生成展示；或者先形成独立差异模型，再映射到现有图数据。结合 4.2 找到的调用关系，核对它们分别会改动哪里、怎样验证、是否重复逻辑。当前课程方向是将差异模型与图映射分开；最终影响文件、可复用入口与验证命令，需要有源码依据后写进 `PLAN.md`。

Plan 记录所选方案、取舍、影响范围、风险和回退安排。它接受 Spec 的行为要求，同时允许实现手段调整。若只是换一个图数据适配位置，更新 Plan 与相关任务；若需要改变数组匹配行为，则回到 Spec，由人决定，并同步验收。

再按依赖拆出四个任务。下表的 `TASK-*` 编号用于本稿说明，正式编号随规格资产确定。

| 任务 | 实施范围 | 主要验证对象 |
| --- | --- | --- |
| `TASK-01` 差异模型 | 输入对应关系、直接状态与派生标记、计数 | 固定 JSON 输入与期望差异，先验证纯逻辑 |
| `TASK-02` 合并图映射 | 将模型映射到现有图，保留 removed 节点与必要祖先 | 图数据能够表达既定状态及筛选上下文 |
| `TASK-03` 双输入与错误状态 | 接入 Before/After、单侧错误与最后一次有效结果 | 正常比较、错误及恢复路径 |
| `TASK-04` 摘要、筛选与验收 | 接入摘要、只看变化与非纯颜色表达，完成整体验收 | 所有当前验收项与原有单输入路径的回归 |

任务按顺序验证，后续任务承接前一步已确认的结果。每项还要写明输入、允许范围、依赖、对应 `REQ-*` 与 `AC-*`、验证方法及完成定义。执行时让 Agent 读取当前任务、相关规则和案例，同时保留全局约束与非目标，避免把按需读取做成遗漏约束。

用同一条“忽略对象键顺序”的需求串一次追踪：Spec 写规则，Acceptance 固定换序样例和零差异期望，差异模型任务引用它；整体验收再确认 UI 的计数与展示遵守同一规则。改动某条需求时，也能沿对应关系找到要复核的案例和任务。`REQ-*`、`AC-*`、`TASK-*` 的完整对应表在 `TASKS.md` 集中维护，各文档通过编号引用规则和案例正文。

小任务让一次改动的检查与本地回退更具体，仍需对照关联验收判断是否做完。这里不预设“一次性实现一定失败”，也不以模型碰巧漏项作为本节转折。学员看到的是：任务范围缩小后，人可以更清楚地核对改动、验证结果并保留检查点。

**学员判断**：差异模型的几个案例通过后，能否把 JSON Diff 整个功能标记完成？讲师解释：这只支持当前模型任务的相应结论；图映射、界面、错误恢复及整体验收还有各自的任务和验证去向。

**留下与转场**：`PLAN.md`、`TASKS.md` 与完整追踪关系。检查规格及新增素材，单独提交规格基线，交给第 5 章按任务实现；本章保持生产代码不变。

回到章首的问题，沿着已经完成的工作回答：原文经过调查形成 Brief，歧义经过人决定形成 Spec，规则经过核算形成 Acceptance，方案和工作范围落实为 Plan 与 Tasks。今后仍通过 Prompt 发起工作，但实现依据是这些可维护的约定。

## 4.6 工程经验：飞书 MCP 使用介绍与常用 MCP 推荐

本节以“除了读一份需求，MCP 日常还能怎么帮我们干活？”开场；节标题保留，开场说明 MCP 是把工具交给 Agent 的一种方式，飞书官方目前给个人用户的推荐是官方 CLI。承接 4.2 的最小读取（当时用 MCP），飞书主案例改走官方 CLI，其他短演示仍用 MCP。JSON Diff 规格基线在 4.5 已经形成；本节使用独立的合成教学材料，学员以看懂工具用途和结果核对为主。连贯内容以[4.6 STORYBOARD](../../../courseware/ch04/lessons/06-mcp-practice/STORYBOARD.md)为准（2026-11-11 讲师确认改用官方 CLI）。

### 飞书主案例：把一组资料整理成可核对的结果

沿用已有设计中的“开发者分享会”：活动方案、评审补充材料、几条教学评论和一张报名意向普通表格。先展示要处理的资料，再让 Agent 搜索对应云文档，读取正文与评论，整理已定安排、建议和待决定事项。讲师抽查一条原文和一条评论，说明归纳结果如何回到来源。

核对整理内容后，由讲师明确指定新建整理稿的位置和范围，创建“评审结论与待办草稿”，再打开实际文档检查。随后给出一个明确决定，例如“答疑环节确定为 20 分钟”，只修改整理稿中的相关安排与待办，并比较实际变化。

详细介绍围绕这一完整案例展开：如何找到正确文档、区分正文与评论、理解读取和写入所需的权限、指定创建与更新目标，以及怎样核对实际结果。4.2 已做过的最小连接只作回指；接入配置随录制版本核实，凭证不进入公开材料。所有演示写入仅针对讲师准备的教学文档，不向群聊发送消息。

### AntV 短案例：复用同一份表格数据

从刚才方案正文的普通表格提取三个主题和报名意向，先核对工具输入，再交给 AntV Chart MCP 生成柱状图。打开结果检查类别、数值、中文标签和标题是否对应源表。数据明确标为教学数据。

这里增加的是“工具如何接续”：一个工具取得资料，Agent 整理出输入，另一个工具形成可见结果。图表能否生成、中文能否正确显示、数据会经过哪里，以所选实现和实际运行核验。本节不扩展为多维表格教程，也不增加自动回写图表的环节。

### 高德短案例：把出行约束落实到真实地点与路线

沿用“从杭州东站出发的半日安排”：查询地点和路线，区分到景点的交通段与景点之间的步行段，再检查地图结果。讲师分别核对文字行程、实际地图与 APP 打开情况，按实际完成范围讲解。地点选择和返回内容由真实查询决定，不预写成功结果。

**学员判断**：Agent 回复“整理稿已创建”，接下来应检查什么？讲师解释：打开实际文档，核对位置、标题、正文、来源与待决定事项；定点更新后再检查实际变化。对话说明和可见结果各有核对对象。

**留下与衔接**：带来源与结果核对的演示材料，以及附使用条件的 MCP 清单。学员可以按需选做，JSON Diff 后续实施继续从 4.5 的规格基线进入。
