## 二、故事线

**一句话**：把第 1 章的首页 v0 补完整并发布上线；一路打开 Codex 实际发出的请求，看清 context 长什么样、怎么变。

**这一章在做什么**：先用 claude-tap 启动 Codex，只发一句话，就能看到请求里远不止这句话。接着把自己的项目经历加进首页：对话多了，context 跟着变长；`/clear` 和 compact 之后还剩什么，也在记录里看得到。Codex 交回改动时，回到记录里看它是根据哪些内容改的，再决定要不要接受；回退靠 git，不靠对话。发布时，在记录里看 Codex 怎样调用 `gh`。最后，Codex 说“只是重构”，而 context 里没有测试，它证明不了行为没变。

**学员获得**：

- 一个公开 URL，以及一份评审过、可回退的提交。
- 能从一份请求记录里指出不是自己写的内容，并说出缺了会怎样。
- 能根据 context 的状态选择继续、`/clear`、compact 或新建会话，并说出理由。
- 习惯在接受改动前问“它当时看到了什么”。

## 三、逐节要点

只写每节的问题、证据和归纳，逐页分镜在讲师确认本文后再写。

### 2.1 只发一句话，context 里有什么

- **开场**：一页说清本章目标，不用漫画和熟人反馈。开发服务器重启保留为操作，2.2 再解释。
- **启动**：PPT 一页给出 claude-tap 的启动方式，录屏演示；说明它是本地代理，会经手 API 密钥，只看得到经过代理的内容。
- **证据**：
  1. 只发一句与项目无关的话，看请求的组成：系统指令、工具定义、Skills 列表、环境信息、权限说明，最后才是自己那句话。
  2. 再发一个设计过的、与项目相关的只读问题（沿用“Codex 怎么知道 1.4 的决定”这个钩子），看工具调用和返回怎样进入 context。

  两个 Prompt 都要事先设计，保证稳定触发要展示的内容。
- **对比**：同一句话在不同权限下发出，权限说明不同；隔离环境下 Skills 列表不同。
- **归纳**：这些加在一起就是 context。引用一份官方对 context 的解释，不自造定义；具体引用哪一份，写分镜时选定，录制前核对。Skills 只指出“列在这里”，不展开，留到第 3 章。
- **待评审**：隔离 HOME 与 `CODEX_HOME` 的对比（原 p15、p15-home）按“没有它，本节问题还答不答得上来”判断，答得上来就移到配套页。

### 2.2 context 怎么变长，怎么清

- **项目动作**：由人提供项目经历，Codex 只负责呈现，不得编造；三种视口、键盘与 `npm run build` 验证（三种视口从原 2.1 移来，只作验证步骤）。
- **证据**：
  - 相邻两次请求：前一轮的内容被重发。
  - token 与缓存：重发的代价。
  - p24：失败的调用留在 context 里，见第四节。
  - `/clear`：context 回到初始状态。
  - compact：用本节的真实长任务对比压缩前后，看哪些具体证据被换成了摘要。
- **判断**：继续、`/clear`、compact 后继续，还是新建会话加交接？理由要引用 context 的具体状态。
- **归纳**：三种状态（模型不保存状态，会话由 Harness 保存并重发，文件与进程独立存在）；恢复对话不等于恢复文件或服务。
- **待评审**：Codex 版本与模型指令对比（原 p25、p26）按同一标准判断是否移到配套页。

### 2.3 它是根据什么改的

- **项目动作**：先看范围再看内容，对照本轮目标决定接受、缩小或拒绝；commit 是让拒绝变便宜的检查点，未提交用 `git restore`，已提交用 `git revert`。
- **context 视角**：打开同一份记录，看 Codex 读了哪些文件、依据什么改。范围扩大时，常能在 context 里找到原因：多读了无关内容，或缺了本轮目标。
- **衔接**：`/clear` 和 compact 改的是对话，不会撤销文件改动；回退靠 git，呼应 2.2 的三种状态。承接 2.2 p24 的结论“判断要看这一轮的证据”。

### 2.4 发布，并看 Codex 怎样调用 `gh`

- **项目动作**：保留 10-12 确认的流程，即先建个人空远端、检查 `HEAD` 的完整历史、`git push -u origin HEAD`。推送由人执行；Pages 来源由 Codex 用 `gh` 设置，人批准每条命令。三项发布检查不变。
- **context 视角**：在请求记录里指出一次 `gh` 调用的命令、批准和返回，作为“一次清楚的 CLI 调用”的示范。
- **隐私**：推送前检查照常做；“请求里的文件内容也发给了模型”最多口播一句，不单独成页。

### 2.5 context 里没有测试

- **项目动作**：五张分拣卡不变。第 ⑤ 张“让卡片可聚焦”原来写成“看似回应 2.1 第 2 条反馈”，反馈卡去掉后改为就地复述第 1 章“项目卡不跳转”的决定（第一节第 14 条）。
- **context 视角**：Codex 判断“行为没变”只能依据 context 里看得到的东西；本项目没有测试，context 里就没有行为证据。收尾引出后面的规格与测试章节：把“行为”写成能放进 context 的东西。

## 四、2.2 p24 的改写

**现状**：p24 是一页三步，标“看懂”。同一句只读提问跑两次：第一次 4 次请求，中途调用了不存在的 `read_file`，报错后改用 `cat`；第二次 2 次请求，直接读到了文件。结论是“每轮都看这一轮的证据”。素材来自 2026-10-02 的一次运行（Codex 0.160.0 + MiniMax）。

**为什么不算和 0.1 重复**：0.1 p05a 用鹈鹕杯看同一个 Prompt 的**产物**会变，p24 看**过程**会变，角度不同。

**改写**：

- 开头一句回指 0.1：“0.1 看到结果会变，这里看到过程也会变”，不再重讲随机性本身。
- 重点放在 context 上：失败的 `read_file` 调用和报错返回都留在 context 里，之后每次请求都会重发。这是“context 怎样变长、怎样混进无用信息”的例子，在同一份请求记录里指给学员看。
- 原结论“判断要看这一轮的证据”移到 2.3，作为看 diff 的铺垫。
