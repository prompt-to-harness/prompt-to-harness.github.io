## 一、不变与改变

**不变**：本章目标与定位（普通 Vibe Coding 做记忆翻牌 → Game Studio Plugin 做“60 秒躲避与收集” → 需求债务引出 SDD）；七个小节的顺序；3.7 工程经验；交付物与退出门禁；全章暂估 120 分钟（内部大纲现值）。

**改变**：

1. **3.2 的转折改为“这条规则是谁定的？”，不依赖 AI 出错**。记忆翻牌是常见 benchmark 题（2026-09-03 讨论中已提到），模型大概率一次写对。两张牌不匹配时，游戏通常会让它们停留约一秒，在这段时间里点第三张是正常玩法，不需要特别快。之后发生什么取决于 Codex 的实现：加锁（点了没反应）、先翻回再翻开第三张，或三张同时朝上。前两种都合理，但规则是 AI 替你定的；第三种才是缺陷。无论哪种，转折都成立。**预检后**：4 轮都选了加锁，3 轮把它写在计划里但没有当作问题问人（其中一轮列在“我自行定的默认”下），1 轮计划里没写；人回复的是“问题都按你推荐的做”。3.2 直接指着计划原文问：这条规则你确认过吗？
2. **接受 Phaser 作为第二个游戏的技术栈**。Game Studio 对 2D 游戏默认 Phaser + TypeScript + Vite，纯前端，Vite 打包为静态资源后可在 GitHub Pages 运行，发布流程与第 2 章相同。大纲中“不使用复杂游戏引擎”改为“允许 Phaser；不引入 3D、后端或第二套构建”。
3. **3.5 开头加入 2D / 3D 对比**（看懂即可），压缩为一段预录短片和一张对比表，不另增时长。3D 版本不合入主线、不进入公开历史。
4. **Memory 改为独立实验**（2026-10-06 确认）。自动整理记忆依赖后台任务、跨会话状态和时间条件（从普通会话自动提取需要会话闲置至少 1 小时，默认 6 小时），学员自己的项目未必具备，属于“需要特殊状态”的知识内容。主线 3.3 只由人定下规则；3.6 切到准备好的 Memory 实验，看完回到主线做信息来源表。
5. **录播没有“隔天”**。原来“隔天回来”的情境改为“新开一个会话”；3.4 安装插件后本来就要开新会话。
6. **知识线改为“给 AI 的说明，是谁写的”**（见第三节），Skill 与 Memory 并排讲，不单独成块。
7. **“旧计时器”线索不作为自然线索**（预检 A：0/4 出现），3.7 用明确标注的预备版本。
8. **小节时长按下表暂排，全章仍为 120 分钟**。按[设计原则](../../design/course-design-principles.md)“章节故事线先行”，故事线从内容出发，时长试讲后再核算，本表不作为待确认事项。插件安装从 3.5 前移到 3.4 末尾；记忆的长期维护（定期检查、两种立场对照）移到第 7 章 7.4。
9. **新增“从第三章开始”**：沿用第二章的追赶方式，见第五节开头。

## 二、故事线

**一句话**：把只有首页的个人站点变成能玩两个小游戏的实验室，并发现“能玩”背后有一串没人亲自定过、也没写下来的规则。

**这一章在做什么**：你用一句话让 Codex 在主页里加一个记忆翻牌，很快就能玩了。换几种玩法试试，发现有些情况下游戏怎么反应，是 AI 替你定的；顺着其中一个问题，你按证据修好一个缺陷，也在对话里定下了一条规则。接着做第二个游戏时，你发现有人已经把“做游戏的经验”打包成了插件；插件有它自己的主张，和你的 Brief 不完全一致，由你决定听谁的。最后你问：刚才那些规则，下次开会话时 Codex 从哪里知道？对话会结束，插件会停用，Codex 自己记的东西不一定对；哪些已经写进仓库，哪些没有？没落档的那些，就是需求债务，第 4 章要用规格还掉它。

**学员获得**：两个可玩、已发布的游戏；“先复现、再假设、再修改”的调试习惯；审查和安装一个插件的清单；一张能说清每条规则是谁写的、存在哪里的信息来源表，以及由它整理出的需求债务清单。

| 节 | 结构 | 情境 | 留下的东西 |
| --- | --- | --- | --- |
| 3.1 | 起 | 一句话加一个记忆翻牌，很快就能玩了 | 记忆翻牌 v0 |
| 3.2 | 转① | 第二张牌还没翻回去，我又点了第三张：这条规则是谁定的？ | 状态图；问题清单（缺陷与 AI 替你定的规则分开记） |
| 3.3 | 承 | 挑一个缺陷，按证据修；由人定下一条规则 | 记忆翻牌 v1、缺陷记录 |
| 3.4 | 承 | 做游戏的经验，有人打包好了吗？ | 插件审查结论与允许范围 |
| 3.5 | 转② | 插件有自己的主张：2D 还是 3D，Phaser 还是不用 | 第二个游戏与插件生命周期证据 |
| 3.6 | 合 | 刚才那条规则，下次 Codex 从哪里知道？ | 信息来源表、需求债务清单 → 第 4 章 |
| 3.7 | 尾声 | 游戏状态之外，还有什么要在重开时清理？ | 资源清理判断 |

两个转折都稳定发生：3.2 的“规则是谁定的”不依赖代码质量；3.5 的“插件默认 Phaser、我们要求接进现有 React 仓库”来自插件源码中写明的默认路线。

### 贯穿线索

1. **一条规则**：3.2 发现“等待翻回时点第三张”怎么处理是 AI 定的；3.3 由人确认这条规则（例如“等待期间的点击一律忽略”）；3.6 追问它存在哪里。学员可能按第二章的习惯把它写进记录，也可能只留在对话里，两种情况都能进入信息来源表。这条线不依赖任何缺陷出现。
2. **计时器（预检后：不自然出现，只在 3.7 用预备版本）**：不匹配时用计时器延迟翻回；如果重开时不清理，旧回调会在新的一局里执行。这是真实存在的一类缺陷，但 Codex 不一定写出来。按第六节预检 A，若多轮生成的版本多数会出现，则作为 3.2→3.3→3.7 的第二条线索，并在 3.4 对照 Game Studio 中“计时器属于游戏状态”的条目、在 3.5 对照 Phaser 实例的销毁；若很少出现，3.7 使用明确标注的预备版本，贯穿线索只保留第 1 条。

## 三、知识线：给 AI 的说明，是谁写的

本章的知识内容都由同一个问题引出：**给 AI 的说明是谁写的，放在哪里，什么时候进入请求，会不会过期？**第 2 章已经用请求查看工具看过一次真实请求；本章沿用同一工具，每次只看一个新位置。

| | 谁写的 | 放在哪里 | 什么时候进入请求 | 会不会过期 | 本章出现 |
| --- | --- | --- | --- | --- | --- |
| 对话历史 | 你和 AI | 当前会话 | 本会话的每次请求 | 开新会话就没了 | 3.3 伏笔 |
| Skill | 别人（如 Game Studio） | 插件或 Skill 目录 | 平时只有名称和描述；用到时才读全文 | 随插件版本变化 | 3.4–3.5 |
| Memory | AI 自己整理 | 本机 Codex home，不在仓库里 | 平时只有记忆摘要；需要时才读细节 | 会，代码改了它不会自动跟着改 | 3.6 独立实验 |
| 仓库 | 你和团队 | 代码、测试、文档（第 7 章正式讲 `AGENTS.md`） | 按需读取；`AGENTS.md` 每次加载 | 和代码一起维护 | 3.6 对照 |

Skill 和 Memory 是同一种结构：平时只放一段摘要，需要时才展开。3.6 可以把两段请求记录并排放，学员会发现这是 3.4 的同一个机制，Memory 就不显得突兀。“什么时候进入请求”一列由 Codex 代码决定，课件引用子模块固定版本的源码位置，多次运行只用来核对实际请求与源码一致。

| 节 | 故事里的问题 | 看到的证据 | 归纳 |
| --- | --- | --- | --- |
| 3.3 | 刚定下的规则记在哪？ | 对话历史里有；学员的记录文件里可能有，也可能没有 | 留伏笔：开新会话后，对话里的就不在了 |
| 3.4 | 插件里有 9 个 Skill，Codex 每次都读全文吗？ | 请求里只有 Skill 名称和描述 | Skill 是一份按需加载的经验说明 |
| 3.5 | 插件说 2D 默认 Phaser，我们的 Brief 说接进现有仓库，听谁的？ | Skill 原文里的“除非用户另有要求” | Skill 是前人的经验，不是规则；冲突时由人按证据决定 |
| 3.5 | 停用插件后，它写的代码还在吗？它的经验呢？ | 代码在仓库里；Skill 不再出现在请求里 | 停用不等于撤销；项目在没有插件时仍要能构建和运行 |
| 3.6 | 让 Codex 自己记住，下次它知道吗？知道的还对吗？ | Memory 实验的三层验证（见下） | 记忆是辅助回忆，不能证明代码现在的行为 |

### Plugin 与 Skill 的说法

- **Skill**：一个包含 `SKILL.md` 的目录，写着某类任务的经验和做法，Agent 按需加载。`SKILL.md` 是开放格式，Claude Code、Codex、Gemini CLI、GitHub Copilot 等都能读取，日常用得最多。
- **Plugin**：把 Skill 和其他组件一起打包、安装、更新、停用的单位。按 Codex 的 manifest 定义，一个 Plugin 可以包含 Skill、MCP 服务器、应用连接器和 Hook；Game Studio 只包含 9 个 Skill，外加精灵图脚本和图标。
- **跨工具**：各工具都有类似的打包方式，但格式不通用：Claude Code、Codex、Copilot CLI 叫 Plugin，Gemini CLI 叫 Extension。课上讲 Skill 时可以说“各工具通用”，讲 Plugin 时只说 Codex 的做法。

| 观察（三层验证） | **文件里有没有**：Codex home 下 `memories/` 的笔记和记忆摘要；**请求里有没有**：请求记录中的记忆摘要段落；**回答用没用、还对不对**：回答末尾的 `<oai-mem-citation>` 引用了哪些记忆文件；关闭记忆的新会话作对照（`/memories` 的开关从下一个会话起生效）；最后回到代码核对规则现在是否成立。预检 B 里最值得讲的是**记忆会“长出”人没说过的内容**：Codex 写笔记时自己加了“用显式锁定标志、不要靠延时回调”，整理后这条被写成用户规则，会话三回答还说它是“长期契约，不重新讨论”；关闭记忆的对照会话回答“这个决定目前不存在”，并说要由人确认口径 |
| 可以加的一步 | 改代码让规则不再成立，再问一次，看记忆会不会跟着变（直接演示“会过期”）；预检 B 未做 |
| 允许变化 | 回答措辞、是否主动引用记忆；整理被跳过时，使用参考记录并标明 |
| 回到主线 | 记忆里有、代码里没有、人也没说过的内容，都能被当成规则；接上可信度顺序：当前代码与测试 > 仓库文档 > 记忆；回到信息来源表。（预检后：第三版引用的“Memory is not proof of current behavior”只在 v2 记忆说明里，默认 v1 的请求里没有，不再引用） |
| 学员要求 | 看懂即可，重跑选做；学员默认不开启 Memories |

### 3.1 起：一句话加一个记忆翻牌

- **情境**：用“在主页加入一个记忆翻牌小游戏”的自然语言需求，允许 Codex 提少量问题并给计划。
- **证据**：能翻牌、配对、完成、重开；首页原功能可用；build 通过。
- **归纳**：垂直切片很快；“能玩”是起点，不是验收。
- **跟做**：是。
- **预检后**：草案需求句下，4 轮执行用时 8–22 分钟，多数花在 Codex 自行启动浏览器验证（每轮 4–10 条相关命令），与第二章 p29 改前一样。需求句要像 p29 一样写明“浏览器里的检查由我做；你跑 build”，改后重跑预检 A。

### 3.2 转①：这条规则是谁定的

- **情境**：换几种玩法：两张不匹配时立刻点第三张、等待中重开、完成后重开、快速连点、手机上双击。
- **证据**：先画最小状态图（初始、首张、两张不匹配、等待翻回、匹配、完成、重开），再按短检查路线逐项观察，记录最小步骤、期望、实际与截图。
- **判断**：每条记录是缺陷（违背了明确的期望），还是 AI 替你定的规则（合理，但没人问过你）？
- **归纳**：只走成功路径不等于验证；“没出错”也可能只是 AI 替你做了决定。
- **跟做**：是；本节不修。

### 3.3 承：挑一个缺陷，按证据修

- **情境**：从清单里挑一个已复现的缺陷。
- **证据**：按三段式：先让 Codex 只调查、列可证伪假设、不改代码；用日志和状态变化缩小范围；确认后最小修复；原场景和相邻场景复验。
- **结尾**：由人确认 3.2 里那条规则。不要求学员把它写进文件，也不阻止；3.6 按实际情况归类。
- **归纳**：先复现再修改；修复只处理根因。
- **跟做**：是；未自然出现缺陷时用预备 tag，并明说。

### 3.4 承：做游戏的经验，有人打包好了吗

- **情境**：3.3 里我们自己摸索出来的游戏经验（状态要清楚、等待和重开要处理好），有没有现成的？找到 Game Studio。
- **证据**：审查来源、版本、manifest、9 个 Skill、脚本、网络与许可证；读 `web-game-foundations` 中关于游戏状态与计时器的条目，与 3.3 对照；安装前先在请求记录中确认此时还没有这些 Skill。
- **判断**：采用、限定范围采用，还是不采用；写下允许修改的范围和不运行的脚本。
- **操作**：审查通过后安装，开新会话，在请求记录中看到 9 个 Skill 的名称和描述（只有这些，没有全文）。不通过时走课程快照降级。
- **归纳**：Skill 是一份按需加载的经验说明，Plugin 是把它们打包安装的单位；审查沿用 1.3 的权限知识。
- **跟做**：是（审查记录与安装）。

### 3.5 转②：插件有自己的主张

- **情境**：在 3.4 装好插件的会话里调用 Game Studio。插件给出的计划默认走 Phaser，可能还想新建独立项目。
- **对比短片（独立材料，看懂即可）**：同一份“60 秒躲避与收集”Brief，在临时分支各出一个 2D（Phaser）与 3D（React Three Fiber）原型，用 URL 参数切换；对比表列新增依赖、build 后包体积、首次加载、手机流畅度、相机与 WebGL 处理、playtest 是否需要截图。结论选 2D。
- **跟做**：在现有 React 仓库中以懒加载模块接入 Phaser，只用几何图形；playtest 移动、收集、碰撞、HUD、结束、重开；Review diff（资源路径与 `base`、离开页面时销毁 Phaser 实例、是否新增路由）；停用或卸载插件，开新会话确认 Skill 已不在请求中，重新 build 并检查两个游戏和首页。
- **归纳**：Skill 是经验不是规则；停用插件不撤销它写入的代码；项目在没有插件时必须仍能运行。

### 3.6 合：刚才那条规则，下次 Codex 从哪里知道

- **情境**：本章定下了好几条规则：等待期的点击、插件允许改的范围、用 Phaser 而不新建项目……开一个新会话，这些 Codex 从哪里知道？
- **独立实验**：切到第三节的 Memory 实验，看“让 Codex 自己记住”这条路的三层验证；看完回到自己的项目。
- **证据**：在自己的项目里指认：新会话没有旧对话历史；`AGENTS.md` 里没有；代码里有行为，没有原因；第二章习惯下写进记录的那几条，仓库里有。
- **判断**：哪条信息可信？可信度从当前代码与测试，到仓库文档，再到记忆。
- **操作**：把本章所有规则和决定列进信息来源表（仓库证据 / 只在对话里 / 插件 Skill / 记忆 / 模型猜测），没有落在仓库里的就是需求债务。已经落档但只有结论、没有原因或验收方法的，也标出来。
- **归纳**：记忆是辅助回忆，不是团队规则的来源，也不在仓库里；零散记录能留住结论，但留不住一份可执行的契约。第 4 章的规格要把这些决定写成持久契约。规格能解决“决定没留档”，不能代替人做决定。
- **跟做**：信息来源表与需求债务清单是；Memory 部分看懂即可。

### 3.7 尾声：游戏状态之外，还有什么要在重开时清理

- **情境**：若计时器线索成立，复用 3.2–3.3 的场景，画“旧计时器建立 → 重开 → 旧回调触发”的时间线，对照修复后的清理点；否则使用明确标注的预备版本。再指出 3.5 中离开页面时销毁 Phaser 实例是同一类问题。
- **归纳**：状态、副作用与清理责任；界面重置不等于资源重置。不重复调试流程。

## 七、待确认

第一批预检后讲师追问的三件事已补测（2026-10-06 晚），结论如下，仍需讲师定夺：

1. **3.4 的发现与安装路径**。补测：直接把官方仓库加为市场会被拒绝（保留名）；不用 OpenAI 账号也能用官方仓库的 Skill，有三种装法——本地市场装插件、内置 `skill-installer` 装 Skill、把 Skill 放进仓库 `.agents/skills/`（进 git）。见[预检 C](../../../courseware/ch03/materials/plugin/README.md)。待定：主路径用哪一种；三种装法的对比（在哪、进不进 git、怎样停用）是否作为 3.4–3.5 的讲解内容。
2. **3.3 用自然出现的缺陷**。补测：扩展探查在 6 份实现里发现 3 个真实缺陷（配上第一对就通关、首次翻牌计时显示“-1:-1”、牌组没有成对的牌所以永远打不完），但都要“完整打完一局”“对照计分规则”才看得到。见[预检 A](../../../courseware/ch03/materials/mainline/README.md)。建议：不构造缺陷，3.2 的检查路线加入“完整打完一局”；讲师主线选一份有缺陷的实现，学员没找到时用它作复现材料。待定：是否采纳。
3. **Memory 在课程里的位置**。补测：对照组已用权限配置修好；Memory 的写入要等（普通对话至少闲置 1 小时、默认 6 小时，整理成功后 6 小时冷却），不进 git、各机器不同；在请求里它是一条 `developer` 消息，`AGENTS.md` 是 `user` 消息，自定义文件不在请求里。见[预检 B](../../../courseware/ch03/materials/memory/README.md)。待定：3.6 是否把重点从“演示 Memory”改为“对照 Memory、`AGENTS.md`、仓库文件三处说明的差别”，Memory 演示用参考记录。
4. 记忆的长期维护移到 7.4，是否同意？7.4 的具体改法在写第 7 章时另提。
5. **3.3 与 3.5 的备用分支**（2026-10-07 补）：见第六节“重跑与录制定稿”。3.5 的 Phaser 分支只写了要点，没有做页面；录制时若走这一支，需要临时补 p31–p35。待定：是否提前做好这一支的页面。
6. **讲师参考成品上线**（2026-10-07 实测）：用 course-starter 的 `course-run` 部署到该仓库的 Pages，学员仍在自己仓库的 `main` 部署。在临时公开仓库（只有 `main` 无 workflow、`course-run` 带 2.4 的 Pages workflow，与 course-starter 结构相同）实测：
   - 开启 Pages（来源选 GitHub Actions）时自动建的 `github-pages` 环境只允许 `main` 部署；`course-run` 的 push 能触发 workflow，但部署一步报 `Branch "course-run" is not allowed to deploy to github-pages due to environment protection rules`。在环境的部署分支规则里加上 `course-run` 后重跑成功，页面上线。
   - `main` 上没有 workflow 文件时，`gh workflow run --ref course-run` 返回 404（`workflow_dispatch` 要求文件在默认分支，与 GitHub 文档一致），只能靠 push 触发。
   - `course-run` 上原样使用学员版触发条件 `branches: [main]` 时，push 不触发任何运行。所以 `course-run` 的 workflow 必须写成 `branches: [main, course-run]`，这一行会随参考起点标签被学员的“从这一章开始”看到；`base` 写 `/course-starter/`。
   - 未测：从 Template 生成仓库时不带 `course-run`（GitHub 默认只复制默认分支，未实测）。
   结论：可行，需要两项仓库设置和 workflow 一行差异。待讲师定夺后写入 [course-starter 契约](../../design/course-starter-contract.md)；若采用，追赶预检加一项：Codex 不把 `course-run` 抄进学员的 workflow。
