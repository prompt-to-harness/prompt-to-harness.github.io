## 一、不变与改变

**不变**：本章目标与定位（普通 Vibe Coding 做记忆翻牌 → Game Studio Plugin 做“60 秒躲避与收集” → 需求债务引出 SDD）；七个小节的顺序；3.7 工程经验；交付物与退出门禁；全章暂估 120 分钟（内部大纲现值）。

**改变**：

1. **3.2 的转折改为“这条规则是谁定的？”，不依赖 AI 出错**。记忆翻牌是常见 benchmark 题（2026-09-03 讨论中已提到），模型大概率一次写对。两张牌不匹配时，游戏通常会让它们停留约一秒，在这段时间里点第三张是正常玩法，不需要特别快。之后发生什么取决于 Codex 的实现：加锁（点了没反应）、先翻回再翻开第三张，或三张同时朝上。前两种都合理，但规则是 AI 替你定的；第三种才是缺陷。无论哪种，转折都成立。
2. **接受 Phaser 作为第二个游戏的技术栈**。Game Studio 对 2D 游戏默认 Phaser + TypeScript + Vite，纯前端，Vite 打包为静态资源后可在 GitHub Pages 运行，发布流程与第 2 章相同。大纲中“不使用复杂游戏引擎”改为“允许 Phaser；不引入 3D、后端或第二套构建”。
3. **3.5 开头加入 2D / 3D 对比**（看懂即可），压缩为一段预录短片和一张对比表，不另增时长。3D 版本不合入主线、不进入公开历史。
4. **Memory 从“开关对照实验”改为可观察的机制讲解**：3.3 结尾明确要求 Codex 记住一条规则，3.4 和 3.6 的新会话里检查它是否被写入、注入和使用。自动从普通会话提取记忆需要会话闲置至少 1 小时（默认 6 小时），录制中不依赖它。
5. **录播没有“隔天”**。原来“隔天回来”的情境改为“新开一个会话”；3.4 安装插件后本来就要开新会话。
6. **知识线改为“给 AI 的说明，是谁写的”**（见第三节），Skill 与 Memory 并排讲，不单独成块。
7. **“旧计时器”线索先验证再决定**（见第六节）。
8. **小节时长重新分配，全章仍为 120 分钟**（见下表）。插件安装从 3.5 前移到 3.4 末尾；记忆的长期维护（定期检查、两种立场对照）移到第 7 章 7.4。

## 二、故事线

**一句话**：把只有首页的个人站点变成能玩两个小游戏的实验室，并发现“能玩”背后有一串没人亲自定过、也没写下来的规则。

**这一章在做什么**：你用一句话让 Codex 在主页里加一个记忆翻牌，很快就能玩了。换几种玩法试试，发现有些情况下游戏怎么反应，是 AI 替你定的；顺着其中一个问题，你按证据修好一个缺陷，也在对话里定下了一条规则，并让 Codex 记住它。接着做第二个游戏时，你发现有人已经把“做游戏的经验”打包成了插件；插件有它自己的主张，和你的 Brief 不完全一致，由你决定听谁的。最后开一个新会话问 Codex：刚才那条规则是怎么定的？它从哪里知道、哪里不知道、知道的还对不对——没落在仓库里的那些，就是需求债务，第 4 章要用规格还掉它。

**学员获得**：两个可玩、已发布的游戏；“先复现、再假设、再修改”的调试习惯；审查和安装一个插件的清单；一张能说清每条规则是谁写的、存在哪里的信息来源表，以及由它整理出的需求债务清单。

| 节 | 结构 | 情境 | 留下的东西 |
| --- | --- | --- | --- |
| 3.1 | 起 | 一句话加一个记忆翻牌，很快就能玩了 | 记忆翻牌 v0 |
| 3.2 | 转① | 第二张牌还没翻回去，我又点了第三张：这条规则是谁定的？ | 状态图；问题清单（缺陷与 AI 替你定的规则分开记） |
| 3.3 | 承 | 挑一个缺陷，按证据修；定下一条规则，让 Codex 记住 | 记忆翻牌 v1、缺陷记录、一条记忆笔记 |
| 3.4 | 承 | 做游戏的经验，有人打包好了吗？ | 插件审查结论与允许范围 |
| 3.5 | 转② | 插件有自己的主张：2D 还是 3D，Phaser 还是不用 | 第二个游戏与插件生命周期证据 |
| 3.6 | 合 | 新会话里问：刚才那条规则，Codex 从哪里知道？ | 信息来源表、需求债务清单 → 第 4 章 |
| 3.7 | 尾声 | 游戏状态之外，还有什么要在重开时清理？ | 资源清理判断 |

两个转折都稳定发生：3.2 的“规则是谁定的”不依赖代码质量；3.5 的“插件默认 Phaser、我们要求接进现有 React 仓库”来自插件源码中写明的默认路线。

### 贯穿线索

1. **一条规则**：3.2 发现“等待翻回时点第三张”怎么处理是 AI 定的；3.3 由人确认这条规则（例如“等待期间的点击一律忽略”），并明确让 Codex 记住；3.6 在新会话中追问它存在哪里。这条线不依赖任何缺陷出现。
2. **计时器（待验证）**：不匹配时用计时器延迟翻回；如果重开时不清理，旧回调会在新的一局里执行。这是真实存在的一类缺陷，但 Codex 不一定写出来。按第五节验证后，若多数生成版本都会出现，则作为 3.2→3.3→3.7 的第二条线索，并在 3.4 对照 Game Studio 中“计时器属于游戏状态”的条目、在 3.5 对照 Phaser 实例的销毁；若很少出现，3.7 使用明确标注的预备版本，贯穿线索只保留第 1 条。

## 三、知识线：给 AI 的说明，是谁写的

本章的知识内容都由同一个问题引出：**给 AI 的说明是谁写的，放在哪里，什么时候进入请求，会不会过期？**第 2 章已经用请求查看工具看过一次真实请求；本章沿用同一工具，每次只看一个新位置。

| | 谁写的 | 放在哪里 | 什么时候进入请求 | 会不会过期 | 本章出现 |
| --- | --- | --- | --- | --- | --- |
| 对话历史 | 你和 AI | 当前会话 | 本会话的每次请求 | 开新会话就没了 | 3.3 伏笔 |
| Skill | 别人（如 Game Studio） | 插件或 Skill 目录 | 平时只有名称和描述；用到时才读全文 | 随插件版本变化 | 3.4–3.5 |
| Memory | AI 自己整理 | 本机 Codex home，不在仓库里 | 平时只有记忆摘要；需要时才读细节 | 会，代码改了它不会自动跟着改 | 3.6 |
| 仓库 | 你和团队 | 代码、测试、文档（第 7 章正式讲 `AGENTS.md`） | 按需读取；`AGENTS.md` 每次加载 | 和代码一起维护 | 3.6 对照 |

Skill 和 Memory 是同一种结构：平时只放一段摘要，需要时才展开。3.6 可以把两段请求记录并排放，学员会发现这是 3.4 的同一个机制，Memory 就不显得突兀。

| 节 | 故事里的问题 | 看到的证据 | 归纳 |
| --- | --- | --- | --- |
| 3.3 | 刚定下的规则记在哪？让 Codex 记住，它做了什么？ | 对话历史里有这条规则；请求记录中有一次写入记忆笔记的操作，笔记文件立即出现 | 留伏笔：写下了，不等于下次就能用上 |
| 3.4 | 插件里有 9 个 Skill，Codex 每次都读全文吗？ | 请求里只有 Skill 名称和描述 | Skill 是一份按需加载的经验说明 |
| 3.5 | 插件说 2D 默认 Phaser，我们的 Brief 说接进现有仓库，听谁的？ | Skill 原文里的“除非用户另有要求” | Skill 是前人的经验，不是规则；冲突时由人按证据决定 |
| 3.5 | 停用插件后，它写的代码还在吗？它的经验呢？ | 代码在仓库里；Skill 不再出现在请求里 | 停用不等于撤销；项目在没有插件时仍要能构建和运行 |
| 3.6 | 新会话里，Codex 知道那条规则吗？知道的还对吗？ | 文件里有没有、请求里有没有、回答用没用（见下） | 记忆是辅助回忆，不能证明代码现在的行为 |

### Plugin 与 Skill 的说法

- **Skill**：一个包含 `SKILL.md` 的目录，写着某类任务的经验和做法，Agent 按需加载。`SKILL.md` 是开放格式，Claude Code、Codex、Gemini CLI、GitHub Copilot 等都能读取，日常用得最多。
- **Plugin**：把 Skill 和其他组件一起打包、安装、更新、停用的单位。按 Codex 的 manifest 定义，一个 Plugin 可以包含 Skill、MCP 服务器、应用连接器和 Hook；Game Studio 只包含 9 个 Skill，外加精灵图脚本和图标。
- **跨工具**：各工具都有类似的打包方式，但格式不通用：Claude Code、Codex、Copilot CLI 叫 Plugin，Gemini CLI 叫 Extension。课上讲 Skill 时可以说“各工具通用”，讲 Plugin 时只说 Codex 的做法。

### 3.6 的 Memory 演示

1. **3.3 结尾**：讲师在已开启 Memories 的隔离 Codex home 中说“记住：等待翻回期间的点击一律忽略”。Codex 注入的说明要求它在用户明确要求时，在 `memories/extensions/ad_hoc/notes/` 下追加一条笔记；笔记立即写入，但要等下一次新会话启动时的后台整理，才会合进记忆摘要。
2. **3.4 开新会话**（安装插件后本来就要开）：启动时后台整理笔记。
3. **3.6 再开新会话**，问同一个问题，分三层验证：
   - **文件里有没有**：打开 Codex home 下的 `memories/` 目录，看笔记和记忆摘要；
   - **请求里有没有**：请求记录中的 `MEMORY_SUMMARY` 段落；
   - **回答用没用、还对不对**：用到记忆时回答末尾会带引用标记；再用 `/memories` 关闭本会话的记忆问一次作对照；最后回到代码核对这条规则现在是否成立。
4. **讲 Codex 自己的提醒**：Codex 注入的记忆说明里写着“Memory is not proof of current behavior”（记忆不能证明当前行为）。这句话正好接上可信度顺序：当前代码与测试 > 仓库文档 > 记忆。
5. **学员**默认不开启 Memories，3.6 的 Memory 部分看懂即可；跟做部分是信息来源表和需求债务清单。

## 四、Game Studio 的安装与停用

插件**默认不安装**。Game Studio 在 OpenAI 官方插件目录（`openai-curated`）中的安装策略是“可安装”，不是“默认安装”；Codex 的 Plugin 功能本身默认开启。录制和学员都在 3.4 审查通过后安装。

| 操作 | 方式（以录制时版本核验为准） |
| --- | --- |
| 浏览 | Codex CLI 中 `/plugins`；桌面端 Plugins 页 |
| 安装 | 在上述界面安装，或 `codex plugin add game-studio@openai-curated` |
| 生效 | 安装后开新会话，Skill 才可用 |
| 停用（保留安装） | `config.toml` 中 `[plugins."game-studio@openai-curated"]` 设 `enabled = false`，或界面中的停用开关（待核验） |
| 卸载 | `codex plugin remove game-studio@openai-curated`，或界面中的卸载 |
| 限制 | 官方文档说明部分插件不支持 API key 登录，IDE 扩展不支持插件；Game Studio 不含连接器，预计不受影响，待核验 |

讲师录制使用隔离的 Codex home，避免把真实环境的插件和记忆带进画面；学员在自己的环境中安装，3.5 结束时停用或卸载，再从新会话确认 Skill 已不在请求中，并重新 build。

## 五、逐节要点

只写到故事线确认所需的粒度；逐页分镜在确认后另写。

### 3.1 起：一句话加一个记忆翻牌

- **情境**：用“在主页加入一个记忆翻牌小游戏”的自然语言需求，允许 Codex 提少量问题并给计划。
- **证据**：能翻牌、配对、完成、重开；首页原功能可用；build 通过。
- **归纳**：垂直切片很快；“能玩”是起点，不是验收。
- **跟做**：是。

### 3.2 转①：这条规则是谁定的

- **情境**：换几种玩法：两张不匹配时立刻点第三张、等待中重开、完成后重开、快速连点、手机上双击。
- **证据**：先画最小状态图（初始、首张、两张不匹配、等待翻回、匹配、完成、重开），再按短检查路线逐项观察，记录最小步骤、期望、实际与截图。
- **判断**：每条记录是缺陷（违背了明确的期望），还是 AI 替你定的规则（合理，但没人问过你）？
- **归纳**：只走成功路径不等于验证；“没出错”也可能只是 AI 替你做了决定。
- **跟做**：是；本节不修。

### 3.3 承：挑一个缺陷，按证据修

- **情境**：从清单里挑一个已复现的缺陷。
- **证据**：按三段式：先让 Codex 只调查、列可证伪假设、不改代码；用日志和状态变化缩小范围；确认后最小修复；原场景和相邻场景复验。
- **结尾**：由人确认 3.2 里那条规则，并让 Codex 记住（见第三节）。
- **归纳**：先复现再修改；修复只处理根因。
- **跟做**：修复是；未自然出现缺陷时用预备 tag，并明说。让 Codex 记住为看懂。

### 3.4 承：做游戏的经验，有人打包好了吗

- **情境**：3.3 里我们自己摸索出来的游戏经验（状态要清楚、等待和重开要处理好），有没有现成的？找到 Game Studio。
- **证据**：审查来源、版本、manifest、9 个 Skill、脚本、网络与许可证；读 `web-game-foundations` 中关于游戏状态与计时器的条目，与 3.3 对照；安装前先在请求记录中确认此时还没有这些 Skill。
- **判断**：采用、限定范围采用，还是不采用；写下允许修改的范围和不运行的脚本。
- **操作**：审查通过后安装，开新会话，在请求记录中看到 9 个 Skill 的名称和描述（只有这些，没有全文）。不通过时走课程快照降级。
- **归纳**：Skill 是一份按需加载的经验说明，Plugin 是把它们打包安装的单位；审查沿用 1.3 的权限知识。
- **跟做**：是（审查记录与安装）。

### 3.5 转②：插件有自己的主张

- **情境**：在 3.4 装好插件的会话里调用 Game Studio。插件给出的计划默认走 Phaser，可能还想新建独立项目。
- **对比短片（看懂即可）**：同一份“60 秒躲避与收集”Brief，在临时分支各出一个 2D（Phaser）与 3D（React Three Fiber）原型，用 URL 参数切换；对比表列新增依赖、build 后包体积、首次加载、手机流畅度、相机与 WebGL 处理、playtest 是否需要截图。结论选 2D。
- **跟做**：在现有 React 仓库中以懒加载模块接入 Phaser，只用几何图形；playtest 移动、收集、碰撞、HUD、结束、重开；Review diff（资源路径与 `base`、离开页面时销毁 Phaser 实例、是否新增路由）；停用或卸载插件，开新会话确认 Skill 已不在请求中，重新 build 并检查两个游戏和首页。
- **归纳**：Skill 是经验不是规则；停用插件不撤销它写入的代码；项目在没有插件时必须仍能运行。

### 3.6 合：刚才那条规则，Codex 从哪里知道

- **情境**：新会话里问 Codex：“等待翻回期间的点击，我们是怎么定的？”
- **证据**：按第三节的三层验证 Memory；同时指认：这里没有旧对话历史；`AGENTS.md` 里没有；代码里有行为，没有原因。
- **判断**：哪条信息可信？可信度从当前代码与测试，到仓库文档，再到记忆。
- **操作**：把本章所有规则和决定列进信息来源表（仓库证据 / 只在对话里 / 插件 Skill / 记忆 / 模型猜测），没有落在仓库里的就是需求债务。
- **归纳**：记忆是辅助回忆，不是团队规则的来源，也不在仓库里；第 4 章的规格要把这些决定写成持久契约。规格能解决“决定没留档”，不能代替人做决定。
- **跟做**：信息来源表与需求债务清单是；Memory 部分看懂即可。

### 3.7 尾声：游戏状态之外，还有什么要在重开时清理

- **情境**：若计时器线索成立，复用 3.2–3.3 的场景，画“旧计时器建立 → 重开 → 旧回调触发”的时间线，对照修复后的清理点；否则使用明确标注的预备版本。再指出 3.5 中离开页面时销毁 Phaser 实例是同一类问题。
- **归纳**：状态、副作用与清理责任；界面重置不等于资源重置。不重复调试流程。
