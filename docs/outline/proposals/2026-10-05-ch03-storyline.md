# 提案：第 3 章故事线

> 状态：草稿（2026-10-05），待两位讲师确认。确认后再写逐节分镜，最后同步[共同内部大纲](../course-outline-internal.md)第 3 章和[平台交付版](../../course-outline.md)第 3 章。
> 本文不是课程承诺，也不是已验证的教学效果；所有内容未经试讲。Game Studio 的描述来自 2026-09-28 的插件源码阅读，尚未在 Codex 中实际运行；Codex Memories 的描述来自官方文档，尚未实测。

## 一、不变与改变

**不变**：本章目标与定位（普通 Vibe Coding 做记忆翻牌 → Game Studio Plugin 做“60 秒躲避与收集” → 需求债务引出 SDD）；七个小节的顺序；3.7 工程经验；交付物与退出门禁。

**改变**：

1. **主转折不依赖 AI 出错**。记忆翻牌是常见 benchmark 题（2026-09-03 讨论中已提到），模型大概率一次写对。3.2 的转折改为“有些规则从来没人定过”：游戏能玩，但“第二张牌还没翻回去，又点了第三张”之类的问题没有人做过决定。这类问题无论代码质量如何都会出现。真实缺陷自然出现时在 3.3 就地使用；未出现时使用明确标注的预备 tag（大纲已允许）。
2. **接受 Phaser 作为第二个游戏的技术栈**。Game Studio 对 2D 游戏默认 Phaser + TypeScript + Vite，纯前端，Vite 打包为静态资源后可在 GitHub Pages 运行，发布流程与第 2 章相同。大纲中“不使用复杂游戏引擎”改为“允许 Phaser；不引入 3D、后端或第二套构建”。
3. **3.5 开头加入 2D / 3D 对比演示**（看懂即可）。同一份 Brief，让插件在临时分支各出一个原型，用证据比较后选 2D。3D 版本不合入主线、不进入公开历史。
4. **Memory 从“开关对照实验”改为一段机制讲解**，沿用第 2 章的请求查看工具，看 `AGENTS.md`、Skill 描述与记忆分别出现在请求的什么位置。Memory 生成是异步的，现场开关对照结果不可控；改为使用预先准备的记忆快照。
5. **知识内容嵌进同一条故事**，不单独成块（见第三节）。

## 二、故事线

**一句话**：把只有首页的个人站点变成能玩两个小游戏的实验室，并发现“能玩”背后有一串只存在于聊天里的决定。

**这一章在做什么**：你用一句话让 Codex 在主页里加一个记忆翻牌，很快就能玩了。换几种玩法试试，发现有些情况该怎么反应，从来没人定过；顺着其中一个问题，你按证据修好了一个真缺陷，也在对话里顺手定下了几条规则。接着做第二个游戏时，你发现有人已经把“做游戏的经验”打包成了插件。插件有它自己的主张，和你的 Brief 不完全一致，由你决定听谁的。最后隔天回来问 Codex：上次那条规则是怎么定的？它从哪里知道、又从哪里不知道——这份清单就是需求债务，第 4 章要用规格还掉它。

**学员获得**：两个可玩、已发布的游戏；“先复现、再假设、再修改”的调试习惯；审查一个插件的清单；一张能说清每条规则存在哪里的信息来源表，以及由它整理出的需求债务清单。

| 节 | 结构 | 情境 | 留下的东西 |
| --- | --- | --- | --- |
| 3.1 | 起 | 一句话加一个记忆翻牌，很快就能玩了 | 记忆翻牌 v0 |
| 3.2 | 转① | 第二张牌还没翻回去，又点了第三张，游戏该怎么反应？ | 状态图；问题清单（缺陷与未定规则分开记） |
| 3.3 | 承 | 挑一个真缺陷，按证据修 | 记忆翻牌 v1、缺陷记录；对话里定下的几条规则 |
| 3.4 | 承 | 做游戏的经验，有人打包好了吗？ | 插件审查结论与允许范围 |
| 3.5 | 转② | 插件有自己的主张：2D 还是 3D，Phaser 还是不用 | 第二个游戏与插件生命周期证据 |
| 3.6 | 合 | 隔天回来：上次那条规则，Codex 从哪里知道？ | 信息来源表、需求债务清单 → 第 4 章 |
| 3.7 | 尾声 | 重开之后，旧计时器为什么还在 | 资源清理判断 |

两个转折都稳定发生：3.2 的“未定规则”不依赖代码质量；3.5 的“插件默认 Phaser、我们要求接进现有 React 仓库”来自插件源码中写明的默认路线。

### 贯穿线索

1. **那个计时器**：3.2 发现等待翻回期间可以重开或继续点击；3.3 复现并定位到计时器或等待状态没有清理；3.4 在 Game Studio 的 Skill 里读到“计时器属于游戏状态，渲染对象要可丢弃”，正是我们刚刚踩过的坑；3.5 的 Phaser 实例离开页面时也要销毁；3.7 画出时间线收束。
2. **一条只在对话里定下的规则**：3.3 修复时决定“等待翻回期间的点击一律忽略”，只留在聊天里；3.6 隔天追问它存在哪里。

## 三、知识线：这条规则存在哪里

本章的知识内容不单独讲，都由同一个问题引出：**一条规则或一段经验，存在哪里，Codex 什么时候能看到它？**第 2 章已经用请求查看工具看过一次真实请求；本章沿用同一工具，每次只看一个新位置。

| 节 | 故事里的问题 | 看到的位置 | 归纳 |
| --- | --- | --- | --- |
| 3.3 | 修好了，刚才定下的“等待期间点击忽略”记在哪？ | 只在本次对话历史里 | 留个伏笔，不展开 |
| 3.4 | 插件里有 9 个 Skill，Codex 每次都读全文吗？ | 请求里只有 Skill 名称和描述；调用时才读入全文 | Plugin 是可安装的能力包；Skill 是按需加载的经验 |
| 3.5 | 插件说 2D 默认 Phaser，我们的 Brief 说接进现有仓库，听谁的？ | Skill 原文里的“除非用户另有要求” | Skill 是前人的经验，不是规则；冲突时由人按证据决定 |
| 3.5 | 停用插件后，它写的代码还在吗？它的经验呢？ | 代码在仓库里；Skill 不再出现在请求里 | 停用不等于撤销；项目要在没有插件时仍能构建和运行 |
| 3.6 | 隔天新会话，Codex 知道那条规则吗？ | 对话历史不在了；记忆可能有，也可能过时；`AGENTS.md` 没写；代码只有行为，没有原因 | 当前代码、测试、仓库文档的可信度高于记忆；记忆只能辅助回忆 |

### 3.6 的记忆快照

- 讲师在隔离的 Codex 配置中开启 Memories，正常完成 3.1–3.3 的录制会话，让 Codex 自然生成记忆，保存快照。
- 快照中如果自然出现与当前代码不一致的条目（例如在 3.2 会话里记下“重开后计时器未清理”，但 3.3 已修复），就用它演示“先回到代码核对，再相信记忆”；没有出现就如实讲，不伪造过时条目。
- 学员默认不开启 Memories，3.6 的 Memory 部分看懂即可；跟做部分是信息来源表和需求债务清单。

### 已核对的产品事实

- **Game Studio**（[openai/plugins](https://github.com/openai/plugins/tree/main/plugins/game-studio)，版本 0.1.2，提交 `5fd93af`，2026-09-28，MIT）：9 个 Skill；路由 Skill 写明“2D 默认 Phaser，除非用户明确要求 3D”；React 项目中的 3D 走 React Three Fiber；`web-game-foundations` 写明计时器、碰撞等属于游戏状态；附带 3 个 Python 脚本，只用于精灵图处理。
- **Codex Memories**（[官方文档](https://developers.openai.com/codex/memories)）：默认关闭；`[features] memories = true` 开启；存放在 `~/.codex/memories/`；会话空闲后异步生成；官方建议必须遵守的规则放在 `AGENTS.md` 或仓库文档，记忆只作辅助回忆。

## 四、逐节要点

只写到故事线确认所需的粒度；逐页分镜在确认后另写。

### 3.1 起：一句话加一个记忆翻牌

- **情境**：用“在主页加入一个记忆翻牌小游戏”的自然语言需求，允许 Codex 提少量问题并给计划。
- **证据**：能翻牌、配对、完成、重开；首页原功能可用；build 通过。
- **归纳**：垂直切片很快；“能玩”是起点，不是验收。
- **跟做**：是。

### 3.2 转①：第二张牌还没翻回去，又点了第三张

- **情境**：换几种玩法：快速连点、等待翻回时点第三张、完成后重开、等待中重开、手机上双击。
- **证据**：先画最小状态图（初始、首张、两张不匹配、等待翻回、匹配、完成、重开），再按短检查路线逐项观察，记录最小步骤、期望、实际与截图。
- **判断**：每条记录是缺陷（违背了明确的期望），还是未定规则（本来就没人说过该怎样）？
- **归纳**：只走成功路径不等于验证；有些问题不是代码写错，而是规则没定。
- **跟做**：是；本节不修。

### 3.3 承：挑一个真缺陷，按证据修

- **情境**：从清单里挑一个已复现的缺陷，优先选与等待或重开相关的。
- **证据**：按三段式：先让 Codex 只调查、列可证伪假设、不改代码；用日志和状态变化缩小范围；确认后最小修复；原场景和相邻场景复验。
- **伏笔**：修复时顺手定下“等待期间点击一律忽略”，只留在对话里。
- **归纳**：先复现再修改；修复只处理根因。
- **跟做**：是；未自然出现缺陷时用预备 tag，并明说。

### 3.4 承：做游戏的经验，有人打包好了吗

- **情境**：3.3 里反复告诉 Codex 的那些游戏经验（状态要清楚、计时器要清理），有没有现成的？找到 Game Studio。
- **证据**：审查来源、版本、manifest、9 个 Skill、脚本、网络与许可证；在请求记录中看到只有 Skill 名称和描述；读到 `web-game-foundations` 中关于计时器和状态的条目，与 3.3 对照。
- **判断**：采用、限定范围采用，还是不采用；写下允许修改的范围和不运行的脚本。
- **归纳**：Plugin 是可安装的能力包，Skill 是按需加载的经验；审查沿用 1.3 的权限知识。
- **跟做**：是（审查记录）。

### 3.5 转②：插件有自己的主张

- **情境**：按审查结论启用插件，新会话调用。插件给出的计划默认走 Phaser，可能还想新建独立项目。
- **演示（看懂即可）**：同一份“60 秒躲避与收集”Brief，在临时分支各出一个 2D（Phaser）与 3D（React Three Fiber）原型，用 URL 参数切换；比较新增依赖、build 后包体积、首次加载、手机流畅度、相机与 WebGL 处理、playtest 是否需要截图。结论选 2D；3D 版本不合入。
- **跟做**：在现有 React 仓库中以懒加载模块接入 Phaser，只用几何图形；playtest 移动、收集、碰撞、HUD、结束、重开；Review diff（资源路径与 `base`、离开页面时销毁 Phaser 实例、是否新增路由）；停用插件后重新 build 并检查两个游戏和首页。
- **归纳**：Skill 是经验不是规则；停用插件不撤销它写入的代码；项目在没有插件时必须仍能运行。

### 3.6 合：隔天回来，上次那条规则 Codex 从哪里知道

- **情境**：新会话里问 Codex：“等待翻回期间点击，我们是怎么定的？”
- **证据**：用请求记录逐一指认：没有旧对话历史；有记忆快照时它出现在哪里、内容是否与代码一致；`AGENTS.md` 里没有；代码里有行为，没有原因。
- **判断**：哪条信息可信？可信度从当前代码与测试，到仓库文档，再到记忆。
- **操作**：把本章所有规则和决定列进信息来源表（仓库证据 / 只在聊天里 / 插件工作流 / 记忆 / 模型猜测），没有落在仓库里的就是需求债务。
- **归纳**：记忆是辅助回忆，不是团队规则的来源；第 4 章的规格要把这些决定写成持久契约。规格能解决“决定没留档”，不能代替人做决定。
- **跟做**：信息来源表与需求债务清单是；Memory 部分看懂即可。

### 3.7 尾声：重开之后，旧计时器为什么还在

- **情境**：复用 3.2–3.3 的场景，画“旧计时器建立 → 重开 → 旧回调触发”的时间线，对照修复后的清理点；再指出 3.5 中 Phaser 实例销毁是同一类问题。
- **归纳**：状态、副作用与清理责任；界面重置不等于资源重置。不重复调试流程。

## 五、风险与待核实

| 项目 | 风险 | 处理 |
| --- | --- | --- |
| Game Studio 实际行为 | 是否坚持新建独立项目、是否引入路由、计划的格式，都只读过源码 | 录制前用冻结的讲师首页 v1 实跑一遍 3.5，再定 Brief 措辞 |
| 3D 原型 | 生成慢或失败 | 提前录制，标“一次运行” |
| Phaser 包体积 | 未实测 | 实跑后记录 build 输出；用懒加载 |
| Memories 注入 | 预置快照能否被正常注入、在请求中的形态，均未实测 | 实测后再定 3.6 演示方式；不可行则改为讲解官方文档并展示快照文件 |
| 过时记忆条目 | 可能不会自然出现 | 不伪造；没有就只讲可信度顺序 |
| 3.3 真实缺陷 | 记忆翻牌可能一次写对 | 用预备 tag，明说 |
| 插件可用性 | 学员账户或地区可能无法使用插件目录 | 沿用大纲的课程快照降级，不把观察记作实操通过 |
