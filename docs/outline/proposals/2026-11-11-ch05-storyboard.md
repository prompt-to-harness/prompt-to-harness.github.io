## 本章故事线

**一句话主线**：拿着第 4 章的规格和任务，在 JSON Crack 里把 JSON Diff 一层层做出来；每走一层，多看见一个原来看不见的问题，最后交出可解释、经过本章验收的功能。章末另用一节，分享一组能带走的 Vibe Coding 招数。

第 4 章回答了「要做什么、怎样算做对，以及准备怎么做」。现在学员拿到一份已有工程和一套规格，还没有 JSON Diff 的生产实现。我们从其中一个很小、但能立刻核对的结果出发：对象里的键换了顺序，为什么仍应是零处差异？随后把差异接到图上、接到双输入界面，再补上摘要与筛选，最后回到同一组验收，判断整个功能有没有做完。

实现中可能遇到不同情况：代码与已批准规则不一致，需要定位实现或测试；验收没写清楚，需要依据已有规则补案例；产品行为本身仍未决定，则由人确认后再修订规格。讲师按实际发现选择下一步，不预设 Agent 一定犯错。到本章末，还要把结果交给第 6 章；GSD 和 CR-01 的明确提示都不进本章。

### 写法原则

- 每一节用「看见了什么新问题」来组织，不要用「读任务、实现、检查、勾完成」来组织。
- 任务闭环只在 5.1 讲一次，而且要短，当作本章的工作方式，不要当成每节的主要内容。5.2–5.4 沿用这一做法，每次实际检查，不重复讲流程，也不再画任务闭环图。
- 用同一组案例往前推，让学员看见功能一点点长出来，而不是每节换一套新练习。
- 每节只留一个学员判断，判断完就往下走。5.5 是只看不跟做的分享，不设学员判断，也不新增练习。

### 本章要讲透的两个问题

1. **怎样让一个任务有可检查的完成边界？** 5.1 首次讲清任务级执行：读取本任务和关联规则、案例及全局约束，限定修改范围，实施并运行相关检查，结合 diff 和结果决定是否完成。后面各节用新问题来调用这套做法，不再定义步骤。
2. **实现、案例和规格对不上时，该回到哪里？** 规则明确时对照规则检查实现与测试；案例缺失时补验收并检查覆盖；需要改变或补充产品行为时，由人决定并同步相关文档。5.4 后半段把这条关系放到整体验收与 Review 中讲清。

第四章介绍五层规格，本章使用它们做实施与反馈；第六章再用 GSD 承接已完成的功能和原验收。本章不是 GSD 教程，测试要随任务实际开展，也不把第六章的完整测试闭环提前压进来。

## 5.1 规格写好了，怎么知道第一个任务做对了？

### 从一组能立刻核对的输入开始

第 4 章结束时，讲师和学员各自留下了 JSON Crack 的规格基线：经人确认的行为、可核算的验收案例，以及结合源码拆好的实施任务。进入本节，先核对当前副本与规格提交，打开差异模型任务和它关联的规则、案例。讲师的实际编号不要求与学员相同；每个人都要能在自己的文件里找到对应内容。

先看一组很小的输入：Before 为 `{"name":"Lin","age":20}`，After 为 `{"age":20,"name":"Lin"}`。字段与值相同，只是对象键的顺序不同。4.3 已由人决定：对象键顺序忽略；4.4 给这一规则安排了固定输入和零差异的期望。学员先根据这条规则判断结果，再由讲师说明零差异的依据。这里用一组合成数据讨论讲法，演示时打开第四章实际交接的 fixture；检查的是键顺序，不是交换 Before 和 After 两侧的含义。两侧对调时，新增和删除本身就会反向，不能写成「输入顺序不能改变确定结果」。

这组输入让人立刻看见第一项工作的一部分应该达到什么结果，但它还不能覆盖数组、类型变化和嵌套路径。差异模型任务要完成哪些规则、哪些固定案例，仍以 4.5 形成的任务和关联验收为准。

### 用很短的一段立住本章怎么干活

有了这个可核对的结果，再确定本次操作的起点。讲师从规格提交创建本地功能分支，核对版本和工作区，按 4.5 确定的方式检查已有工程基线。若已有改动或检查受阻，保留现场并先处理起点；不能把未运行或失败的检查记为通过。

4.2 的一次仓库调查只找到 lint 和 build，没有发现测试命令。本节不能直接假设仓库已有可用的单元测试入口。先核对 4.5 对检查方式的调查和选择：如果现有入口足够，就说明它怎样运行本任务的固定案例；如果不足，就结合实际工程确定最小验证方式，并在任务范围内建立所需入口。具体工具、依赖、文件和命令留待源码核实与备课实跑，不能预写测试已经跑通。

然后用很短的一段说明本章怎么干活：让 Codex 读取当前差异模型任务、关联的 Spec 和 Acceptance、固定素材，以及全局约束和非目标，再请它只完成这个任务。请求中要让 Agent 知道本次做什么、以哪些案例核对、允许修改到哪里。本次先做差异计算及其验证，图映射和界面留给后续任务。按需读取关联文件时，仍要带上适用的全局约束，不能只截一条规则就忽略非目标。

这段只讲一次，当作本章的工作方式，不要写成独立的「流程」小节，后面也不再重讲、不再画闭环图。5.2 起仍然做这些动作，但讲述重点放在每次新增的问题上。

### 完成边界在哪里

Codex 完成一次工作后，镜头不要停在「又走完一遍流程」，而要落到完成边界上。先看它实际改了什么：差异是否集中在当前任务允许的范围，是否有可定位的验证入口，是否顺手修改了界面或其他客户端。再运行与当前任务相关的检查，打开固定输入和期望，抽查对象键换序案例，结合测试输出核对结果。检查结果以实际运行和人工核对为准，不能把 Agent 的完成说明当成测试结果。

固定期望应从已经批准的行为和人工核算得到。比如键换序的预期是零差异；数组 `[10,20]` 变为 `[5,10,20]` 时，按已批准的索引规则核算为两处 `changed`、一处 `added`。测试不能调用同一套待验证的比较逻辑来生成自己的期望。若结果不一致，先确认输入、期望与 Spec，再看实现和测试各自哪里偏离；不能为了让测试通过而把预期改成当前实现的结果。4.3 留下的 `null` 与字段缺失冲突若仍未决，不能在本节先写成实现决定。

**学员判断**：如果相同输入和对象键换序两个案例通过了，差异模型任务就一定完成了吗？没有。这两个结果只覆盖对应案例；数组、类型变化、嵌套路径等若属于该任务，仍要按各自的要求检查。检查通过后，还要回看允许修改的范围和可解释的 diff，才有依据标记这个任务完成。其他任务的验收仍留给后续步骤。

学员用自己的规格和任务完成差异模型，并检查当前任务要求的案例。实现可以与讲师不同，但要能解释固定输入、预期、实际结果和代码改动。运行或环境受阻时，记录实际进展与错误，从学员已有的本地提交和课程提供的排障材料继续；不能承诺章节级恢复点。具体检查点和恢复方式要在后续备课核实。

完成本节后，留下差异模型、任务要求的目标测试，以及 `CH05_IMPLEMENTATION.md` 初稿，记录本次任务、关联依据、实际检查结果和未解决的问题。下一节拿着已验证的模型，去看被删除的字段怎样出现在合并图里。

## 5.2 字段删掉了，结果图上怎样看见它？

不要再解释怎么做任务。直接打开 4.4 嵌套案例里的 `/active`：它只存在于 Before，规则要求它作为 `removed` 留在结果里。先回到两份输入，让学员判断：如果只拿 After 构造图，这个字段在哪里？

这一节要让人看见的是：删除节点的原始信息来自 Before，所以必须把两侧信息映射到同一张能够表达这些状态的图上。随后打开 5.1 的差异结果和当前任务，检查现有图数据的入口，说明为什么现有「只由 After 构图」的路径不够用。

本节让 Codex 完成合并图映射：保留新增、删除和变化节点及正确的路径、父子关系；为后续筛选保留所需的祖先信息。讲师用同一组案例核对 `/active`、`/role` 和 `/user/age` 的位置与状态，再检查相同输入以及原有单 JSON 图数据路径。只做最小映射，不修改渲染引擎，也不引入第二套图组件。具体实现位置和命令以 4.5 方案与实跑结果为准。

这里验证的是图数据能不能表达规则，以及后面做「只看变化」时还找不找得到必要的祖先。完整的筛选界面和摘要留到 5.4，避免学员以为第二节就已经验收了筛选。

**学员判断**：只在 After 中找节点，为什么无法核对删除？因为删除节点的原始信息来自 Before；要看映射后的实际节点和关系，才能判断是否保留。完成后留下映射实现、相关检查及结果，再进入双输入接入。

## 5.3 一边输入错了，已经得到的结果怎么办？

前两节已经有可以检查的差异逻辑和图数据，但用户还需要在 Web 界面输入两份 JSON。不要再从任务步骤讲起。先做一次正常比较，沿实际代码解释输入、解析、差异模型和图更新的路径；再把其中一侧改成非法 JSON。

这一节要让人看见的是：错误状态和上一次成功的比较结果是两件事，错误不能把已经得到的结果冲掉。恢复合法输入后，继续观察结果如何更新。首次输入就非法时，还要按对应验收检查没有历史结果的状态。

本节让 Codex 把双输入和错误状态接到现有 Web 路径，讲师核对操作、错误恢复、约定的窄屏及原有单输入主路径；UI 调用已有差异逻辑，不再复制一套算法。测试与人工操作各自覆盖哪些情况，以实际检查记录为准。不顺带修改 VS Code、浏览器扩展或其他非目标 workspace。第 6 章才批准「明确提示当前图是上次有效结果」的 CR-01；本节不把该提示设为必做，也不要求刻意移除已有的等价行为。

**学员判断**：一侧输入非法时，错误状态与上一次成功的比较结果各由什么证据确认？结合页面与输入操作回答；只看 Agent 回复或一次正常路径，还不足以说明错误恢复符合验收。完成后留下可以操作的双输入和错误路径。

## 5.4 各部分都做了，能说整个功能完成了吗？

一节分两段，不拆节。开头可以先把问题亮出来，但不要一上来就做整功能验收——摘要和筛选还没做出来，这个问题还问不完整。

### 先把还没看见的部分做出来

前半段完成差异摘要、「只看变化」和非纯颜色表达。这是「用户能不能看懂并筛差异」，不是再走一遍任务流程。

用同一组嵌套案例看完整功能：三处直接差异是否对应输入？筛选后 `/user` 是否为了保留上下文而出现，计数是否仍为 3？这里才是端到端操作筛选界面的地方；5.2 留下的是图数据里的祖先信息，本节把它用出来。

### 再问整个功能有没有做完

后半段才真正回答开篇那个问题。按当前 Acceptance 检查错误恢复、节点上限、窄屏、本地处理及原有单输入路径等实际适用的项目。模型测试、图映射测试和界面观察分别说明各自检查了什么，不能互相替代；最终结论要对照当前 `AC-*` 和任务完成定义。

若检查发现实现与已批准规则冲突，先定位代码、输入和测试，依据既定规则处理；若规则已定但案例确有遗漏，补上可核算的验收并核对任务；若行为本身需要新决定，则由人批准后同步 Spec、Acceptance 和相关任务，再实施与回归。用实际发现决定走哪条路径。4.4 已为嵌套筛选安排案例，不能预设它一定缺失；如果本次没有发现规格缺口，就直接验证，并可回指 4.3 已记录的 `null` 与字段缺失冲突，结合最终处理状态说明为什么当时要回到规格。真正需要改变产品规则时必须另行批准，不能将已批准规则重新说成 Open。

Review 从本次 diff 与相关验收出发，按需查看源码、调用方和测试，核对关键数据流、错误处理及范围。审查意见要能指出触发条件、位置和依据，再由讲师判断接受、驳回或补充验证。是否引入新会话协助 Review 仍待讲师决定；无论采用什么形式，检查结论都以实际证据为准，不预设审查者会发现问题。本节可以使用产品自带的 `/review` 作为检查入口之一，但不把命令用法展开成教学内容；5.5 也只在口播里提一句，不作为第三个演示项。

**学员判断**：差异模型和映射测试都通过了，但错误恢复还没有操作过，可以宣布整个 JSON Diff 通过验收吗？不能。前两类结果支持它们覆盖的行为；错误恢复需要其对应输入、操作和观察结果。完成当前任务、验收和 Review 后，留下实际结果、可解释的 diff、本地检查点及已知缺口，交给第 6 章。

## 5.5 做着做着，还有哪些招数可以带走？

本节和前四节不同：不再推进 JSON Diff 的实现，也不回头总结 5.1–5.4 的模块结构。全节是 15 分钟的工程经验分享，允许在 10–15 分钟内试讲调整。看懂即可，不新增练习和自检题，不改本章代码，不要求学员安装任何插件。地图短标题为「可带走的招数」。

**一句话**：前四节已经把功能往前推完，这一节把课程主线里还没展开、但马上能用的 Vibe Coding 招数拿出来看一眼，做着做着就能带走。

先用两个不必额外安装的官方技巧。最先演示 `/side`（CLI 里也写作 `/btw`）：主会话正在实现时，把一句报错或某个 API 问到侧聊里，主记录保持连续。再演示 `/fork`：把当前对话复制出去试另一种做法，原来的记录还在；这里只回答「不如换个写法看看」，不展开 Worktree，那是第 7 章的正课。第三个技巧是把界面截图贴进对话，让它按画面改：讲的是实现做到一半时怎么用，不当成把截图交给 AI 看的入门介绍。

`/review` 不作为第三个演示项。5.4 后半已经是整体验收与 Review；本节只在口播里提一句：产品自带的 `/review`（需要看具体文件时再配 `/diff`）可以检查未提交改动，不改工作区，也不能代替本章验收。语音或 `/app` 仅在录制版本核验通过后作为一句补充。桌面版的 `/pet` 如需出现，只作约 10 秒的趣味收尾，不占正片。课程规定 Codex App 为可选入口；对学员应使用「Codex App」这一名称。

技巧讲完后，用 `/plugins` 打开官方目录，只深看一个插件：[Remotion 的官方 Codex 插件](https://www.remotion.dev/docs/ai/codex-plugin)。用代码做视频，和前面做网页、改开源仓库的感觉都不同，负责本节的「有趣」。演示预先审查过的官方示例或短片段，用 `$技能名` 显式调用，点到为止。不在课上新建 Remotion 项目。若录制时该插件在教学账号中不可用，改用 [openai/plugins](https://github.com/openai/plugins) 里的 Build Web Apps 作为备选，只展示它在界面设计上的指导，避开第 4.6 节已经提过的浏览器测试类能力。Figma 官方插件需要额外账号，不作为本节首选。

本节演示节奏与核验清单，以 [5.5 工程经验：做着做着，还有哪些招数可以带走？](2026-11-11-ch05-5.5-experience.md) 为准。
