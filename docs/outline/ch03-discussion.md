## 项目范围与完成依据

- 输入：第二章留下的个人主页，或经核对的课程参考起点。

#### 整节讲解推进（2026-11-12 讲师确认）

整节沿“给自己的主页做一个游戏 → 在等待开发时理解结果为什么会有差异 → 从案例认识开发过程的不确定性 → 思考怎样复用有效做法 → 回到自己的作品检验和交付”推进。以下明确每部分形成的认识及转向下一部分的理由，作为后续 PPT、演示与逐字稿的编排依据，不预先限定 PPT 页数。既有页面和口播尚需按这条推进核对；下文旧画面安排与此处不一致时，以本次确认的推进为准。

**第一部分：给主页增加游戏——先让学员知道我们要做什么**

从第二章已经完成的个人主页出发，提出本节目标：给主页增加一个翻牌游戏。接着打开已有游戏，简单演示翻牌、配对，让学员对要做的作品形成具体认识。

这里不急着展开随机性、检查方法或 Skill。先建立一个清楚的任务：我们也要让自己的主页拥有这样的互动功能，具体外观可以不同。

**讲完得到的认识：** 本节是在已有主页上增加一个能玩的功能；学员知道翻牌游戏是什么，也知道自己最终要得到什么。

**为什么转到下一部分：** 目标已经具体，可以把它交给 Codex 开始开发。

**第二部分：发出开发请求——明确交给 AI 什么，自己还要负责什么**

进入已有主页项目，展示并发送简短请求。请求指定了要加入翻牌游戏，也约定 AI 负责跑通构建，最终试玩和验收由我们负责，Codex 可以自行做浏览器检查。图案、布局等细节没有逐一规定，留给 AI 决定。

这里让学员意识到：我们给出了目标，但没有把整个方案写完。AI 接下来不仅要写代码，还要补出许多具体选择。现在还不知道它会做成什么样，也不能提前宣布结果正确。

**讲完得到的认识：** 一次委托中，AI 会自主补齐方案和实现；构建与试玩各有分工，收到交付回复后仍有需要核对的事情。

**为什么转到下一部分：** 本次任务正在运行，正好带着“它可能做成什么样、拿到结果后该怎样看”的问题，观察已有案例。历史案例帮助我们理解和判断，不能替代本次任务的验收。

**第三部分：分析结果差异与质量——从成品差异走到开发过程的不确定性**

先展示六份成品，让学员直接看到：同类翻牌游戏可以有不同的牌阵、布局和功能。这里先观察差异，不急着评出哪个最好，也不把不同条件下的结果全部归因于随机性。

**2026-11-15 素材展示决定**：六份成品的图片统一打开各自的纯游戏展示，支持试玩；历史完整产物保留用于核对来源。开发过程使用 Inspect AI Log Viewer 展示原始记录，保留原文顺序与上下文，定位须落在与逐字稿对应的具体原句、代码或输出行，只对文字加背景高亮，空白区域不着色；同条记录含多处依据时逐处切换。不用摘要、总结或代码节选代替原记录。05 号游戏保留 CLI 日志与同一会话的补档；04 号游戏 目前仅有历史导出的计划、交付、步骤节选和 diff，明确标注完整运行日志缺失。完整记录与查看器留在本机材料目录。 本约定覆盖 3.1 主讲与备用稿：04 号游戏 的计划、实现与交付，05 号游戏的规划、规则测试、浏览器检查、修正和复测，以及备用 02 号游戏 开发链路、01 号游戏/02 号游戏 检查路径、03 号游戏 数量修正、06 号游戏 反馈修改均使用 Inspect 的原文定位。备用案例不恢复为当前主讲，现场任务继续在 Codex 与真实游戏中核对。

**3.1 材料分工（2026-11-15）**：底层保留真实任务的原始对话、执行记录与对应产物。产物直接展示，六例比较才使用唯一聚合页；聚合页只提供图片、试玩与原始记录入口及比较条件，不再维护请求、案例讲解或发布步骤。过程直接使用 Inspect，按需要定位、高亮，不增加摘要查看层。第二章实际主页加入游戏是后续整合示例，独立于六份历史游戏；历史日志不能作为此次整合的过程记录。讲述线组织切换，PPT 与口播解释关系和结论。21 例总画廊只作备课档案，旧入口只作兼容跳转。


随后进入两个案例，把观察逐步推进。

先试玩04 号游戏，看到只配了三对就提前结束。这个现象使问题从“长得不同”变成“没有按玩法工作”。再看计数代码，解释张数与对数混用；接着核对交付中的检查范围，说明构建通过没有回答能否完整通关。由此引出按玩法确定预期、补上通关和重开验收的需要，再看05 号游戏怎样实际检查这些行为。

然后继续观察05 号游戏的难度、成绩和视觉效果。此时问题从“怎样避免错误”推进到“较完整的体验怎样形成”。对照实现前的规划，解释开始、游玩、结束后的选择怎样被一起考虑，以及共同视觉方向怎样影响各个界面区域。这里也讲清楚：功能更多不自动说明其他版本做错，设计范围可以有不同选择。

最后看05 号游戏已有检查却仍漏过牌面错误的记录。它进一步说明：有规划、有测试，仍不能直接等同于实际效果符合要求；还要看检查究竟覆盖了什么。

案例讲完，再把分散的事实收束到本节的核心认识：**AI 开发中的变化，不只体现在最终外观，也可能体现在设计、实现和检查过程里，并影响作品质量。** 前面沿用的随机性认识，在这里有了具体的观察位置；这些案例用于解释过程与质量的关系，不承担证明随机性是全部差异原因的任务。

**讲完得到的认识：** 不能只凭“做出来了”判断结果。方案与执行过程可能变化，既可能形成好的设计，也可能留下问题；一次成功不意味着下一次仍会采用同样的做法。

**为什么转到下一部分：** 既然我们已经看到了值得采用的做法，就会自然产生一个问题：下一次开发时，能不能提前把这些做法告诉 AI，而不是每次重新等待它自行选择？

**第四部分：从案例方法到 Skill——从认识不确定性，走向提供可复用的指导**

先接住上一个问题，从案例中提炼值得继续采用的做法：考虑完整使用过程、先确定视觉方向、按规则验收、核对实际画面并在修改后复查。这里不重新讲案例全过程，只说明哪些经验值得带到下一次。

接着区分具体任务条件与可复用的方法。例如，“配齐六对才通关”属于这局游戏的规则；“根据本次规则确定预期并验收”则能用于其他游戏。这样既能提供明确指导，也能保留题材、布局和难度的选择空间。

最后再提出复用问题：如果以后做同类任务，都需要这些方法，每次重新整理、重新写进请求会产生重复工作。因此可以把适用任务、做法和检查要求组织成 Skill，在需要时读取。

这里讲到复用动机即可，不展开文件结构和调用细节，也不把 Skill 说成质量保证。

**讲完得到的认识：** 有效经验可以提前写成指导，并通过 Skill 保存复用；但提供了指导，不等于实际采用了，更不等于结果已经正确。

**为什么转到下一部分：** 无论有没有指导，最终都要核对实际作品。现在回到刚才发出的任务，用案例中已经建立的判断方法检查自己的游戏。

**第五部分：试玩、发布与思考——把认识用于自己的作品，完成本节交付**

回到同一次 Codex 会话，查看真实返回与构建结果，再从本地主页进入游戏。先确认本次的牌数和玩法，再检查未配齐时能否继续、全部配齐后是否通关、重开是否恢复，以及实际牌面是否符合预期。发现问题就反馈、修正、复验，不照搬历史案例的数字，也不预设本次一定成功。

通过后，沿第二章的方法更新发布，再从公开主页确认访客能够进入和游玩。这样，前面的案例分析就真正落到了自己的项目上。

最后收束两项收获：主页上多了一个可玩的作品；对 AI 开发结果的认识也从“能不能生成”推进到了“过程可能变化，需要判断和验证”。

在这个基础上留下紫色风格的问题：如果希望以后生成的游戏持续符合某种明确的视觉要求，应该怎样提供指导？后续先学习调用和读懂 Skill，再修改指导用于新的开发任务。

**讲完得到的认识：** AI 完成实现之后，人仍需按要求核对并完成交付；可复用指导与实际验证需要配合使用。

**为什么接到下一节：** 本节已经建立了使用指导的需要，下一节可以带着这个需要，具体认识 Skill 怎样被调用、里面的内容怎样指导工作。

#### 3.4.2 怎样持续追踪 AI Coding 的进展

**讲解思路**：直接表达观点：大模型能力提升，会让部分 Skill 过时或被淘汰；社区也会分享近期对 Skill 的调整，可以关注大家在讨论什么、有哪些新的用法和趋势。案例在 PPT 上作为证据，不要求口播完整复述人物、出处、事件和原因。随后推荐官方渠道与社区作者，讲清值得关注什么、如何按自己的需要选择。此处直到本节结束，口播都以讲师对着 PPT 表达观点和建议为主，作者资料、链接和非重点案例的细节交给画面；网页只在有助于理解或操作时打开。仍保留“部分 Skill”及结合自己的模型与任务判断的范围，不推导成所有 Skill 都会淘汰。
