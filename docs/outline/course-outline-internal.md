## 一、课程设计结论

### 1.1 已确认事项

- 第 0 章为独立双讲师开场访谈，新增暂估 25–30 分钟、11 页课件，不纳入正课 46 小节计数；含导入总时长暂估 878–883 分钟，待试讲。原第 1–9 章编号与项目验收保持不变。
- 正课采用九章结构：Vibe Coding、SDD、Harness 各三章。本版共 46 小节、暂估 853 分钟（14 小时 13 分钟）；第 1-6 章共 628 分钟，第 7-9 章共 225 分钟。每章至少 4 节、建议不超过 8 节，章末工程经验 10–15 分钟；本版第 1 章暂排 10 分钟，其余各章暂排 15 分钟。Harness 每章暂排 75 分钟，试讲后重新核算，不承诺实际完成时间。
- 学员具备基础编程和 Git 能力，但不预设 React、TypeScript 或前端工程化经验。
- 课程按 `Prompt -> Vibe Coding -> SDD -> Harness` 逐层推进；Model 只用一两句话说明能力来源与不确定性，不单独展开。
- 课程使用三个互不依赖、难度递进的教学仓库：第 1-3 章使用个人主页，第 4-6 章使用 JSON Crack，第 7-9 章使用 dependency-cruiser。最终考核对应三份独立成果，不再以一个仓库贯穿全程。
- 课程方不维护 JSON Crack 或 dependency-cruiser 的教学 Fork；对每个上游仓库记录确定的 Release tag 和完整 commit SHA，学员从该 commit 创建本地课程分支。学员自己的 Fork、远程仓库、Git bundle 或 patch 只是成果交付方式，不是课程基线。
- JSON Crack 固定为 2026-09-07 时最新正式 Release `v5.0.0`，commit `e99288b4eff060dcd53428f2a3a5c2f28eecffa6`；dependency-cruiser 固定为同期最新正式 Release `v18.2.0`，commit `ec603451d07d699280234808f91c4c8d3813f6e8`。个人主页没有上游 Release，使用课程 Starter Repo 在录制冻结时记录的完整 commit。
- JSON Crack 的 SDD 主任务确定为“JSON Diff 可视化模式”：比较 Before/After 两份 JSON，在现有图中表示新增、删除、修改和未变化节点，并提供差异摘要与“只看变化”。Web 是唯一必做表面，数组按索引比较；JSON Patch、按业务主键匹配数组和其他客户端同步均不进入正课。
- dependency-cruiser 的 Harness 产品方向确定为“可审计的代码地图快照与过期门禁”；正课只实现其中“快照身份与新鲜度判定核心”这一垂直切片，基于固定 cruise JSON 与 provenance fixtures 生成规范化指纹并判定 `fresh`、`equivalent`、`stale` 或 `unknown`。CLI/Git 自动探测、新 reporter 和新可视化不进入最低门禁。
- dependency-cruiser 的固定评测输入由课程提供，包括任务规格、Acceptance、合成 fixtures、统一评分表、无 Harness 基线和参考 Harness v1 补丁。无 Harness 与 Harness 两次运行使用相同代码基线、任务输入、模型、权限和时间预算；参考补丁只用于恢复，不替代学员第 7 章的 Harness 设计。
- 三个仓库分别从自己的固定基线开始，不继承前一个仓库的代码、Git 历史、聊天或 Harness；课程不额外为上游仓库维护章节级恢复 tag。
- 个人主页仓库的正课小游戏包括：用普通 Vibe Coding 完成的记忆翻牌，以及用 Game Studio Plugin 完成的“60 秒躲避与收集”微型游戏；2048 降级为同一仓库中的可选作业，不作为进入 JSON Crack 或 dependency-cruiser 的前置条件。
- SDD 指 Spec-Driven Development。第 4 章建立工具无关的 `brief -> spec -> acceptance -> plan -> tasks`，第 5 章按自建规格开发；第 6 章使用 GSD Core 接手已有项目，以原五层文档为需求依据，补齐测试闭环并完成 CR-01“上次有效结果提示”规则变更。
- GSD Core 固定为 2026-09-09 核验时的最新正式 Release `v1.13.0`，commit `b5b9814f033b6d32810562fd4068e1f107da29ec`，MIT；第 6 章原 GSD 实践链保留 4 小节、80 分钟，另设 15 分钟工程经验，全章 5 小节、95 分钟。实际安装、派发和试讲验证由 [TODO-24](TODO.md#todo-24) 承接。
- Harness 指围绕 coding agent 建立的工程约束系统，包括上下文、工具、权限、可见性、自动验证、评审、可复用经验和人工决策点；本课程不从零开发 Agent SDK 或 Harness 框架。
- Codex CLI 是主要教学界面和完整验收路径；第 1.1 节允许使用 ChatGPT 桌面端中的 Codex 作为可视化替代入口，但最迟在第 1.3 节结束前切回 CLI。桌面端不能替代账号可用性，也不作为后续 CLI 专属操作的验收证据。
- GitHub Pages 部署是必做自检作业，但不要求统一提交给讲师。
- GSD 的 Skill 工作流属于第 6 章必做实践，课程内引导安装与审查；其他额外第三方 Skill 用于发现、审查、试用和拒绝，不作为入门前置条件。GSD 不可用时仍能继续产品验证，但须另行补做框架实操。
- 课程先用一个最小任务建立“明确需求 -> 讨论与计划 -> 执行 -> 验证 -> Review -> 修正”的体验，再从真实操作中解释通用工具与选择判断；覆盖 Agent、Tool、Context、Context Window、Session、Compaction、Sandbox、Approval、Memory、`AGENTS.md`、Skill、Plugin、MCP、Sub-agent、Worktree、Hook 和 `codex exec`。
- Game Studio Plugin 的概念与审查放在第 3.4 节，项目实践放在第 3.5 节，作为个人主页小游戏章节中的必做 Plugin 生命周期实验；它不再绑定 2048、JSON Crack 或 dependency-cruiser。
- 飞书文档 MCP 作为第 4.1 节的一次只读需求摄入应用：审查后来源清楚的课程测试文档，保存权限、读取时间和仓库快照，再写入 Brief。它不单独成章，不并入 Plugin 实验，也不进入第 6 章 GSD。MCP 调用成功不是第 4 章退出门禁；无法接入时使用带来源和时间戳的课程快照，并标明这是降级路径。
- 工具概念只做宽松验收：能够说明用途、完成一次操作或观察、并对具体场景给出基本选择理由即可。
- 第 1.2 节在讲清课上要用的工具后，用 1-2 分钟口播代码补全、RAG、工具调用、多模态理解和 AI Coding 发展脉络；每个概念只回答解决什么问题、何时可能用到、和本课的关系、想深挖去哪。这不是教学内容，不练习、不考核、不另加课时。Auto Research 不进入该口播。大纲 6.1 用一张不考核附表固定范围。

### 1.2 课程设计假设

以下内容是本版大纲采用的设计假设，不等同于已经验证的产品事实：

- 个人主页使用课程 Starter Repo 规定的包管理器与版本；JSON Crack 和 dependency-cruiser 保留各自固定 Release 中的包管理器、锁文件和 Node.js 要求，不为统一命令而改写上游工程。
- 第 1.1 节使用与正式 React 应用隔离的单文件 `setup-check/index.html` 完成首次可见改动；它不进入生产源码或最终发布站点。
- 第 1.1 节的教师主演示使用 Codex CLI；只有在录制版本、平台和账号已经验证支持本地项目操作时，才把 ChatGPT 桌面端列为同任务的替代入口。
- 个人主页项目是纯前端静态站点，不包含后端、登录、云数据库、在线排行榜和支付功能；该限制不自动扩展到两个上游仓库，后者以各自课程任务的明确非目标控制范围。
- 个人主页采用单页结构，小游戏作为同一站点中的功能模块，避免把前端路由配置变成课程主线。
- 记忆翻牌和 Game Studio 微型游戏都作为个人主页中的正课功能；2048 只作为可选迁移作业。所有小游戏均不承担 SDD 或 Harness 主案例。
- 自动验证以 ESLint、TypeScript、Vitest、React Testing Library、Playwright、Vite build 和 GitHub Actions 为候选工具链，具体版本在录制前锁定。
- 正课实践使用讲师准备的占位个人资料和有明确许可的图片；学员可替换为愿意公开的信息。
- 第 4.1 节使用飞书文档 MCP 做一次读取为主的最小权限演示。飞书内容是不完整、存在歧义的产品笔记，只作为外部需求输入；对象顺序、数组匹配、删除节点等会改变实现的规则仍在第 4.3 节由讲师批准。写入 Git 仓库并经人工批准的 SDD 文档才是实现依据。
- Memory 对照使用隔离的课程配置和预先准备的合格历史会话；由于记忆生成可能异步或被跳过，不把“每名学员都成功生成同一条 Memory”设为验收条件。
- Game Studio Plugin 实验默认复用个人主页的 React + Vite 技术栈，使用简单几何图形或 CSS 作为素材，不使用后端、账号、3D 或复杂游戏引擎；新增依赖必须由人说明必要性并批准。
- 第 1.2 节末尾的行业概念口播不展开模型结构或实现，不占用额外课时，第 1.2 节仍为 15 分钟。口播具体产品名和延伸阅读链接以录制前核验的公开资料为准，不把未核验的产品行为写成固定事实。
- JSON Diff 正课采用以下产品基线：对象键顺序不构成差异；数组按索引比较；同一路径的原始值或类型改变记为 `changed`；两侧都存在且容器类型相同的祖先保持 `unchanged`，另以 `hasDiffDescendant` 表示下层有变化且不计入差异数量；差异图保留 removed 节点；“只看变化”仍保留理解路径所需祖先；输入错误标明 Before 或 After 且不覆盖最后一次有效结果；合并图遵守固定 Release 的节点上限；状态不能只用颜色表达。
- JSON Diff 的所有输入只在本地处理；正课不增加账号、后端、分享、远程保存、遥测或真实用户数据。
- dependency-cruiser 的课程垂直切片只处理确定性数据层：时间戳不得进入规范化指纹；模块、依赖或规则的输入顺序变化不能制造假差异；源码、secret、机器绝对路径不得进入快照。必要 provenance 缺失或 dirty 时为 `unknown`；图、配置、规则、扫描范围或 dependency-cruiser 版本不同为 `stale`；这些指纹相同且 commit 相同为 `fresh`；指纹相同但 commit 不同为 `equivalent`。实际 CLI 子命令、Git 探测和报告包装留作课后扩展。

## 二、课程定位与适用人群

### 2.1 课程定位

本课程不是 React 系统教程，也不是 Prompt 模板合集。课程通过三个相互独立、难度递进的真实仓库，训练学员先从零完成可见产品，再接手中等规模和较大规模的陌生代码库，使用 Codex 完成从模糊想法到可验证交付的完整软件工程循环。

四个阶段不是互相替代的四种方法，而是逐层叠加：

| 阶段 | 新增能力 | 解决的问题 | 保留下来的能力 |
| --- | --- | --- | --- |
| Prompt | 把目标、上下文、约束和完成标准说清楚 | AI 不知道要做什么，或默认了错误前提 | 自然语言表达与人工判断 |
| Vibe Coding | 在真实运行结果上持续观察、反馈、修改和评审 | 一次 Prompt 无法覆盖实现过程中的新发现 | Prompt、运行、diff 和反馈 |
| SDD | 用版本化规格固定需求、验收、计划和任务 | 规则散落在聊天里，后续修改容易漂移 | Vibe Coding 的快速协作循环 |
| Harness | 把上下文、工具、验证和人工门禁做成可重复环境 | 正确做法依赖记忆，新会话和新任务容易退化 | Prompt、Vibe Coding 与 SDD 全部能力 |

### 2.2 目标学员

- 在校大学生；
- 工作 1-2 年、具备基础编程能力但项目经验有限的初级开发者；
- 会使用基本 Git 命令，能够阅读简单函数、条件、循环和错误信息；
- 希望使用 AI 编程智能体完成真实项目，而不是只生成孤立代码片段的人。

### 2.3 不要求的前置能力

- 不要求已有 React 项目经验；
- 不要求能够独立配置前端测试和 CI；
- 不要求理解模型训练、推理架构或 OpenAI API；
- 不要求购买域名、服务器或云数据库；
- 不要求课前安装第三方 Skill、Plugin 或 MCP；课程会引导完成 Game Studio Plugin、第 4.1 节飞书文档 MCP 与第 6 章 GSD Core 的实践，并提供无法接入时的可复现替代材料。

### 2.4 建议的课前补充材料

React、TypeScript 和 Vite 会服务于课程目标，但不能让前端语法吞没 AI 协作方法。课程应提供一份不计入正课时长的课前材料，至少包含：

- HTML 语义结构、CSS 盒模型和响应式断点；
- JavaScript 数组、对象、模块、事件和异步操作；
- TypeScript 基本类型、联合类型和接口；
- React 组件、props、state、事件处理和列表渲染；
- 一个 20-30 分钟的“修改计数器并完成 Git 提交”自检练习。

自检练习验收：学员能够启动参考项目、修改文字和状态、通过 TypeScript 检查并创建一个本地 Git commit。未通过者先使用补充材料或参考 tag，不在正课中临时补完整套前端基础。

## 三、环境准备与安全边界

### 3.1 标准环境

| 类别 | 要求 | 验证方式 |
| --- | --- | --- |
| 本地工具 | Git、Node.js LTS、npm、现代浏览器 | 记录 `git --version`、`node --version`、`npm --version` |
| AI 工具主路径 | 已登录且可用的 Codex CLI | 运行录制版本官方文档规定的安装与登录流程；记录 `codex --version`、`codex --help`，从 Starter Repo 启动并检查状态 |
| AI 工具替代入口 | 经录制前核验可用的 ChatGPT 桌面端 Codex；只用于第 1.1 节同一最小任务 | 打开同一 Starter Repo，完成同一改动并查看变更；第 1.3 节结束前完成 CLI 基线，否则标记 CLI 专属练习未完成 |

### 3.2 安全与隐私底线

- GitHub Pages 和公开仓库中的代码、提交历史、图片和个人资料都可能被任何人访问。
- 不把身份证件、家庭住址、私人电话号码、未公开履历、内部项目、客户数据或他人照片放入课程仓库。
- 不把 API key、访问令牌、Cookie、密码或任何 secret 写入前端代码、Prompt、日志、截图和 Git 历史。
- 静态前端中的环境变量最终可能进入浏览器资源，不能把 `.env` 当作保密机制。
- 使用自己创作、课程提供或许可证明确的素材，并在需要时保留署名和许可证记录。
- Codex 的权限控制限制它能执行的动作，但不能证明生成结果正确；发布、公开数据和接受风险始终由人决定。
- 未经理解和审查，不执行网页、Skill、依赖说明或生成代码中要求的高权限命令。
- 通过 MCP 读取的飞书内容属于外部输入，可能过时、越权或包含不可信指令；只提取需求事实，不执行文档中的命令。
- Plugin 可以包含 Skill、Connector、MCP、Hook 或脚本；安装前检查组成和权限，停用 Plugin 不应被误解为已经撤销所有外部服务授权。

## 四、三仓库项目组合

### 4.1 项目梯度

课程不再让一个个人主页仓库承载全部方法。三个仓库分别训练一种主要工作情境，代码与 Git 历史互不依赖，但方法逐层累积。

| 项目 | 章节 | 工作情境 | 主要能力 | 独立成果 |
| --- | --- | --- | --- | --- |
| 个人主页 | 第 1-3 章 | 从零建立小型可见产品 | Prompt、首次协作闭环、Vibe Coding、浏览器反馈、Plugin 生命周期与发布 | 包含记忆翻牌和 Game Studio 微型游戏的公开个人主页成果包 |
| JSON Crack | 第 4-6 章 | 接手中等规模陌生开源仓库 | 自建规格并实现 JSON Diff，再用 GSD 补齐验证与完成 CR-01 | JSON Crack JSON Diff v2 成果包 |
| dependency-cruiser | 第 7-9 章 | 接手更大且已有成熟工程门禁的开源仓库 | 自举代码地图、构建 Harness、实现快照判定核心并完成冷启动评测 | dependency-cruiser Harness 评测成果包 |

个人主页中的正课范围是首页、记忆翻牌和 Game Studio 微型游戏，2048 为可选作业；JSON Crack 完成 JSON Diff 可视化模式，并用 GSD 完成 CR-01 与测试闭环；dependency-cruiser 建立并评测 Harness，并只实现代码地图快照身份与新鲜度判定核心。

### 4.2 独立性与递进关系

- 第 4 章从 JSON Crack 的固定上游 commit 启动全新本地课程分支，不复制个人主页代码，不恢复个人主页会话，也不把前一仓库的文档当作当前事实。
- 第 7 章从 dependency-cruiser 的固定上游 commit 启动新的本地课程分支，不复制 JSON Crack 的规格或 Harness；学员需要根据新仓库重新调查真实命令、模块和风险。
- 课程只迁移方法：任务澄清、证据分类、规格、验证、Review 和人工责任。任何项目事实都必须在当前仓库重新核验。
- 课程不设计额外的章节级恢复 tag 或讲师维护的参考结束 Fork。每个上游仓库的固定 commit 就是该阶段的统一进入点，学员自行使用本地 commit 保留练习检查点。

### 4.3 三份成果的组成

每份成果都由“可使用结果、工程资产、最低验收证据”三部分组成。验收证据用于证明成果达标，不等于成果本身，也不要求提交完整聊天记录。

| 成果 | 可使用结果 | 工程资产 | 最低验收证据 |
| --- | --- | --- | --- |
| 个人主页成果包 | 可在手机和桌面访问的个人主页、记忆翻牌和“60 秒躲避与收集”微型游戏 | 学员自己的仓库、运行/构建/发布说明、Plugin 生命周期记录、课程完成 commit 或 tag | 公开 URL、两个小游戏的核心路径证据、手机与桌面截图、2-3 轮 Vibe 迭代摘要、一次接受/缩小/拒绝 AI 建议的记录 |
| JSON Crack JSON Diff 成果包 | JSON Diff v2：比较、筛选结构差异，并在输入无效时明确标记上次有效结果 | 五层规格、GSD `.planning/`、版本与文档映射、JSON Diff 实现、测试、最终 commit 序列或 patch | MCP 或快照来源记录、固定 fixtures、CR-01、实际 mapper 委派与核验、GSD 计划/执行/UAT、失败与通过证据、截图、最终 diff |
| dependency-cruiser Harness 评测成果包 | 完成快照身份与新鲜度判定核心，并用相同任务比较无 Harness 与 Harness 两次冷启动 | `AGENTS.md`、经核验的 `CODEBASE_MAP.md`、任务模板、统一检查入口、课程 fixtures、Harness v1、项目 Skill、最终垂直切片 commit 或 patch | 两次可比较轨迹、`fresh/equivalent/stale/unknown` 验收结果、人工干预次数、风险记录和 `HARNESS_EVALUATION.md` |

### 4.4 非目标

- 不把三个仓库合并成一个 monorepo，也不要求后一个仓库依赖前一个仓库的代码或提交历史；
- 课程方不维护 JSON Crack 或 dependency-cruiser 的教学 Fork，不追踪上游 `main`，也不承诺把课堂修改提交给上游；
- 不为了统一技术栈、包管理器或命令而重构上游项目；
- 不要求学员提交完整 Codex 聊天记录、私人配置、Memory、token、Cookie 或其他敏感信息；
- 不额外维护章节级恢复 tag；上游项目只提供一个固定进入 commit，练习中的回退点由学员在自己的本地分支创建；
- 不把可选的 2048 或 Game Studio 生成结果作为进入 JSON Crack、dependency-cruiser 或完成后两份成果的前置条件；
- JSON Diff 正课不实现按业务主键匹配数组、移动检测、JSON Patch、YAML/XML/CSV Diff、VS Code/浏览器扩展同步、云端保存或分享；
- dependency-cruiser 正课不新建依赖图算法、HTML/Mermaid/D2 reporter、metrics、baseline 或 `affected` 影响分析，也不完成真实 Git 自动探测和最终 CLI 产品化；
- 以安装更多 Skill、Plugin、MCP 或依赖数量作为学习成果；
- 把 MCP 服务端实现、飞书租户配置或 MCP 调用成功当作第 4 章退出条件；无法接入时必须走标明降级的课程快照；
- 用“页面看起来不错”替代行为测试、可访问性检查和代码审查。

## 五、可衡量的学习目标

完成正课后，学员应能够：

1. 按录制版本的官方文档完成 Codex CLI 环境检查，从 Starter Repo 启动会话，并用“复述目标 -> 计划 -> 执行 -> 浏览器验证 -> Review diff -> 修正”完成一次范围明确的可见改动。
2. 用自己的话区分 Agent、Tool、Context 和 Context Window，并在 Codex CLI 中核对工作目录、仓库状态和权限边界；若从桌面端起步，能够说明替代入口的边界并在规定节点切回 CLI。
3. 将一个模糊网页需求改写为包含 Goal、Context、Constraints 和 Done when 的任务 Prompt，并指出其中仍需人工决定的事项。
4. 根据任务连续性选择继续、恢复、压缩或新建 Session，并通过 Memory 对照说明它为什么不能代替版本化项目事实。
5. 使用 React、TypeScript 和 Vite 完成一个可构建、可浏览并能部署到 GitHub Pages 的个人站点。
6. 根据浏览器现象、终端输出和 Git diff 完成至少三轮范围明确的 Vibe Coding 迭代，并记录每轮证据。
7. 在切换到 JSON Crack 和 dependency-cruiser 时，核对上游仓库、Release tag、完整 commit、分支和工作树，并在不恢复前一项目会话的情况下建立当前仓库事实基线。
8. 把 JSON Crack 的 JSON Diff 需求写成 `BRIEF.md -> SPEC.md -> ACCEPTANCE.md -> PLAN.md -> TASKS.md`，明确对象、数组、类型变化、删除节点、错误、节点上限和隐私边界，并建立 `REQ-*`、`AC-*` 和 `TASK-*` 的追踪关系。
9. 按任务逐步实现 JSON Diff 的差异模型、图结构映射、双输入状态和筛选摘要，解释关键数据流、模块边界和失败方式，而不是只复述 AI 的说明。
10. 用 GSD Core 接手第 5 章已有项目，以五层规格为依据规划并完成 CR-01；明确测试目标与约束，检查失败测试、最小实现、回归和 UAT，交付可复用的框架操作记录，不以截图或框架完成状态代替验证。
11. 发起一次 GSD mapper 委派，说明生产代码只读与调查文档分区写入的边界；由主 Agent 抽查结论并裁决冲突，区分命名角色派发、generic fallback 与顺序降级，并保持后续生产修改串行。
12. 区分全局 `~/.codex/AGENTS.md` 的个人跨项目偏好与仓库 `AGENTS.md` 的团队项目规则，并在新会话验证实际作用域。
13. 区分 Skill、Plugin 和 MCP；在个人主页仓库中完成一次 Game Studio Plugin 的“发现与审查 -> 安装或启用 -> 新会话调用 -> 构建并 playtest -> Review -> 停用或移除 -> 无 Plugin 复验”闭环，并说明 Plugin 输出为什么仍需人工判断和仓库自身验证。在第 4.1 节完成一次飞书文档 MCP 只读需求摄入，或使用带来源和时间戳的课程快照完成相同来源核对；能说明外部文档不是 Approved 需求。
14. 使用统一检查命令、Hook、`codex exec` 的非交互能力和 GitHub Actions 建立自动化边界，并说明确定性 CI 不应被 Agent 判断替代。
15. 在 dependency-cruiser 中从无 Harness 冷启动证据构建最小 Harness，并借助课程预置的相同任务、fixtures、Worktree 和全新会话，评测它是否减少遗漏、重复已有功能、越界修改和人工干预；能够区分 `fresh`、`equivalent`、`stale` 与 `unknown` 的确定性证据。
16. 当 Codex 输出无法理解、无法验证或超出范围时，能够暂停、拆小、要求解释、补证据、拒绝或回退。
17. 对每章工程问题，用自己的话解释核心术语，指出项目中的具体证据，并完成一次有理由的接受、修正、拒绝或停止判断。

### 6.1 通用概念地图与学习深度

课程先在第 1.1 节完成一次最小协作闭环，再从刚刚发生的操作中提炼工具无关判断，并在项目需要时逐步加深。验收重点是“能否为场景选择合适机制并说明基本理由”，不要求背诵完整定义、路径、命令或配置字段。课上要用的工具见下表。行业里常听到、但本课不做的周边概念见同节附表，只在第 1.2 节末尾用 1-2 分钟口播。

### 第 0 章：开场访谈——我们为什么这样学 Vibe Coding

- **形式与时长**：双讲师访谈，暂估 25–30 分钟，待试讲；开场自我介绍加 8 个正式问题，11 页课件。不套用正课每章至少 4 节的结构，原第 1–9 章编号和 46 小节不变。
- **学习目标**：说清三个独立项目、希望获得的协作能力，以及第 1.1 节的首次任务。
- **开场**：两位讲师各用 60–90 秒介绍姓名、工作方向、接触 Vibe Coding 的时间与起因。
- **访谈顺序**：①哪次经历让你觉得值得认真用；②工作发生的变化；③踩过的坑与调整；④人与 AI 怎样分工；⑤三个课程项目及安排理由；⑥成果与可独立完成的任务；⑦适合的基础与卡住时怎么办；⑧怎样跟课才能真正学会。每题两人分别回答，交替首答，避免重复。
- **课程路线**：第 1–3 章个人主页与小游戏，第 4–6 章 JSON Crack JSON Diff，第 7–9 章 dependency-cruiser 快照身份与新鲜度判定核心。用通俗语言介绍 Prompt、Vibe Coding、SDD、Harness，不提前展开工具操作。
- **输入与产出**：两位讲师经核对的真实履历、案例与现行大纲；产出为学员的一句学习目标与课程路线自检，不新增代码交付或计分作业。
- **验收与衔接**：能说出三个项目、一个希望独立完成的任务、首次实操的目标；进入 1.1，完成环境检查、修改指定欢迎语并检查结果与 diff。
- **讲解边界**：个人经历必须由讲师提供，未提供处明确待填；不编造效率数据，不承诺零基础就业、全自动开发或工具永远可用。三个项目各自从固定基线开始，Harness 正课只完成限定垂直切片。

- **讲师分工与节奏**：奇数题 A 先答、偶数题 B 先答；每题首答约 60–90 秒，另一人约 45–60 秒，第 5、6 问适当延长。开场约 3 分钟、经历三问约 8 分钟、分工约 3 分钟、项目与成果约 7 分钟、基础与学习方法约 5 分钟、收束约 1 分钟，总预算约 27 分钟，待试讲。

#### 1.1 环境搭建与第一次 AI 协作闭环

- **时长**：28 分钟（原 25 分钟，新增 3 分钟官方安装入口与课程模型介绍，不压缩其他内容）
- **新增导入页**：在环境检查前，从 OpenAI 官方资料展示 Codex CLI 的安装入口与平台选项，说明安装后在练习目录运行 `codex` 并按提示登录；说明课程主要使用 MiniMax M3，简要介绍 GPT-6 Astra、Claude Opus 5、Claude Fable 5 等观察对象。MiniMax M3 接入教学 Codex 的方式尚待实测，Claude 两个名称与定位尚待官方资料核验；不作未经验证的性能排名。区分应用/CLI 安装与模型选择，不声称需要本地下载模型权重。授课账号的模型可用性和安装实操仍需核验，不给未经实测的速度、效果或价格结论。

#### 1.2 Agent 执行机制与 AI 协作基础

- **时长**：15 分钟（含末尾 1-2 分钟行业概念口播，不另加课时）
- **知识点与 Codex 操作**：集中讲清 Model、Agent、Context、Context Window、Tool，用一张“任务输入→提出动作→工具执行→结果返回→下一步”的图解释 1.1。区分可访问与已读取的信息、操作请求与执行结果；只用一句话说明模型输出的不确定性。四阶段课程主线用于定位后续学习；Session、Memory、Plugin、MCP 等在首次使用的小节再讲，不逐项提前讲解。保留末尾 1–2 分钟行业路标口播，不展开模型结构或 RAG。

- **验收方式**：能各用一句话解释 Agent、Tool、Context 和 Context Window；能够从自己的首次任务中指出对应证据；分类理由可解释；没有把 AI 输出直接标成事实；能说出至少 3 种失败方式。术语表述不要求逐字一致。听过或未记住代码补全、RAG、工具调用、多模态理解或发展脉络，均不作为本节不合格理由。

#### 1.3 工具使用与权限

- **讲授顺序**：工具入口介绍 → 动作辨认 → 权限三层 → 授权流程 → 执行结果 → 场景判断。先比较 ChatGPT App 的图形入口与 Codex CLI 的终端入口，再说明课程以 CLI 统一实操与记录；桌面端的项目接入、工具执行与权限行为须按授课版本核验。复用 1.1 的环境检查结果，不再单设环境验收页；仅从桌面端临时起步者补 CLI 只读检查，环境变化者复核变化项，所有学员核对本次实际权限与停止条件。结合欢迎语任务辨认读取、修改、命令执行与对外操作的影响，并阅读请求、批准、工具返回和结果证据，区分执行成功与任务完成。本节仍为 15 分钟。

- **时长**：15 分钟
- **知识点与 Codex 操作**：承接循环图，集中说明 CLI/临时桌面端的路径选择，以及 Sandbox、Approval、可写范围和外部副作用。讲清操作前怎样查看、判断和停止；最小权限的经典背景与取舍在 1.6 回顾，不在本节重复讲授。按录制版本核验界面，不将替代入口视为 CLI 完整验收。
- **教师演示**：使用同一 Starter Repo 对照两种界面的工作目录、变更视图和权限提示；若桌面端未通过录制前核验，只展示官方资料和“不采用”的决定。随后在 CLI 中先做只读检查，再仅授权一个明确文件的写入；展示越界文件修改、安装依赖或外部发布请求应如何暂停。
- **学员练习**：输入为第 1.1 节环境记录和 4 个权限场景；说明选择 CLI 或临时桌面端的理由，判断每个场景应只读、允许项目内写入、请求人工批准还是拒绝；从桌面端起步者在 CLI 中复现一次只读仓库检查并更新环境记录。
- **阶段产出**：工具路径与权限选择记录，以及完整 CLI 环境基线。
- **验收方式**：能说明两种界面的选择理由和替代边界；CLI 的路径、状态和权限已经核对；没有使用危险的全权限配置；外部副作用保留人工确认；失败环境没有靠改源码或改用其他工具伪装成功。从桌面端起步但未完成 CLI 基线者不得进入后续 CLI 专属验收。

#### 1.4 写清首页任务：从模糊需求到可执行 Prompt

- **时长**：20 分钟
- **知识点与 Codex 操作**：Prompt 四要素：Goal、Context、Constraints、Done when；让 Codex 先阅读、提问和提出小计划；控制允许修改的范围；把第 1.1 节的最小循环迁移到正式首页任务。

- **学员练习**：输入为 `PROJECT_BRIEF.md` 和占位内容；编写首页任务 Prompt，并根据 Agent 的问题补全人工决定；输出 `PROMPT_V1.md` 或证据文档中的 Prompt。
- **阶段产出**：可复用的首页任务 Prompt。
- **验收方式**：四要素齐全；完成标准能观察或执行；写明非目标、文件范围和停止条件；执行前存在人工确认点；未知项没有被偷偷决定。

#### 1.5 完成首页任务：从已确认 Prompt 到可验收的首页 v0

- **时长**：20 分钟
- **知识点与 Codex 操作**：使用已经确认的 Prompt 创建 React + TypeScript + Vite 骨架；运行开发服务器和 production build；查看 Git diff；建立检查点；确保环境检查页不进入正式应用或发布产物。
- **教师演示**：让 Codex 按已确认 Prompt 脚手架并实现首页 v0，展示实际浏览器结果和代码差异，按完成标准作出接受、修正或停止决定，不在现场追加无限美化。
- **学员练习**：输入为通过评审的 Prompt；完成首页 v0；输出源码、运行截图、构建记录、Review 结论和 `ch01-prompt-baseline` tag。
- **阶段产出**：本地可见的首页 v0。
- **验收方式**：页面能启动；`npm run build` 成功；无明显控制台错误；diff 只包含目标范围；环境检查页未进入正式应用；仓库无 secret 和私人资料。

#### 1.6 工程经验：为什么不能给 Agent 所有权限

- **时长**：10 分钟（工程经验允许在 10–15 分钟内试讲调整）
- **知识点与 Codex 操作**：解释 Permission / 权限与 Least Privilege / 最小权限：只给完成当前任务需要的访问范围；能区分说明意图、实际限制与人工批准。
- **教师演示**：回看 1.3 的欢迎语任务，用权限图比较“只改指定文件”和“读取私人目录、安装依赖、发布站点”；说明 Saltzer & Schroeder 的最小权限原则，历史观点与当前产品实现分开。
- **学员练习**：输入为同一主页项目中的一张新任务卡：“仅核对本地链接，不发布”，以及已知权限选项；学员选择最小权限并解释与欢迎语任务的差别。只做判断，不重演 1.3 的四个权限场景，不实际访问私人目录或发布。
- **阶段产出**：在现有工具路径与权限记录中补充一张最小权限判断表。
- **验收方式**：能把权限选择对应到具体任务；不把 Prompt 中的禁止语句当作已生效的技术限制；不执行危险操作来证明风险。
- **参考与讲解边界**：Saltzer & Schroeder 的系统保护原则；知识线中即时解释操作前提，本节集中解释取舍，不重复安装与权限操作。

#### 本章常见错误与风险

- 把录屏的大部分时间花在下载和等待，却没有提供按平台拆分的排障与恢复材料；
- 把第 1.2 节末尾的行业概念口播扩成原理课，或把 RAG、代码补全写成课上要做的项目；
- 把桌面端、其他智能体或其他模型未经核验地说成 Codex CLI 的等价替代；
- 首次任务直接执行修改，没有目标复述、计划、结果检查和 Review；
- 把长 Prompt 当作完整规格，写入大量未经决定的设计细节；
- 因为页面“看起来像成品”就跳过构建、diff 和代码理解；
- 在不了解仓库和命令的情况下直接给予过大权限；
- 将真实手机号、私人邮箱、证件、公司内部项目或 token 放入公开仓库；
- React 初始化或依赖安装失败时，让 Codex 随意改配置直到“看起来能跑”。

#### 本章交付物与退出门禁

- 完成第 1.6 节工程判断，记录具体证据与理由；允许合理接受 AI 建议，不按术语背诵评分。
- 环境与首次闭环记录、工具与权限选择记录、首页 v0、结构化 Prompt、浏览器截图、构建结果、Review 结论和 Git tag；
- CLI 环境基线必须完成；使用桌面端起步的学员已经切回 CLI，`setup-check/index.html` 与正式应用和发布产物保持隔离；
- 学员能够解释首次闭环中的目标、计划、工具调用、实际修改和人工决定，并能解释首页入口、主要组件、样式入口和构建命令；
- 明确记录 v0 仍是 Prompt 原型，不把当前视觉和行为当作正式产品规格。

#### 2.1 用真实页面建立反馈基线

- **时长**：25 分钟
- **知识点与 Codex 操作**：反馈四要素（复现条件、期望、实际、证据）与四类标签（视觉现象、行为事实、个人偏好、既有决定）；在 360×800、768×1024、1440×900 三种视口与键盘下核对。用请求查看工具看懂一次请求的组成：系统指令、工具定义、Skills 列表、环境信息、权限说明与用户输入，逐块说明“如果没有它会怎样”；同一句话在隔离 Codex 环境或不同权限配置下发出的请求不同，请求由个人、项目、本次三层来源组装。会话选择与压缩在 2.2。
- **教师演示**：回到项目先重启开发服务器（只操作，2.2 再解释）；用课程示例反馈卡逐条核对冻结的讲师首页 v0；让 Codex 只读核对三条建议对应的代码，再打开请求记录回答“Codex 怎么知道 1.4 的决定”。隔离环境与权限配置的对比为示例。
- **学员练习**：输入为首页 v0、示例反馈卡（或自己收集的建议）与三种视口；逐条核对并分类，选定第 3 条“看不出你做过什么”进入下一轮，写入 `docs/evidence/CH02_VIBE_ITERATIONS.md`。请求查看与对比实验按配套页自主尝试，不计入验收。
- **阶段产出**：带证据的反馈基线和下一轮任务输入。
- **验收方式**：每个问题有复现条件、期望、实际、证据和类型；第 2 条（与 1.4 决定不同的建议）是否修改由人决定；能从讲师请求记录中指出至少四类非用户内容，并说出缺了其中一类会怎样。

#### 2.2 小反馈、小改动、小验证

- **时长**：25 分钟
- **知识点与 Codex 操作**：三种状态：模型不保存状态，会话由 Harness 保存并在每次请求中重发，文件与进程独立存在；重发的代价是 token 与注意力，重复前缀可被缓存；输出有不确定性，Codex 的系统指令也随版本和模型变化（以其开源仓库历史为例）；继续、恢复、压缩或新建会话的条件，压缩后模型看到的是摘要，恢复对话不等于恢复文件或服务。一轮只解决一个连贯结果；Prompt 必须引用当前证据；发现新问题时不顺带扩大范围。
- **教师演示**：对比相邻两次请求；对比“继续 + 压缩”与“新建 + 交接文件”，选择新建；由人提供项目经历（讲师使用提前写好的虚构人设），Codex 只负责在项目区呈现、不得编造；用三种视口、键盘与 `npm run build` 验证。
- **学员练习**：输入为 2.1 的反馈清单与自己愿意公开的项目经历；写本轮 Prompt，完成 1 轮完整闭环；课后 0–2 轮选做，不计分。按第 2 章轻量模板记录：问题证据、本轮目标、会话选择与理由、改动文件、验证结果、剩余问题、回退点。
- **阶段产出**：项目区内容迭代与本轮记录。
- **验收方式**：第 3 条反馈对应的内容已呈现；三种视口与键盘没有回归；本轮记录完整；会话选择理由引用具体状态；内容由人提供，没有 AI 编造的经历。

#### 2.3 读懂 AI 代码、Review 与回退

- **时长**：15 分钟
- **知识点与 Codex 操作**：先看范围再看内容：走读候选 diff 中的内容数据、组件渲染与样式影响面，对照本轮目标决定接受、缩小或拒绝；commit 是让“拒绝”变便宜的检查点；未提交用 `git restore`，已提交用 `git revert`，不教改写历史。三层检查（自动检查、自动 Review、人工 Review）中本章只有人工这一层。2.3 判断范围，2.5 判断性质。
- **教师演示**：走读 2.2 的真实 diff；范围扩大自然出现时就地处理，没有出现时在临时分支演示回到检查点；不准备坏 diff，不把演示包装成事故。
- **学员练习**：输入为 2.2 的 diff、验证证据和完成标准；形成评审结论，完成必要修正或回退，输出 homepage-v1 提交。
- **阶段产出**：可发布的 homepage-v1 提交与评审记录。
- **验收方式**：修改目的与影响面可解释，阻塞问题已处理；无无关依赖、整页重写或未说明的行为变化；能说出本次回退点及回到它的命令。

#### 2.4 GitHub Pages 首次发布

- **时长**：20 分钟
- **知识点与 Codex 操作**：推送是本课第一个对外副作用；公开的不只是页面，还有源码和整段提交历史（含历史中出现过又删除的文件）。推送前用固定命令列出待公开的提交与文件，由人判断能否公开；发现 secret、他人信息或截图隐私时先停下。公开仓库、Vite production build、GitHub Actions 和 Pages 的关系；审查 `base`、资源路径、工作流权限与触发分支；Actions 成功不等于页面可用。本章只建立包含 build 的最小部署流程，第 7 章在独立 dependency-cruiser 仓库建立统一检查入口；推送与启用 Pages 由人确认。
- **教师演示**：推送前检查，以第 1 章环境记录中的系统用户名示范“由人判断可以公开”；Codex 生成部署工作流与 Vite 配置，人工审查后推送并启用 Pages；做三项发布检查。首次部署若自然出错，就地从 Actions 日志、build 输出和 Network 定位；不准备错误的 `base`。
- **学员练习**：输入为本地通过检查的首页；确认仓库为公开，完成推送前检查后发布；输出 URL、部署记录、三项检查结果和 `ch02-homepage-live` tag（只推送这一个 tag）。
- **阶段产出**：公开首页 v1。
- **验收方式**：URL 可在未登录窗口访问；Network 中没有 404 资源；刷新后仍可用；推送前检查记录完整，公开内容与提交历史通过隐私检查。

#### 2.5 工程经验：AI 说只做重构，意味着什么

- **时长**：10 分钟（工程经验允许在 10–15 分钟内试讲调整）
- **知识点与 Codex 操作**：解释 Refactoring / 重构、Observable Behavior / 可观察行为与 Regression / 回归；区分保留行为的结构调整和需求变化。
- **教师演示**：使用两份标注为教学材料的 diff，都把项目卡提取为独立组件：一份保持行为，另一份让卡片可点击、可聚焦，正好“解决”2.1 第 2 条反馈；先看页面和键盘，再借 Fowler《重构》解释区别。收尾指出：本项目没有测试，确认“行为不变”只能手工重查三种视口和键盘，为后续规格与 Harness 章节铺路。
- **学员练习**：输入为两份 diff、原完成标准和 1.4 的决定；判断修改性质，指出需复查的视口与键盘行为。
- **阶段产出**：在 `CH02_VIBE_ITERATIONS.md` 中补充重构与行为变化判断。
- **验收方式**：判断引用具体行为证据；不因代码更短或截图更好看认定重构正确；受欢迎的行为变化也需另行确认。
- **参考与讲解边界**：Fowler《重构》；代码气味只作一句补充，不新增一轮无必要重构。

#### 本章常见错误与风险

- 连续说“再高级一点”“再好看一点”，但没有问题证据和停止条件；
- 让 AI 为解决一个 CSS 问题重写全部组件或引入大型 UI 依赖；
- 让 AI 替自己编写项目经历，或把不愿公开的内容写进公开仓库；
- 只看最终截图，不检查键盘操作、链接、控制台和已有视口；
- 把请求记录里的 token 数、请求次数或指令长度当成固定值；
- 硬编码讲师仓库名，导致学员的 Vite `base` 或 Pages 路径错误；
- 把 GitHub Actions 成功等同于页面已经可用；
- 在公开站点或提交历史中暴露个人敏感信息、未授权图片或 secret。

#### 本章交付物与退出门禁

- 完成第 2.5 节工程判断，记录具体证据与理由；允许合理接受 AI 建议，不按术语背诵评分。
- 1 轮必做、证据完整的 Vibe Coding 迭代记录（轻量模板）；
- 推送前检查记录，以及一个可公开访问的 GitHub Pages 首页；该 URL 是必做自检项，但课程不统一收取；
- 学员能用公开 URL、Network 面板和 Actions 日志验证发布结果，不把 Actions 成功当作页面可用；出现失败时能指出出在哪一环。

### 第 3 章：Vibe Coding + Plugin - 用小游戏体验快速迭代与 Plugin


本章目标：学员能够先用普通 Vibe Coding 为个人主页加入记忆翻牌并完成一次真实调试，再审查和使用 Game Studio Plugin 创建一个范围固定的微型游戏，比较两种工作方式并说明 Plugin、Skill、Agent 与项目验证之间的边界。个人主页在本章结束后形成独立成果；后续 SDD 与 Harness 不再依赖该仓库。

**本章学习路径**（知识说明计入相应小节，章末判断不重复实操）：

| 小节 | 主要作用 | 输入 | 产出与下一步 |
| --- | --- | --- | --- |
| 3.1 | 实践 | 公开首页 v1 | 记忆翻牌 v0→3.2 |
| 3.2 | 知识＋观察 | 游戏 v0 | 状态图与复现步骤→3.3 |
| 3.3 | 实践 | 已复现问题与日志 | 修复、回归与游戏 v1→3.4 |
| 3.4 | 知识＋审查 | 固定游戏 Brief 与插件资料 | 审查结论及允许范围→3.5 |
| 3.5 | 实践 | 已审查插件与游戏 v1 | 第二个游戏及生命周期证据→3.6 |
| 3.6 | 知识＋对照 | 两种开发记录与 Memory 样本 | 来源分类、需求债务→第 4 章的方法引入 |
| 3.7 | 工程经验 | 3.2–3.3 状态/缺陷记录 | 资源清理判断；本项目独立收尾 |

#### 3.1 用 Vibe Coding 加入记忆翻牌

- **时长**：20 分钟
- **知识点与 Codex 操作**：从用户意图出发快速形成垂直切片；允许 Codex 提少量问题并给出计划，但暂不建立正式规格；保持一个仓库和现有视觉语言。
- **教师演示**：使用“在主页加入一个记忆翻牌小游戏”的自然语言需求，让 Codex 实现可玩的最小版本并运行。
- **学员练习**：输入为首页 v1；加入游戏入口、卡片和最小配对循环；输出记忆翻牌 v0。
- **阶段产出**：可玩的记忆翻牌垂直切片。
- **验收方式**：能翻牌、配对、完成和重开；首页原功能可用；production build 通过；未加入非目标功能。

#### 3.2 探索状态空间而不是只走 Happy Path

- **时长**：15 分钟
- **知识点与 Codex 操作**：列出初始、首张牌、两张不匹配、匹配、等待翻回、完成、重开等状态；使用测试 charter 指导人工探索。
- **教师演示**：先画初始、等待、匹配、完成、重开的最小状态图，再按快速点击、等待时点第三张、完成后重开的短检查路线观察；仅记录证据和一个可调试问题，不在本节试修。状态定义在此讲清，资源清理的工程解释留到 3.7。
- **学员练习**：输入为记忆翻牌 v0；执行状态与交互探索；输出可复现问题清单。
- **阶段产出**：游戏探索记录。
- **验收方式**：每个问题有最小步骤、期望、实际和截图或日志；至少覆盖快速操作、重开和移动端。

#### 3.3 基于证据调试一次真实缺陷

- **时长**：20 分钟
- **知识点与 Codex 操作**：先复现再修改；让 Codex 列可证伪假设；用日志和状态变化缩小范围；修复后检查回归。
- **教师演示**：选择一个真实遗漏，例如等待阶段仍可点击或重开未清理计时器；若现场版本未出现，则明确使用预先准备的真实场景 tag。
- **学员练习**：输入为稳定复现步骤；形成假设、验证并最小修复；输出缺陷记录、diff 和验证结果。
- **阶段产出**：记忆翻牌 v1。
- **验收方式**：修复前问题可稳定重现；修复只处理根因；原场景和相邻场景复验；不伪装成现场随机发现。

#### 3.4 理解 Plugin 与 Skill，并审查 Game Studio

- **时长**：10 分钟
- **知识点与 Codex 操作**：集中区分可安装能力包 Plugin 与其中的工作流 Skill；以 Game Studio 的实际材料解释来源、版本、manifest、所含能力、脚本、网络、权限和许可证。检查步骤沿用 1.3 的权限知识，不重复讲最小权限理论。
- **教师演示**：使用录制版本支持的入口发现 Game Studio，逐项核对审查清单，并说明下一节采用或降级的条件；本节不安装、不生成游戏。具体标识、命令和 Skill 名称以核验版本为准。
- **学员练习**：输入为通过 3.3 的个人主页、固定游戏 Brief 与实际插件资料；判断能力是否合适、哪些访问需要确认，形成采用或不采用结论。
- **阶段产出**：CH03_GAME_STUDIO_PLUGIN_LAB.md 中的审查结论、版本与允许范围，交给 3.5 执行。
- **验收方式**：能区分 Plugin 与 Skill；结论有来源和权限依据。不可用或未通过审查时明确使用课程快照/普通协作降级，不把观察计作 Plugin 实操通过。

#### 3.5 Game Studio Plugin：创建“60 秒躲避与收集”

- **时长**：20 分钟
- **知识点与 Codex 操作**：按 3.4 的审查结论安装或启用 Game Studio，并按实际要求启动新会话。调用已核验工作流，先确认游戏循环、素材、HUD、控制和浏览器测试计划，再批准实施。概念和来源审查不重复讲；新增权限或依赖仍需重新判断。完成后停用或移除，再运行仓库自身检查。
- **教师演示**：在个人主页中新增与记忆翻牌独立的“60 秒躲避与收集”：玩家使用 WASD 或方向键移动，收集目标增加分数，碰到障碍产生明确后果，HUD 显示时间与分数，倒计时结束后可以重新开始。素材限定为简单几何图形或 CSS；复用 React + Vite，不使用后端、账号、3D 或复杂游戏引擎。审查 Plugin 给出的计划和依赖选择后，只允许修改游戏模块、入口和必要测试；在浏览器完成控制、计分、碰撞、结束与重开的 playtest，检查控制台和 diff，修正一个有证据的问题。最后停用或移除 Plugin，并确认仓库自身的构建与验证仍可运行。
- **学员练习**：输入为 3.4 审查结论、通过 3.3 的个人主页和固定游戏 Brief；完成“安装或启用→新会话确认→调用→playtest→diff Review→停用或移除→无 Plugin 复验”，将证据接续写入 CH03_GAME_STUDIO_PLUGIN_LAB.md，供 3.6 对比信息来源。
- **阶段产出**：“60 秒躲避与收集”微型游戏，以及 Game Studio Plugin 生命周期证据。
- **验收方式**：能够区分 Plugin 与其所含 Skill；记录实际来源、版本、能力和权限；游戏具备移动、收集、障碍、HUD、结束和重开这一完整循环；production build 通过，记忆翻牌和首页无回归；diff 没有无理由更换技术栈、引入复杂引擎或扩大功能；停用或移除 Plugin 后项目仍可运行。目录或版本不可用时可用课程快照继续分析和 Review，但不得把快照观察记作实际 Plugin 操作通过。

#### 3.6 Memory 对照与需求债务

- **时长**：20 分钟
- **知识点与 Codex 操作**：沿用 2.2 的 Session/Compaction 结论，本节只新增 Memory 的辅助回忆作用及其与仓库事实的区别。用信息来源表归类聊天、Memory、Plugin 工作流和源码证据，提取未明确或未留档的需求决定。“需求债务”是本课描述，不直接等同于 Cunningham 的技术债；Memory 异步或未生成不能判定练习失败。
- **教师演示**：在隔离配置中使用两个全新会话询问同一个记忆翻牌问题，一个允许使用预先准备的 Memory，另一个禁用；比较有帮助、无关或过时的信息，再回看 Prompt、diff 与缺陷提取需求债务。
- **学员练习**：输入为两份对照输出、普通 Vibe Coding 与 Plugin 实验记录和当前代码；标出哪些内容来自仓库证据、Memory、Plugin 工作流或模型猜测，并分类需求债务；输出 `CH03_MEMORY_EXPERIMENT.md`、`CH03_REQUIREMENTS_DEBT.md` 和个人主页完成 commit 或 tag。
- **阶段产出**：Memory 对照记录和需求债务基线。
- **验收方式**：能说明 Memory 与 `AGENTS.md`/仓库文档的边界；不因 Memory 未生成而判定练习失败；每条需求债务指向证据；能说明 SDD 将解决什么、不能解决什么。

#### 3.7 工程经验：为什么重开游戏后，旧计时器还在影响结果

- **时长**：15 分钟（工程经验允许在 10–15 分钟内试讲调整）
- **知识点与 Codex 操作**：解释 State / 状态、Side Effect / 副作用与清理责任；区分界面重置和计时器、事件监听等运行资源的重置。
- **教师演示**：复用 3.2–3.3 的重开或等待场景，画“旧计时器建立→重开→旧回调触发”的时间线，再对照修复后的资源清理；无现场缺陷时使用明确标注的已有场景。
- **学员练习**：输入为游戏状态记录、局部代码与时间线；标出重开前后需要清理的资源，预测快速重开的结果，并核对已有验证记录。
- **阶段产出**：在现有游戏缺陷记录中补充状态图、清理点与判断依据。
- **验收方式**：能指出具体状态和副作用；不把所有状态变化都当 Bug；不新增后端重试或支付场景，不重复完整调试流程。

#### 本章常见错误与风险

- 未核对固定 commit 或基线命令就开始写规格；
- 让 AI 代替产品负责人决定规则，再把决定写成“行业标准”；
- 未审查来源、认证和权限就连接 MCP，或把飞书原文、MCP 读取结果直接标成 Approved 需求；
- 未记录来源、权限和读取时间，或把课程快照观察记作实际 MCP 调用；
- 在 Spec 中写组件名和文件路径，使需求与实现强耦合；
- 用 JavaScript 对象枚举顺序、字符串序列化或第三方 diff 库的默认行为代替产品决定；
- 只渲染 After 树，导致 removed 节点从结果中消失；
- Acceptance 只是换一种说法重复需求，没有固定输入、动作和精确结果；
- 未阅读仓库就生成 Plan，引用不存在的路径、命令或 workspace；
- 一个 Task 同时包含共享逻辑、多个客户端、重构、测试和发布，无法独立验收。

#### 本章交付物与退出门禁

- 完成第 4.6 节工程判断，记录具体证据与理由；允许合理接受 AI 建议，不按术语背诵评分。

- 当前里程碑不存在未决定但会改变实现的阻塞项；
- 学员随机抽取一个需求时，能找到对应验收场景、实现任务和验证方法；
- 规格基线单独提交，便于与后续实现区分。

#### 本章常见错误与风险

- 把整份 Spec 交给 Codex 后等待一次性生成全部功能；
- 测试和实现使用同一段错误逻辑，造成“自证正确”；
- 为方便实现静默缩小或改变 fixture 和验收标准；
- 在 UI 中复制共享逻辑，或顺带修改 VS Code/浏览器扩展等非目标 workspace；
- 实现与规格冲突时只修改代码或测试，不更新权威需求；
- 学员无法解释代码却因为测试通过而直接合入。

#### 本章固定小型规则变更：CR-01 上次有效结果提示

- **原规则**：Before 或 After 输入非法时，标明错误侧，保留最后一次有效比较结果。第 5 章并未强制结果区域解释“这是旧结果”。
- **新增规则**：已有有效结果且任一输入非法时，图与差异摘要继续保留，但结果区域必须展示可见文本“上次有效结果（当前输入无效）”，错误区域仍分别标明 Before/After。仅当两侧恢复有效并完成重新比较，才移除提示并更新结果。首次输入就非法且没有历史结果时，只显示错误/空状态，不声称存在上次有效结果。
- **规格处理**：第 6.2 节由人批准 `CR-01`，在 `SPEC.md` 增加 `REQ-CR01`，在 `ACCEPTANCE.md` 增加下表 `AC-CR01-*`；Brief 记录变更原因，Plan/Tasks 追加本轮链接和状态。保留第 5 章 commit 与原验收，不把新增规则追溯认定为旧实现缺陷。
- **非目标**：不修改对象/数组差异算法、四种差异状态、`hasDiffDescendant`、计数口径、筛选语义、节点上限；不新增历史列表、自动保存、账号、网络上传或后端；本章“旧结果提示”与第 7 章快照四状态无关。

| 验收 | 输入与动作 | 期望与证据 |
| --- | --- | --- |
| `AC-CR01-1` | Before 为 `{"n":1}`、After 为 `{"n":2}`，成功比较后将 After 改为 `{` | 保留 `n` 的一处 changed 与原摘要；显示旧结果文本及 After 错误；组件/交互测试与可见截图 |
| `AC-CR01-2` | 在上一状态把 Before 也改为 `{`，随后只恢复 After 为 `{"n":2}` | 两侧非法时分别显示错误；仅 After 恢复后仍标 Before 错误，旧结果提示不消失，旧比较不变 |
| `AC-CR01-3` | 接着把 Before 恢复为 `{"n":2}`，等待比较完成 | 两侧有效，移除旧结果提示，摘要变为零差异；一条浏览器回归路径覆盖此恢复过程 |
| `AC-CR01-4` | 全新页面还没有成功比较，直接输入非法 JSON | 错误/空状态正确，不显示不存在的历史结果与旧结果提示 |

先运行新验收确认差距。如果第 5 章生成结果恰好已满足 CR-01，如实记录“行为已有、现纳入正式契约”，补齐测试后在隔离本地检查点受控移除提示来证明断言会失败，再恢复；不能故意破坏原版本并伪装为原始缺陷。

#### 本章常见错误与风险

- 在课上安装 `@latest`、沿用过期 Node.js 门槛、直接复制 Claude 命令或跳过权限控制；
- 将原五层规格静默替换为框架生成的另一套需求，或让 ingest 的自动综合代替人工决定；
- 把 GSD mapper 描述成完全只读，允许多个角色写相同文档，或没有实际委派却标记 Sub-agent 通过；
- 把 verify-work 当作单元测试执行器，或用测试数量、覆盖率、框架完成状态替代行为证据；
- 为实现提示重构差异算法、加入历史管理或网络保存；
- 先修改实现后补永远通过的测试，或把 CR-01 新契约冒充第 5 章遗漏的旧需求；
- 自动测试和实际用户体验脱节，UAT 未操作就回答通过；
- 将全章 95 分钟教学预算写成未经试讲验证的完成时间保证。

- 五层文档与 `.planning/` 可追踪且无冲突；学员能复述“已有项目 -> 规格交接 -> GSD 规划 -> 执行 -> 验收”的路径；
- GSD 或派发不可用时用标明来源的回放和第 4-5 章流程继续产品验证，分别标记 GSD/Sub-agent 实操未完成，后续补做；不以降级结果冒充框架通过；
- 第 7 章不继承本仓库的 `.planning/`、GSD 地图或会话；源码核验不替代 TODO-23、TODO-24 的实机与试讲门禁。

### 第 7 章：Harness - 建立可复用的项目环境


> 第 7-9 章按“建立环境—执行与失败控制—评测与改进”递进，每章暂估 75 分钟（知识与实践三节各 20 分钟，章末工程经验暂排 15 分钟），合计 225 分钟；工程经验可在 10–15 分钟内试讲调整，并重新核算全章时间，不承诺每章 90 分钟。时间为录播内容预算，学员暂停跟做和长运行等待另计。

> 产品范围保持“快照身份与新鲜度判定核心”：固定 cruise JSON 与 provenance fixtures 生成规范化 snapshotId，判定 fresh、equivalent、stale、unknown；不增加真实 Git 探测、CLI 子命令、新 reporter 或可视化产品。任务包及评分须在第一次基线运行前冻结。

本章目标：学员能够从固定任务和冷启动观察建立可复用上下文与检查入口，使新会话能找到正确入口并控制修改范围。

**本章学习路径**（知识说明计入相应小节，章末判断不重复实操）：

| 小节 | 主要作用 | 输入 | 产出与下一步 |
| --- | --- | --- | --- |
| 7.1 | 知识＋实践 | 运行前冻结的任务、评分与基线 | A 原始记录→7.2；保留到9.1 |
| 7.2 | 知识＋实践 | A 记录与源码 | 版本化地图和规则→7.3 |
| 7.3 | 实践 | 有效地图、命令与冻结任务 | Harness v1→第 8 章 |
| 7.4 | 工程经验 | 独立的过期地图练习 | 维护判断；不污染冻结评测输入 |

#### 7.1 无 Harness 冷启动与摩擦基线

- **时长**：20 分钟
- **知识点与 Codex 操作**：先用一句话说明 Worktree 隔离文件状态、Session 隔离对话，两者不能互相替代；从固定 Release 建立 Worktree A；向全新 Session 提供课程冻结的同一任务卡、fixtures、权限和时间预算，不提供课程 Harness。任务包、Acceptance、fixtures、七项评分、模型设置、权限、时间预算和停止条件必须在本次运行前全部冻结。记录 Agent 如何调查、计划和实现判定核心，不为了证明 Harness 有用而诱导错误。
- **教师演示**：运行无 Harness 基线，记录是否核对 SHA、找到正确数据模型与测试入口、识别已有 reporter、控制修改范围、运行目标门禁，以及人工纠正次数；到达预设时间或停止条件即结束。
- **学员练习**：输入为固定 commit、`SNAPSHOT_TASK.md`、合成 fixtures 和预先锁定评分表；完成一次独立运行，输出原始轨迹摘要、diff、测试结果、人工介入记录和未解决问题。
- **阶段产出**：`BASELINE_RUN.md` 与无 Harness 评分基线。
- **验收方式**：运行条件在开始前锁定；失败和成功均如实保留；没有事后修改评分标准；A 工作树与后续 B 工作树隔离；一次运行只作为本课对照证据，不宣称普遍结论。

#### 7.2 自举代码地图与版本化上下文

- **时长**：20 分钟
- **知识点与 Codex 操作**：使用 dependency-cruiser 分析自身依赖，结合源码和测试核验“CLI -> analyze -> graph/result schema -> report/format -> validation”的任务调用链；`CODEBASE_MAP.md` 必须记录适用 commit 和证据。区分全局个人偏好、项目 `AGENTS.md` 与更具体目录规则；隔离 Codex 环境与请求来源沿用 2.1，本节只新增规则作用域验证。
- **教师演示**：先区分常驻项目规则、按需地图和个人偏好，再用已有 archi/Mermaid/JSON 的适用部分核验快照任务入口；在隔离配置中展示全局规则，把有证据的事实和命令写入项目层。学员说明存放位置和来源即可，本节不讨论完整文档老化案例，留给 7.4。
- **学员练习**：输入为自举地图、无 Harness 轨迹和源码证据；建立 `CODEBASE_MAP.md`、根 `AGENTS.md` 及必要的局部规则，并从新会话核验加载来源。
- **阶段产出**：版本化上下文层。
- **验收方式**：能说明“个人跨项目偏好”和“团队项目规则”的区别；新会话能指出规则来源、项目入口和验证命令；仓库文件没有复制整份教程；不存在尚未运行成功却写成事实的命令。

#### 7.3 建立任务模板与统一检查入口

- **时长**：20 分钟
- **知识点与 Codex 操作**：复核 7.1 前已冻结的中性任务包；区分产品规格与执行环境。用仓库实际包管理器建立确定性的检查入口，不重新编写 SDD 规格。
- **教师演示**：核验 same、input-order-only、commit-only、graph-change、config-change、scope-change、dirty、missing-provenance fixtures；建立 HARNESS.md 和 TASK_TEMPLATE.md，串联适用单测、依赖规则、lint 与 build。
- **学员练习**：输入为冻结任务包、已核验命令和代码地图；建立检查脚本与任务模板，明确范围、停止条件和人工介入点，从新会话运行。
- **阶段产出**：Harness v1 本地 commit、统一检查入口、版本化规则与任务模板。
- **验收方式**：检查实际运行成功；命令不暗中修改文件；模板不引入隐藏产品要求；Harness patch 与任务包、产品实现分离。四状态优先级为：必要 provenance 缺失或 dirty 为 unknown；否则图、配置、规则、范围或工具版本指纹不同为 stale；指纹相同且 commit 相同为 fresh，否则为 equivalent。


#### 7.4 工程经验：上下文与文档为什么会过期

- **时长**：15 分钟（工程经验允许在 10–15 分钟内试讲调整）
- **知识点与 Codex 操作**：解释信息失效、单一事实来源与维护成本，关联代码地图适用 commit；借 Naur 的理解交接视角说明文档记录不自动等于接手者理解。
- **教师演示**：使用独立练习中的过期地图片段，让学员先判断适用版本与证据缺口，再解释为什么文档不能自动传递理解；7.2 已讲清存放位置，本节只讨论失效、维护责任和更新触发，不重建 Harness。
- **学员练习**：输入为练习地图、源码与测试；指出失效信息，补充适用版本、证据与更新触发条件，并说明接手者还需确认什么。
- **阶段产出**：地图维护说明与一处有依据的修订。
- **验收方式**：能区分仓库事实、AI 推断和个人偏好；不把未经核验的命令写成事实；地图练习不更改冻结任务与评分。
- **参考与讲解边界**：Naur《Programming as Theory Building》及试讲卡；应用到 Agent 是教学映射，不把多写文档当作唯一解法。

#### 本章常见错误与风险

- 任务执行后才冻结评分，或向 Harness 分支加入隐藏产品要求。
- 把仓库命令写入全局规则；地图无适用版本；未验证即封装 Skill。

#### 本章交付物与退出门禁

- 完成第 7.4 节工程判断，记录具体证据与理由；允许合理接受 AI 建议，不按术语背诵评分。
- BASELINE_RUN.md、冻结任务包与评分、CODEBASE_MAP.md、项目规则、HARNESS.md、TASK_TEMPLATE.md、统一检查与 Harness v1。
- 新会话能说明规则来源并运行有效检查；任务包在 A 运行前冻结；第 7 章不创建项目 Skill；第 9.2 节才封装已验证流程。

### 第 8 章：Harness - 执行任务与处理失败


本章目标：学员能够在固定环境中执行快照任务，完成检查、定位、有限修复、复验与人工交接，并保留原始对照证据。

**本章学习路径**（知识说明计入相应小节，章末判断不重复实操）：

| 小节 | 主要作用 | 输入 | 产出与下一步 |
| --- | --- | --- | --- |
| 8.1 | 实践 | 相同基线、任务与 Harness v1 | B 原始证据→9.1 |
| 8.2 | 知识＋实践 | 独立故障分支与固定预算 | 失败分类、有限修复、交接→8.4 |
| 8.3 | 知识＋实践 | 7.3 检查入口与独立练习分支 | 触发/阻断/恢复证据→8.4 |
| 8.4 | 工程经验 | 失败与自动化记录 | 停止/重试决策；原始 A/B 保持隔离 |

#### 8.1 在 Harness 条件下执行固定任务

- **时长**：20 分钟
- **知识点与 Codex 操作**：从与 A 相同的固定 Release 和中性任务包建立 Worktree B，只额外应用第 7 章 Harness v1；使用全新 Session、相同模型、推理设置、权限、Prompt、fixtures、时间预算和停止条件实现同一垂直切片。
- **教师演示**：让 Codex 实现规范化 `snapshotId` 与四状态判定核心；记录它是否核对基线、读取规则与代码地图、复用现有 cruise 结构、避免新增 reporter、运行门禁和控制范围。保存未经教学故障练习污染的 B 运行证据，留待第 9.1 节比较。
- **学员练习**：输入为 A 运行记录、Worktree B、Harness v1 和冻结任务包；完成 B 运行，输出 B 运行轨迹、diff、四状态测试、人工介入与停止记录。
- **阶段产出**：Worktree 隔离记录和 Harness 执行证据。
- **验收方式**：能指出两个 Worktree 的共同代码基线和唯一 Harness 差异；两次输入、设置、权限和停止条件一致；`fresh/equivalent/stale/unknown` 及输入顺序无关案例可重复；结果互不污染；结论区分产品结果、过程差异和非确定性，不能用单次实验声称普遍提升。

#### 8.2 检查失败后的有限修复与人工交接

- **时长**：20 分钟
- **知识点与 Codex 操作**：区分测试失败、环境失败与规格歧义；检查、定位、有限修复、复验或停止构成执行闭环。Harness 不要求长时间无人值守。
- **教师演示**：在独立练习工作树预置可复现错误，例如把 equivalent 误判为 fresh；读取失败日志，定位并限定修复范围，再运行目标检查与回归。另用缺失环境依赖展示停止与交接。
- **学员练习**：输入为标注教学用途的故障补丁、失败日志和固定预算；最多进行两轮修复，超预算、范围扩大或遇到权限/规格问题即停止，形成交接记录。
- **阶段产出**：FAILURE_RECOVERY.md、故障与修复 diff、失败及复验日志、人工交接记录。
- **验收方式**：成功路径能因正确原因失败并在修复后通过；停止路径说明已尝试内容、剩余问题与所需人工决定。教学故障不混入 A/B 评测，不修改验收期望来消除失败。


#### 8.3 自动化触发与确定性门禁

- **时长**：20 分钟
- **知识点与 Codex 操作**：区分低风险 Hook、非交互 Agent 辅助、确定性 CI 与发布批准；具体接口以录制前核验版本为准。
- **教师演示**：先画“触发→执行检查→读取退出状态→阻断或继续→人工批准”的图，再查看或配置一个已核验低风险 Hook，做一次只读 codex exec 汇总，令 CI 与本地使用同一检查入口并演示失败/恢复。指出哪条约束来自实际技术措施；示意文件列表检查不能冒充真实权限隔离。
- **学员练习**：输入为 7.3 检查脚本与独立练习分支；记录触发方式、权限、日志和退出状态，完成一次失败与恢复演示。
- **阶段产出**：AUTOMATION_BOUNDARIES.md、经审查的 workflow 与运行证据。
- **验收方式**：本地与 CI 运行一致；失败不能继续发布或覆盖证据；Agent 判断不替代客观测试。Hook 与 codex exec 不要求成为永久依赖，能力未核验时不得声称实操通过；自动化练习不回写冻结的 Harness v1 对照基线。

#### 8.4 工程经验：自动化的责任边界与快速失败

- **时长**：15 分钟（工程经验允许在 10–15 分钟内试讲调整）
- **知识点与 Codex 操作**：解释快速失败、最小权限与人工决策点；按本次动作是否产生副作用判断能否重试，Idempotency / 幂等指重复执行的预期效果与一次相同，不代表只执行一次。
- **教师演示**：使用已有故障记录改换一个判断条件，例如修复需要超出授权目录或改动验收；要求决定继续还是交接，再解释重试的副作用。8.3 已演示门禁，本节不再次配置 Hook/CI，不把正确停止归为失败。
- **学员练习**：输入为一次失败轨迹、实际命令性质与固定预算；标出可重试、需检查副作用、必须停止与人工批准的边界，并说明依据。
- **阶段产出**：执行与交接决策表。
- **验收方式**：能说明何时继续、何时停止以及谁对验收和发布负责；不把所有失败都归为可重试；不引入真实外部写入实验。
- **参考与讲解边界**：最小权限原则与问题池的 Retry / Side Effect 主题；RFC 9110 只提供 HTTP 语义参考，不能证明任意 shell 命令幂等。

#### 本章常见错误与风险

- 把教学故障和修复补丁混入 A/B 原始运行，或事后修改 Harness v1。
- 无限重试、擅自修改验收、把 CI 绿色视为发布批准，或给 workflow 过大权限。

#### 本章交付物与退出门禁

- 完成第 8.4 节工程判断，记录具体证据与理由；允许合理接受 AI 建议，不按术语背诵评分。
- B 运行轨迹、四状态测试与 diff；独立教学故障分支、FAILURE_RECOVERY.md、自动化边界和停止交接记录。
- 固定任务检查通过；故障演示因正确原因失败并恢复；超预算或歧义场景能够停止交接。

### 第 9 章：Harness - 评测、改进与沉淀 Harness


本章目标：学员能够依据前后对照完成最小改进，将已验证流程沉淀为 Skill，并从干净环境交付可复核成果。

**本章学习路径**（知识说明计入相应小节，章末判断不重复实操）：

| 小节 | 主要作用 | 输入 | 产出与下一步 |
| --- | --- | --- | --- |
| 9.1 | 知识＋实践 | A/B 原始证据与固定评分 | 单因素复验与候选 Harness→9.2 |
| 9.2 | 知识＋实践 | 已验证的重复流程 | Skill 调用与移除复验→9.3 |
| 9.3 | 实践 | 补丁、Skill 与评测证据 | 干净 checkout 交付包→9.4 |
| 9.4 | 工程经验 | 交付包与规则清单 | 维护取舍、未验证项与迁移建议 |

#### 9.1 比较 Harness 前后结果并改进一个因素

- **时长**：20 分钟
- **知识点与 Codex 操作**：按预先固定的上下文发现、范围控制、现有能力复用、验证选择、安全、人工介入、最终验收七项评分，分别评价产品结果和过程成本。
- **教师演示**：先用 7.1 冻结的条件与评分核对 A/B 是否可比，再比较原始轨迹、产品结果和过程成本；定位一个有证据的缺口，只修改一个因素并复验。记录单次样本局限，不另讲排行榜；是否值得长期保留规则的取舍留给 9.4。
- **学员练习**：输入为 A/B 证据、冻结评分及两个固定 case：“让代码地图更智能”“新增完整 Web 地图产品”；完成评分、范围与停止检查、单因素改进和相关复验。
- **阶段产出**：HARNESS_EVALUATION.md、候选 Harness v2、TOOL_SELECTION.md（含六个工具选择场景）。
- **验收方式**：模型、设置、权限、输入、时间和停止条件一致，工作树隔离；产品正确率、人工介入、耗时与可观察成本分开记录；原始 A/B 不被覆盖。无证据时可保留 v1 并说明暂不能证明改进，不强造 v2。

#### 9.2 将已验证流程沉淀为项目 Skill

- **时长**：20 分钟
- **知识点与 Codex 操作**：仅封装已经发生、可重复且通过检查的工作流；Skill 是可复用步骤，不能成为核心检查的唯一载体。
- **教师演示**：将已验证的依赖变更流程封装为 .agents/skills/dependency-change-workflow/SKILL.md，审查触发条件、输入、步骤、输出、停止与验收。
- **学员练习**：输入为成功流程与复验记录；创建并调用一次项目 Skill，验证触发和不触发场景，再检查移除 Skill 后核心检查仍可运行。
- **阶段产出**：项目 Skill、来源证据与调用记录。
- **验收方式**：Skill 不包含臆造路径或理想流程；能解释适用边界；无成功证据先补验证，不能直接标记 Skill 实操完成。


#### 9.3 最终 Review 与评测包交付

- **时长**：20 分钟
- **知识点与 Codex 操作**：从干净 checkout 应用任务包、Harness patch 和垂直切片 patch，执行统一门禁、代码 Review、隐私和许可证检查；核对前后实验条件与证据索引；明确完整 CLI/Git/reporter 产品化仍是 Deferred。
- **教师演示**：从 dependency-cruiser 固定 Release commit 重建干净环境，依次应用已记录补丁并运行四状态 fixtures 与适用上游检查；抽查轨迹、diff 和人工干预计数，区分已经证明、尚未证明和超出范围的结论。
- **学员练习**：输入为候选最终提交或 patch；完成交付检查；输出最终 commit 序列或 patch、`DELIVERY.md` 和 `HARNESS_EVALUATION.md`。

- **验收方式**：固定基线可追溯；干净环境能复现四状态判定核心和适用检查；Harness 前后条件可比较；没有声称已完成 CLI、Git 探测或新 reporter；无 secret、源码正文、机器绝对路径或许可证遗漏；Review 无未处理阻塞项。

#### 9.4 工程经验：度量与过度工程

- **时长**：15 分钟（工程经验允许在 10–15 分钟内试讲调整）
- **知识点与 Codex 操作**：解释样本局限、规则维护成本与单因素改进；借 Ousterhout 的复杂度视角判断新规则或封装是否降低理解和使用成本。
- **教师演示**：比较“继续追加特殊规则”和“删除重复规则”的证据与成本，回顾三个阶段的人工责任；使用当前评测包，不新增排行榜或函数风格竞赛。
- **学员练习**：输入为最终评测包与规则清单；保留或删除一条规则并说明收益、维护成本和验证依据，列出尚未验证的结论。
- **阶段产出**：工程取舍说明与后续验证清单。
- **验收方式**：不以一次胜负宣称普遍提升；改进不得损害其他固定案例；不按规则数、抽象层数或 Skill 数量评分，能说明哪些环节仍需人工。

#### 本章常见错误与风险

- 凭单次运行宣称普遍提升，事后修改评分，或一个 bad case 对应一条永久规则。
- 预先编写理想 Skill；没有成功证据仍标记完成；将课程补丁描述为上游已发布功能。

#### 本章交付物与退出门禁

- 从干净 checkout 复现适用门禁；无阻塞 Review 项或敏感信息泄漏；明确有效、依赖人工及尚未证明的结论。


## 八、章节递进与证据闭环

### 8.1 为什么先保留一次不完整的 Vibe 版本

课程不应通过故意制造低质量代码来证明 SDD 和 Harness 有价值。正确做法是：

1. 使用合理但不完整的真实 Prompt 完成首页和记忆翻牌；
2. 保留模型真实输出、运行结果和 Prompt 记录；
3. 通过多视口、快速交互和重新开始等真实操作发现遗漏；
4. 用证据说明遗漏源于未决需求、实现缺陷还是验证不足；
5. 将这些问题转化为下一阶段的规格和 Harness 设计输入。

如果录制时模型恰好规避了预设问题，讲师应明确说明并切换到预先保存的代表性 tag。不得把准备好的缺陷伪装成随机现场事故，也不得为了录制效果临时破坏代码。

### 8.2 每次变更的统一证据链

从第 2 章开始逐步要求：第 2 章使用轻量记录（问题证据、本轮目标、会话选择与理由、改动文件、验证结果、剩余问题、回退点），完整证据链从第 4 章开始。每次可合入变更最终至少回答：

- 目标是什么，非目标是什么；
- 使用了哪些仓库事实，哪些仍是假设；
- 修改了哪些文件，为什么必须修改；
- 运行了哪些命令，结果是什么；
- 浏览器中实际发生了什么；
- 哪些验收已经通过，哪些尚未覆盖；
- 选择了哪些上下文、工具或扩展机制，为什么没有选择其他机制；
- review 发现了什么，如何处理；
- 出现问题时回到哪个 commit 或 tag。

### 8.3 无法理解 AI 方案时的五步处理法

1. **暂停**：不合入，不继续在看不懂的实现上叠加功能。
2. **拆小**：要求把方案拆成数据、控制、界面和验证等可单独判断的部分。
3. **解释**：要求说明目的、关键状态、输入输出、影响范围、失败方式和替代方案。
4. **验证**：使用规格、源码、测试、日志、浏览器结果和一手文档独立核对。
5. **决策**：证据充分才接受；否则缩小、拒绝、回退或交给具备相关知识的人复核。

## 九、课堂练习与作业安排

### 9.1 课堂练习原则

- 每小节只交付一个可观察结果；
- 讲师演示后必须留出学员操作、失败和核对时间；
- 练习明确给出输入、任务、产出和验收；

- 课程不提供章节级恢复 tag，学员在自己的本地课程分支创建必要检查点；
- 不按 Prompt 长度、代码行数、依赖数量或调用次数评分。

### 9.2 成果一：个人主页必做自检

作业目标：把自己的课程仓库发布到 GitHub Pages，并在公开环境完成验证。

最低完成条件：

- 公开 URL 可以在未登录浏览器中访问；
- 首页、记忆翻牌和“60 秒躲避与收集”均可进入，两个游戏的核心循环可以完成；
- 手机与桌面视口不存在内容遮挡或无法操作；
- GitHub Actions 最近一次运行成功；
- 仓库和历史中没有 secret、私人数据或未授权素材；
- README 记录本地运行、检查、构建和公开 URL。

该作业属于课程必做路径，但默认采用自检，不要求发给讲师，也不承诺逐份反馈。

### 9.3 可选作业：在个人主页中加入 2048

- **定位**：2048 是个人主页仓库中的方法迁移练习，不是 SDD 或 Harness 主案例，不计入 JSON Crack 或 dependency-cruiser 的进入条件。
- **输入**：完成第 3 章的个人主页、2048 简要需求模板和游戏验收清单。
- **任务**：学员自行选择普通 Codex 协作循环或已经审查过的 Game Studio Plugin，先说明选择理由，再实现棋盘初始化、移动、一次合并、计分、有效移动后生成新方块、胜负状态、重新开始和窄屏控制；不得增加后端、排行榜、账号或付费素材。
- **产出**：独立本地分支或 commit、选择理由、实现代码、关键规则验证、桌面与移动截图，以及一次 diff Review。
- **验收方式**：production build 通过；`[2,2,2,2]` 等关键合并案例可以人工核算；无效移动不会无故改变状态；键盘和窄屏控件可用；重开能清理旧状态；首页和两个正课小游戏无回归。
- **完成影响**：该作业默认不计分、不要求统一提交，也不会在后续课程中继续使用。未完成者直接从 JSON Crack 固定 Release commit 进入第 4 章。

### 9.4 通用工具与概念宽松自检

本项不进行严格名词考试，也不要求所有学员得到完全相同的产品输出。最低完成条件为：

- 能用一句话说明 Agent、Tool、Context 与 Context Window 的关系；

- 看过 Memory 启用/禁用对照，并说明为什么项目规则仍需进入仓库；
- 在第 4.1 节使用飞书文档 MCP 只读读取课程测试需求，或通过带来源和时间戳的课程快照完成相同来源核对；能说明外部文档不是 Approved 需求；
- 完成一次 GSD mapper 实际委派，核对生产代码只读、文档分区写入与主 Agent 证据抽查；
- 用 GSD 完成五层规格交接、CR-01 规划、执行和 UAT；会看帮助和操作记录即可，不考命令背诵；
- 正确区分全局与项目 `AGENTS.md` 的典型内容；
- 创建并调用一次项目 Skill；
- 完成 Game Studio Plugin 的发现与审查、安装或启用、新会话调用、游戏构建与 playtest、diff Review、停用或移除和无 Plugin 复验；
- 使用 Worktree 隔离一次对照任务；
- 面对 3 个工具选择场景，给出基本合理的选择、理由和一项风险。

代码补全、RAG、工具调用、多模态理解和 AI Coding 发展脉络只作为第 1.2 节 1-2 分钟口播，不纳入本项自检，也不能因为未记住这些名词判定不合格。

除安全和权限边界外，术语不精确、命令需要查看帮助、或选择了另一个同样合理的机制，都不应直接判为不合格。讲师优先纠正“作用域混淆、把外部输入当事实、无审查安装、并行写冲突”四类高风险错误。

### 9.5 三份独立成果的结课交付

结课考核不再要求在同一个仓库继续追加综合大作业，而是分别验收三个项目成果：

1. **个人主页成果包**：公开 URL、最终仓库或提交、`DELIVERY.md`、多视口截图、Vibe 迭代摘要和一次人工判断记录。
2. **JSON Crack JSON Diff 成果包**：固定上游基线、第 4.1 节 MCP 或快照来源记录、GSD 版本与五层规格映射、JSON Diff v1/v2 提交或 patch、CR-01 与固定 fixtures、GSD 计划/执行/UAT、实际 mapper 委派核验、失败与通过测试、可见结果和 Review。
3. **dependency-cruiser Harness 评测成果包**：固定上游基线、快照身份与新鲜度判定核心、Harness 资产、统一验证，以及同一垂直切片在 Harness 前后的两次冷启动评测；另附独立教学故障的失败/修复/复验日志、停止交接记录、自动化边界说明、单因素复验与 Skill 调用证据。

三份成果分别验收、分别判定完成状态。一个成果不合格不应通过复制另一项目的资产补足。学员可以提交远程仓库 URL，也可以提交 Git bundle 或 patch 加证据目录；不要求把完整聊天历史、个人 Memory 或全局配置交给讲师。

- 通用概念地图、工具选择题和不依赖命令记忆的宽松验收说明；
- 隔离的 Memory 对照环境、第 4.1 节飞书测试文档与仓库快照、Sub-agent 任务卡；
- 为 Game Studio Plugin 准备已核验的来源、版本、许可证、manifest、所含能力、脚本、网络与权限声明、实际安装/调用/停用步骤和无 Plugin 降级材料；具体命令和 Skill 名称以录制版本为准；
- GSD 为第三方工作流安装，单独审查 Skill、agent、Hook、网络和自动提交；不把它当作已完成 Game Studio 的 Plugin 生命周期验收，也不因开源直接信任；
- 网络或 AI 输出不稳定时的透明备用方案。

### 11.2 单节录制节奏

常规实践小节按 15-25 分钟组织（1.1 经确认额外增加 3 分钟，现为 28 分钟），建议节奏如下；各章最后一节为 10–15 分钟工程经验，不套用常规实践时长：

- 3-5 分钟：说明本节问题、输入、边界和完成标准；
- 8-12 分钟：Codex 与项目实操；
- 4-6 分钟：运行、浏览器或测试验证；
- 2-4 分钟：diff、人工判断、产出和下一节衔接。

工程经验的 10 分钟版本按“问题 1 分钟、现象对照 3 分钟、术语与边界 2 分钟、判断及解析 4 分钟”组织；15 分钟版本依次为 2、4、3、6 分钟。暂停跟做另计，预录解析计入预算；先解释现象再引入术语，不将经典阅读或新功能塞入短讲。

概念说明、讲师演示、学员实践与反馈验证的总体比例建议约为 25%：45%：30%。验证和 review 不能为了压缩视频而省略。第 1.2 节的行业概念口播计入概念说明，控制在 1-2 分钟并在四问说完后停止，不得挤占首次闭环回放和学员分类练习。

### 11.3 AI 非确定性的录制处理

- 不保证 Codex 每次生成相同代码或提出相同问题；课程验收行为和证据，不验收逐字输出。
- 录制前至少彩排两次，准备“输出已满足预期”和“输出遗漏边界”两条分支。
- 使用预先准备的演示 commit、截图或录屏时明确告诉学员这是可复现教学现场，不伪装为实时生成。
- Codex 功能、模型、权限入口或 UI 可能变化，正式录制前以 `codex --help` 和官方 OpenAI 文档为准。
- Memory 可能异步生成或跳过，本节使用预先确认存在的教学样本，不把现场生成成功作为课程承诺。
- GSD 安装、角色派发或工作流失败时保留错误与实际版本，以课程回放和工具无关流程继续验证；实际 GSD/Sub-agent 操作仍须补做，不能静默换版本、伪造命名角色派发或把回放当实时执行。
- 第 4.1 节飞书文档 MCP 不可用时，使用带来源和时间戳的仓库快照继续 SDD，并明确这只验证降级流程，不伪装成实际 MCP 调用；第 4 章仍以五层规格为退出门禁。
- Game Studio 目录不可用、账号无权限或版本不兼容时，使用经过核验的课程快照完成概念、审查和 Review 学习，再用普通 Codex 或参考 commit 保持个人主页进度；不能把普通 Skill 文件冒充 Plugin，也不能把降级观察记作实际 Plugin 操作通过。
- 其他第三方服务不可用时，核心本地构建、测试、SDD 和 Harness 教学仍能继续；Pages 部署使用录制好的成功证据补充说明，并安排学员课后重试。

## 十二、课程核心原则

1. Prompt 写得清楚，是开始工作，不是完成需求工程。
2. Vibe Coding 的价值来自快速反馈循环，不来自放弃理解和验证。
3. SDD 固定的是可观察契约，不是让文档替代用户决定或运行证据。
4. Harness 的价值必须通过新会话、固定任务和回归结果证明，不能按文件数量判断。
5. AI 生成代码只是候选变更，能够解释、验证、评审和回退后才可合入。
6. 自动测试证明特定行为，截图和人工检查补充视觉与体验判断；两者不能互相冒充。
7. Memory 是辅助回忆，全局 `AGENTS.md` 是个人跨项目偏好，项目 `AGENTS.md` 才承载仓库共享规则；三者不能互相替代。
8. Skill 沉淀已经验证的重复经验，Plugin 分发可安装能力，MCP 连接外部系统；三者都不能成为未经审查的指令入口。
9. Sub-agent 只承担边界清楚的委派，Worktree 隔离文件状态；并行不取消主 Agent 的核验责任。
10. 工具越多不代表 Harness 越好，每项能力都必须对应真实问题并保留简单降级路径。
11. 公开发布前必须由人复核隐私、版权、secret、权限和可访问性。
12. 看不懂的方案不直接接受；证据不足时应暂停、拆小、拒绝或回退。
13. Codex 是主要课堂工具，最终学习成果是可迁移的 AI 协作开发能力。
